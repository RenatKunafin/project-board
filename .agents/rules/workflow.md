# Работа с задачами

- Единица работы: одна PBT-задача, один OpenSpec change, один PR в develop. Ветку feature/pbt-xxx-slug создавать от свежего develop. Не менять коды задач.
- Начинать с карточки и зависимостей, если доступен локальный реестр .context/tasks/README.md. В чистом checkout брать согласованный scope из поручения/PR и артефактов openspec/changes. Не придумывать статус задачи.
- До реализации подготовить proposal/design/tasks и delta specs; показать владельцу существенные решения. Начальные артефакты не коммитить до одобрения. Уже данное одобрение сохраняет силу: повторно его не запрашивать.
- Для tooling/docs/research без продуктового поведения использовать skip_specs: true в .openspec.yaml. Технические решения хранить в design, наблюдаемое поведение — в requirements/scenarios.
- Проверять openspec validate <change> --strict и openspec validate --all --strict. У validate нет флага --no-interactive.
- Реализовывать согласованный объём. Самостоятельные находки описывать явно; дополнительные работы не прятать в текущем PR.
- Перед PR выполнить проверки по testing.md. PR должен объяснять итоговое поведение, проверки и существенные ограничения; использовать .github/pull_request_template.md.
- После одобрения PR владельцем, заключительным коммитом перед merge архивировать change с sync specs (для tooling — без продуктовых дельт). Дождаться CI этого коммита, затем merge.
- In review — PR на рассмотрении; Done — только после фактического merge. Обновлять локальный реестр/архивные задачи; не добавлять журналы стадий в AGENTS или README.
- Код идёт через PR. Прямые коммиты в develop допустимы для документации/реестра, например фиксации состоявшегося merge.
- Содержание документов и общение — по-русски; служебные заголовки OpenSpec и SHALL/GIVEN/WHEN/THEN — английские.
- Дополнительные подтверждения нужны для реальной развилки или действия вне согласованного объёма. Не превращать техническую рекомендацию в новый запрет; при обязательном подтверждении назвать источник требования.
