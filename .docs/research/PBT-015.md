# PBT-015 — Проверка компонента ресурсных дорожек (спайк React Calendar Timeline)

- **Дата:** 2026-10-09
- **Тип:** Исследование
- **Change:** `pbt-015-resource-timeline-spike` (skip_specs — новых продуктовых требований нет)
- **Ветвь:** `feature/pbt-015-resource-timeline-spike` → PR в `develop`

## Вопросы

1. Укладываются ли пересекающиеся задачи одного ресурса по высоте внутри его дорожки?
2. Виден ли отпуск у конкретного ресурса, а общий нерабочий день — на всей шкале?
3. Возвращают ли drag/resize календарные даты по нашей семантике (включительное окончание, A2/A3)?
4. Работает ли изменение размеров контейнера? Какова React-совместимость и версия зависимости?
5. Годится ли кандидат для решения PBT-017 (учёт: цель вида — загрузка ресурса: когда занят и где окна)?

## Окружение и воспроизведение

- Node v22.12.0, npm 11.2.0, Chromium (Playwright MCP), macOS arm64.
- `react-calendar-timeline@0.30.0-beta.19` (MIT; TS/React 18–19 ветка, пакет обновлён 2026-07-24; peer: react ^18||^19 — совместим с 18.3.1, dayjs 1.11.x, interactjs 1.10.27). Стили: `react-calendar-timeline/dist/style.css`.
- Запуск: `npm install` → `npm run dev:resource-spike` → `http://localhost:5175`.
- Данные: `tests/fixtures/gantt/small-plan.json` (ресурсы R1/R2; задачи A–E все назначены R1; отпуск R1 26–27.10; календарь пн–пт, праздник 14.10).
- Проверки: `npm run lint`, `npm run typecheck` (7 проектов, вкл. спайк), `npm test` — зелёные.

## Что реализовано в спайке

- `apps/resource-timeline-spike` — изолированное Vite-приложение; продуктовые пакеты и `apps/gantt-spike` не изменялись.
- Адаптер `small-plan.json` → RCT: ресурсы → groups; назначенные задачи → items на дорожке каждого ресурса (D1); неназначенные — скрыты (D2); отпуск → item недоступности (canMove/canResize off); границы дней — полночь начала / полночь дня после включительного окончания (конвертация A1).
- **Лента занятости ресурса** (по образцу Resource View OnlineGantt): union непрерывных интервалов назначений — тёмные items верхнего ряда; окна видны разрывами ленты. Обновляется автоматически при изменении задач.
- Правила ADR PBT-003 кодом спайка: drag — сохранение рабочей длительности с привязкой к рабочему дню (A2); resize краёв — дата как введена, даже нерабочая (A3); снап к суткам — своим кодом.
- Стиль консистентен `apps/gantt-spike`: синие полосы задач, выходные `#e3e7ec`, праздник `#f8d3d3`, легенда, таблица загрузки (интервалы занятости и свободные рабочие дни за период).

## Наблюдения

### 1. Укладка и загрузка

- Пересекающиеся задачи одной дорожки укладываются по высоте (`stackItems`): C (19–23) и D (20–21) у R1 — C верхним рядом, D под ним (DoD-1 ✓).
- Лента занятости R1 — union задач: 12–16, 19–23, 26–28 (стык пт/пн слит, «окна» на выходных не разрывают ленту); при изменении задач пересчитывается. После drag A (→15–20) лента смержилась в 15–23 ✓.
- Ключевое отличие от согласованного вида: OnlineGantt Resource View использует иерархию «ресурс → подстроки задач» (отвергнутый в 13.2 вариант); у нас компактная дорожка + тёмная лента занятости — суть референса (когда занят/где окна) сохранена.

### 2. Жесты и даты (главные находки)

- **В 0.30.0-beta.19 `onItemMove`/`onItemResize` при жестах НЕ эмитятся.** Работает только `onItemDrag` (событие на каждый кадр: `{eventType: 'move'|'resize', itemId, time, edge?}`). Факт жеста применяется после mouseup по проверенной схеме PBT-014 («стор → правила → стор»). Для PBT-017: релизная линия API беты нестабильна — это риск интеграции.
- **Жесты активны только у выделенной задачи**: interactjs `draggable/resizable` включается при `props.selected === true` (код Item); перед drag обязателен клик-выделение. В прототипе это учтено сценарием.
- Drag A (+2 клетки, на праздник): привязка вперёд → 15–20, рабочая длительность 4 сохранена (A2 ✓), полоса растянулась с 5 до 6 клеток (A4 ✓).
- Resize правого края на выходной (24–25.10): окончание осталось на выходном, рабочая длительность пересчитана 4→7 (A3/A4 ✓); resize левого края — начало сохраняется как введено (A3, уточнение из ревью PBT-014 перенесено сюда).
- Отпуск и чужие задачи жестом одной задачи не двигаются (canMove off / изоляция items) ✓.

### 3. Календарь и стиль

- Выходные — фон колонок на всю высоту (классы дней RCT `rct-day-0/6`; дефолт RCT красит воскресенья кремовым усиленным селектором — перекрыт нашим); праздник 14.10 — акцентная колонка через `verticalLineClassNamesForTime`.
- Отпуск R1 (26–27.10) — штрихованный элемент в дорожке R1, задача E (26–28.10) визуально пересекается с ним (E7 ✓); у R2 отпуска нет.
- Resize контейнера/окна: дорожки и шкала перестраиваются (ширина 974→1374 при 1200→1600) ✓.
- Дефолтный стиль RCT требует правок (красный header, кремовые выходные) — переопределены в спайке; в проде войдёт в тему.

### 4. Известные ограничения/риски

- Бета-линия пакета: API событий жестов отличается от документируемого (`onItemDrag` вместо `onItemMove/onItemResize`), drag требует выделения. Риск закрепления за бетой — аргумент против для PBT-017.
- Точность до дня обеспечивается собственным снапом; встроенный `dragSnap` на поведение жеста в этой сборке не влиял.
- Признака выделения полосы в DOM нет — стилизация выделения потребует шаблонов/классов (в PBT-014 аналогично решалось шаблоном).

## Использованные API

`Timeline` (props: `groups`, `items`, `keys`, `defaultTimeStart/End` (мс), `sidebarWidth`, `lineHeight`, `itemHeightRatio`, `stackItems`, `canResize='both'`, `useResizeHandle`, `timeSteps`, `onItemDrag`, `onItemSelect`, `verticalLineClassNamesForTime`), классы дней `rct-day-0..6`; версии: react-calendar-timeline 0.30.0-beta.19, dayjs 1.11.23, interactjs 1.10.27.

**Лицензии:** MIT (react-calendar-timeline, dayjs), ISC (interactjs).

## Вывод

**Подходит с ограничениями** — как кандидат ресурсного представления для PBT-017.

- Подтверждено: компактные дорожки с укладкой пересечений, лента занятости ресурса (окна видны разрывами), отпуск у ресурса, день-точность, drag/resize с нашей семантикой дат, React 18, MIT.
- Ограничения/риски: бета-версия с нестабильным API жестов (`onItemDrag`, отсутствие `onItemMove/onItemResize` в жести); обязательное выделение перед drag; дефолтную тему приходится переопределять; снап к дням — свой код.
- Сравнение с PBT-014 (SVAR): SVAR сильнее по стабильности API и компонентам (формы/шаблоны), RCT проще в ресурсной укладке. Решение — PBT-017; возможна и гибридная стратегия (проектный вид на SVAR, ресурсный — кастомный рендер на RCT-подходе или собственный), требует отдельного обсуждения владельцем.
