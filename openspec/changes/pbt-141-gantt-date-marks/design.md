# Design — PBT-141 Цветовые метки дат на Гантте

## Context

Подсветка фона шкалы сегодня жёстко привязана к рабочему календарю плана: `calendarView(plan.calendar).dayKind(iso)` возвращает `weekend`/`holiday`, проектный вид красит дни через `highlightTime` SVAR (режим «Дни») и собственным слоем в `.wx-gantt-holidays` (режим «Недели», PBT-076 D2.3), ресурсный вид — собственным слоем `rt-day-layer`. Декоративных меток дат в модели нет. Прецедент расширения схемы опциональным полем без миграции — `tasks[].color` (PBT-084): опциональное поле, валидация в `parsePlanContent`, `PLAN_SCHEMA_VERSION` не менялся.

Решения владельца (2026-11-11): метки хранятся в документе плана, отрисовываются **только проектным Ганттом** (ресурсный вид не трогаем); при совпадении с нерабочим днём **метка перекрывает фон** (приоритет: метка > праздник > выходной). Палитра — 5–7 контрастных цветов; предлагается 6.

## Goals / Non-Goals

Goals:

- Опциональный раздел `dateMarks` в документе плана, не затрагивающий рабочую семантику.
- Управление в существующем диалоге «Настройки плана» через общий черновик (механизм PBT-044/PBT-086), одна запись документа на сохранение.
- Отрисовка в обоих масштабах проектного вида с дневной точностью и приоритетом над нерабочими.
- Перенос в собственном формате файла без потерь.

Non-goals (помимо proposal): миграция схемы не выполняется (поле опционально); легенда меток в тулбаре/статусе не вводится; поиск/фильтрация по меткам не вводится; счётчик меток не отображается.

## Decisions

### D1. Модель: опциональный раздел `dateMarks`, схема v1 не меняется

`PlanContent` получает опциональное поле:

```ts
interface PlanDateMark {
  readonly date: string;   // ISO YYYY-MM-DD
  readonly color: DateMarkColor; // union идентификаторов палитры
}
PlanContent {
  ...
  readonly dateMarks?: readonly PlanDateMark[];
}
```

- Отсутствие поля = нет меток; фабрика пустого плана поле не пишет (как `color` задач).
- Валидация в `parsePlanContent`: дата ISO и существующая, дата уникальна в разделе, цвет — известный идентификатор; нарушение — диагностическое сообщение с местом и причиной, документ не рабочий (стиль PBT-084, без молчаливого сброса).
- Альтернатива «записать метки внутрь `PlanCalendar`» отклонена: календарь питает `createWorkingCalendar` и кэш `calendarView` (PBT-080); декоративные данные в нём загрязняли бы арифметику и кэш рабочего календаря.
- Альтернатива «`Record<date, colorId>`» отклонена: остальная модель — массивы сущностей с явной сортировкой при записи; массив объектов даёт единый стиль валидации и сериализации.

### D2. Палитра: 6 цветов из палитры задач, притушенные прозрачностью

Решение владельца 2026-11-11: цвета меток — те же, что у задач, но с прозрачностью, чтобы метки выглядели притушёнными и не конфликтовали с полосами, оставаясь заметными.

- Новый `packages/gantt/src/date-mark-colors.ts` объявляет `DATE_MARK_COLORS` — шесть записей существующей палитры задач PBT-084 по идентификаторам: `coral` (#F05653), `pumpkin` (#F3821D), `ochre` (#EAB532), `jade` (#2FC183), `sapphire` (#3186E9), `plum` (#9F5DCB); `DateMarkColor` — union этих идентификаторов; `isDateMarkColor(value)` для валидации и нормализации импорта. Hex-значения не дублируются: единственный источник — `task-colors.ts`.
- Приложение: заливка — полупрозрачное смешение с поверхностью, плотнее праздника (15% `--warning`): `color-mix(in oklch, <hex> ~32%, var(--surface))`; плотность уточняется живым осмотром с владельцем. CSS-классы заливки генерируются из палитры при монтировании по образцу `ganttBarColorRules` (PBT-084) — новых литеральных цветов в `tokens.css` не появляется; свотчи формы используют те же сгенерированные значения.
- **Совместимость с PlantUML (решение владельца 2026-11-11)**: один базовый hex на идентификатор, два детерминированных представления. Приложение подмешивает к поверхности (выше), экспорт PlantUML публикует осветлённое к белу представление того же hex сплошной заливкой `is colored in #rrggbb` — эмуляция той же прозрачности на светлом фоне диаграммы; коэффициент осветления единый для палитры, подбирается рендером вместе с плотностью приложения (4.2/4.4). Насыщенные hex полос задач метки не используют — конфликт с задачами исключён по построению. Палитра MUST оставаться различимой от `lightgray` (выходные) и `DarkGreen` (отпуска) в рендере диаграммы и различимой между собой в обоих рендерах. Паритет по цвету фиксируется, по плотности — нет.
- 6 цветов — середина согласованного диапазона 5–7; подмножество палитры задач сохраняет единый цветовой язык приложения.

### D3. Команда ядра `updateDateMarks` — отдельно от `updateCalendar`

Чистая операция в `plan-commands.ts`: `updateDateMarks(plan, marks)` → `PlanCommandResult`; в union `PlanCommand` добавляется `{ type: 'updateDateMarks'; marks }` с диспетчеризацией в `applyPlanCommand`.

- Валидация и коды ошибок в существующем стиле (`PlanCommandErrorCode`): не-ISO/несуществующая дата, повторяющаяся дата, неизвестный цвет (единый код `invalid-date-marks` по образцу `invalid-calendar`).
- Успех — атомарная замена раздела с сортировкой по дате; календарь и прочие разделы не меняются.
- Альтернатива «расширить `updateCalendar` четвёртым аргументом» отклонена: смешивает декоративные данные с рабочей семантикой в одной команде и ломает существующую сигнатуру; отдельная команда оставляет `working-calendars` чистыми.
- Тесты декоративности (unit): метки не меняют `dayKind`, рабочую длительность, `dependencyViolations`, `resourceConflicts`.

### D4. Рендер: приоритет в двух точках проектного вида

- Определение цвета дня: чистый помощник в `svar-adapter.ts` / рядом с `calendar-view.ts` — `dateMarkColor(plan, iso): DateMarkColor | undefined` (Map из `dateMarks`, строится в `useMemo` по плану; объём сопоставим с праздниками, отдельный кэш не нужен).
- Режим «Дни» (`highlightTime`): если есть метка — вернуть `gantt-date-mark-<id>`; далее праздник/выходной как сейчас. Классы статичны в `gantt.css`: `.plan-gantt .gantt-date-mark-<id> { background: var(--color-gantt-mark-<id>-fill); }`.
- Режим «Недели» (слой `.wx-gantt-holidays`): полосы слоя для помеченных дней получают класс метки вместо `gantt-weekend`/`gantt-holiday`; подряд идущие дни одного цвета метки объединяются в один блок (как сейчас для видов нерабочих), дни разных цветов не сливаются.
- Ресурсный вид не изменяется (решение владельца); `resource-timeline-adapter` копирует план без потерь — проверить, что поле `dateMarks` переживает производные копии плана (`filterPlanForView` в PBT-049): фильтрация должна переносить раздел как есть, иначе отфильтрованный вид потеряет метки.
- `data-gantt-day-mark="<colorId>"` на полосах слоя — стабильный хук для e2e (по образцу `data-gantt-nonworking`).

### D5. Управление: раздел «Особые даты» в секции «Календарь»

`PlanCalendarSection.tsx` дополняется третьим списком по образцу праздников/исключений:

- форма: дата «с–по» + радио-палитра из 6 свотчей (свотч — `var(--color-gantt-mark-<id>-fill)`, доступное имя цвета); диапазон раскладывается `expandRange` → `addCalendarDays` (существующая утилита);
- повторная дата в наборе — замена цвета (последний выбор выигрывает), не ошибка; дубли в черновике невозможны по построению (набор — Map);
- список меток: дата + свотч + имя цвета, удаление по образцу `data-calendar-remove-holiday`;
- применение — через общий черновик `ResourceCatalogDialog` → команда `updateDateMarks` в цепочке `applyPlanCommand` черновика; «Сохранить настройки» — одна запись документа (существующий механизм `onSave(plan, expectedRevision)`), конфликт ревизии — существующее поведение;
- data-атрибуты для e2e: `data-calendar-mark-from/to`, `data-calendar-add-mark`, `data-calendar-remove-mark`, палитра `data-calendar-mark-color`.

Альтернатива «диапазоны хранить как интервалы» отклонена: модель и валидация остаются плоскими датами, как праздники; раскладка на даты уже есть.

### D6. Перенос файла: round-trip без потерь, случайный цвет для неизвестного

`serializePlanFile` проходит по всему `PlanContent` — раздел попадает в файл автоматически. `deserializePlanFile` получает шаг нормализации по образцу `normalizeImportedTaskColors`: метки с неизвестным `color` получают случайно выбранный известный цвет палитры до валидации (решение владельца 2026-11-11 — метка не удаляется). Детали:

- одному неизвестному идентификатору соответствует один случайный цвет в пределах одного разбора (диапазон дат с неизвестным цветом остаётся одноцветным, разные неизвестные идентификаторы могут получить разные цвета);
- случайность между импортами допустима: повторный импорт создаёт независимый план (контракт plan-transfer), совпадение цветов не гарантировано;
- повреждённая дата метки остаётся диагностикой (файл отклоняется).

Отклонённые альтернативы: удаление метки (отклонено владельцем 2026-11-11), отклонение всего файла (теряется план из-за одной метки), детерминированное отображение неизвестного id в цвет по индексу (владелец выбрал случайный выбор). Версии формата/схемы не меняются.

### D7. Экспорт PlantUML: особые даты заливкой дня, после блока выходных

Механизм — из эталонного примера владельца (`.context/examples/plant-uml-example.plantuml`, раздел «Выделенные даты (мобильные релизы сторов)»): `<дата> is colored in <цвет>` и диапазоны `<дата> to <дата> are colored in <цвет>` — заливка дня без `is closed`, то есть чисто визуально, длительности не трогает (семантика меток совпадает с приложением).

- **Цвет**: осветлённое к белу представление hex палитры меток (D2) сплошной заливкой `is colored in #rrggbb` — эмуляция прозрачности приложения на светлом фоне диаграммы; насыщенный hex полос задач метки не используют, визуальный конфликт с задачами исключён (решение владельца 2026-11-11).
- **Порядок**: текущий блок серых выходных идёт последним с комментарием «перекрывают всё» (наблюдение владельца по эталону). Для приоритета приложения (метка > праздник > выходной) строки меток ставятся **после** выходных, комментарий обновляется. Перекрытие подтверждается рендером (задача 4.2); если рендер PlantUML применяет иное правило precedence — fallback: не выводить серую строку выходных на дату метки (исключение дат меток из weekend-набора), приоритет сохраняется в любом случае.
- **Диапазоны**: соседние даты одного цвета объединяются переиспользованием `groupConsecutive` по каждому цвету (детерминированный вывод, компактный diff).
- **Горизонт**: как календарь, метки выводятся в пределах горизонта дат плана; выходящие за горизонт перечисляются в отчёте экспорта (масштаб диаграммы определяется задачами, метка вне горизонта не видна).
- Метка не порождает `is closed`; взаимодействие с серым рендером закрытых праздников (метка на празднике) проверяется рендером в 4.2.

Импорт `.gantt` OnlineGantt без изменений: в формате нет соответствующего понятия.

## Risks / Trade-offs

- [Путаница метки с праздником по цвету] → метки плотнее праздника и перекрывают его; живой осмотр с владельцем до приёмки (плотность/оттенки — D2).
- [Один базовый hex — два рендера, и базу нельзя тюнить под один из них] → настройка только коэффициентами представлений: плотность `color-mix` в приложении и коэффициент осветления в PlantUML (D2); оба проверяются живым осмотром и рендером 1.2023.9 (4.2/4.4); если цвет всё же нечитаем в одном из рендеров — меняется выбор идентификатора из палитры задач, а не hex.
- [`filterPlanForView` или другие производные копии плана потеряют новое поле] → задача 2.5 проверяет и фиксирует перенос; регресс-тест на метку при активном фильтре.
- [Слой недельного режима: наложение полос разных цветов в один день] → полоса на день одна (приоритет D4), слияние только одинаковых цветов; e2e на границу цветов.
- [Рост реактивности: пересборка Map меток на каждый рендер] → `useMemo` по `plan.dateMarks`; объём мал (десятки дат), отдельный FIFO-кэш как в `calendar-view` не нужен.
- [Обновление подсветки без пересборки чарта] → метки меняются только через диалог настроек (remount по ревизии уже подавлён для собственных записей, PBT-084); жесты и прокрутка не затронуты.

## Migration Plan

Миграция не требуется: поле опционально, старые документы валидны, новые документы читаются старой версией приложения (неизвестное поле раздела игнорируется как «дополнительное поле» при round-trip старой версии — политика дополнительных полей уже описана в `plan-transfer`). Откат — удаление раздела меток в UI, данные других разделов не затронуты.

## Open Questions

- Итоговые плотности заливки и оттенки 6 цветов (D2) — уточняются живым осмотром с владельцем на этапе реализации; на контракт спек не влияют (идентификаторы палитры фиксированы).
