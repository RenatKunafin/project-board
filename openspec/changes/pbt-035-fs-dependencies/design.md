# Design — PBT-035: FS-зависимости и их проверка

## Context

База: модель v1 с `dependencies: [{ id, fromTaskId, toTaskId, lagDays }]`; валидатор чтения уже отклоняет лаг < 0 (`invalid-lag`), ссылки на несуществующие задачи (`unknown-reference`), но не проверяет циклы рёбер (только циклы групп); контракт команд PBT-031 (коды `unknown-task` / `inverted-interval` есть), арифметика PBT-013 (`addWorkingDays`: лаг 0 → `nextWorkingDay`, лаг N — N шагов по рабочим дням; праздники и исключения учитываются), модульный шаблон PBT-032–034. Правила ADR PBT-003: C1 (лаг 0 — начало в ближайший рабочий день после окончания предшественника), C2 (лаг целое ≥ 0, отрицательный отклоняется), C3 (только задача → задача), C4 (циклы, включая A→A и косвенные, отклоняются при создании с сообщением), C5 (нарушение — только подсветка, даты не изменяются).

## Goals / Non-Goals

**Goals:** команды create/update/delete зависимости с защитой графа; диагностика нарушений на ребро с IDs и объяснением; лаг в рабочих днях с учётом праздников; идемпотентность точного дубля; тесты цепочки, ветвления, цикла, границ лага, ручного конфликта.

**Non-Goals:** автоперенос дат, зависимости на группы, отрицательный лаг, отображение (PBT-037/046), конфликты ресурсов (PBT-036).

## Decisions

### D1. Команды: create с идемпотентностью дубля, update только лага, delete

`plan-dependencies.ts` по шаблону PBT-032–034 (type-only импорт результата, локальные хелперы, порядок «в конец»).

- `createDependency(plan, { fromTaskId, toTaskId, lagDays })`: проверки по порядку — обе задачи существуют (`unknown-task`); лаг — целое ≥ 0 (`invalid-lag`, C2); `from === to` → `circular-dependency` (C4); косвенный цикл — BFS от `toTaskId` по рёбрам (`to →* from` достижим) → `circular-dependency`; ребро `from→to` существует: с тем же лагом — **noop** (идемпотентность по прецеденту назначений PBT-034 D1: источник UI не должен ошибаться на повторе), с другим лагом — `duplicate-dependency` (конфликтный ввод: два лага у одного ребра невозможны, подсказка — использовать изменение лага). Новая запись — в конец массива.
- `updateDependency(plan, dependencyId, patch: { lagDays? })` — только лаг: изменение концов ребра = удаление и создание (перестройка связи редка, а смена конца требует повторной проверки циклов — операция создания это уже умеет; раздвоение ответственности усложнило бы контракт). `unknown-dependency`; `invalid-lag`; тот же лаг — noop.
- `deleteDependency(plan, dependencyId)` — фильтр, порядок остальных стабилен.

Новые коды: `invalid-lag`, `circular-dependency`, `duplicate-dependency`, `unknown-dependency`. `PlanCommand` += 3 варианта.

### D2. Диагностика нарушений — чистая функция на ребро

`dependencyViolations(plan): readonly DependencyViolation[]`:

```text
DependencyViolation { dependencyId, fromTaskId, toTaskId, expectedStart, actualStart, message }
expectedStart = addWorkingDays(from.end, lagDays)   // C1: лаг 0 → следующий рабочий день
нарушение ⇔ to.start < expectedStart (лексикографическое сравнение ISO)
```

- Нарушение вычисляется **на каждое ребро независимо** (не агрегат max по предшественникам): в UI связь и её индикатор живут на ребре (PBT-037/046), список конфликтов агрегирует сам. Задача может нарушать одно ребро и соблюдать другое — оба факта честны.
- Позднее начало не нарушение: ручной план допускает люфт (C5; «окончание → начало» — минимум, не равенство).
- Календарь создаётся один раз на вызов; праздники в окне задержки влияют на `expectedStart` автоматически (`addWorkingDays`), DoD-5 подтверждается тестом «одинаковые даты, другой календарь — другой результат, даты не изменены».
- Рёбра с отсутствующими задачами пропускаются защитно: функция предназначена для валидного плана (после `parsePlanContent`), повреждённые данные — ответственность валидатора чтения; падение на невалидном входе не нужно ни одному потребителю.
- `message` — на русском, называет обе задачи, ожидаемое и фактическое начало: DoD «IDs и объяснение».

### D3. Нулевой и положительный лаг: точная семантика

`expectedStart = addWorkingDays(from.end, lagDays)` покрывает C1 без особых случаев: лаг 0 → `nextWorkingDay(from.end)` (начало в следующий рабочий день, DoD-1a); лаг 1 → пропускает ещё один рабочий день (пн→вт, DoD-1b); лаг N → N рабочих дней задержки; праздник внутри окна сдвигает `expectedStart` на следующий рабочий. Проверка на границе года/високосного покрыта тестами PBT-013, здесь — сценарий праздника и обычная неделя.

### D4. Граф: только структурная защита в командах

C3 «зависимости только между задачами» выполняется самим API (ссылки на задачи, группы не участвуют). Валидатор чтения дополнять проверкой циклов рёбер не требуется: команды не дают создать цикл, а повреждённый извне документ с циклом не нарушает правил чтения формата (структура корректна) — цикл в данных даст нарушения в диагностике, но не сломает вычисления (обход диагностики идёт по рёбрам, не по цепочкам). Углублять валидатор не буду — вне границ карточки, расширение отдельным решением при потребности.

### D5. Границы и экспорт

`plan-dependencies.ts` — типы `plan-document.ts` + type-only из `plan-commands.ts`, без React и UI-библиотек. `PlanCommand` += 3 варианта (итого 19); группировка объединения по разделам — по-прежнему откладываю до представления (потребителя), рефакторинг механический и без изменения контракта. Экспорт из `index.ts`.

## Risks / Trade-offs

- **`duplicate-dependency` при другом лаге, noop при том же** — разнобой на первый взгляд: причина — различие ситуаций. Повтор точного ввода — безвредный ретрай (UI), повтор с другим лагом — противоречивое намерение, молча сменить лаг командой «создать» значило бы скрывать операцию редактирования.
- **Диагностика per-edge дублирует суть для пользователя** («два ребра нарушены, исправь хотя бы одно») — решение агрегирования остаётся за UI (PBT-046); ядро не угадывает приоритет.
- **Концы ребра не редактируются** — редкая операция; при потребности в PBT-045 добавляется `relinkDependency` отдельным решением.

## Migration Plan

Не требуется: формат v1 не меняется; только чистые функции и расширение объединения команд.

## Open Questions

- Развилок нет: правила C1–C5 зафиксированы ADR PBT-003, механика — прецеденты PBT-031–034.
