# Design — PBT-120

Исследование без продуктового поведения (`skip_specs: true`). Технические решения фиксируются здесь; наблюдаемого поведения в specs не добавляется.

## D1. Единица знания и статусы

Каждое свойство среды фиксируется строкой таблицы со статусом:

| Статус | Значение |
| --- | --- |
| `подтверждено владельцем` | Сообщено владельцем как факт о его среде (исходная запись; сверка поведением — не обязательна) |
| `проверено` | Воспроизведено наблюдением по протоколу (владельцем во внутреннем клиенте или нами локально) |
| `неизвестно` | Ответ не получен или проверка недоступна; используется в планировании как неопределённость |
| `не поддерживается` | Установлено отсутствие свойства; влияет на выбор альтернатив |

Стартовое состояние: `MCP поддерживается клиентом` = подтверждено владельцем (пример использования Playwright MCP); остальные строки — `неизвестно` до ответа. Предположения о поведении конкретных публичных клиентов не используются ни в одном статусе.

## D2. Состав анкеты — только необходимое для пробы PBT-121

Каждый вопрос анкеты привязан к решению, которое без него нельзя принять. Группы:

1. **Платформа клиента агента:** ОС и способ запуска клиента. Снимает выбор упаковки компонента (npm/Node против самодостаточного бинарника) и путей каталога очереди.
2. **Дашборд:** браузер, версия, вкладка или установленная PWA; корпоративная политика локальной сети. Снимает проверку канала HTTPS → loopback (Local Network Access, mixed content) и выбор места пробы (публичный сайт/локальная сборка).
3. **Конфигурация MCP в клиенте:** какие поля есть у описания сервера (команда/args/env, URL), можно ли добавить сторонний сервер и откуда. Снимает выбор транспорта компонента (stdio-кандидат по модели Playwright MCP) и источника установки.
4. **Инструкции/скилл:** поддерживает ли клиент пользовательские инструкции/скиллы, в каком виде. Снимает формат поставляемого скилла обслуживания очереди (PBT-129).
5. **Цикл и ожидание:** может ли агент обрабатывать задания по команде пользователя (минимум), есть ли длительный цикл/расписание; таймауты вызова инструмента. Снимает решение: ручной запуск как базовый режим, цикл — необязательное расширение.
6. **Источник:** есть ли у агента разрешённый инструмент чтения выбранной доски/проекта (только факт, без имени системы и версии в отчёте). Снимает допуск к планированию PBT-130.
7. **Ограничения компании:** установка локального ПО, разрешённые источники пакетов, loopback-соединения, допустимое размещение дашборда. Снимает выбор способа распространения (PBT-131) и сборки без аналитики (PBT-123).

Вопросы, не влияющие на пробу 121 (единицы спринта, история, семантика Done, формат очереди), в анкету не входят — это PBT-122+.

## D3. Целевая среда и способ установки — согласованы владельцем 02.11.2026

- **Целевая среда пробы:** macOS — та же основная машина владельца, где работает внутренний клиент агента.
- **Способ пробной установки компонента (PBT-121):** `npx`/npm-пакет по модели Playwright MCP, уже используемой клиентом; модель `npx`-запуска MCP-сервера в этой среде подтверждена фактом работы Playwright MCP. Бинарник — запасной путь, если проба выявит препятствие.
- **Место дашборда для пробы 121:** публичный HTTPS-сайт проекта — проверяет реальный путь HTTPS → loopback (Local Network Access). Локальная сборка — запасной путь при блокере политики.
- **Браузер пробы:** Chrome, обычная вкладка (базовый случай канала; PWA-режим — позже, отдельным решением).

Решения зафиксированы по ответам владельца от 02.11.2026 и переносятся в отчёт `docs/research/PBT-120.md` со статусом «подтверждено владельцем»/«решение владельца».

## D4. Ручной запуск — база, цикл — необязательное расширение

Обработка одного запроса по явной команде пользователя считается достаточным режимом первой версии (владелец запускает агента; агент берёт одно задание). Отсутствие длительного цикла/расписания не блокирует интеграцию и не считается отрицательным результатом пробы; оно лишь определяет, что скилл PBT-129 описывает одношаговую обработку. Обратное (цикл есть) расширяет, но не меняет архитектуру очереди.

## D5. Граница работ 120 и 121

В 120 владелец выполняет только действия без нашего сервера: отвечает на анкету и делает тривиальные наблюдения в клиенте — какие поля конфигурации MCP существуют, какие инструменты уже доступны (только имена), наблюдаемые таймауты. Подключение синтетического MCP-сервера, сквозной обмен и браузерный канал — протокол пробы PBT-121, который готовится здесь как согласованная инструкция, но выполняется в 121. Отчёт 120 не утверждает работоспособность обмена.

## D6. Обезличенный отчёт

`docs/research/PBT-120.md` по формату research-отчётов проекта: вопросы, таблица знаний со статусами, ответы анкеты (обезличенные: без названия клиента, компании, имён систем и версий, без токенов и URL внутренних систем), критерии перехода к 121 и зафиксированные блокеры/альтернативы. Недоступные проверки явно отмечаются `неизвестно`, а не пропускаются.

## D7. Критерии перехода к PBT-121

Продолжаем стенд, если по итогу отчёта:

1. Известна ОС клиента и доступен хотя бы один способ запуска стороннего MCP-сервера (конфигурация полей подтверждена).
2. Известен браузер/режим дашборда для пробы и хотя бы одно допустимое размещение дашборда (публичный сайт или локальная сборка).
3. Подтверждена допустимость ручного запуска обработки (минимум); цикл может оставаться `неизвестно`.
4. Ограничения компании по установке ПО зафиксированы хотя бы как «неизвестно» или «запрещено»; при запрете — зафиксированная альтернатива установки (бинарник/внутренний источник) или решение владельца о смене подхода.

Блокер канала (запрет HTTPS → loopback) не останавливает серию: фиксируем фактическую причину и выбираем альтернативу (локальная сборка дашборда, расширение — как отдельное решение с владельцем).

## Риски

- Анкета расширяется до исследования клиента — ограничитель D2: только свойства, необходимые для пробы 121.
- Владелец не может раскрыть свойство — легитимный ответ `неизвестно`; он не трактуется как поддержка.
- Смешение 120/121 (объявление обмена доказанным) — ограничитель D5; в отчёте обмен не утверждается.

## Приложение A. Анкета среды (минимальная)

| № | Вопрос | Что решает |
| --- | --- | --- |
| 1 | На какой ОС работает ваш внутренний агентский клиент? | Упаковка компонента, каталог очереди |
| 2 | Каким браузером откроете дашборд: вкладка или установленная PWA, Chrome/Edge/другой, корпоративные политики локальной сети известны? | Канал HTTPS → loopback, место пробы |
| 3 | Как в клиенте описывается MCP-сервер: команда запуска/args/env, URL, можно ли добавить сторонний сервер? Откуда можно установить (npm, файл, внутренний источник)? | Транспорт и способ установки компонента |
| 4 | Поддерживает ли клиент пользовательские инструкции/скиллы для агента и в каком виде? | Формат скилла PBT-129 |

| 6 | Есть ли у агента разрешённый инструмент чтения выбранной доски/проекта (достаточно факта)? | Допуск к планированию PBT-130 |
| 7 | Разрешает ли компания установку локального ПО (Node-скрипта/бинарника) и loopback-соединения на вашей машине? Где допустимо открывать дашборд? | Распространение PBT-131, сборка PBT-123 |

## Приложение B. Наблюдения владельца в клиенте (для статуса «проверено»)

1. Открыть экран/файл конфигурации MCP клиента; перечислить поля описания сервера (без значений секретов).
2. Спросить агента, какие MCP-инструменты ему доступны сейчас; вернуть только имена инструментов.
3. Если в клиенте видны настройки таймаутов/лимитов — зафиксировать их наличие и величины (без снимков экрана).

## Приложение C. Протокол пробы PBT-121 (согласуется здесь, выполняется в PBT-121)

1. Владелец получает синтетический MCP-сервер стенда (без корпоративных данных) и инструкцию установки по выбранному D3-способу.
2. Добавляет сервер в клиент по конфигурации из ответа №3.
3. Открывает дашборд в выбранном браузере/режиме (ответ №2), выполняет сопряжение с локальным компонентом.
4. Нажимает «Обновить» синтетического запроса; агент по команде обрабатывает задание; результат возвращается в дашборд и сохраняется.
5. Возвращает обезличенный результат: сработало/не сработало по шагам, наблюдаемая ошибка (текст без токенов), имя браузера, режим (вкладка/PWA).

Успех пробы 121: один полный синтетический обмен в реальном клиенте и браузере без отключения защиты.
