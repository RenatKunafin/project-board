## Context

См. proposal.md. Ветка feature/pbt-083-empty-first-launch создаётся от develop3016129. PR#69 внешней приёмки PBT-059 пока открыт отдельно и в задачу не включается.

В main.tsx bootstrap создаёт срез через ensureTwoChecklists, а при восстановлении вызывает firstChecklistId/secondChecklistId, которые снова создают недостающие документы. App получает list1Id/list2Id и при отсутствии restored сам открывает три окна. Пустое состояние уже реализовано в TabSurface: «Пустой дашборд» и действие добавления виджета.

Многие browser-проверки зависят от названий «Экземпляр 1 · Список 1», фиксированных w-1 и двух стартовых документов. Проверки Pages и planning тоже используют этот срез. Двухверсионный PWA-набор имеет свою композицию виджетов, но использует bootstrap приложения. Нагрузочные сценарии ранее закрывали три стартовых окна перед измерением, но оставляли два документа в БД. Эквивалентный сохранённый срез готовится явно до их прежней подготовки/закрытия, чтобы сохранить исходную нагрузку.

## Goals / Non-Goals

**Goals:** убрать создание примеров из обеих ветвей bootstrap и начального состояния App; сохранить восстановление данных и полезные регрессионные сценарии через явную тестовую подготовку.

**Non-Goals:** миграция или удаление старых примеров, новые схемы/SDK/зависимости, новый онбординг, изменение режимов раскладки, цвет задач, merge PR#69, публикация или изменение main.

## Decisions

### D1. Исходное пространство — одна пустая вкладка

При отсутствии сохранённых вкладок App создаёт вкладку «Дашборд» без окон. Сохраняется существующий режим по умолчанию и существующее оформление пустого состояния, включая доступное действие «Добавить виджет на вкладку». Само открытие каталога не создаёт документ; он появляется после явного создания/импорта.

Альтернатива без вкладок требует нового состояния и управления каталогом. Для запроса владельца достаточно пустой вкладки; отдельный экран приветствия не нужен.

### D2. Bootstrap восстанавливает данные без создания чек-листов

Удаляются ensureTwoChecklists, firstChecklistId/secondChecklistId, их вызовы и специфичные list1Id/list2Id из внутренних props App. Начальные panesByTab без restored пусты. В bootstrap остаются восстановление документов и пространства, существующие title fixup и диагностика ошибок/миграций.

Если документы существуют без сохранённых вкладок, они остаются в каталоге, а новая вкладка пуста. Сохранённая пустая вкладка считается полноценным восстановленным пространством. Нулевое количество чек-листов, отсутствие окон или удаление последнего документа не являются поводами создавать примеры.

Альтернатива скрыть только стартовые окна оставляет лишние документы и пополнение каталога при каждом запуске, поэтому не подходит.

### D3. Существующие записи сохраняются

Схемы и данные не мигрируют. В хранилище нет надёжного признака происхождения документа: имя «Список 1» или пустое содержимое не доказывают, что запись можно удалить. Поэтому сохранённые документы и окна, включая старый демонстрационный срез, восстанавливаются как прежде; новые примеры не добавляются.

Пустой новый старт проверяется в чистом профиле. Для существующего профиля проверяются неизменность документов, точное восстановление окон и отсутствие дополнительных записей. Автоматическая очистка старых данных требует отдельного решения и сюда не входит.

### D4. Фикстуры — в тестовой подготовке

Проверки первого запуска используют настоящий bootstrap с чистым профилем без подготовки примеров. Новые пользовательские цепочки явно создают необходимый набор через общие UI-helper: два документа чек-листа и нужное количество окон только там, где проверяются общий документ, изоляция, раскладки или жизненный цикл. Helper возвращает фактические идентификаторы/локаторы; прежние w-1 и названия экземпляров не становятся новым продуктовым контрактом.

Регрессии ранее сохранённого пространства, включая существующие проверки раскладок, жизненного цикла и общего документа, явно загружают именованный снимок старого среза в тестовую IndexedDB (restoreChecklistWorkspace). Его фиксированные ID/подписи — данные совместимости старого профиля, а не контракт нового старта. Для остальных тестов восстановления также допускается явная запись согласованного снимка в тестовую IndexedDB. Такой setup маркируется как подготовка сохранённого пространства и не применяется к проверке первого запуска. Не добавляются продуктовый флаг деморежима, скрытый URL/seed API или глобальная автоподготовка всех тестов. Существующие read/writeDocumentContent остаются в пределах текущего контракта.

Сценарии, которым чек-листы не нужны, запускаются с пустым дашбордом. Отдельно пересматриваются утверждения о количестве окон/документов и доступных названиях вкладок. Настройки новых экземпляров проверяются по реальному ID, полученному после создания окна. Проверки старого снимка используют ID из самой фикстуры. Для низкоуровневых mouse-жестов Гантта перед замером boundingBox выполняется bar.hover(): при более быстром пустом старте прежние тесты снимали координаты во время анимации RGL и попадали в фон сетки. Hover ждёт стабильность и получение события, расчёты/жестовая логика продукта не меняются.

### D5. Проверки подпути и производительности сохраняют смысл

Pages-проверка настоящего артефакта дополнительно подтверждает пустой старт. Для проверки сохранения и A→B→A нужный документ создаётся явно. В tests/planning и tests/widget-example учитывается новая первая вкладка и отсутствие лишних окон. В tests/pwa-updates обновляются только зависимости от bootstrap; историческая baseline PBT-028 остаётся настоящей старой сборкой с её прежним поведением.

В tests/performance исследуется, участвуют ли старые чек-листы в исходной нагрузке/счётчиках. Если участвовали, эквивалентный набор явно готовится до измеряемого участка: нельзя получить улучшение метрик просто удалением части исходной нагрузки или менять бюджеты. Полный benchmark выполняется, если setup или условия измерения изменены.

### D6. Ошибки восстановления сохраняют диагностику

Успешно восстановленный пустой каталог и ошибка чтения остаются разными состояниями. Удаление демосреза не должно скрыть существующий documentsLoadError. Тест ошибки подтверждает и сообщение в каталоге, и отсутствие автоматически созданных документов. При реализации fault injection выявил, что DocumentCatalogPanel одновременно показывал предупреждение об ошибке и успешное сообщение «Документов пока нет». Условия пустого каталога/фильтра ограничиваются успешной загрузкой; регрессия проверяется browser-сценарием реального отказа чтения. Новая система восстановления/повторных попыток не вводится.

## Risks / Trade-offs

- Массовые падения сценариев из-за неявной демоподготовки → общий явный setup и обновление только нужных ожиданий, без skip/retry и ослабления проверок.
- Helper сам маскирует дефект первого запуска → отдельные проверки чистого профиля обходятся без helper и проверяют реальные записи БД.
- Потеря пользовательских данных под видом уборки примеров → отсутствие удаления/миграции и регрессия сохранённого пространства со старым срезом.
- Изменение исходной нагрузки benchmark → сохранить эквивалентную подготовку и фиксировать условия; не менять бюджеты.
- Старые профили сохранят уже созданные примеры → намеренная совместимость; пользователь может закрыть окна и удалить ненужные документы штатными действиями.

## Migration Plan

1. После ревью реализовать App/bootstrap и тестовую подготовку в ветке PBT-083.
2. Проверить production первый запуск, создание документа, reload/offline и восстановление существующей БД; пройти обязательные и затронутые специализированные наборы.
3. Открыть один PR в develop. После принятия архивировать change с sync workspace-tabs/document-management и дождаться CI перед merge.
4. Main и Release не менять. На следующем отдельно разрешённом выпуске использовать сохранённый профиль v1.0.0 для внешних проверок PBT-059; локальные PWA-тесты не заменяют ту приёмку.
