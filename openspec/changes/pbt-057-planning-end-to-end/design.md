# PBT-057 — Проверка полной цепочки планирования

## Context

Основа: карточка PBT-057, принятые ADR PBT-002/003/017, действующие спецификации и сценарии импорта, преобразования отпусков, групп, календаря, конфликтов, round-trip, PlantUML и офлайн. Базовая ветка develop содержит PR#59/PBT-078; запуск — production build/preview. В существующем наборе 134 browser-теста и 492 unit; отдельный набор PWA-обновлений — 8 сценариев. Они сохраняются, новый набор проверяет связи между функциями.

Задача — проверка действующих требований. Delta specs и изменение продуктового поведения не нужны. Реализация одобрена владельцем 2026-10-23 («делаем»). Фактические результаты и оставшийся пробел матрицы приведены в `.docs/research/PBT-057.md`.

## Goals / Non-Goals

Каждый пункт DoD PBT-057 получает воспроизводимый пользовательский сценарий и доказательства на действительном приложении. Блокирующий дефект регистрируется отдельно. Производительность, hosting и полная матрица приёмки MVP остаются задачами 058/059/061.

## Decisions

### D1. Два независимых пользовательских сценария

**A. Рабочий план от импорта до публикации.**

1. Новая вкладка, создание плана, загрузка `tests/fixtures/gantt/onlinegantt-20261016.reference.gantt` через UI. Предпросмотр: 47 задач, 2 группы, 9 ресурсов, 21 FS-связь, 16 задач без исполнителя; применение создаёт независимый документ. Отпуск не назначается по названию автоматически.
2. Создать через UI контрольную группу и задачи с уникальными именами на фиксированные даты: A — 19–23.10.2026 (5 рабочих дней), B — 20–22.10.2026 (3 рабочих дня). Назначить явно QA и непараллелизуемый тип из справочника (при необходимости создать его через UI). Перенести задачу в контрольную группу, проверить вычисляемые сводные сроки.
3. Преобразовать выбранную импортированную отпуск-строку с явным выбором QA и контрольными датами 21–22.10.2026. Проверить исчезновение задачи и появление периода недоступности, а не угадывание исполнителя по имени.
4. Создать A → B с лагом 0. Проверить объяснимые FS-/ресурсные/отпускные проблемы по именам контрольных задач. Нарушения не должны автоматически двигать A/B и остальные задачи. Сделать ручную правку и проверить согласованность двух представлений общего документа.
5. Добавить праздник 21.10.2026. Даты A остаются 19–23.10, рабочая длительность становится 4. Проверить те же даты и назначение в проектном и ресурсном видах; отпуск 21–22.10 всё ещё пересекает рабочий четверг. Для B — 20–22.10 и 2 рабочих дня. Ожидаемые даты заданы заранее, а не вычисляются тем же кодом, который тестируем.
6. Выгрузить native JSON и PlantUML через UI. Импортировать скачанный JSON как независимый документ и повторно экспортировать: сравнить полное содержимое, title, schemaVersion и дополнительные поля, не сравнивая ID самого документа/метаданные времени создания. Проверить в PlantUML наличие контрольных задач, отпуска и выходного/праздника, парные теги и ожидаемый отчёт ограничений. Не проверять визуальную идентичность SVG стороннего рендера.
7. Закрыть окна исходного плана, открыть его из каталога документов, проверить сохранённые данные. Импортированная копия остаётся независимой.

**B. Восстановление и продолжение работы без сети.**

1. В новом изолированном контексте импортировать существующий небольшой native эталон через UI. Открыть проектное и ресурсное представления одного плана, создать две вкладки; явно настроить каскад и сетку, переместить окно и настройки представления.
2. Дождаться отдельно записи документов, структуры workspace и готовности ресурсов к офлайн. Никаких предположений, что «Сохранено» документа означает завершение другой очереди.
3. Закрыть все страницы контекста, отключить сеть и открыть новую страницу того же origin. Проверить документы, вкладки, режимы, геометрию и настройки по идентификаторам/содержимому, не по случайному DOM-порядку.
4. Отредактировать задачу через форму офлайн, проверить второй вид, закрыть/открыть страницу ещё раз и убедиться в сохранении правки. Холодный запуск означает новую страницу при отключённой сети с сохранёнными хранилищами контекста; переустановка браузера/очистка хранилищ в сценарий не входит.

Оба сценария независимы: B не использует файл, оставшийся после A. При реализации допустимо разделить длинный A на два независимых теста с одинаковой UI-подготовкой, если это улучшит диагностику; не создавать межтестовые зависимости или serial-цепочку общих данных.

### D2. Только продуктовые операции и устойчивые проверки

Подготовка и изменение плана — через существующий UI, загрузку файлов и реальные события. `window.__projectBoard.writeDocumentContent` не подменяет импорт/планирование. Скачанный native JSON и read-only IndexedDB допустимы как независимое подтверждение сохранения/идентичности документа и диагностика. Не менять записи БД, не добавлять специальные продуктовые маршруты/модули для теста.

Контрольные имена и заранее известные даты отделяют проверку от существующих конфликтов большого рабочего файла. При необходимости применять штатный поиск и максимизацию окон для виртуализированных строк; проверять содержимое, а не пиксельное совпадение разных библиотек. Проектный и ресурсный вид — один документ, импортированная копия — другой. Layout выбирается явно там, где нужна конкретная геометрия; отдельная офлайн-цепочка проверяет оба режима.

Длинные ожидания — по наблюдаемому состоянию, сохранённому снимку и наличию элементов. Таймаут сценария может быть больше стандартных 30с из-за числа пользовательских шагов; он не заменяет точных ожиданий. Без глобальных retries и fixed sleep как основного способа стабилизации.

### D3. Браузеры и честная матрица

ADR PBT-002 задаёт две последние мажорные версии Chrome/Edge/Firefox/Safari; PWA-установка — Chromium-десктопы. Три Playwright-движка не равны этой продуктовой матрице.

Первичная read-only проверка окружения 2026-10-23: Playwright 1.63.0, установлены только chromium-1243/headless-shell; Firefox/WebKit Playwright отсутствуют. В /Applications найдены Chrome 155.0.8059.86 и Safari 26.6.2; Edge и Firefox не найдены. Это сведения о наличии, а не результаты тестов.

Реализован отдельный `playwright.planning.config.ts` с проектами Chromium/Firefox/WebKit и установленного Chrome, запуск по одному worker для ресурсоёмких представлений и последовательные команды браузеров. Недостающие тестовые движки устанавливаются на этапе реализации/проверок с требуемым доступом к сети. Существующий полный набор не размножается на три движка и не получает скрытого fallback на Chromium при выборе Firefox/WebKit.

В отчёте — движок, фактическая версия, ОС, команда, результат каждого сценария; отдельно реальные Chrome/Edge/Safari/Firefox и предыдущие мажорные версии. Нативный Safari, отсутствие Edge, недоступность старых версий и невозможность конкретной автоматизации фиксируются явно. WebKit не объявляется Safari, а desktop-эмуляция не объявляется реальной установкой. Уточнение владельца 2026-10-23: полученных результатов достаточно для PBT-057; остальные браузеры проверяются вручную на бета-тестировании. Целевые браузеры ADR не меняются, непроверенные версии не объявляются проверенными.

### D4. Воспроизведение и отчёт

Запуск новых сценариев отдельной командой (предлагается `npm run test:planning`) на свежей production-сборке. Production preview работает на localhost:4173, тестовый origin — 127.0.0.1:4185 через транспортный прокси; перед тестом чистая среда по AGENTS.md, dev/MCP/старые preview остановлены. Все браузерные прогоны последовательны. Браузерные контексты новые, без пользовательских документов основного профиля. Существующая baseline PWA-обновлений не переписывается.

Отчёт `.docs/research/PBT-057.md` содержит таблицу: пункт DoD/правило ADR → сценарий/проверка → browser/version → результат/артефакт. Указываются SHA базы и итогового тестового коммита, команда сборки, версии Node/npm/Playwright, точные воспроизводимые команды, trace/screenshot при отказах и снимки ключевых этапов при успешном проходе. Связанные продуктовые дефекты получают отдельные карточки со свободными ID; текущая проверочная задача не маскирует функциональный scope.

### D5. Проверка офлайн и ограничения Playwright 1.63

Firefox/WebKit установлены; оба сценария прошли во всех четырёх проектах (8/8, retries=0). Chromium 153.0.8010.12, Firefox 155.0, WebKit 26.6, реальный Chrome 155.0.8059.86. Реальный Safari, Edge, обычный Firefox и предыдущие версии не проверены; последний пункт DoD закрыт по уточнённому владельцем критерию (остальные браузеры — ручная бета-проверка).

`tests/planning/network-proxy.mjs` передаёт обычную production-сборку и добавляет `Cache-Control: no-store`, чтобы HTTP-кэш не подменял precache Service Worker. После закрытия страниц прокси разрывает соединения с приложением; независимый API-запрос подтверждает недоступность origin. Chromium/Chrome/Firefox дополнительно получают `context.setOffline(true)`. Для WebKit используется только недоступность origin: это не проверка полного отключения сети или `navigator.onLine === false`.

Причина: минимальный независимый `tests/planning/offline-probe.mjs` воспроизводит отказ холодной SW-навигации WebKit при `setOffline` даже для буквального HTML-ответа. В Firefox сочетание routing + offline также ломает навигацию, поэтому route для управления HTTP-кэшем не используется. Диагностическая страница не заменяет сквозной продуктовый сценарий. Проблема WebKit 1.63 описана в [Playwright #42775](https://github.com/microsoft/playwright/issues/42775) (issue закрыт с меткой 1.64); текущая зависимость не обновлялась. [Документация Playwright](https://playwright.dev/docs/service-workers) отдельно описывает ограничения API Service Worker и перехвата запросов.

Во время разработки устранены гонка ожидания импорта с одинаковым названием (ждём новый ID), перекрытие кнопки максимизации соседним окном (активируем видимый заголовок) и исчезновение локатора каталога при переименовании (стабильная строка вместо фильтра старого названия). Это исправления новых тестов; самостоятельных продуктовых дефектов в проверенных цепочках не найдено.
