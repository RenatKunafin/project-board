## Context

Сервис документов готов (PBT-007): контракт в `widget-sdk`, реализация `createDocumentService()` в `dashboard`. Пропсы `WidgetProps` пока содержат только `widgetInstanceId` и настройки — ссылки на документ нет (SDK v0 п.2, [ADR PBT-002](../../.docs/adr/PBT-002.md)). Демо-виджет PBT-006 объявлен временным и заменяется первым настоящим модулем. Реестр и состояния «неизвестный тип» работают. Паттерн контракт(SDK)/реализация(dashboard) отработан.

## Goals / Non-Goals

**Goals:**

- Модуль `checklist`: содержимое, иммутабельные операции, компонент, определение типа.
- Контекст экземпляра получает `documentId` + `documentService` через пропсы; контракт `DocumentService` переезжает в SDK (модуль не импортирует внутренности платформы — DoD).
- Приложение: один документ чек-листа, два экземпляра — демонстрация согласованности (сценарий этапа 1 решений).

**Non-Goals:**

- Хранение на диске (PBT-009), автосохранение и retry (PBT-010), второе представление списка (PBT-011), каталог создания документов (PBT-025), связь пунктов с задачами Гантта (исключена решениями, раздел 14).
- Каталог типов как рабочий UI, иконки, перетаскивание — PBT-019+.

## Decisions

- **`DocumentService` переезжает в `widget-sdk`.** Модуль обязан обращаться к документам через SDK (DoD), значит интерфейс сервиса — часть контракта SDK; dashboard остаётся единственным местом реализации (`createDocumentService` импортирует тип из SDK). Механический перенос, потребители (`packages/dashboard`) обновляют импорт.
- **`WidgetProps` расширяется опциональными полями.** `documentId?: string`, `documentService?: DocumentService` — не у всех типов будет документ (нарушения существующих сценариев реестра нет: поля добавлены, старые сценарии про `widgetInstanceId`/settings не меняются). Виджет документа отвечает сам: нет `documentId`/`documentService` — рендер состояния «документ не привязан».
- **Содержимое документа чек-листа — `{ items: ChecklistItem[] }`**, `ChecklistItem { id: string; text: string; done: boolean }`. Иммутабельные чистые операции `addItem/renameItem/setItemDone/removeItem(content, ...) → content` в `packages/checklist/src/model.ts` — без React и без SDK-типов документов: модель тестируется изолированно (карточка: проверки операций, затрагивающих содержимое).
- **Правила модуля — вне сервиса.** «Пустой текст не добавлять» — правило операции `addItem` (возвращает исходный content при невалидном тексте), а не валидация сервиса. Компонент перед обновлением строит next-content через операции модели и вызывает `update(documentId, expectedRevision, nextContent)`; конфликт редакций (PBT-007) на данном шаге просто прокидывается — retry-политика придёт с автосохранением (PBT-010).
- **id пунктов — `crypto.randomUUID()`** на стороне операции добавления (генерируется в модели, чтобы компонент не решал задачу идентификации).
- **Виджет в приложении.** `main.tsx`: создаёт `documentService` и один документ `checklist/list` (schemaVersion 1, items: []); реестр типов: `checklist`; оболочка рендерит **два экземпляра** одного документа (side-by-side) + каталог + unknown-блок. Демо-виджет PBT-006 и его e2e удаляются.
- **Иконка типа.** SDK v0 декларирует иконку; в этом change поле не вводится (UI каталога не рендерит иконки; поле появится в PBT-019 вместе с каталогом) — отклонение от буквального состава ADR-6.1 фиксируется здесь.

## Risks / Trade-offs

- [Два экземпляра в одном окне — слабая проверка рассинхронизации] → для PBT-008 достаточно (синхронные подписки покрыты unit-тестами сервиса); реальное разделение по вкладкам появится с PWT-стеком (PBT-018+).
- [Опциональные documentId/documentService допускают забытую передачу] → виджет чек-листа рендерит явное состояние «документ не привязан»; в PBT-019 привязка станет обязательной для документных типов.
- [Переименование через prompt-подобный inline-инпут усложняет e2e] → редактирование по двойному клику с автофокусом; e2e использует getByDisplayValue.
