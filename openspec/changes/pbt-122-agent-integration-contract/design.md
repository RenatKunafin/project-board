## Goals / Non-Goals

**Goals:** независимо реализуемые PBT-123–132; один разрешённый источник/доска, один текущий спринт, явное обновление, проверяемые факты, сохранность ручных данных, восстановление после потери ответа/ACK. Доставка допускает повторы; применение одного результата к одному документу идемпотентно.

**Non-Goals:** exactly-once доставка, облачный relay, автономный агент/расписание, запись в Jira, перепланирование Гантта, чтение произвольных документов, перенос полномочий через backup, поддержка всех ОС/браузеров, обещание сохранности при физической потере диска.

## Decisions

### D1. Транспорт и размещение разделены

Предлагаемый контракт: **клиент агента → MCP stdio → локальный компонент; страница → HTTP JSON на `127.0.0.1`**. Браузерный API — собственный API приложения, не MCP Streamable HTTP. Браузер инициирует короткие запросы и опрашивает состояние; компонент не подключается к браузеру. WebSocket и браузерное расширение сейчас не нужны.

Компонент принимает один явно настроенный `allowedOrigin`, например `https://renatkunafin.github.io` либо `http://127.0.0.1:4390`. Схемы сообщений и права одинаковы при обоих размещениях. Публичный origin остаётся кандидатом; локальный origin — проверенный запасной вариант. TLS на компоненте не вводим на основании неподтверждённого диагноза. Ранее данный предварительный выбор локальной сборки возвращён владельцем к обсуждению; обязательного локального размещения этот дизайн не устанавливает.

Повторная синтетическая проверка на рабочем Mac: сохранённое разрешение сайта → reload → новый pair → URL/ошибка запроса и факт получения OPTIONS/POST компонентом. Только если новый запрос снова отклонён, проверяются действующие политики и ограничения среды. Эта проверка определяет профиль поставки до пилота, но не меняет протокол, очередь или сохранение. Если потребуется другой транспорт, это пересмотр D1 до его реализации, а не скрытая доработка PBT-131.

**Без аналитики ≠ обязательно локально.** PBT-123 готовит отдельный профиль сборки без аналитики с самого bootstrap и с различимым manifest профиля. Размещение может быть разрешённым HTTPS-origin или локальным HTTP-origin. Текущий публичный сайт с Метрикой не является таким профилем. Переход между origin создаёт отдельное браузерное хранилище; перенос данных — явный backup/restore с новым сопряжением. Service worker не кеширует API, токены и ответы; API имеет `Cache-Control: no-store`, не попадает в navigate fallback. Старый кеш сборки с аналитикой не должен подменять обещанный профиль. Публикация не входит в PBT-122.

### D2. Один процесс, стабильный адрес, ограниченный локальный доступ

Клиент агента владеет процессом. Продуктовый экземпляр использует фиксированный конфигурируемый порт; базовый кандидат — `43821`, занятость означает явный отказ. Не искать следующий порт автоматически, не завершать чужой процесс и не подключаться к нему молча. `--port 0` допустим только для изолированных тестов: смена порта ухудшает воспроизводимость адреса. При закрытии stdin процесс прекращает обслуживание и освобождает ресурсы; оставшийся процесс диагностируется адресом, PID и идентификатором запуска без секретов.

HTTP слушает только `127.0.0.1`; точные Host и Origin проверяются до чтения тела. Origin `null`, отсутствующий или чужой отклоняется. OPTIONS не требует bearer, но проверяет Host/Origin и возвращает только разрешённые методы/заголовки; остальные вызовы требуют bearer, кроме pair и публичной версии протокола. Origin сравнивается целиком, без масок и без пути. Это не защита от вредоносного процесса под тем же пользователем ОС. Произвольный URL/команду/путь из payload компонент не исполняет.

MCP stdout содержит только протокольные сообщения; диагностические события идут в stderr без payload, кодов, токенов, внутренних URL и названий задач. Наличие процесса обозначает «Компонент подключён», а не «Агент работает». Активность исполнителя — отдельное время последнего claim/submit.

### D3. Идентичность и версии

| Поле | Владелец / срок жизни |
| --- | --- |
| `componentId` | UUID установки в каталоге компонента; не меняется при обычном restart |
| `runId` | Новый UUID каждого запуска; ограничивает действительность сессионных секретов, не адресует долговечное задание |
| `workspaceId` | UUID платформы в локальных непереносимых настройках; переживает reload, заменяется при restore/сбросе |
| `bindingId` | UUID связи компонента и workspace; очередь не усыновляется по одному documentId |
| `grantId` | UUID конкретного разрешения documentId + operation + configRevision; отзыв необратим для этого UUID |
| `sessionId` | Сессия одного browser-контроллера с текущим runId; истекает/отзывается отдельно от очереди |
| `documentId`, `baseRevision` | Существующая оболочка документа и её редакция при создании запроса |
| `configRevision` | Версия конфигурации предметного документа: источник, доска, фильтр/метрика; любая смена инвалидирует старый grant |
| `requestId`, `resultId`, `attemptId` | UUID запроса, единственного принятого результата и конкретной аренды исполнителя |

`protocolVersion: 1` — точная версия конверта; `operationVersion: 1` — схема `sprint.refresh`; `queueSchemaVersion: 1` — формат файла; `schemaVersion` документа — независимая версия модуля. Версия MCP согласуется SDK отдельно. Hello возвращает версии приложения/компонента, поддержанные protocol/operation versions и лимиты. Нет общего протокола/операции — явный отказ до сопряжения/постановки, без downgrade payload и перезаписи очереди. Инструкция агента заявляет protocol/operation versions, а не равенство npm-версий трёх компонентов.

### D4. Сопряжение, полномочия, reload и отзыв

1. MCP `connection_info` по явной команде выдаёт адрес, componentId/runId и одноразовый случайный код минимум 128 бит, действующий 5 минут. Код не записывается в журнал; после 5 неверных попыток аннулируется.
2. Пользователь вводит код на странице и явно выбирает один документ и `sprint.refresh`. Сервер связывает workspace, documentId, configRevision и операцию; браузер подтверждает эту же область локально. Pair не открывает чтение других документов. В новый запрос передаётся только нужная конфигурация источника.
3. Сервер выдаёт случайный bearer минимум 256 бит на 8 часов без автоматического продления. В памяти сервера хранится его digest, в браузере — sessionStorage контролирующей вкладки. Токен не входит в URL, IndexedDB, backup, документ, очередь или MCP-аргументы агента. После reload той же вкладки он может использоваться до истечения; после restart компонента требуется новое сопряжение.
4. Restart сохраняет задания/результаты, но приостанавливает доступ к ним до повторного сопряжения. Пользователь выбирает продолжение именно прежней связи, сверяя workspace/документ/область. По одному совпадению UUID нельзя открыть старую очередь другому профилю. Для восстановления владения связь имеет отдельный случайный секрет 256 бит, действующий 30 дней: платформа сохраняет его через свой адаптер в непереносимых локальных settings, компонент хранит только digest. Он переживает закрытие вкладки, но работает только вместе с новым одноразовым кодом и явным согласием; это не bearer для чтения/применения. При восстановлении секрет ротируется. При утрате/истечении секрета старая связь не восстанавливается: новое сопряжение создаёт новый bindingId, старые задания остаются недоступными до очистки. Backup не переносит секрет.
5. «Отключить и отозвать доступ» сначала фиксирует локальный запрет grant, затем уведомляет компонент и уничтожает bearer/секрет восстановления. Если компонент недоступен, локальный запрет всё равно действует; UI сообщает, что удалённое подтверждение не получено. Компонент при получении отзыва запрещает новые claim/submit/применения, сохраняет tombstone отзыва. Новое согласие создаёт новый grantId; старый не возобновляется. Квитанции и непереносимые локальные запреты сохраняются для диагностики, не становятся полномочиями нового grant.

Потеря сети/закрытие вкладки сами по себе не означают отзыв: агент может завершить уже взятое задание, а результат ждёт приложения в пределах TTL. Истечение сессии блокирует дальнейшие обращения браузера/выдачу новых заданий; ранее взятая аренда ограничена своим сроком и областью. Явный отзыв прекращает и её.

Для v1 один workspace обслуживает одна browser-вкладка-контроллер. Она удерживает Web Lock по workspace и не передаёт токены через BroadcastChannel. Другие вкладки показывают, где интеграция активна; takeover требует освобождения lock и сопряжения. Несколько окон виджетов внутри дашборда пользуются одним контроллером. Два профиля — разные workspace и binding; один сервер v1 допускает только одну активную связь. Ограничение не запрещает обычную offline-работу остальных вкладок.

### D5. Очередь: ограниченный JSON, один писатель

Для первой версии предлагаем **JSON-снимок за адаптером хранилища**. SQLite полезна при большом объёме/конкурентных писателях; сейчас один процесс и малая очередь не оправдывают новую библиотеку или runtime-зависимость. Граница адаптера допускает отдельную миграцию позже.

Каталог macOS: `~/Library/Application Support/Project Board/agent/<profile>/`, права 0700; файл очереди и служебные файлы — 0600, исключаются symlink/чужой владелец. `profile` — ограниченный идентификатор, не произвольный путь от агента. В файле есть componentId, связи, отозванные grant, запросы, результаты и версии; секреты источника, bearer и открытые коды/токены попыток отсутствуют. Корпоративные факты в результатах присутствуют: файл не считается обезличенным или зашифрованным.

Переходы сериализуются. Подтверждение операции следует после записи полного нового снимка во временный файл в том же каталоге, sync файла, rename и sync каталога. При неоднозначной ошибке после rename компонент прекращает мутации до перечитывания; нельзя продолжать с отставшим состоянием памяти. Второй писатель исключается lock-файлом, создаваемым эксклюзивно. Живой/неопределённый владелец lock — отказ; оставшийся после аварии lock снимается диагностической командой только после проверки отсутствия владельца. Порт и каталог проверяются независимо. Повреждённая/будущая версия файла блокирует работу с диагностикой, не сбрасывает данные молча. Оставшийся tmp не считается подтверждённым состоянием.

Предлагаемые лимиты v1, показываемые в hello: 20 незавершённых запросов на компонент, один незавершённый запрос на `(bindingId, documentId, operation)`, результат до 1 MiB UTF-8 и до 2000 задач, файл до 32 MiB. Превышение — явный отказ, без усечения. Повтор create с тем же requestId и телом возвращает прежнее состояние; иное тело с тем же ID — конфликт. Второе нажатие при активном запросе возвращает его ID. После завершения новое явное обновление получает новый ID.

Lease исполнителя — 5 минут, максимум 3 попытки; `renew` может продлевать аренду до общего предела 15 минут на попытку. Попытка имеет секретный токен, выдаваемый только claim; на диске хранится digest. Истёкшая попытка не может submit/renew. После restart старые попытки инвалидируются; повторная выдача возможна после восстановления связи. Общий TTL queued/running — 24 часа с создания; ready — 24 часа с приёма результата. Серверные часы задают сроки; после обнаруженного отката часов компонент приостанавливает выдачу до безопасного восстановления, не продлевает аренды молча.

Повторы транспортного обращения используют тот же ID. Автоматически повторять смысловой запрос после конфликта нельзя. Временная ошибка источника/429 даёт `retryAfterMs`; минимальная пауза 30 секунд, экспоненциально до 5 минут, максимум попыток прежний. Вызовы модели инициирует пользователь/клиент, сервер их сам не запускает. Пустая очередь завершает один запуск инструкции без бесконечного polling агентом. Браузер опрашивает статус примерно раз в 2 секунды при активном запросе, при недоступности увеличивает паузу до 30 секунд; скрытие всей страницы допускает задержку, скрытие отдельного виджета не отключает контроллер.

Payload терминальных заданий очищается в течение суток; компактные записи ID/итога/digest сохраняются 30 дней, затем неизвестные старые ID отклоняются (submit не создаёт запрос). Ограничения места никогда не удаляют незавершённые задания молча. Явная очистка очереди требует прекращённого обслуживания и не затрагивает документы.

### D6. Конверты и операции

Пример данных без секретов; короткие ID ниже заменяют UUID только для читаемости:

```json
{
  "protocolVersion": 1,
  "requestId": "req-1",
  "bindingId": "bind-1",
  "workspaceId": "ws-1",
  "grantId": "grant-1",
  "documentId": "doc-1",
  "operation": "sprint.refresh",
  "operationVersion": 1,
  "baseRevision": 7,
  "configRevision": 2,
  "parameters": {
    "sourceId": "source-1",
    "boardId": "board-1",
    "selection": "single-active-sprint",
    "metric": "issue-count"
  }
}
```

Сервер назначает createdAt/expiresAt и сверяет все адресные поля с правами; клиент их не расширяет. Источник — настроенный пользователем разрешённый locator (без токена), связанный с sourceId; внутренний адрес допускается только в локальной конфигурации/задании, не в диагностике. baseRevision — положительное целое, configRevision — положительное целое; ID непустые и ограниченной длины. JSON имеет строгую схему, неизвестные поля и версии отклоняются. Все времена — RFC3339 UTC, даты спринта — ISO date с явно указанной зоной источника; числа конечные, лимиты проверяются до разбора/применения.

Claim возвращает конверт, attemptId, leaseUntil и отдельный attemptToken. Submit повторяет requestId/bindingId/documentId/configRevision/operationVersion и attemptId/token; сервер не принимает цель из ответа на доверии. Payload результата:

```json
{
  "resultId": "result-1",
  "snapshot": {
    "sourceId": "source-1",
    "boardId": "board-1",
    "sprint": {"id": "sprint-1", "name": "Спринт", "startDate": "2026-11-02", "endDate": "2026-11-15", "timeZone": "Europe/Moscow"},
    "observedAt": "2026-11-07T10:00:00Z",
    "coverage": {"kind": "complete", "reason": null},
    "metric": "issue-count",
    "items": [{"id": "issue-1", "key": "DEMO-1", "title": "Пример", "statusId": "status-1", "isSubtask": false}]
  }
}
```

`resultDigest` вычисляется сервером по нормализованному валидированному payload (UTF-8 JSON: ключи объектов сортируются рекурсивно, порядок массивов сохраняется); браузер пересчитывает тем же алгоритмом. SHA-256 — проверка идентичности повторов, не подпись достоверности Jira. Один resultId/attempt с тем же digest идемпотентен; другое содержимое — `result-conflict`. Повтор уже принятого submit возвращает прежнее состояние до проверки истечения прежней аренды, но не обходит отзыв полномочий.

Полный submit-конверт содержит обязательные `protocolVersion, requestId, bindingId, documentId, configRevision, operationVersion, attemptId, attemptToken, resultId, snapshot`. Status возвращает исходный конверт запроса и серверные `state, createdAt, expiresAt, attemptCount`; при ready/applying добавляет `resultId, resultDigest, snapshot, readyUntil`, при applying — `permitId`. Секрет попытки в status не возвращается. ACK содержит `protocolVersion, requestId, bindingId, documentId, permitId, resultId, resultDigest, appliedRevision`; grant/workspace сверяются по сессии и исходному запросу. Повтор ACK с теми же полями идемпотентен; иные revision/digest/permit отклоняются. `observedAt` не может быть позднее серверного receivedAt более чем на 5 минут и не может быть старее уже принятого снимка того же спринта; нарушение даёт `invalid-result`, а не молчаливое обновление времени.

Ошибка: `{ "error": { "code": "revision-conflict", "message": "Документ изменён", "retryable": false, "retryAfterMs": null }, "requestId": "req-1" }`. Коды: `unauthorized`, `origin-forbidden`, `version-unsupported`, `grant-revoked`, `scope-mismatch`, `lease-expired`, `request-expired`, `queue-full`, `payload-too-large`, `invalid-result`, `result-conflict`, `revision-conflict`, `config-changed`, `document-missing`, `persistence-failed`, `source-unavailable`, `source-permission-denied`, `ambiguous-sprint`. HTTP 401/403/409/413/429/503 отделяются от доменных ошибок; недоступный CORS-ответ в браузере показывается как ошибка связи с инструкцией диагностики, без выдуманной точной причины.

| Сторона | Разрешённые операции |
| --- | --- |
| Браузерный API `/v1/*` | hello, pair, create/list/status, cancel, begin-apply, acknowledge, reject, revoke; кроме hello/status GET остальные POST; list/status доступны только своей связи |
| MCP | connection_info, list_requests, claim_request, renew_claim, submit_result, fail_request; агент не может pair от имени страницы, ACK или читать произвольные документы |
| Модуль спринта | Чистая проверка и построение нового content из текущего документа, конфигурации и валидированного snapshot |

### D7. Состояния и гонки

| Из | Событие / условие | В | Кто фиксирует |
| --- | --- | --- | --- |
| — | Валидный create и действующий grant | queued | Компонент после записи |
| queued | Атомарный claim | running | Компонент; один победитель |
| running | renew в пределах общего лимита | running | Компонент |
| running | Lease истёк/временная ошибка, попытки и TTL остались | queued с notBefore | Компонент |
| running | Валидный submit текущей попытки | ready | Компонент после записи payload |
| queued/running/ready | Отмена/отзыв/TTL | cancelled/revoked/expired | Компонент; токены попыток недействительны |
| ready | begin-apply браузера при действующей сессии/grant | applying | Компонент сохраняет permitId до ответа |
| applying | Квитанция атомарного сохранения | applied | Только браузерный ACK; компонент сохраняет итог |
| applying | Доказанный отказ без записи, локальный permit закрыт | rejected | Браузер + компонент |
| running | Неисправимая ошибка или исчерпаны попытки | failed | Компонент |
| Любое | Повтор того же запроса/ответа | Прежнее состояние | Без второго эффекта |

Терминальные состояния не возобновляются. Новый запрос — новый ID. **applying не переходит обратно в ready по таймеру:** после выдачи permit сервер не знает, произошла ли запись. Lease агента уже завершён. Потеря вкладки/процесса означает «Нужно проверить сохранение», а не автоматическую отмену. До сверки квитанции новый запрос для этого документа блокируется; applying занимает одно из 20 мест и не очищается по TTL.

Cancel до begin-apply отменяет запрос. Если применение уже началось, UI не обещает немедленную отмену: «Применение началось; проверяем сохранение». Платформа атомарно закрывает локальный permit или обнаруживает уже сохранённую квитанцию. Только затем серверу передаётся итог. Локальное закрытие permit и commit соревнуются в одной транзакционной области: победил commit — уже сохранённые факты остаются; победил запрет — поздняя запись невозможна. Нажатие кнопки не откатывает ранее завершённую запись.

Отзыв через UI также сначала сохраняет локальный запрет. Серверный отзыв/истечение сессии прекращают новые разрешения; уже выданный permit требует сверки. Нельзя гарантировать удалённую отмену транзакции, которая уже началась в другом процессе; этот случай показывается отдельно, без ложного статуса «ничего не применено». После отзыва допускается только ограниченное подтверждение существующей квитанции через новое явное сопряжение владельца, без повторного применения старого результата.

### D8. Сохранение документа и восстановление ACK

Предлагаемая платформа PBT-126 добавляет внутреннюю асинхронную операцию `commitIntegrationResult`, а не меняет смысл публичного `DocumentService.update`. В адаптере IndexedDB появляются локальные таблицы разрешений/permit и квитанций. Документ и квитанция записываются **в одной readwrite-транзакции**, вместе с проверкой workspace generation, grant/config и ожидаемой сохранённой revision. Это новая миграция БД в PBT-126, не изменение схем существующих предметных документов.

Последовательность:

1. Контроллер проверяет результат, адресацию, версии и права; создаёт локальную pending-запись permit для requestId. При потере ответа begin-apply повтор с тем же requestId возвращает тот же серверный permitId. Закрытая локальная pending-запись не может ожить от позднего ответа.
2. Сервис завершает очередь сохранения **целевого** документа и проверяет `baseRevision` как в памяти, так и в хранилище. Изменение любого поля, включая заголовок, означает конфликт; старый payload не повторяется с новой revision. Нужен новый запрос пользователя.
3. Зарегистрированный чистый обработчик модуля валидирует snapshot и формирует новый content, сохраняя локальные дополнения. Платформа знает только тип операции и контракт обработчика; регистрация находится в composition root. Никаких импортов модуля из платформы.
4. Сервис сериализует мутации целевого документа на время фиксации; синхронная ручная мутация в этот короткий интервал получает явный busy-отказ и сохраняет черновик. Другие документы не блокируются. Адаптер атомарно проверяет всё ещё открытый permit, grant, generation и revision; сохраняет revision + 1 и квитанцию `{workspaceId, bindingId, grantId, requestId, resultId, resultDigest, documentId, appliedRevision, permitId}`.
5. Только после завершения транзакции сервис обновляет память и уведомляет все окна. Ошибка записи не публикует новый snapshot как сохранённый и не оставляет его в обычной очереди автосохранения. Повтор после ошибки разрешён лишь при неизменных правах/config/baseRevision и том же permit; иначе rejected.
6. Контрольное чтение квитанции и документа через адаптер даёт основание для ACK. Нужны точные ID/digest/revision квитанции; одного индикатора saved или `flushAll()` недостаточно. Если документ уже имеет более позднюю ручную revision, квитанция всё ещё доказывает совершившийся commit, но не заявляет, что нынешний content равен снимку.
7. Сбой после commit до ACK: после reload читается квитанция, повторяется только ACK, revision не увеличивается. Если квитанции нет, сервис проверяет pending/closed permit и данные; может повторить commit при сохранённых исходных условиях либо атомарно закрыть permit и сообщить rejected. Нельзя удалять неизвестный permit, пока старый контроллер способен записать его.

Транзакция делает эффект атомарным относительно браузерной БД; ACK означает завершённую запись, подтверждённую чтением. Это не обещание аппаратного fsync при потере питания. Квитанция принадлежит платформе, не виджету и не агенту; последующая ручная правка не уничтожает её. Квитанции незавершённых applying не удаляются, терминальные очищаются согласованно со сроком серверных tombstone.

Предметный SDK получает только минимальные типы регистрации операции и ограниченный сервис команд для виджета в реализующих changes: запросить/посмотреть/отменить операцию **своего документа**. Фабрика платформы связывает сервис с documentId; виджет не передаёт произвольный target, bearer или URL. Проверка доступа повторяется платформой и компонентом. Доступ к persistence, квитанциям и IndexedDB не появляется в публичном DocumentService.

### D9. Restore, удаление, смена источника и несколько окон

- Backup переносит факты и локальные дополнения, но исключает workspaceId, grant, binding-секреты, permits и receipts. Restore атомарно заменяет workspaceId, повышает generation, очищает локальные полномочия/permits/receipts и сигнализирует контроллеру. Все старые in-flight операции отклоняются по generation; новое сопряжение создаёт новую связь. Документы из копии не получают чужую очередь даже при прежних documentId.
- Удаление документа в той же области сериализации закрывает permits и отзывает grant. Commit не создаёт отсутствующий документ. Квитанция уже состоявшейся записи может остаться для сверки ACK, но документ не восстанавливается. Закрытие окна виджета не удаляет документ и не отзывает доступ автоматически.
- Смена source/board/фильтра/правила Done повышает configRevision, закрывает permits и отзывает прежний grant. Незавершённые задания не переносятся на новый источник. Новая конфигурация требует явного разрешения; сохранённые факты старого источника не показываются как свежие данные нового.
- Два окна одного документа в приложении получают один commit и общую очередь; настройки сортировки/фильтрации вида остаются в settings экземпляра. Скрытый виджет не владеет доставкой. Между отдельными browser-вкладками CAS и generation защищают БД от перезаписи; нельзя выдавать это за уже существующую мгновенную синхронизацию их React-состояния. PBT-126 тестирует внешний конфликт и явное перечитывание.

### D10. Первая предметная операция и метрика

Предлагаемая единица v1 — **количество задач**, без story points и часов. Один настроенный источник, одна доска, один активный спринт; нет активного или несколько активных — структурированная ошибка, агент не выбирает случайный. Это снимает зависимость первой пробы от формата оценок старой Jira. В PBT-127 уточняются только реальные поля выбранного источника, а изменение единицы требует отдельного пересмотра договора.

Идентичность задачи `(sourceId, issueId)`, спринта `(sourceId, sprintId)`; key/title не служат ID. Подзадачи не входят в счётчик v1, их `isSubtask` должен быть известен. Done задаётся явным набором statusId в конфигурации источника; неизвестный статус диагностируется, не считается нулём/Done по догадке. Для полной выборки: total — количество верхнеуровневых задач, done — количество с разрешённым Done-statusId, remaining = total − done. Это текущее состояние, не исторический burndown.

Snapshot содержит source/board/sprint, время наблюдения, полноту и причину неполноты. `complete` означает проверенную агентом пагинацию всего согласованного scope; компонент проверяет форму, но не может доказать истинность сведений источника. Сверка владельцем — PBT-130.

Для полного снимка состав импортируемых фактов заменяется в пределах источника/спринта, локальные заметки/метки сохраняются отдельно по стабильным ID. Частичный снимок того же спринта обновляет только полученные задачи, остальные остаются с прежним временем наблюдения и отметкой неподтверждённости. Общий счётчик не выдаётся за полный. Частичный снимок другого спринта не смешивается с прежним: rejected, прежние факты сохраняются. Пустой полный снимок допустим; неизвестное значение — null/диагностика, не 0. Название/описание задачи — данные, не инструкции агенту и не HTML для исполнения.

## Risks / Trade-offs

- [Рабочий Chrome отклоняет публичный канал] → отдельная проверка нового запроса после разрешения; локальный origin остаётся запасным. Не распространять отказ одной среды на весь транспорт.
- [Секрет восстановления потерян] → новое сопряжение/новая связь; прежняя очередь не присваивается новому профилю. Удобство восстановления ограничено намеренно.
- [Неизвестный исход применения после сбоя] → applying блокирует новое обновление до сверки квитанции; нет ложного автоматического rollback или success.
- [JSON ограничивает масштаб и требует аккуратной атомарной записи] → малые явные лимиты, один писатель, fault injection; SQLite возможна отдельной миграцией.
- [Платформенная операция commit увеличивает объём PBT-126] → миграция, сериализация и receipts составляют один инвариант сохранения; не добавлять в этот PR UI спринта или иные SDK-функции. Если реализация не обозрима, явно разделить карточку до кода.
- [Данные агента могут быть неполны/ошибочны] → schema/coverage/provenance, ручная сверка пилота; валидный JSON не доказывает истинность источника.
- [Автоматическая запись source snapshot конфликтует с ручной правкой] → строгий baseRevision, новый запрос после конфликта. Автоматический rebase полного snapshot не выполняется.

## Migration Plan

PBT-122 не мигрирует приложение: после принятия дизайна выпускает постоянную документацию и корректировку интерпретации отчёта 121. Реализация по отдельным changes:

1. **123**: профиль без аналитики независимо от места размещения. **124**: stdio/HTTP, версии, pairing, непереносимая identity и разрешения в служебных settings платформы; исключение этих записей из backup и очистка при restore проверяются уже здесь.
2. **125 → 126**: долговечная очередь → платформа commit/receipt/restore. Новые таблицы БД и общий schema version меняются только в 126, с отказом старого приложения перед записью будущей схемы. Откат сборки не понижает БД молча.
3. **127** после 122 независимо от очереди: отдельный документ спринта и чистый обработчик. **128** после 126/127: UI и минимальный сервис команд своего документа. **129** после 124/125/127: инструкция одной обработки с лимитами.
4. **130** после 123/128/129 и проверки выбранного origin: реальный пилот. **131 → 132**: воспроизводимая поставка и сквозная приёмка. Сборка/установка пакета проверяются уже в 124; упаковка 131 не откладывает проверку жизнеспособности.
5. **133–136** остаются последующими самостоятельными этапами. Публичная публикация и перенос корпоративных данных не входят в подготовку контракта.

После одобрения этого дизайна уточнить карточки 123–129 и дорожную карту; в PBT-122 не отмечать будущую реализацию выполненной. Будущие capabilities: `agent-connection` (124), `agent-requests` (125/126), `sprint-data` (127), `sprint-widget` (128); изменения существующих persistence/backup/SDK specs — в соответствующих реализующих changes.

## Open Questions

- Фактическая причина отказа нового запроса на рабочем Mac после выданного разрешения; нужен ли локальный профиль для этой среды. Протокол допускает оба origin, пилот требует доказанного выбранного маршрута.
- Конкретные source locator/boardId/Done-statusId и доступный формат инструкции внутреннего клиента — в 127/129/130, без секретов в репозитории.
- Поддержка установленной PWA и других браузеров не заявляется до соответствующих проб; первая подтверждённая среда — Chrome, обычная вкладка, macOS.
