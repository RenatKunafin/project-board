# Design — PBT-033: ресурсы и типы работ

## Context

База: модель v1 с `resources: [{ id, title }]`, `workTypes: [{ id, title, allowsParallel }]`, ссылками `tasks[].assigneeIds` / `tasks[].workTypeIds` / `unavailability[].resourceId`; валидатор `parsePlanContent` отклоняет ссылки на несуществующие записи (`unknown-reference`); контракт команд PBT-031 (`PlanCommand`, `PlanCommandResult`, коды `unknown-resource` / `unknown-work-type` уже есть) и прецеденты модулей `plan-hierarchy.ts` (PBT-032: type-only импорт типов результата, локальные хелперы, порядок «в конец»). Согласованные правила: ресурсы — отдельные исполнители, `QA` и `QA2` — разные люди (11.1); типы работ с флагом параллельности, «ПСИ» может выполняться параллельно (11.2); смена параллельности — только правкой типа в справочнике (D5); планы независимы (11.1, ADR-8 PBT-002).

## Goals / Non-Goals

**Goals:** команды справочников в едином `PlanCommand`; идентичность по ID; хранение `allowsParallel` в документе; удаление используемой записи без висячих ссылок (план остаётся валидным при чтении); независимость планов; пустые названия отклоняются.

**Non-Goals:** операции назначения и недоступности (PBT-034), проверки конфликтов (PBT-036), UI-редакторы (PBT-041), календарь (PBT-044).

## Decisions

### D1. Модуль `plan-catalogs.ts`, команды в едином `PlanCommand`

Файл `plan-catalogs.ts` по шаблону `plan-hierarchy.ts`: чистые функции + type-only импорт типов результата из `plan-commands.ts` (без runtime-цикла). Объединение `PlanCommand` дополняется шестью вариантами:

```text
PlanCommand +=
  | { type: 'createResource'; input: { title: string } }
  | { type: 'updateResource'; resourceId: string; patch: { title? } }
  | { type: 'deleteResource'; resourceId: string }
  | { type: 'createWorkType'; input: { title: string; allowsParallel: boolean } }
  | { type: 'updateWorkType'; workTypeId: string; patch: { title?; allowsParallel? } }
  | { type: 'deleteWorkType'; workTypeId: string }
```

Диспетчер делегирует; результат — тот же `PlanCommandResult`. Прецедент PBT-032: одна команда с патчем вместо пары «переименовать / изменить признак» — поля справочника однострочные, дублирование не оправдано.

Новый код отклонения: `'invalid-title'` — название создаётся/переименовывается из пустого или пробельного значения после `trim` (прецедент `assertDocumentTitle` SDK). Названия сохраняются обрезанными. Отсутствие этого кода заставило бы либо писать мусорные записи в справочник (мусор виден в UI и импорте), либо молча заменять название — против стиля «диагностика вместо молчаливого fallback».

### D2. Удаление используемой записи: чистка ссылок без удаления задач (утверждено владельцем)

DoD требует «удаление используемой записи по согласованному правилу» — правило в ADR PBT-003 не зафиксировано. Варианты:

**Вариант A (утверждён владельцем 2026-10-14):** чистка ссылок, задачи сохраняются. Удаление ресурса: фильтрует его из `assigneeIds` всех задач (опустевший массив удаляется из задачи — минимальное представление; «нет назначений» и «пусто» семантически равны, D2 ADR PBT-003) и каскадно удаляет недоступности ресурса (без ресурса они невалидны — продолжение D6 PBT-031). Удаление типа: фильтрует его из `workTypeIds`. Задачи, их даты и зависимости не изменяются. Основания: продолжение контракта D6 PBT-031 и утверждённого варианта A PBT-032 (без каскадного удаления данных); задача, потерявшая единственное назначение, перестаёт отображаться в ресурсном виде — это согласованное следствие D2 ADR PBT-003, а не побочный эффект; при чтении план остаётся валидным (нет висячих ссылок).

Отклонённые альтернативы: **вариант B** — запрет удаления при ссылках (против прецедентов ADR-7 PBT-002 и варианта A PBT-032: вынуждает вручную расчищать назначения); **вариант C** — каскадное удаление задач с ресурсом (массовая потеря данных, против всех прецедентов).

### D3. Идентичность по ID, независимость планов

Все операции ссылаются на записи по `id`; переименование меняет только `title` и не трогает ссылки (они на id). Независимость планов — по построению (каждый план — свой `PlanContent`, операции чистые и не имеют общего состояния); DoD-2 подтверждается тестом на два плана с ресурсом-тёзкой: переименование в первом не изменяет второй. Имена не уникализируются: `QA` и `QA2` — разные записи по id, совпадение названий допустимо и внутри одного плана (правило — только не связывать по имени).

### D4. Параллельность хранится в документе, меняется только справочником

`allowsParallel: boolean` создаётся обязательным полем `createWorkType` и меняется через `updateWorkType` — единственный способ (D5 ADR PBT-003: переопределений на уровне задачи нет). Применение флага — проверки PBT-036; здесь только хранение и редактирование. Отсутствующие поля патча `updateWorkType` не меняют значения (прецедент `updateTask` / `updateGroup`).

### D5. Порядок и границы

Создание — в конец массива справочника; переименование/смена признака не меняют порядок; удаление — фильтр, порядок остальных стабилен (преемственность D4 PBT-032). `plan-catalogs.ts` импортирует типы `plan-document.ts` и type-only из `plan-commands.ts` — без React и UI-библиотек (ADR-3 PBT-002). Экспорт из `index.ts`.

## Risks / Trade-offs

- **Удаление используемого ресурса меняет вид плана** (задачи без назначений уходят из ресурсного представления) — согласованное следствие D2 ADR PBT-003; помечено в спеке сценарием.
- **`invalid-title` — новый класс отклонений валидности ввода** (не ссылок и не интервалов). Расхождение с группами (PBT-032 допускает пустые названия) осознанное: справочники показываются в редакторах и импорте, где пустое имя — мусор; унификация правил названий по всем сущностям — отдельное решение вне границ карточки.
- **Опустевший массив vs явный пустой при чистке:** `deleteResource` убирает поле, `updateTask` с `assigneeIds: []` оставляет `[]` — поведение различается намеренно (первое — автоматическая чистка, второе — явное действие пользователя); тесты фиксируют оба.

## Migration Plan

Не требуется: формат v1 не меняется; только чистые функции и расширение объединения команд.
