## Context

Причина — в [proposal.md](proposal.md). Текущие оболочки используют absolute overlay внутри ограниченного окна; содержимое живёт в gantt. Проектный вид при hidden отключает тяжёлый чарт вместе с вложенными формами, ресурсный оставляет форму смонтированной. Родители уже реализуют операции, захват/возврат фокуса и переключение документа.

## Goals / Non-Goals

**Goals:** единая внутренняя оболочка, размеры от viewport, постоянные действия, безопасный lifecycle и проверка нативного решения на одном редакторе до переноса остальных.

**Non-Goals:** общая библиотека UI, новый SDK, платформенный менеджер модалок, изменение доменных команд и контрактов сохранения, новые поля и компоновка будущих PBT-086/087/084/088/089/090.

## Decisions

### D1. Нативный диалог внутри модуля

Выбран согласованный внутренний `PlanDialog.tsx` с `<dialog>.showModal()`; CSS viewport/fixed, ширина до672px, широкий вариант до896px, высота до min(820px,90dvh), отступы от экрана16px. Содержимое остаётся в React/DOM-поддереве модуля и в прежней границе ошибки. CSS использует семантические токены; закрытый dialog явно скрыт, чтобы legacy display:flex не сделал его видимым.

Нативный верхний слой решает ограничение transform/overflow контейнера и порядок относительно фоновых меню. Новых библиотек нет. Альтернативы: локальный portal требует дополнительного управления модальностью; ModalHost/API через SDK расширяют контракт; общий UI-пакет пока не оправдан. Если обнаружится конкретное ограничение, локальный portal рассматривается явно, без автоматического расширения SDK.

### D2. Явная принадлежность экземпляру

Два представления передают внутренний объект owner: идентичность экземпляра/документа, название документа и visible. Это локальные props модуля; SDK не меняется. При смене owner identity редактор закрывается до применения действий к новому документу. При hidden нативное окно закрывается без сохранения и потери локального черновика; при visible возвращается. Диалоги проектного вида выносятся из условного блока тяжёлого чарта, сохраняя принадлежность модулю.

При React-unmount/error cleanup закрывает нативное окно и освобождает обработчики. Состояние не передаётся платформе или другому виду. Название документа может обновляться без сброса полей.

### D3. Оболочка и клавиатура

Общий заголовок, название плана, описание, крестик; отдельное прокручиваемое тело и неподвижный footer с прежними кнопками. Для настроек и проблем — широкий вариант. Существующие поля, локальные ошибки и onSubmit/onApply сохраняются. Native cancel обрабатывается контролируемо, Escape закрывает только верхнюю панель. Inline-редакторы сохраняют preventDefault/stopPropagation для собственного Escape. По затемнению диалог не закрывается; новые dirty-confirm не вводятся, поскольку изменение контракта черновиков относится к следующим задачам.

Фокус при явном закрытии восстанавливается после освобождения нативной модальности; переход PBT-082 остаётся приоритетнее возврата к кнопке. Кнопки тулбара и диалога получают фокус до своего click-действия без прокрутки: WebKit может не фокусировать их мышью, поэтому одного activeElement при открытии недостаточно. Локальная обработка границ Tab/Shift+Tab замыкает переходы на доступных элементах диалога, поскольку нативный обход может уходить в интерфейс браузера. Вложенное преобразование использует нативный стек, не закрывая редактор задачи при отмене.

### D4. Прокрутка и независимость от дашборда

Не менять overflow/ширину body и не искать классы контейнеров платформы: такие изменения способны пересобрать чарт и нарушить положение шкалы. Тело диалога прокручивается отдельно с ограничением scroll chaining; локальные непассивные обработчики останавливают wheel/touch фона и прокрутку через заголовок/подвал, освобождаясь при закрытии. Конкретное поведение проверяется в Chrome/Firefox/WebKit, включая короткую форму и края длинного содержимого.

### D5. Проверки результата

Сначала перенести форму задачи и проверить viewport, focus, backdrop/wheel и закрытие в трёх браузерах. Затем остальные панели и ресурсный вид. Проверять1024×778/1856×1269, каскад/сетку/максимизацию, длинные данные, nested Escape, hidden/resume/unmount/document switch, навигацию конфликтов и неизменность документа/геометрии.

Отдельный сценарий переносит DOM-корень модуля за пределы оболочки дашборда, оставаясь внутри корня React с делегированием событий, и проверяет реальный диалог, затем возвращает узел на место. Это проверка отсутствия зависимости от DOM платформы; модуль продолжает получать обычные SDK props. Ошибка содержимого/размонтирование должны освобождать фон; целевой fault-сценарий не требует новых production API.

## Risks / Trade-offs

- Нативный диалог не гарантирует нужную прокрутку фона сам по себе → проверка реальными wheel/touch и локальная блокировка без глобального scroll-lock.
- Закрытие/повторное открытие при owner/visible может сбросить draft/focus → стабильные props, сохранение компонента при hidden, контроль identity, проверка вложенных панелей.
- Разные старые оболочки/CSS могут перекрыть новые размеры → удалить использованные только прежними оболочками правила, сохранить специфические стили полей/кнопок.
- По мере переноса возможны изменения e2e, которые раньше взаимодействовали с фоном открытого редактора → согласовать сценарий с явной модальностью; не ослаблять проверки данных и жестов.

## Migration Plan

Миграций SDK/БД/файлов нет. После proof одного редактора переносить остальные в том же change, затем обязательные проверки, живой браузер и PR в develop. Результаты и снимки хранить вне OpenSpec. Архивировать/sync specs после принятия PR; main и Release не меняются.
