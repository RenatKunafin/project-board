# Design — PBT-050 Native plan format

## Context

Модель плана v1 (`PlanContent`, `PLAN_SCHEMA_VERSION = 1`, PBT-030) хранится целиком в `content` записи `documents` (ADR-5 PBT-002); производные значения (длительности, сводные, конфликты) не хранятся и в файл не попадают по построению. Название плана живёт в метаданных оболочки документа, а не в содержимом (PBT-025); `PlanContent.title` — опциональный легаси-путь, фабрика его не создаёт. Валидатор `parsePlanContent` даёт полную диагностику структуры, дат, ссылок, циклов и интервалов (прецедент «диагностика вместо fallback»). Фикстуры PBT-012 (small-plan, plan-500) — база контрольных данных.

## Goals / Non-Goals

- Goals: полный перенос одного плана в файл и обратно; версионирование формата; структурированная диагностика; явная политика идентификаторов; эталонный файл и описание формата.
- Non-Goals: см. proposal (UI — PBT-051; `.gantt` — PBT-052+; PlantUML — PBT-055+; замена существующего плана и миграции формата — вне v1).

## Decisions

### D1. API — чистые функции в `packages/gantt/src/native-plan-format.ts`

```ts
export const PLAN_FILE_FORMAT = 'project-board-plan';
export const PLAN_FILE_FORMAT_VERSION = 1;

export type PlanFileIssueCode =
  | 'invalid-json'
  | 'invalid-envelope'
  | 'unknown-format'
  | 'unsupported-future-version'
  | 'plan-invalid';

export interface PlanFileIssue {
  readonly code: PlanFileIssueCode;
  readonly path: string;
  readonly message: string;
  readonly details?: readonly PlanIssue[]; // при code: 'plan-invalid'
}

export interface PlanFilePayload {
  readonly title: string;
  readonly content: PlanContent;
}

export function serializePlanFile(payload: PlanFilePayload): { ok: true; json: string };
export function deserializePlanFile(
  text: string,
): { ok: true; payload: PlanFilePayload } | { ok: false; issues: readonly PlanFileIssue[] };
```

Функции без Node/DOM API — работают в браузере и в Vitest (прецедент фикстур PBT-012). Стиль результата — union ok/issues, как `parsePlanContent`. Экспорт из `packages/gantt/src/index.ts`.

### D2. Конверт файла

```json
{
  "format": "project-board-plan",
  "formatVersion": 1,
  "title": "Название плана",
  "schemaVersion": 1,
  "content": { "calendar": …, "workTypes": …, "resources": …, "groups": …, "tasks": …, "dependencies": …, "unavailability": … }
}
```

- `format` — строковый маркер формата: чужой/переименованный формат распознаётся до любых попыток парсинга содержимого.
- `formatVersion` — версия **формата файла**; `schemaVersion` — копия версии схемы содержимого (`PLAN_SCHEMA_VERSION`). Разные оси: смена полей конверта поднимает `formatVersion`, миграция содержимого — `schemaVersion` (термины §15.5 решений).
- `title` — перенос названия плана из метаданных документа (каноническое место, PBT-025); при импорте передаётся создателю документа.
- `content` — passthrough `PlanContent` без фильтрации полей (см. D6).
- `JSON.stringify(value, null, 2)` — файл читается в редакторе и диффается.

### D3. Сериализация

`serializePlanFile` не повторяет валидацию: содержимое в памяти валидно по построению — все записи идут через команды ядра с проверками, чтение из БД проходит `parsePlanContent` (guard PBT-026). Двойная валидация добавила бы расхождение диагностики без защиты. Сериализуются только разделы модели — производные значения (сводные, конфликты) в файл не попадают по построению (DoD-2).

### D4. Десериализация — пайплайн с ранними отклонениями

1. `JSON.parse` падает → одна проблема `invalid-json` с сообщением синтаксической ошибки.
2. Корень не объект, или `format`/`formatVersion`/`schemaVersion`/`title`/`content` отсутствуют/неверного типа → `invalid-envelope` с путём.
3. `format !== PLAN_FILE_FORMAT` → `unknown-format` (файл не этого приложения).
4. `formatVersion > PLAN_FILE_FORMAT_VERSION` → `unsupported-future-version`: файл создан более новой версией приложения; данные не трогаются (прецедент guard будущих версий PBT-026). `formatVersion` — нецелое/меньше 1 → `invalid-envelope` (в v1 других версий нет; механизм миграций формата — отдельное решение при первой смене версии).
5. `schemaVersion !== PLAN_SCHEMA_VERSION` → `invalid-envelope` («версия содержимого не поддерживается») — аналогичная защита; содержимое v1 — единственное известное.
6. `parsePlanContent(content)` — весь существующий валидатор; при проблемах → `plan-invalid` с полным перечнем `details` (коды `invalid-structure`, `unknown-reference`, `circular-group`, … без дублирования логики).

Любое отклонение — полный отказ без частичного плана; вход пользователя не изменяется.

### D5. Политика идентификаторов: файл всегда создаёт новый независимый план

- Импорт создаёт **новый документ платформы** (новый `documentId`); «замена содержимого существующего плана» — Non-goal v1.
- Идентификаторы сущностей (`id` задач, ресурсов, …) сохраняются из файла как есть. Ссылки внутри `content` указывают только на сущности того же файла — валидатор проверяет внутренние ссылки; внешних ссылок в модели нет.
- Случайное связывание планов исключено по построению: документы независимы (spec `document-management`), планы не разделяют ресурсы даже при совпадении названий (spec `planning-documents`). Совпадение внутренних ID двух планов не создаёт связей — ссылки резолвятся внутри своего содержимого.
- Проверка DoD-4 тестом: два импорта одного файла → два независимых плана с одинаковыми внутренними ID; мутация одного не видна в другом.
- Кому нужен ремап ID (например, слияние планов) — будущая задача, здесь не проектируется.

### D6. Расширяемость: passthrough дополнительных полей

Сериализация переносит `content` без фильтрации полей; `parsePlanContent` проверяет известные поля и игнорирует неизвестные (не отвергает файл) — поддержанные дополнительные поля проходят round-trip (DoD-1). Контракт: неизвестные поля не имеют гарантий и могут быть отброшены при смене `formatVersion`; программных «слотов расширения» v1 не вводит.

### D7. Эталонный файл и описание формата

- `tests/fixtures/gantt/native-plan-sample.json` — эталон на базе контрольного набора PBT-012: группа, 5 задач, FS с лагом, 2 ресурса, 2 типа работ, праздник, отпуск; все разделы модели.
- `packages/gantt/NATIVE-PLAN-FORMAT.md` — описание для пользователя/разработчика: назначение, структура конверта, семантика дат (ADR PBT-003: включительное окончание, ISO), коды диагностики, политика идентификаторов, шаблон имени файла (D8), ограничение v1 (без миграций).

### D8. Имя файла экспорта — `pb-plan-YYYY-MM-DD_HH-mm-ss.json`

Шаблон предложен владельцем (2026-10-16): префикс `pb-plan-`, дата `YYYY-MM-DD`, нижнее подчёркивание, время `HH-mm-ss`, расширение `.json`. Двоеточия из первоначального предложения (`HH:mm:ss`) заменены дефисами: `:` — запрещённый символ имён файлов Windows, а Windows-десктопы входят в целевые платформы (ADR-4 PBT-002); браузер на Windows подменяет такие символы при сохранении, и шаблон нарушался бы.

- Утилита `planFileName(now: Date): string` в `native-plan-format.ts` — единственное место сборки имени; PBT-051 (UI-экспорт) и ручное сохранение дают одинаковое имя. Время — аргумент, а не `new Date()` внутри: детерминизм в тестах.
- Имя файла — **конвенция генерации, не контракт формата**: `deserializePlanFile` принимает строку содержимого и имя файла не проверяет; переименованный пользователем файл импортируется как обычно.

## Risks / Trade-offs

- Двойная ось версий (`formatVersion`/`schemaVersion`) избыточна, пока существует одна версия каждой: принято ради разделения будущих миграций файла и содержимого; в v1 обе жёстко проверяются.
- Passthrough неизвестных полей не отличит опечатку от расширения: осознанно — файл пользователя не отвергается из-за лишнего поля (диагностика важнее строгости для data-transfer формата).
- `serializePlanFile` без валидации доверяет вызывающему: риск минимален (в памяти только валидные планы), при появлении потребности «сериализуй с проверкой» добавляется отдельной обёрткой.
- Во время задачи воспроизведены 4 красных e2e SVAR-спек (plan-gantt ×3, dependencies ×1) на прод-сборке — и в ветке задачи, и бисектом на чистом `develop` (2387f3a): предсуществующая деградация локальной тестовой среды (прецедент разбора 2026-10-15), не регресс этой задачи; задача не трогает UI и обёртки SVAR/RCT. Разбор — вне границ карточки.

## Migration Plan

Первая версия формата: миграций нет, старых файлов не существует. Механизм миграций `formatVersion` будет спроектирован при первой смене версии (отдельное решение).

## Open Questions

Нет — развилка расширения файла решена владельцем до старта (`.json`, идентификация конвертом внутри).
