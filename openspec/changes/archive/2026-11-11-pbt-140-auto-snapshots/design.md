## Context

См. proposal.md и delta specs. Основная БД `project-board` содержит документы, workspace, настройки и ручную историю пяти копий. `WorkspaceBackupStore.readCapture()` даёт согласованную транзакционную выборку, `workspace-backup.ts` проверяет переносимый формат, `replace()` атомарно восстанавливает данные с защитой от устаревших писателей. `main.tsx` загружает данные до рендера App. Восстановление должно предшествовать созданию дефолтного пространства. SDK и предметные модули не меняются.

## Goals / Non-Goals

**Goals:** хранить полную аварийную копию вне хранилища браузера; отделить её от ручной истории; корректно показать отсутствие доступа к папке; восстановить данные после пересоздания основной БД или очистки данных сайта через повторный выбор папки.

**Non-Goals:** автоматический выбор папки без действия пользователя, облачная копия и сохранение незавершённой транзакции. Это локальная защита на том же или другом выбранном диске, а не защита от удаления файлов пользователем или отказа диска.

## Decisions

### D1. Выбранная пользователем папка

После действия пользователя приложение вызывает `showDirectoryPicker({ mode: 'readwrite' })`. Два файла снимков создаются непосредственно в выбранной папке через File System Access API. Для последующих запусков дескриптор папки сохраняется структурным клоном в небольшой отдельной IndexedDB конфигурации, без полезной нагрузки снимков. Удаление основной БД не удаляет файлы, а потеря конфигурационной БД не мешает повторному выбору той же папки. При каждом запуске проверяется доступ; если разрешение не действует, запись останавливается, статус показывает необходимость повторного разрешения. Запрос разрешения и выбор папки происходят только по действию пользователя.

До реализации выполняется короткая проба на рабочем Chrome: выбор папки, запись файла, удаление основной БД и данных сайта, повторный выбор папки и чтение файла. Если корпоративная политика запрещает API, это блокер согласованного способа размещения; переключать хранилище без нового решения нельзя. OPFS и вторая IndexedDB рассмотрены, но обе остаются внутри данных сайта и могут исчезнуть при их очистке.

### D2. Два слота, целостность и публикация

Файлы с фиксированными именами `project-board-recovery-a.json` и `project-board-recovery-b.json` содержат версию конверта, время, монотонное поколение, длину и SHA-256 полезной нагрузки. Внутри — существующий JSON backup v1 без истории ручных копий. При чтении проверяются конверт, digest и `deserializeWorkspaceBackup` с текущей комплектацией; выбирается последний годный слот. Новый снимок пишется в пустой или более старый слот через `createWritable()` и `close()`, затем перечитывается и проверяется. До успешной проверки статус не обновляется; второй слот не меняется. Если оба файла повреждены, восстановление недоступно, файлы не удаляются молча.

Межвкладочные публикации сериализуются одним Web Lock; под ним перечитываются поколения. Без поддерживаемого lock автоматическая запись останавливается с явным статусом, чтобы две вкладки не затирали друг друга. Защита работает офлайн. Файлы не занимают пять мест ручной истории.

### D3. Триггер и согласованный состав

После подтверждённой записи документа, workspace или настроек координатор отмечает состояние dirty. Обычный debounce составляет 30 секунд от последнего подтверждённого изменения, без maxWait. Каждое следующее изменение перезапускает таймер; при непрерывной активности новая копия не создаётся до паузы. Скрытие или закрытие вкладки не запускает отдельную запись; штатные flush PBT-139 остаются. Перед захватом ожидаются очереди записи, после чего `readCapture()` даёт persisted-срез. Изменения во время долгой записи формируют следующую dirty-серию. Сбой не подтверждает новый снимок; статус показывает ошибку и время последней проверенной копии.

Пока папка не выбрана, копии не создаются. После выбора для непустого действующего пространства первый снимок можно создать без нового редактирования. Пустой первый запуск не создаёт снимок до прохождения развилки восстановления. Настройки разрешённой папки и автоматические файлы не входят в переносимый backup.

### D4. Старт и восстановление

Bootstrap отличает действительно пустую основную БД от ошибки открытия, неподдерживаемой версии и частично сохранившихся данных. При пустой БД до создания вкладок показывается развилка: если сохранённый дескриптор доступен, файлы проверяются и показывается найденный снимок; иначе пользователь может выбрать папку с копиями или продолжить с пустым пространством. Это работает и после потери всех данных сайта, когда дескриптор уже не сохранён. При наличии годного снимка показываются дата, возраст и количество документов/окон, затем действия «Восстановить» и «Продолжить без восстановления». Выбор папки сам по себе не применяет снимок. Если снимок отсутствует или повреждён, UI сообщает это и позволяет выбрать другую папку либо продолжить.

Отказ не меняет файлы. После него снимок доступен в настройках; дальнейшие автоматические сохранения по обычной ротации могут со временем вытеснить старый, что интерфейс объясняет. Восстановление использует существующую проверку формата и атомарный `replace()` с generation guard; после успеха страница перезагружается. Ни повреждённый снимок, ни ошибка доступа не превращаются в успешное восстановление. Для действующей непустой БД автоматического предложения замены нет; ручное восстановление из папки требует отдельного подтверждения.

## Risks / Trade-offs

- Непрерывная работа без паузы 30 секунд → новая копия откладывается; владелец принял этот предел.
- Разрешение на папку отозвано или дескриптор потерян → показать остановку защиты и предложить повторный выбор; файлы остаются на диске.
- Корпоративный Chrome запрещает File System Access API → проверить на рабочем Mac до реализации, не объявлять защиту включённой.
- Две вкладки и долгая запись → Web Lock, повторное чтение поколения и новая dirty-серия; ввод не блокируется записью файла.
- Два полных файла занимают место в выбранной папке → показать ошибки записи/квоты, сохранить прежний годный слот; оценить объём на реальных данных.
- Пустая БД после аварии → сначала развилка восстановления, затем запись нового пространства; проверить e2e.

## Migration Plan

Полезная нагрузка основной БД не мигрирует. Новая маленькая БД хранит только дескриптор выбранной папки; при её потере папку выбирают повторно. После обновления существующее пространство остаётся, первый снимок появляется после выбора папки. При откате старая версия игнорирует внешние файлы и не удаляет их.
