## Context

Каркас PBT-004: npm workspaces, пакеты-заглушки, точка регистрации `apps/project-board/src/widgets.ts` (пустой список). Контракт SDK v0 — [ADR PBT-002](../../../../docs/adr/PBT-002.md) ADR-6: регистрация типов (id, название, иконка, компонент, ограничения размеров, стартовые настройки), контекст экземпляра, документы, настройки представления, жизненный цикл, дополнительное представление. В этом change реализуется **только п.1 регистрации** и минимальный контекст пропсов; документы/жизненный цикл — PBT-007+. Инструменты проверок готовы (PBT-005): Vitest для unit, Playwright для UI.

## Goals / Non-Goals

**Goals:**

- Публичный контракт регистрации в `widget-sdk` (типы и ошибка), реализация реестра в `dashboard`, подключение демо-виджета в приложении.
- Состояние «неизвестный тип» как UI-компонент платформы.
- Первые продуктовые unit-тесты (реестр) и расширение browser-smoke.

**Non-Goals:**

- Документы и подписки (PBT-007), жизненный цикл окон и перетаскивание (PBT-018–PBT-023), каталог в UI как рабочий инструмент (здесь — демонстрация), иконки типов (SDK v0 декларирует иконку; поле вводится, но UI-отображение иконки откладывается до PBT-019).
- Чек-лист как настоящий модуль (PBT-008); демонстрационный виджет живёт в приложении и удаляется при подключении чек-листа.

## Decisions

- **Разделение контракта и реализации.** `widget-sdk` экспортирует только типы (`WidgetTypeDefinition`, `WidgetProps`, `WidgetTypeSettings`) и класс ошибки `WidgetRegistryError` (ошибка — часть контракта: модули и тесты должны ловить конкретный тип). Реестр (`createWidgetRegistry`, `WidgetRegistry`) реализует `dashboard` — платформа владеет исполнением, SDK остаётся декларацией.
- **React-типы в SDK — type-only.** `import type { ComponentType } from 'react'` в `widget-sdk`; в `dependencies` React не попадает (peer/devTypes не нужны до первого настоящего компонента). Runtime-зависимости SDK остаются нулевыми (ADR-3).
- **Форма определения.** `WidgetTypeDefinition { id: string; title: string; component: ComponentType<WidgetProps>; startSettings: WidgetTypeSettings; sizeConstraints: WidgetSizeConstraints }`, где `WidgetSizeConstraints { minWidth, minHeight, maxWidth?, maxHeight? }` (в ячейках сетки — единица появится с тайлингом PBT-021; сейчас безразмерные числа). `WidgetProps { widgetInstanceId: string; settings: WidgetTypeSettings }`. Настройки — `Record<string, unknown>` до появления схемы настроек.
- **Валидация реестра.** `createWidgetRegistry` отклоняет: пустой id, дубликат id (`WidgetRegistryError` с идентификатором в сообщении). `get(id)` возвращает `WidgetTypeDefinition | UnknownWidgetType` — маркер-объект `{ kind: 'unknown', id }` вместо undefined, чтобы UI рендерил состояние без проверок на undefined. `list()` — стабильный порядок подачи.
- **Демо-виджет в приложении.** `apps/project-board/src/widgets/demo-widget.tsx`: панель с названием из настроек, `widgetInstanceId` и текущими настройками. Подключается в `widgets.ts` через `defineWidgetType({...})` — фабрика SDK, дающая типизацию без `as const`-танцев. Реестр строится в `main.tsx` и передаётся в `App` через пропс (контекст провайдера — не нужен до появления множества потребителей).
- **Оболочка.** `App` отображает: список зарегистрированных типов (каталог-заглушка), один экземпляр демо-виджета и один блок «неизвестный тип» (запрос заведомо отсутствующего `checklist`) — оба сценария спецификации видны в UI без интерактива.

## Risks / Trade-offs

- [`startSettings: Record<string, unknown>` не защищает от опечаток в ключах] → типизированные настройки появятся с первым настоящим модулем (PBT-008, генерик `defineWidgetType<S>` уже заложен в форму SDK); для демо достаточно.
- [`kind: 'unknown'` вместо исключения при get] → неизвестный тип — штатная ситуация восстановления (закрытый/удалённый модуль), а не ошибка программирования; требование спецификации — продолжение работы.
- [Демо-виджет — временный код] → живёт в `apps/`, удаляется в PBT-008; не мигрирует в packages.
