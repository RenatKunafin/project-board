## Context

См. `proposal.md` и `specs/`. Приложение уже имеет меню настроек с резервными копиями и механизм обнаружения/применения обновлений PWA. Release notes должны оставаться статическим содержимым приложения и не требовать сервера пользовательских данных.

## Goals / Non-Goals

**Goals:**
- Поддержать один удобный для сопровождения источник заметок по версиям.
- Дать доступ к заметкам из настроек, а также из предложения обновиться.
- Сохранить чтение заметок офлайн.

**Non-Goals:**
- Автоматически генерировать пользовательские заметки из коммитов.
- Добавлять backend, телеметрию, подписки или автоматические обновления без согласия пользователя.
- Менять формат резервных копий или жизненный цикл пользовательских документов.

## Decisions

- Хранить версионные заметки в репозитории как структурированные статические данные, включаемые в приложение при сборке. Это позволяет PWA читать их офлайн и делает выпуск воспроизводимым. Рассматривался внешний URL, но он не обеспечивает автономную доступность и добавляет зависимость от сети.
- Начальное наполнение охватывает все публично выпущенные версии, доступные к моменту реализации. В этом checkout имеются теги `v1.0.0`, `v1.0.1`, `v1.0.2`, а также rollback/republication теги; состав и пользовательское представление специальных выпусков нужно сверить с GitHub Releases, не выводить его только из имён тегов. Источники для текстов: описания релизов, сравнение коммитов тегов, `docs/deployment.md` и отчёт PBT-059. Заметки формулируются для пользователей, не копируются из инженерных отчётов.
- Пункт «Что нового» разместить в существующем разделе настроек рядом с «Резервными копиями» и показывать журнал в интерфейсе приложения. Отдельная страница/внешний сайт не нужны, так как журнал — часть локально доступного продукта.
- В модалке обновления показывать заметки кандидата, полученные от ожидающего Service Worker, с сохранением текущего подтверждения/откладывания. Если данные кандидата недоступны или некорректны, скрыть блок заметок и оставить существующее уведомление обновления.
- Версионные данные должны проверяться на корректность при сборке или тестировании, чтобы ошибочная структура не приводила к пустому/сломавшемуся экрану.
- Зафиксировать обновление журнала как обязательный шаг существующего релизного процесса в `docs/deployment.md`: до публикации GitHub Release заметки для его версии сверяются с пользовательскими изменениями кандидата, а сборка проверяет, что у версии есть запись. Это использует текущий workflow и не меняет автоматический триггер публикации.
- Передавать заметки кандидата из ожидающего Service Worker через уже используемый `MessageChannel`-протокол до активации новой версии. PWA генерирует worker через Workbox `generateSW`; его импортированный guard уже обрабатывает сообщения `PB_UPDATE_CHECK` и `PB_UPDATE_ACTIVATE`. При сборке тот же структурированный источник встраивается в импортированный guard, так что каждая версия worker отвечает заметками своей сборки. Модалка получает данные именно от установленного ожидающего worker, в том числе после успешной офлайн-подготовки, без запроса к постоянно обновляемому URL.

## Risks / Trade-offs

- Запись заметок может быть забыта при подготовке выпуска → добавить ведение release notes в чек-лист релиза и проверку наличия версии в поставляемых данных.
- Ранние выпуски могли содержать только технические описания или несколько тегов одной выкладки → сверить официальные Release и историю тегов, не объединять и не исключать версии молча.
- Ожидающий worker может исчезнуть или не содержать корректные заметки → показывать пользовательское описание только после успешного ответа по каналу сообщений; при ошибке оставить стандартное уведомление обновления и доступ к журналу текущей версии.

## Migration Plan

Добавить источник с заметками для всех восстановленных публичных версий, подключить его к приложению и ожидающему worker, затем добавить экран журнала и интеграцию модалки обновления. Миграция локальных данных не требуется. Откат кода возвращает прежнее поведение PWA и не затрагивает пользовательские документы.
