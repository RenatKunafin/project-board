# Design — PBT-034: назначения и периоды недоступности

## Context

База: модель v1 с `tasks[].assigneeIds?` / `tasks[].workTypeIds?` и `unavailability: [{ id, resourceId, start, end }]`; валидатор чтения отклоняет ссылки на несуществующие ресурсы/типы и перевёрнутые интервалы недоступностей; контракт команд PBT-031 (`PlanCommand`, коды `unknown-task` / `unknown-resource` / `unknown-work-type` / `inverted-interval` уже есть); модульный шаблон PBT-032/033 (type-only импорт результата, локальные хелперы, патч-семантика «присутствующее свойство заменяет»). Правила: D1 ADR PBT-003 — несколько назначений, конфликт по каждому ресурсу; D2 — задачи без назначений не отображаются в ресурсном виде; вариант A PBT-033 — удаление ресурса чистит `assigneeIds` и недоступности.

## Goals / Non-Goals

**Goals:** идемпотентные назначение/снятие ресурса и типа (не дублируют связь, DoD-1); полный цикл операций недоступности с включительным интервалом (DoD-2); отклонение ссылок вне плана и некорректных интервалов (DoD-3); неприкосновенность дат задач (DoD-4); подтверждение ссылочной целостности удалений (DoD-5).

**Non-Goals:** проверки конфликтов (PBT-036), ресурсное представление (PBT-047+), UI-редакторы (PBT-042/043), импорт `.gantt` (PBT-054), расширение формата v1.

## Decisions

### D1. Назначения — идемпотентные операции над множествами ссылок

`packages/gantt/src/plan-assignments.ts`. Четыре операции: `assignResource(plan, taskId, resourceId)`, `unassignResource(plan, taskId, resourceId)`, `assignWorkType(plan, taskId, workTypeId)`, `unassignWorkType(plan, taskId, workTypeId)`.

Семантика множества:
- `assign`: добавляет id в конец массива, если отсутствует; **уже назначен — noop** (`{ ok: true, plan }` без изменений): DoD «повторное назначение не дублирует связь», и командные источники UI (чекбокс, клик по дорожке) не должны ошибаться на повторе.
- `unassign`: убирает id; **отсутствовал — noop** (состояние уже целевое); опустевший массив убирается из задачи (единообразие с чисткой вариант A PBT-033: «нет назначений» не оставляет следов).
- Проверки порядка: сначала `unknown-task` / `unknown-resource` / `unknown-work-type`, затем мутация; ошибки — целиком, план не меняется (прецедент атомарности PBT-031).

Почему не `updateTask` с массивами: он заменяет список целиком — для UI-назначения нужен «текущий состав + добавить один», и при параллельных командах полной замены легко потерять чужие назначения. Отдельные идемпотентные операции дают безопасную конкурентную модель без потери данных. Точечное массовое редактирование остаётся за `updateTask` (PBT-031).

### D2. Недоступности — полный цикл CRUD

`createUnavailability(plan, { resourceId, start, end })` — id через `crypto.randomUUID()`, добавление в конец массива; `unknown-resource` при несуществующем ресурсе, `inverted-interval` при `end < start`.

`updateUnavailability(plan, unavailabilityId, patch: { resourceId?, start?, end? })` — присутствующее свойство заменяет, отсутствующее не меняет (прецедент `updateTask`/`updateGroup`). Интервал проверяется по **итоговому** состоянию: неприсутствующие стороны берутся из текущей записи — смена только `start` при прежнем `end` валидируется против пары; `unknown-resource` для нового resourceId. Атомарность — вся проверка до построения.

`deleteUnavailability(plan, unavailabilityId)` — фильтр, порядок остальных стабилен.

Новый код: `'unknown-unavailability'` — операция над несуществующим периодом. Классы `invalid-title` здесь не нужны (записи без названия в v1).

### D3. Ссылки вне плана и интервалы (DoD-3)

Ресурс «другого плана» для операций данного плана — просто несуществующий id: справочник принадлежит документу (11.1 решений), проверка одна — `unknown-resource` по массиву `plan.resources`. Тест строит два плана с разными id и подтверждает отклонение. Некорректный интервал — `inverted-interval` в `createUnavailability` и `updateUnavailability` (итоговый интервал); датам задач операции не коснутся.

### D4. Даты задач неприкосновенны (DoD-4)

Ни одна из семи операций не изменяет `start`/`end` задач: назначения и снятия меняют только массивы ссылок, недоступности — только раздел `unavailability`. Тесты фиксируют равенство задач до/после (кроме целевых полей) и постоянство рабочих длительностей. Автоперенос исключён согласованно (раздел 7 решений) — здесь это гарантируется чистотой операций.

### D5. Ссылочная целостность удалений (DoD-5) — подтверждение, не новый код

Контракты уже реализованы: `deleteTask` чистит зависимости (D6 PBT-031), `deleteResource` чистит `assigneeIds` и каскадно недоступности (вариант A PBT-033). В этой задаче — сквозные тесты с новыми операциями: назначить ресурсы и создать отпуск → удалить ресурс → задачи с чистыми назначениями, недоступность удалена, `parsePlanContent` валиден; удалить задачу → её зависимости вычищены, недоступности её ресурсов не тронуты (недоступность связана с ресурсом, не с задачей). Новая логика не пишется — только доказательство целостности.

### D6. Границы и экспорт

`plan-assignments.ts` — типы `plan-document.ts` + type-only из `plan-commands.ts`, без React и UI-библиотек (ADR-3 PBT-002). `PlanCommand` расширяется семью вариантами, диспетчер делегирует; экспорт из `index.ts`.

## Risks / Trade-offs

- **Семь новых вариантов в `PlanCommand`** — объединение растёт (уже 16 вариантов); при дальнейшем росте стоит сгруппировать по разделам (`TaskCommand` / `GroupCommand` / …) — рефакторинг без изменения контракта, вне границ карточки.
- **Noop-семантика assign/unassign** маскирует ошибку «назначали ли вообще?» для вызывающего: для UI-состояний (чекбоксы) noop — желаемое поведение; для строгих сценариев вызывающий может сравнить состав до/после. Отклонение повторного назначения отвергнуто — оно делало бы клик по уже назначенному ресурсу ошибкой.
- **`updateUnavailability` без проверки пересечения с назначенными работами** — это проверка конфликтов PBT-036, здесь только валидность записи.

## Migration Plan

Не требуется: формат v1 не меняется; только чистые функции и расширение объединения команд.
