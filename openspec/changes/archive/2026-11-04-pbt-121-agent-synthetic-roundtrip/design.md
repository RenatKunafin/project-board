# Design — PBT-121

## Context

Мотивация и границы — в proposal. Основание — `docs/research/PBT-120.md` и архив PBT-120. Последнее уточнение профиля: внутренний агент работает на **рабочем Mac** владельца; текущий личный Mac доступа к нему не имеет. Строка об ограничениях «личной машины» в таблице отчёта 120 осталась прежней; для живой пробы ограничения рабочего устройства считаются неизвестными, переносить сведения о личной машине нельзя.

Поддержка MCP сообщена владельцем; конфигурация нового сервера, runtime, версии протокола, браузерный канал и длительное ожидание не проверены. Владелец выбрал для стенда отдельную временную публикацию GitHub Pages. Выбор хостинга не является поручением опубликовать её в ходе подготовки этих артефактов.

Проверенные точки кода:

| Точка | Использование в стенде |
| --- | --- |
| `packages/dashboard/src/index.ts` | Публичные экспорты сервиса и адаптера документов доступны без нового SDK |
| `createIndexedDbDocumentStore(name)` | Отдельная БД с явным именем; IndexedDB использует только платформенный адаптер |
| `createDocumentService({ store })` | Создание/обновление, revision, восстановление и состояния записи |
| `restoreAll()`, `flushAll()`, `getSaveState(id)` | Восстановление и ожидание persistence; дополнительно проверяется фактическая запись через `store.get(id)` |
| `tests/pages/`, `tests/pwa-updates/` | Прецеденты отдельных тестовых сборок; product Vite config с аналитикой/SW не копируется в стенд |

## Goals / Non-Goals

**Goals:** проверить один запрос с одним синтетическим документом, одним процессом и одной вкладкой; отдельно доказать транспорт, фактическое сохранение и работу внутреннего клиента. Получить воспроизводимый артефакт для переноса с личной машины на рабочую.

**Non-Goals:** производство нового виджета/модуля, поддержка нескольких вкладок/агентов, работа без открытого браузера, долговечная очередь, продуктовая совместимость версий и перенос сессионных полномочий через backup. Установленная PWA и другие браузеры не входят в матрицу этой пробы.

## Decisions

### D1. Изолированная тестовая сборка

Код располагается в `tests/agent-integration/`: браузерная панель, конфигурация Vite, fixtures, тесты и отдельный серверный npm-пакет. Корневые команды только запускают сборку/проверки; продуктовые пакеты, каталог виджетов и сборка `apps/project-board` не расширяются.

Панель импортирует платформу через её публичные экспорты, без Dexie и прямого доступа к IndexedDB. Она не является SDK-виджетом: это тестовый composition root. Серверный пакет не импортирует платформу или предметные модули.

Браузерная сборка имеет собственный entry point, локальные assets и статический output. Она не загружает Метрику, product bootstrap, manifest или service worker. Используются существующие инструменты сборки; новые зависимости допускаются только для MCP и необходимых ему адаптеров с точным пином и изолированным lockfile.

Альтернатива — экспериментальные кнопки внутри основного дашборда — не выбрана: она меняла бы продуктовый scope и создавала зависимость от его выпуска.

### D2. Размещение и воспроизводимый артефакт

Для статической сборки используется отдельный временный репозиторий GitHub Pages, кандидат имени — `project-board-agent-probe`. В него передаются только проверенные статические файлы и manifest с идентификатором исходного коммита/сборки и хешами assets. Исходники и PR задачи остаются в основном репозитории. Существующий `deploy-pages.yml` и Pages продукта не меняются.

До публикации уточняются владелец/имя репозитория, полный HTTPS-URL и base path; после неё сверяются реально загруженные файлы с manifest. Произвольные PR не публикуются автоматически. Создание репозитория и публикация выполняются отдельным действием после подготовки результата, не считаются уже выполненными или разрешёнными выбором варианта планирования.

Pages-проекты одного владельца могут иметь один origin и разные пути: путь не является границей CORS/IndexedDB. Поэтому проба использует отдельный чистый профиль Chrome и БД `project-board-pbt-121-probe-v1`; продуктовую БД, localStorage и SW стенд не перечисляет и не очищает. Не обещаем изоляцию от недоверенного кода того же origin. Полномочия браузерной сессии хранятся только в памяти вкладки, а origin допускается сервером явно.

Локальный preview нужен автоматическим тестам. Успех на localhost не заменяет проверку публичного HTTPS → loopback. HTTPS-origin стенда, обычная вкладка и установленная PWA — разные области доказательства.

### D3. Первый транспортный кандидат

```text
Chrome: static HTTPS probe
    | fetch JSON / explicit pairing / bounded polling
    v
127.0.0.1:<port>: one local Node process
    | in-memory request + result
    | MCP stdio
    v
Internal agent OR automated MCP client

Chrome -> DocumentService -> platform store -> probe IndexedDB
```

Для MCP первым проверяется официальный TypeScript SDK со stdio; первая исследуемая линия — актуальный официальный SDK v2. Он закрывается небольшим адаптером инструментов, а протокол не реализуется вручную. Перед установкой фиксируются точные версии SDK/его обязательных зависимостей и совместимый Node runtime; версии всех реально участвовавших компонентов попадают в отчёт. Наличие SDK v2 не доказывает совместимость внутреннего клиента: отдельно фиксируются использованный протокол и наличие/режим совместимости с прежними клиентами.

Стартовая среда компонента — Node 22 либо более новая совместимая версия, сверенная с выбранным SDK. Если на рабочем Mac она недоступна или клиент не запускает stdio, это результат пробы; другой runtime/транспорт не подменяет выбранный сценарий молча.

Для браузера выбирается обычный HTTP JSON на `127.0.0.1` и короткие `fetch`-запросы. Порт задаётся аргументом, по умолчанию `43821`; занятый порт даёт явную ошибку, процесс не завершает чужие службы и не перебирает порты. MCP stdio и HTTP обслуживает один процесс. Логи — stderr, stdout содержит только MCP-сообщения.

HTTP выбран для малого числа запросов и наблюдаемой диагностики CORS/разрешений. WebSocket/длительное ожидание увеличили бы число неизвестных для первого опыта. HTTPS loopback, расширение и Streamable HTTP остаются вариантами для последующего решения при воспроизведённом блокере, а не дополнительными реализациями этого PR.

Опрос браузером: раз в секунду только при активном запросе, один HTTP-вызов не дольше 5 секунд, общий сеанс опроса не дольше 120 секунд. По лимиту показано «Ожидание остановлено», новый запрос не создаётся автоматически. Исполнитель обрабатывает одну задачу по явной команде; пустой ответ завершает обработку. Константы тестов управляют временем, но живая проба использует документированные значения.

### D4. Сопряжение и область доступа

Сервер слушает только IPv4 loopback. Аргумент `--allowed-origin` содержит ровно origin выбранного HTTPS-стенда; локальные тесты запускают отдельный процесс со своим origin. Wildcard и автоматическое доверие пришедшему Origin запрещены.

- Browser endpoints проверяют точный Host `127.0.0.1:<port>` и точный Origin. Отсутствующий/`null`/чужой Origin отклоняется; доверие к proxy-заголовкам не используется.
- CORS разрешает только нужные методы и заголовки выбранному origin. Preflight не требует сессионного bearer, но проверяет Host/Origin и не читает/не меняет запросы. CORS не заменяет авторизацию.
- Владелец запрашивает через MCP `probe_session` одноразовый код сопряжения и адрес компонента, переносит код в панель. Код — случайное значение не менее 128 бит, живёт 5 минут, допускает не более 10 неверных попыток и одно успешное использование.
- `POST /pair` обменивает код на случайный сессионный bearer. Код/ключ не помещаются в URL, статическую сборку, общий лог, IndexedDB или web storage. MCP-ответ с одноразовым кодом не включается в обезличенные артефакты.
- После сопряжения endpoints требуют bearer и связывают запрос с `runId` процесса и единственной тестовой целью. Жизнь сессии ограничена 30 минутами; отключение/перезапуск отзывает полномочия. После reload видны сохранённые данные, а для нового обмена нужно сопряжение.
- Ограничение JSON — 32 KiB, строгая схема; произвольные команды, файловые пути, URL источников и выбор продуктовых документов не принимаются. Текст выводится как текст, без HTML/Markdown-исполнения.

Предел доверия — разрешённый клиент агента и явное сопряжение владельцем. Стенд не защищает от вредоносного локального процесса с полномочиями пользователя; проверяем чужую веб-страницу, неверные полномочия и неверный адресат.

### D5. Минимальный обмен и его границы

Все перечисленные имена — внутренний контракт стенда, не будущий публичный API:

| Сторона | Операции | Назначение |
| --- | --- | --- |
| MCP | `probe_session` | Версии/готовность и одноразовое сопряжение по запросу владельца |
| MCP | `claim_probe_request` | Атомарно взять единственный ожидающий запрос либо вернуть пустой ответ |
| MCP | `submit_probe_result`, `fail_probe_request` | Вернуть синтетический результат/ошибку по идентификатору запроса и токену попытки |
| Browser HTTP | `POST /pair`, `POST /disconnect` | Создать/отозвать сессию |
| Browser HTTP | `POST /requests`, `GET /requests/:id` | Создать запрос и наблюдать его состояние/результат |
| Browser HTTP | `POST /requests/:id/ack` | Подтвердить сохранённую revision после D6 |

Запрос содержит `schemaVersion: 1`, `runId`, `requestId`, `targetDocumentId`, `baseRevision`, `fixtureId`, `expiresAt` и случайный `nonce`. Результат повторяет адресные поля, добавляет идентификатор результата и строго ограниченный синтетический снимок. Сервер хранит ожидаемую fixture и сравнивает содержимое результата; браузер независимо проверяет схему, срок, действующую сессию и соответствие своему запросу перед update. Внутренний агент получает инструкцию вернуть заданные синтетические факты, не обращаться к корпоративным источникам.

Очередь — один слот в памяти: `queued → processing → ready → applied`, отдельно `failed` и истечение срока. Пока слот активен, повторное нажатие возвращает тот же запрос; второй независимый запрос отклоняется. TTL — 10 минут, по его истечении поздний submit/ACK отклоняется. Повторный захват processing не разрешается, автоматического lease/retry нет.

Повтор submit с тем же результатом безопасен; другой результат для завершённой попытки отклоняется. Только browser ACK может поставить applied; submit исполнителя оставляет ready. На ошибке локальной записи браузер показывает ошибку и не посылает ACK. Очередь не сохраняется на диск: падение сервера теряет ожидающий обмен, зато уже записанный браузерный документ остаётся. Перезапуск создаёт новый runId, старая сессия недействительна.

Такое ограничение намеренно: crash recovery, долговечные результаты и несколько исполнителей относятся к PBT-125/126.

### D6. Подтверждение сохранения через существующую платформу

Страница создаёт/восстанавливает один тестовый документ отдельного типа `agent-probe/snapshot`, schemaVersion 1. Начальное содержимое — известная fixture A. Приложение стенда регистрирует поддержку этой версии без миграций; чужие/будущие схемы не перезаписываются.

1. На загрузке вызвать `restoreAll()`; существующий документ не заменять начальным. Создавать A только при отсутствии тестового документа и дождаться его записи до первого запроса.
2. На результате проверить runId/requestId/nonce/target/baseRevision и содержимое. Обновить через `update(id, expectedRevision, nextContent)`; запретить второй сценарий записи до завершения текущего.
3. В содержимое включить `lastAppliedRequestId` и синтетический результат. Запомнить возвращённую revision, дождаться `flushAll()`, проверить отсутствие error/conflict и вызвать `store.get(id)` через платформенный адаптер.
4. Успех означает совпадение сохранённой revision, requestId и всех ожидаемых полей результата; только тогда показать «Сохранено» и отправить ACK. При недоставленном ACK показать отдельно «Данные сохранены, подтверждение не доставлено».
5. При повторе результата уже сохранённый маркер проверяется чтением через адаптер; повторного update нет. Это ограниченная защита повторной доставки в одном эксперименте, не универсальный журнал операций.
6. Для доказательства reload остановить сервер/доставку, перезагрузить страницу и прочитать результат через новый экземпляр сервиса. Нельзя считать данные из памяти процесса/повторного ответа доказательством IndexedDB.

Сбой persistence моделируется обёрткой `DocumentStoreLike` в тестовом harness, которая отклоняет все попытки save/saveAll выбранной операции. Реальные retry сервиса не выключаются; прежняя fixture A должна сохраниться после reload. Обёртка не использует IndexedDB напрямую и не добавляет fault endpoint в опубликованный компонент. В случае ошибки обновлённое in-memory содержимое не помечается сохранённым.

### D7. Поставка на рабочую машину

Готовятся два проверяемых артефакта: статическая сборка страницы и локальный npm tarball сервера с CLI entry point, версиями и хешами. Публичный npm publish не нужен. Инструкция описывает установку tarball в отдельный каталог через разрешённый источник зависимостей и запуск CLI по проверенной команде npm/npx либо явным локальным executable.

На чистом каталоге вне исходного checkout проверяются установка, запуск, stdio и HTTP. Инструкция раскрывает необходимость runtime и доступа к зависимостям; tarball не называется автономным бинарником. Если корпоративная установка блокируется, отмечается воспроизведённый отказ; не обещаем, что другой формат автоматически разрешён.

### D8. Матрица доказательств и приёмка

| Проверка | Где / кто | Достаточное свидетельство |
| --- | --- | --- |
| MCP-сервер и переносимый пакет | Локально, автоматический MCP-клиент | Запуск из артефакта, реальные вызовы по stdio, обработка пустой очереди и неверной схемы |
| Положительный обмен, повтор и reload | Собранная панель + реальный процесс + имитатор | Известные значения/revision прочитаны после reload без доставки |
| Ошибка persistence | Автоматический harness | Нет ACK/ложного успеха, предыдущие данные после reload |
| Host/Origin/сопряжение | HTTP-негативные тесты и другая browser origin | Доступ отклонён до чтения/записи, тестовый документ неизменен |
| Отключение, занятый порт, restart/TTL | Автоматические тесты | Диагностика без ложного успеха, старая сессия/результат отклонены |
| Публичный HTTPS → loopback | Опубликованная сборка, установленный Chrome | Разрешение/отказ браузера, фактический обмен без отключения защиты; версия и origin записаны |
| Внутренний агент | Владелец на рабочем Mac | Один запрос по инструкции, сохранение, reload без доставки, остановка компонента |

Автоматические browser-тесты используют собранный стенд, отдельный конфиг/порты и outputDir. Живая MCP-сессия и dev-сервер не работают одновременно с автоматическими browser-наборами. Локальная эмуляция HTTPS/выданное тестом разрешение не объявляются проверкой корпоративной политики Chrome. В живой пробе используются штатные разрешения; флаги отключения защиты/игнорирования сертификатов не допускаются.

Для новых файлов выполняются lint/typecheck и unit/интеграционные проверки; отдельные команды должны реально охватывать тестовый пакет, который не входит в текущий корневой typecheck. Перед PR также обязательный набор проекта: repository, lint, typecheck, unit, production build, browser и OpenSpec strict. PWA update tests нужны только если реализация всё же затрагивает lifecycle; такой выход из текущей изоляции сначала рассматривается как изменение scope.

Отчёт `docs/research/PBT-121.md` фиксирует commit/hash артефактов, версии Node/SDK/браузера/использованного MCP-протокола, идентификатор среды «личная/рабочая», шаги и отдельные результаты имитатора/внутреннего клиента. Снимки/trace/логи — `test-results/agent-integration/` или вложения PR, без кодов сопряжения/токенов и корпоративных payload.

**Положительный вывод:** обязательные автоматические проверки и живая проба на рабочем Mac пройдены; можно использовать проверенный кандидат при дизайне PBT-122. **Отрицательный вывод:** конкретный блокер воспроизведён, обстоятельства и альтернативы записаны; это допустимый исследовательский результат для ревью, но не подтверждение транспорта. Если рабочая машина пока недоступна, результат — «живая проба не выполнена»; соответствующие пункты остаются открытыми, общий PASS/Done не ставится.

## Risks / Trade-offs

- Клиент поддерживает MCP, но не выбранный stdio/runtime/версию → проверить из переносимого артефакта; неизвестное не заменять предположением.
- Chrome/политики рабочего устройства блокируют HTTPS → loopback → зафиксировать отказ; другой транспорт/хостинг выбирать по результату, не отключать защиту.
- Отдельный Pages-репозиторий имеет общий origin с продуктом → чистый профиль, отдельная БД, bearer только в памяти, отсутствие product bootstrap; не считать путь изоляцией origin.
- После ошибки save актуальное значение остаётся в памяти сервиса → успех определяется контрольным чтением persistence и reload.
- Перезапуск теряет запрос в памяти → явно ограничить обещания стенда; уже сохранённый документ остаётся читаемым.
- Объём стенда растёт в продуктовую платформу → один документ/процесс/слот, без постоянной очереди и общего SDK; самостоятельные находки не включать скрыто.

## Migration Plan

Продуктовых миграций нет. После одобрения дизайна реализовать локальный стенд и выполнить автоматические проверки; подготовить переносимые артефакты, затем отдельно опубликовать выбранную статическую сборку и провести живую пробу. Изменения main/Release продукта для этого не требуются.

Завершение эксперимента: остановить свой компонент, отозвать его сессию, при необходимости отключить временную Pages-публикацию отдельным действием владельца и убрать тестовый профиль. Общую очистку origin или продуктовой БД не выполнять. Результат исследования и воспроизводимые исходники остаются в PR.

## Open Questions

- Точное имя/владелец временного Pages-репозитория и URL — параметр публикации; принцип отдельной публикации выбран.
- Фактические поля конфигурации MCP, версии и ограничения рабочего Mac — вход живой пробы, не условие написания локального стенда.
- Поддерживается ли выбранный канал внутренним клиентом и браузером — исследовательский вопрос PBT-121. Ответ не расширяет реализацию: отказ даёт отрицательный отчёт, смена подхода требует отдельного решения.
