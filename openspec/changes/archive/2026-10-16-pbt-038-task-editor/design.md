# Design — PBT-038 Task editor

## Context

Ядро команд готово и протестировано (PBT-031): `createTask`, `updateTask`, `setTaskDates`, `setTaskDuration`, `deleteTask` — чистые, с диагностикой по `PlanCommandErrorCode`. Виджет PBT-037 рендерит чарт из документа; запись документа — через тот же SDK-канал, что читание (`writeDocument`/автосохранение платформы). Read-only PBT-037 достигнут отсутствием вызывающих редактирование путей, а не блокировкой в компоненте — поэтому форма не «снимает блокировку», а добавляет путь записи.

## Goals / Non-Goals

- Goals: единая форма для создания и редактирования; правила ввода A1–A4 (PBT-003); клавиатура и фокус; мгновенное отражение во втором экземпляре.
- Non-Goals: см. proposal Non-Goals.

## Decisions

### D1. Одна форма — два режима

`TaskEditorDialog` получает `plan`, `mode: 'create' | 'edit'`, `task?`, `groups`, `onSubmit(patch)`, `onClose`. Create: пустые поля (группа — «Без группы»). Edit: значения задачи. Валидация клиента: непустое название, длительность — целое ≥ 1, дата — ISO. Доменные ошибки (`inverted-interval`, `invalid-duration`…) показываются под полем «Длительность»/общей строкой. Отправка — только если результат `ok`; иначе форма остаётся открытой с ошибкой.

### D2. Даты через рабочую длительность

Форма не даёт вводить окончание напрямую: поля «Начало» + «Длительность (раб. дни)», окончание показывается вычисленно (`addWorkingDays(start, duration − 1)` через `workingDaysBetween`/`addWorkingDays` ядра PBT-013). Подтверждение → `setTaskDates(plan, id, start, addWorkingDays(start, d − 1))` — то есть A2-семантика при сохранении формы (ручной ввод A3 остаётся в drag/resize, PBT-039). Праздники в предпросмотре окончания пересчитываются на лету.

### D3. Открытие формы и точки входа

- Тулбар над чартом: кнопка «Добавить задачу» (+ счётчик задач справа — уже есть смысл у пустого состояния).
- Двойной клик по строке задачи: событие SVAR `onTaskDblClick` (проверено на спайке PBT-014; payload — id строки) → режим edit. Клик по строке группы форму не открывает (группы — PBT-040).
- Удаление — кнопка в форме редактирования с подтверждением `window.confirm` (минимум для v1; причинно-следственная чистка в ядре — `deleteTask` уже переносит потомков по PBT-032-контракту удаления задачи… на деле удаление задачи чистит её из групп и зависимостей — контракт PBT-031).

### D4. Диалог и фокус

Диалог — absolute-оверлей внутри контейнера виджета (`position: absolute; inset: 0` + центрированная карточка): не конфликтует с порталом платформы, виден в обоих экземплярах независимо. Клавиатура: Tab по полям, Esc — отмена, Enter в полях — отправка. При открытии фокус в первое поле (название); при закрытии — возврат фокуса на триггер (кнопка тулбара / строка чарта — `document.activeElement` до открытия сохраняется и восстанавливается).

### D5. Запись через SDK

Запись выполняется существующим каналом сохранения документа, который виджет уже использует для чтения (SDK-хук документа): `next = applyPlanCommand(plan, cmd)`; при `ok` — запись новой редакции через `writeDocumentContent`-эквивалент SDK (`document.update(content)` — по API подписки PBT-037). Автосохранение платформы (1500 мс) подхватывает запись; reload восстанавливает. Тест вручную: IDB-ревизия растёт, второй виджет обновляется по `key={revision}` (remount).

### D6. Тесты

- Unit: чистая логика формы — `buildTaskDates(start, duration, calendar)` (конвертация полей в команды + предпросмотр окончания), валидации; мок SDK не нужен (функции чистые).
- E2E (`plan-editor.spec.ts`): создать задачу из тулбара → появилась в чарте; reload → сохранилась; invalid-ввод → ошибка у поля, документ не изменился; отмена → исходные данные; редактирование названия/дат → видно во втором виджете; удаление → исчезла в обоих; фокус возвращается (проверка `:focus` на триггере). Загрузка контрольных данных — dev-хук `__projectBoard.writeDocumentContent` (PBT-037) на prod-сборке; `npm run build` перед `test:browser`.

## Risks / Trade-offs

- `onTaskDblClick` SVAR — событие из документации спайка; если payload нестабилен (как жесты по ADR-5), fallback — кнопка редактирования в своей колонке (резерв не реализуем до необходимости).
- `window.confirm` блокирует поток — приемлемо для v1, замена на инлайн-подтверждение — попутная правка при претензиях UX.

## Migration Plan

Новая поверхность, миграций нет. Обратная совместимость документов не затрагивается (v1-схема).

## Open Questions

Нет — развилок, требующих владельца, не выявлено; серия делается автономно по директиве владельца 2026-10-14.
