## Context

Мотивация и границы — в proposal.md. Владелец уточнил функциональный объём: интерфейс резервного копирования по прототипу, максимум 5 копий и только ручное сохранение. Ниже технический дизайн для ревью до реализации.

Текущая модель:

- `ManagedDocument` в SDK содержит оболочку документа, `schemaVersion`, `revision` и непрозрачное для платформы `content`.
- `WorkspaceSnapshot` в `packages/dashboard/src/workspace-store.ts` содержит вкладки, экземпляры и активную вкладку; у экземпляра независимо хранятся `gridArea` и `cascadeArea`. Порядок глубины каскада хранится во вкладке.
- Настройки представлений сохраняются отдельно, в ключах `view:<instanceId>` таблицы settings; среди них есть фильтры, масштаб, положение видимой области и свёрнутые группы.
- Схема IndexedDB имеет версию 2. Версии схемы БД, содержимого документов и будущего файла — разные понятия.
- Закрытие окна оставляет документ в каталоге. Удаление документа может оставить живое окно с состоянием «документ отсутствует» — это допустимое состояние приложения.
- Реестры виджетов и миграций собираются приложением; SDK не предоставляет общего валидатора содержимого каждого модуля.
- Интерфейс-референс — flexi-dashboard-hub, commit `29bd84bfa17388857964be68f95ba4553b282655`, раздел 7 `MVP-DESIGN-TASKS.md`, `Dashboard.tsx`, `BackupDialog.tsx` и `backups.ts`. В коде прототипа копии лежат в localStorage и создаются автоматически при открытии диалога; эти механизмы заменяются согласно поручению владельца.

## Goals / Non-Goals

**Goals:** ручная копия согласованного состояния всего приложения, хранение пяти копий, перенос JSON-файлом и атомарное восстановление с сохранением идентичности и страховкой. Чистая проверка снимка отделена от операций хранилища.

**Non-Goals:** автоматические копии, расписания, остальные настройки прототипа, merge пространств, изменение схем предметных данных или правил планирования. Кодек не выполняет предметную валидацию; применение использует существующие миграции документов, а не второй движок миграций.

## Decisions

### D1. Чистый кодек в платформе

Добавить `packages/dashboard/src/workspace-backup.ts` с типами формата, сериализатором, десериализатором и диагностикой, экспортируемыми из `index.ts`. Использовать существующие типы документов и workspace через type imports. Нет обращений к Dexie, сети, глобальному приложению и предметным пакетам.

Обе операции используют одну проверку данных. Предлагаемый контракт:

- `serializeWorkspaceBackup(snapshot, createdAt)` возвращает `{ ok: true, json, issues }` либо `{ ok: false, issues }`.
- `deserializeWorkspaceBackup(text, compatibility)` возвращает `{ ok: true, backup, issues }` либо `{ ok: false, issues }`.
- `issues` — массив `{ severity: 'error' | 'warning', code, path, message }`; `ok: true` возможен только без ошибок.
- `compatibility` содержит перечень известных `typeId` и дескрипторы `{ moduleId, documentType, schemaVersion }`, переданные вызывающим кодом; доступ к реестрам внутри кодека не требуется.
- Сериализация проверяет целостность, но не требует информации об установленной комплектации. Совместимость разбора проверяется относительно явно переданного перечня, включая пустой перечень.

Альтернатива — экспорт таблиц БД: привязал бы файл к устройству хранения, скопировал устаревшие settings и усложнил развитие формата.

### D2. Формат v1 и независимые версии

Предлагаемая оболочка:

```text
{
  format: "project-board-workspace",
  formatVersion: 1,
  workspaceSchemaVersion: 1,
  createdAt: <ISO timestamp UTC>,
  documents: ManagedDocument[],
  workspace: WorkspaceSnapshot,
  viewSettings: Record<instanceId, JSON object>
}
```

`createdAt` передаётся явно, чтобы кодек оставался детерминированным. `formatVersion` версионирует оболочку, `workspaceSchemaVersion` — записи платформы; обе поддерживают только 1. `documents[].schemaVersion` принадлежит модулю, `revision` остаётся редакцией документа. Версия Dexie в файл не включается: это внутреннее устройство локальной БД.

Снимок содержит все документы, включая неоткрытые, и только живые вкладки/экземпляры/настройки. Не включать историю копий, service worker, кэш ассетов, подписки, таймеры, ошибки сохранения, черновики диалогов и незавершённые жесты. Сохранённые настройки видимой области и сворачивания переносятся как обычные настройки окна. Глобальные настройки, не входящие в явный контракт v1, в снимок не входят. Служебные ID/тип локальной копии и поколение текущего хранилища также не относятся к содержимому переносимого снимка.

Для v1 поля оболочки и записей платформы ограничены документированным набором: неизвестное поле даёт ошибку, чтобы кодек не потерял его молча. Внутренние поля `content` и `viewSettings` открыты и сохраняются полностью. Необязательные поля экземпляра допускают отсутствие по текущему контракту; `gridArea` и `cascadeArea` допускают также null.

Альтернатива — единая версия с IndexedDB: потребовала бы менять переносимый файл при изменении индекса БД, не связанном с данными.

### D3. Точная передача JSON без нормализации

Все идентификаторы, ссылки, порядок массивов, даты и редакции сохраняются. Один общий документ остаётся одной записью, даже если его открывают несколько окон. Не используются сериализаторы отдельного плана: они предназначены для независимого импорта и могут нормализовать данные.

До `JSON.stringify` проверять JSON-совместимость: конечные числа, строки, boolean, null, массивы и обычные объекты со строковыми собственными полями. Отклонять undefined в присутствующем поле или элементе массива, NaN/Infinity, bigint, функции, symbol, циклы, экземпляры Date/Map/Set, разреженные массивы и accessor-свойства. Необязательный атрибут без значения вызывающий код должен опустить. Это предотвращает молчаливую потерю данных при JSON.stringify. Общая ссылка на объект без цикла допустима: идентичность объектов памяти не часть формата.

Кодек не меняет входные объекты; результат разбора не имеет общих изменяемых объектов с исходным снимком. Прототипные имена вроде `__proto__` не должны менять прототип при обходе или сборке словарей; обработка ключей — через собственные свойства и безопасные Map/словари.

### D4. Структура и ссылочная целостность

Ошибки с точным путём:

- Некорректный JSON/маркер/версия; отсутствие обязательных разделов; неправильные типы, флаги и перечисления.
- Пустые идентификаторы; дубликаты внутри документов, вкладок или экземпляров. Разные пространства ID независимы: одинаковая строка у документа и вкладки допустима.
- Вкладок должно быть не меньше одной; их `position` — уникальные целые числа ≥0. Активная вкладка существует, ровно у неё `active: 1`, у остальных `active: 0`.
- `instance.tabId` обязан указывать на существующую вкладку. Записи `cascadeOrder` уникальны и принадлежат экземплярам этой вкладки; неполный/пустой порядок допустим по текущему контракту.
- Ключи `viewSettings` должны принадлежать живым экземплярам. Отсутствие настроек у экземпляра допустимо; создание настроек по умолчанию кодек не выполняет.
- Сетка: целые x/y ≥0, w/h >0. Каскад: конечные x/y ≥0, width/height >0. Ограничения размера текущего виджета и viewport не применяются к переносимому файлу.
- Оболочка документа: непустые строковые moduleId/documentType/title, schemaVersion — целое ≥0, revision — целое ≥1, корректные временные метки UTC; content обязателен и JSON-совместим. Заголовки вкладок также непустые; кодек не обрезает пробелы и не исправляет вход.

Ссылка окна на отсутствующий документ — предупреждение `document-missing` с путём к `documentId`. Окно и ссылка сохраняются: приложение уже поддерживает этот случай после удаления документа. Это обнаруженная недоступность, а не молчаливое исправление или создание нового документа.

Минимальный набор кодов: `invalid-json`, `unknown-format`, `unsupported-format-version`, `unsupported-workspace-version`, `invalid-data`, `non-json-value`, `duplicate-id`, `invalid-reference`, `document-missing`, `unknown-widget-type`, `unknown-document-type`, `future-document-version`.

### D5. Неизвестные модули и версии содержимого

Неизвестные typeId или пара moduleId/documentType дают предупреждение и сохраняются вместе с содержимым и настройками. Будущая версия известного документа также даёт предупреждение с версиями; она не понижается и не перезаписывается кодеком. Это позволяет сохранить данные, которые приложение пока не умеет редактировать.

Более старая версия известного документа сохраняется без изменений при разборе: миграции принадлежат существующему сервису документов. На подготовке применения чистая цепочка существующих миграций проверяется до записи; разрыв цепочки или сбой отменяет всё восстановление. Повторно реализовывать правила миграций в кодеке не нужно.

Структурно корректное JSON-содержимое известного модуля не равно предметно корректному документу. В документации результата явно указать эту границу: проверяются контейнер и ссылки платформы, а смысл задач, календарей и пунктов списка проверяет владелец модуля.

Альтернатива — отклонять снимок из-за отсутствия модуля: мешала бы переносить данные между комплектациями. Альтернатива — удалять неизвестные записи: создаёт потерю данных.

### D6. Восстановление — подтверждаемая полная замена

Формат v1 описывает целое пространство и сохраняет исходные ID. Восстановление полностью заменяет текущее пространство после предпросмотра, включая непустое приложение. Совпадение ID не означает слияние документов. Повторное применение восстанавливает то же логическое состояние, без дубликатов. История локальных копий остаётся в backups и не заменяется содержимым файла.

Предпросмотр показывает дату и состав выбранной копии, состав заменяемого пространства и предупреждения. Checkbox «Сначала сохранить страховочную копию текущего состояния» включён по умолчанию и сбрасывается в это состояние для каждого нового подтверждения. Страховочная копия — выбранное пользователем действие внутри ручного восстановления; без подтверждения операции она не создаётся. При снятом checkbox никаких дополнительных копий не создавать.

До записи проверяются структура, ссылки, комплектность и миграции. Неизвестные документы сохраняются непрозрачными; будущие версии остаются защищёнными от записи существующим сервисом. Невалидный файл, ошибка подготовки или отмена не изменяют текущее пространство и список копий.

Атомарная транзакция охватывает документы, вкладки, экземпляры, настройки и при необходимости страховочную копию с применением лимита. Ошибка записи откатывает всю транзакцию, включая вытеснение старейшей копии. Целевая копия удерживается в памяти на время операции: её возможное вытеснение при добавлении страховочной не мешает восстановлению. Миграции выполняются до транзакции и не превращаются в отдельные записи после замены.

Альтернатива — merge: требует самостоятельного решения по конфликтам ID/редакций и ссылкам внутри предметных данных. Она не входит в согласованный сценарий.

### D7. IndexedDB: пять ручных копий

Добавить таблицу `backups` в существующую БД, повысив схему 2 → 3. Описать последовательность v1/v2/v3 явно в общем источнике деклараций и использовать её во всех адаптерах платформы, включая self-test; прежнюю схему нельзя переобозначить выражением «текущая версия минус один».

Запись копии: UUID, время добавления, тип `manual | safety`, сериализованный снимок, размер в UTF-8 и сводка документов/вкладок/окон. Формат JSON общий для скачанных и локальных копий; служебная запись БД его оборачивает. Индекс/порядок добавления даёт детерминированный выбор старейшей записи, включая совпадение временных меток.

`MAX_BACKUPS = 5` распространяется суммарно на ручные и страховочные записи. В одной транзакции добавить запись и удалить лишние старейшие; отказ не удаляет прежнюю историю. Число ручных операций не ограничено за день. Ошибка квоты показывается пользователю; «создано» сообщается только после commit. Открытие приложения/модалки, перезагрузка, смена дня и таймеры не создают копий. Тип `auto`, расписание и маркер последней автокопии не добавляются.

Восстановление из файла не сохраняет импортированную копию в историю само по себе; дополнительно создаётся только выбранная страховочная копия. История не включается в снимок рекурсивно. Удаление строки удаляет только эту резервную копию. Пустая история отличается от ошибки её чтения; повреждённые записи не отбрасываются молча.

### D8. Шестерёнка, меню и модалка уровня приложения

В `apps/project-board` разместить шестерёнку справа на панели дашборда рядом с каталогами документов и виджетов, как в Dashboard прототипа. Доступное имя и tooltip — «Настройки», состояние раскрытия — aria-expanded. В меню только «Резервные копии». Использовать существующий DropdownPanel с позиционированием и управлением фокусом; открытие модалки закрывает меню.

Модалка принадлежит приложению и располагается вне окон виджетов. Использовать нативный dialog/showModal по уже принятому подходу PBT-085; модульный `gantt/PlanDialog` в платформу не импортировать, SDK не расширять. Воспроизвести визуальные роли референса на токенах приложения: заголовок, описание, сводка, действия, сообщения, список и подтверждение восстановления. Тело ограничено viewport и прокручивается; крестик/действия доступны на 1024×778 и широком экране. Фокус удерживается внутри; после закрытия возвращается к шестерёнке. Закрытие по Escape/крестику/клику по подложке отменяет только неподтверждённый просмотр, во время записи повторные действия и закрытие блокируются.

Сводка показывает документы, вкладки и окна всего пространства. «Создать копию» сохраняет текущий снимок. «Из файла» читает и проверяет JSON и открывает подтверждение. Для каждой строки — дата, тип «вручную»/«перед восстановлением», число документов и окон, размер, действия восстановления/скачивания/удаления с доступными именами. Счётчик `N / 5`, пустое состояние и ошибки обязательны. Даты/счётчики/размеры — моноширинным шрифтом.

Скачивание формирует Blob `application/json` и безопасное имя `pb-workspace-YYYY-MM-DD_HH-mm-ss.json`; object URL освобождается после инициирования загрузки. Сообщение сообщает передачу файла браузеру, не обещает запись на диск. Ошибка сохраняется до действия пользователя; успех временный и не сдвигает основные действия.

### D9. Согласованный снимок и защита от поздних записей

Добавить координатор операций уровня приложения. При ручном создании или восстановлении блокировать новые изменения, завершить ожидающие записи документов, удалений, workspace и настроек через существующие flush, проверить отсутствие конфликта и зафиксировать согласованный снимок. Отсутствующие необязательные свойства не включать в DTO; viewSettings собирать по живым ID. Сериализация не должна молча отбрасывать невалидное содержимое или неоткрытые документы.

Снимок документов/workspace/settings читать в одной транзакции платформенного адаптера после flush; сверять его с подготовленным состоянием. Если другая вкладка браузера успела изменить источник, отказаться от операции с сообщением о необходимости перечитать данные, а не создавать смешанный снимок. Для сохранения и восстановления защищаться от изменений между чтением и commit проверкой исходных записей в транзакции записи.

Для восстановления в settings ввести служебное поколение пространства; каждая запись документов/workspace/viewSettings/удаления проверяет ожидаемое поколение внутри той же транзакции. Полная замена атомарно меняет поколение. Старые callbacks, pagehide и другие окна приложения со старым поколением не могут записать состояние поверх восстановленного; им сообщается необходимость перезагрузки. Это механизм адаптера платформы, вне документов и формата файла; привычная проверка revision сохраняется.

После успешного commit выполнить управляемый перезапуск приложения с повторным чтением БД; старые таймеры и pagehide не записывают прежний workspace. До перезапуска блокировка остаётся активной. При отказе снять блокировку и оставить доступным прежнее рабочее состояние и сообщение. Ни открытие диалога, ни предпросмотр не размонтируют виджеты; при подтверждённой замене старое пространство завершается целиком.

## Risks / Trade-offs

- Большой снимок и пять его копий расходуют память/квоту IndexedDB → обрабатывать операции последовательно, показывать ошибки чтения/квоты без потери прежних данных; потоковый формат не вводить.
- Сырой снимок из памяти может содержать undefined или устаревшие ключи viewSettings → сборщик формирует явный DTO из живого пространства, а кодек продолжает отвергать невалидные значения.
- Сохранение непрозрачного содержимого не проверяет правила модулей → документировать границу проверки и не трактовать успешный разбор как разрешение редактировать документ.
- Принятие будущего документа не означает поддержку его редактирования → предупреждение и существующая защита будущих схем после восстановления.
- Состав v1 не является побайтовой копией профиля браузера → перечислить сохраняемые и исключённые данные в документации.
- Поздние записи из другого окна могут испортить восстановленное пространство → проверка поколения и исходных данных внутри транзакций, регрессия с двумя контекстами браузера.
- Расширение PBT-064 существенно превышает первоначальный кодек → явно включить адаптер, UI, файлы и восстановление в задачи одного change; отдельные настройки и автокопии не добавлять.

## Migration Plan

1. Добавить явную схему IndexedDB v3 с таблицей backups и служебным поколением, сохранив документы, вкладки, окна и настройки v1/v2. Проверить обновление реальной БД, включая несколько соединений.
2. Реализовать кодек, адаптер и координатор, затем меню/модалку; подключить существующие миграции документов к подготовке восстановления.
3. Проверить PWA-обновление со старой схемы на новую, offline и поведение старой сборки после обновления. Фактический тест v2-адаптера на v3-БД подтвердил открытие прежних таблиц и сохранность backups; старая сборка не предоставляет UI для управления таблицей backups. Для работы с копиями нужна v3-сборка; данные не удалять при откате.
4. Результат PBT-064 — PR в develop; публикация остаётся отдельным действием по поручению владельца. Основная spec обновляется при принятой архивации change.
