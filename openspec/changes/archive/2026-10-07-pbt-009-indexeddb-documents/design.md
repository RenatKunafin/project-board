## Context

`DocumentService` (PBT-007) — синхронный in-memory контракт в SDK с реализацией в dashboard. Согласованный выбор — IndexedDB через Dexie (ADR-5), схема документа — решения 15.2 (поля `ManagedDocument` уже соответствуют), хранилища платформы — 15.2 (`settings/tabs/widgetInstances/documents`). Инструменты: Vitest, Playwright, ESLint-границы (PBT-005). Первый настоящий runtime-зависимость приложения: `dexie` в `packages/dashboard`.

## Goals / Non-Goals

**Goals:**

- Асинхронный адаптер `DocumentStore` на Dexie: save/get/listByModule/listByType/delete/close, транзакционная проверка редакции.
- Единый тип ошибок `PersistenceError` с кодами причин.
- Интеграционные тесты на `fake-indexeddb` + браузерный сценарий повторного открытия.
- Изоляция IndexedDB/Dexie в `packages/dashboard` на уровне ESLint.

**Non-Goals:**

- Переписывание `DocumentService` и подключение store к сервису/чек-листу (PBT-010 — очередь автосохранения).
- Хранилища `settings/tabs/widgetInstances`, версии БД и миграции (PBT-026), экспорт/резервные копии (PBT-064/065).
- Работа с несколькими вкладками браузера (координация — вне первой версии).

## Decisions

- **Dexie 4.x в `packages/dashboard`.** Согласованный кандидат из решений (утверждён ADR-5). Обёртка над открытым IndexedDB: транзакции, индексы, типизация. Альтернатива — голый IndexedDB API: много ручного кода транзакций без выгоды.
- **Контракт `DocumentStore` — в dashboard, не в SDK.** Модули не обращаются к хранилищу напрямую (только через `DocumentService`, PBT-010 свяжет их), значит store — внутренняя деталь платформы. SDK не расширяется.
- **Асинхронность — на store, не на сервисе.** `DocumentService` остаётся синхронным (UI читает из памяти мгновенно); store — отдельный асинхронный контракт (`Promise`-методы). В PBT-010 сервис получит опциональный persistence-хук («записать после фиксации»), что сохранит отзывчивость UI и отделит durable-слой.
- **Атомарность через транзакцию Dexie.** `transaction('rw', documents, ...)` → чтение хранимой записи → сравнение `revision` с `expectedStoredRevision` → `put`. Отклонение внутри транзакции откатывает её целиком; конфликт — `DocumentConflictError` (уже в SDK, переиспользуется). `save` нового документа требует `expectedStoredRevision = 0` (в хранилище «пусто»).
- **Схема БД v1: только `documents`.** `id` — primary key, индексы `moduleId`, `documentType` (сценарии спецификации). Остальные хранилища добавят свои версии схемы в PBT-026 — сознательно не создаём пустых store.
- **`PersistenceError` с кодами** `open-failed | write-failed | schema-version-unsupported | document-not-found` (не найден — только для операций, требующих существования; get/delete мягкие). Неподдерживаемая версия: если открытие ловит `VersionError` (БД от «будущего» приложения) → `PersistenceError('schema-version-unsupported')` с понятным сообщением пользователю.
- **Браузерный сценарий — техническая самопроверка.** Приложение поддерживает hash-маршрут `#storage-selftest`: компонент из dashboard прогоняет save → close → reopen → get → конкурентную запись и отображает результат. Это не продуктовый UI, а воспроизводимый сценарий проверки (e2e + вручную); удаляется при появлении реальной интеграции в PBT-010.
- **Тесты Node — `fake-indexeddb`.** Стандартный способ гонять Dexie вне браузера; `close()` + повторное открытие в fake-IDB сохраняет состояние между соединениями — покрывает «повторное открытие БД» без браузера.

## Risks / Trade-offs

- [Dexie — новая runtime-зависимость приложения (~100KB gzip <)] → без неё транзакционная проверка редакции на IDB — заметный ручной слой; зависимость согласованного стека (ADR-5), размер приемлем.
- [fake-indexeddb может отличаться поведением от реального IDB] → браузерный e2e-сценарий на настоящем Chromium покрывает расхождения для основного пути.
- [Self-test-маршрут останется в проде] → безвреден (доступен только по явному hash), будет заменён реальной интеграцией в PBT-010; в каталоге/навигации не отображается.
- [Отсутствие миграций при росте схемы] → v1 сознательно минимальна; политика версий — PBT-026.
