## Context

Карточка PBT-088: представить результаты действующего движка (PBT-046) группами с фильтрами и поиском; «расширить представление структурированными полями результатов ядра; не извлекать их разбором русского текста сообщения и не менять алгоритм/число конфликтов». Референс — `PlanIssues.tsx` прототипа: группы по типу, кнопки-фильтры со счётчиками, поиск «Задача или исполнитель…», строка «задача + суть + действие», различённые пустые состояния.

Текущее состояние:

- `usePlanIssues` (PlanIssuesDialog.tsx) уже сводит ядро: `dependencyViolations` ({dependencyId, fromTaskId, toTaskId, expectedStart, actualStart, message}) + `resourceConflicts` ({kind, resourceId, firstTaskId/secondTaskId | taskId/unavailabilityId, intervalStart, intervalEnd, message}) — структура есть, представление показывает только `message` плоским списком.
- Переход «Показать» (PBT-082, `showTask` → taskNavigation) закрывает модалку, раскрывает группы, снимает фильтры экземпляра, показывает строку/начало полосы, выделяет.
- Общая форма задачи (PBT-087) доступна из проектного вида; тулбар показывает «Проблемы (N)» по полному ядру.
- Список проблем открывается из тулбара проектного вида; ресурсный вид кнопки проблем не имеет (вне объёма карточки).
- Диалоги экземпляра — один верхний слой (PBT-085): одновременно показывается один диалог.

## Goals / Non-Goals

Goals: читаемость больших списков проблем (группы, фильтры, поиск), структурированная строка из полей ядра, два явных действия, различённые пустые состояния, поведение без изменений для ядра, документа, счётчика тулбара и сценариев PBT-082.

Non-Goals: изменения ядра диагностики (алгоритм, тексты, число), дедупликация записей, список проблем в ресурсном виде, изменение схемы документа, замена перехода «Показать».

## Decisions

### D1. Структура `usePlanIssues` из полей ядра, без разбора текста

Запись проблемы расширяется: `kind`, `taskId` (цель перехода/редактирования — та же, что сегодня), `taskIds` (участники: from+to для FS, first+second для работ, task для отпуска), `resourceId?`, `dates` (`expectedStart/actualStart` для FS; `intervalStart/intervalEnd` для конфликтов), `message` (текст ядра как есть). Порядок записей прежний: FS → конфликты работ → отпуска, внутри — порядок ядра; дедупликация не вводится.

### D2. Группы и фильтры (по прототипу)

Три фиксированные группы в порядке видов; заголовок группы — тип + счётчик видимых записей группы. Панель фильтров: кнопки «Все» и три типа с счётчиками по полному ядру (`aria-pressed`); активный фильтр один. Группа без видимых записей при активном фильтре не показывается. Счётчик тулбара остаётся общим числом проблем ядра — не зависит от фильтра/поиска списка (подтверждение поведения карточки).

### D3. Поиск

Одно поле «Задача или исполнитель…» (по прототипу): подстрока без учёта регистра ищется в названиях задач-участников записи и названиях ресурсов их назначений (для FS-записи — обе задачи связи; для конфликтов — участники и ресурс пересечения). Поиск комбинируется с фильтром типа AND.

### D4. Строка и действия

Строка: заголовок — название задачи-цели; суть — `message` ядра; структурированные данные — даты (ожидаемая/фактическая для FS; интервал пересечения для конфликтов) и ресурс, когда применимо. Два явных действия:

- «Показать» — действующий переход PBT-082 без изменений (закрывает модалку, раскрывает группы, снимает фильтры экземпляра, показывает и выделяет задачу);
- «Открыть» — закрытие модалки проблем и открытие общей формы задачи в режиме редактирования с актуальными данными документа (одновременных диалогов у экземпляра нет — PBT-085).

Задача, отсутствующая в актуальном плане (удалена в другом экземпляре после открытия), исчезает из списка пересчётом — действие по несуществующей задаче недостижимо.

### D5. Пустые состояния и вертикаль

- Ядро без проблем: «Проблем нет» (иконка успеха).
- Есть проблемы, но фильтр/поиск не дают совпадений: «Нет проблем по выбранному фильтру» / «Ничего не найдено по запросу» — состояния различимы.
- Тело списка — прокручиваемая область внутри экранной модалки (PlanDialog wide); длинные названия и сообщения переносятся (`break-words`), действия фиксированы у строки и не перекрываются.

### D6. Представление — производное документа

Группировка/фильтры/поиск — локальное состояние экземпляра внутри открытой модалки, без записи в документ и настройки; закрытие без действий не меняет документ и положение диаграммы (переход «Показать» — единственное, что двигает вид, его сценарии сохранены).

## Risks / Trade-offs

- Поиск по назначениям требует доступа к плану в диалоге: `usePlanIssues` остаётся чистой функцией плана, диалог получает план для разрешении названий (ресурс/задачи) — разрешение имён только для отображения.
- Объём в пределах ориентира PR; тесты покрывают сценарии карточки на импортированном плане с большим числом конфликтов.

## Migration Plan

Не требуется.

## Test Strategy

Unit: структура `usePlanIssues` (поля по каждому виду, участники, даты, ресурс); группировка/счётчики; комбинирование фильтра и поиска; пустые состояния. E2E (production preview): импортированный план с десятками конфликтов трёх типов и длинными названиями — группы и счётчики, фильтры, поиск по задаче и исполнителю, различённые пустые состояния; «Показать» повторяет сценарии PBT-082 (свернутая группа, фильтр, клавиатура, начало полосы); «Открыть» — форма с актуальными данными, после сохранения строка/счётчик обновляются; закрытие без действий — диаграмма на месте, документ без новых ревизий. Обязательный набор: lint/typecheck/unit/build/browser, verify:repository, openspec strict; по прототипу — скриншоты 1024×778 и 1856×1269.
