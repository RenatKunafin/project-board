## Context

Существующий harness запускается через `npm run bench:release` и сохраняет `environment.json`, сырые результаты и итоговую проверку бюджетов. Исторические прогоны PBT-085/PBT-087 дали превышение `addTask`, тогда как релизный прогон PBT-059 показывал результат ниже 400 мс. Сравнение имеет смысл только при одинаковой фикстуре, lockfile, headed-режиме и чистом жизненном цикле preview/dev/MCP.

## Goals / Non-Goals

**Goals:**

- получить актуальную базовую линию `addTask` на `develop` по прежней методике;
- отделить время записи, монтирования и переключения набора от общего действия;
- сохранить воспроизводимые raw/environment артефакты и краткий вывод с уровнем уверенности;
- проверить, не является ли превышение следствием измерительной среды или единичного прогрева.

**Non-Goals:**

- не менять порог 400 мс и существующие тестовые ожидания;
- не оптимизировать production-код в рамках исследовательского change;
- не объявлять бюджет выполненным по одному удачному прогону;
- не добавлять новый telemetry/analytics код.

## Decisions

1. **Сначала повторить штатный полный benchmark, затем локальный диагностический прогон.** Полный `npm run bench:release` остаётся единственным источником итогового budget verdict; выборочные grep/сценарии используются только для локализации и не пересчитывают общий результат.
2. **Сравнивать только сопоставимые среды.** В отчёт попадают commit, lockfile hash, Node/OS/CPU, headed/headless, браузер, fixture и число прогревов/измерений. Прогоны с иным setup помечаются как несопоставимые.
3. **Не смешивать исследование и исправление.** Если профиль укажет на кодовую причину, результат фиксируется в отчёте и создаётся отдельный change с собственным scope, design и PR.

## Risks / Trade-offs

- [Шум окружения] → повторить полный сценарий минимум дважды после прогрева и сохранить оба набора raw; не делать вывод только по медиане одного запуска.
- [Различие preview/dev/MCP] → остановить посторонние серверы перед каждым прогоном и явно записать это в environment/отчёте.
- [Локальный benchmark зелёный, но release budget красный] → считать verdict по `check-budgets.mjs`, а расхождение разобрать по этапам, не повышая порог.
- [Измерения зависят от текущего hardware] → указывать модель CPU и не обобщать результат на все машины.

## Migration Plan

Миграции нет. Исследовательские артефакты добавляются в локальный `test-results/`/отчёт; при подтверждённом дефекте следующий change разрабатывается отдельно.
