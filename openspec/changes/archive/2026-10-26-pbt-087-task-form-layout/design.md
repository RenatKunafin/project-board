## Context

Мотивация и границы — [proposal.md](proposal.md). TaskEditorDialog уже общий для PlanGanttWidget и ResourceTimelineWidget, но читает текущий plan, держит поля локально и вызывает applyDependencyCommand с немедленной записью. useTaskForm.commitPlan автоматически повторяет запись; исчезнувшая исходная задача может попасть в ветку создания. В PBT-086 уже принят общий черновик настроек и добавлен PlanDialog.onBeforeClose. SDK предоставляет синхронные get/update с expectedRevision. Решения D1–D6 одобрены владельцем 2026-10-26 перед реализацией. Изучены DemoTaskForm.tsx и PlanDialog.tsx из flexi-dashboard-hub: переносим компоновку полей, ограниченные списки и неподвижные действия; демо-прогресс и упрощённую модель данных не переносим.

## Goals / Non-Goals

**Goals:** один согласованный снимок задачи, календаря, назначений и входящих связей; атомарное сохранение; доступная форма без потери промежуточного ввода.

**Non-Goals:** автоматическое слияние чужих правок, новый общий сервис диалогов, долговременное хранение черновика, перестройка остальных потребителей commitPlan, новые способы создания задач из ресурсного вида.

## Decisions

### D1. Компоновка и списки

Четыре подписанных раздела расположены последовательно в прокручиваемом теле PlanDialog; вкладки не нужны для небольшой формы. Название занимает ширину раздела «Основное», группа расположена ниже. В «Сроках» начало и рабочая длительность стоят рядом, включительное окончание показано явно. В «Назначениях» — исполнители и типы работ; в «Зависимостях» — входящие FS-связи с лагами. Шапка и действия остаются доступны. На узком экране поля переходят в одну колонку без уменьшения шрифта. Стили используют токены приложения.

У каждого большого списка — собственный поиск по названию, счётчик выбранных и ограниченная высота. Выбранные назначения доступны отдельной областью с возможностью снять выбор независимо от поискового запроса; выбранные предшественники с лагами также остаются доступны отдельно от поиска кандидатов. Пустой справочник и пустая выдача различаются. Поиск не меняет выбор и не считается изменением документа. Альтернатива с длинными select не обеспечивает удобного поиска и доступа к выбранному.

### D2. Снимок и единый черновик

При открытии фиксируются исходные plan/revision и taskId для edit. Значения полей и входящие связи живут в модуле Гантта до Save; строки числового ввода сохраняются как строки до строгой проверки целого значения (без parseInt усечения дробей). Создание допускает выбор существующих задач-предшественников сразу. ID новой задачи и новых связей появляются при подготовке итогового плана через команды ядра, до единственной записи документа.

Чистая подготовка результата сначала валидирует поля, затем создаёт/обновляет задачу, удаляет исключённые входящие связи, обновляет лаги оставшихся и создаёт новые. Существующие ID связей сохраняются; исходящие связи и чужие задачи остаются прежними. Ошибка любого шага отбрасывает весь результат, возвращает адресную ошибку и не вызывает SDK update. Самоссылки, циклы, назначения и лаги проверяются существующими командами ядра. Несовпадение дат FS даёт обычную диагностику, не запрет ручного сохранения и не перенос задач.

Незавершённая строка добавления предшественника или редактирования лага не теряется при Save: пользователь должен завершить действие либо явно очистить его, ошибка направляет фокус в соответствующий ввод. Альтернатива с немедленными записями и обратными командами при Cancel нарушает контракт отмены и опасна при параллельной работе.

### D3. Даты и отсутствие лишних записей

Создание использует существующую арифметику начала и длительности в рабочих днях с минимумом 1. При edit нетронутые сроки сохраняются точно, включая ручное нерабочее окончание и импортированные интервалы с нулём рабочих дней. Открытие формы или изменение названия/назначений/связей не должно пересчитать такие даты. Если пользователь действительно меняет начало/длительность, применяется действующая арифметика формы; минимальная длительность ввода остаётся 1. Сохранение без содержательных изменений закрывает форму без новой revision. Альтернатива с безусловным buildTaskDates уже может нормализовать ручной интервал и здесь неприемлема.

### D4. Одна запись и конкурентные правки

Общий путь формы получает исходную revision и делает одну update с этой expectedRevision, без ретрая; остальные операции useTaskForm.commitPlan не переписываются попутно. Перед Save/Delete/Convert выполняется свежий get: отсутствие документа, новая revision или отсутствие исходной задачи блокируют действие. Не использовать fallback к старому документу и не превращать edit в create. Исключения SDK показываются в открытом редакторе.

При чужой revision сохраняются ввод и предупреждение; сохранение и разрушительные действия блокируются. «Перечитать план» после подтверждения потери изменённого черновика начинает новую сессию с актуальными данными. Если задача удалена, явно сообщить это и позволить закрыть форму; восстановление/создание копии не предлагается. Конфликт всего снимка выбран как в PBT-086: даже чужая правка другой задачи может изменить граф и календарь. Автоматический rebase расширил бы scope.

### D5. Отмена, скрытие и ошибки

Крестик, Escape и «Отмена» проходят единый guard PlanDialog: при изменённых полях/связях или незавершённом вводе подтвердить отказ через существующий native confirm, отказ оставляет редактор и ввод. Без изменений форма закрывается сразу. При скрытии владельца черновик сохраняется без вопроса, при возвращении восстанавливается; смена/удаление документа, закрытие окна и unmount освобождают форму по PBT-085. Внешнее удаление не вызывает запись старого снимка.

При сохранении ошибки отображаются у поля/строки; первая ошибка получает фокус и прокручивается в видимую часть. Общая ошибка документа имеет доступный фокусируемый блок. Enter в обычных полях сохраняет форму, в поиске не запускает Save, в строке связи завершает локальное действие; Escape при редактировании лага сначала отменяет это локальное действие, затем работает обычный guard формы. Фокус после окончательного закрытия возвращается инициатору по PBT-085.

### D6. Удаление и преобразование

Удаление доступно при edit в обоих видах. Подтверждение объясняет удаление задачи с назначениями и связями; если есть черновик, оно также явно сообщает, что он не будет сохранён. Одна команда удаления исходной задачи и одна update по исходной revision, закрытие только после успеха.

Преобразование остаётся там, где уже доступно, — в проектном виде. При несохранённом черновике переход требует подтверждения его отбрасывания; отказ сохраняет ввод. После подтверждения редактор сбрасывается к исходному снимку, диалог преобразования использует сохранённые название/даты, без предвыбора ресурса. Его отмена возвращает неизменённую форму задачи; успешное преобразование одной записью удаляет задачу со связями/назначениями и создаёт отсутствие, закрывая оба диалога. Конфликт/ошибка оставляет диалоги открытыми с сообщением. Альтернатива с неявным сохранением задачи перед преобразованием создаёт лишнюю запись и неожиданно фиксирует черновик.

## Risks / Trade-offs

- Старые e2e предполагают немедленную запись связей → обновить их на общий Save, сохранить проверки настоящего графа и данных после reload.
- Общий commitPlan используется другими действиями → изменить только контракт операций формы, не менять ретраи соседних редакторов.
- Ручные даты легко нормализовать → отдельные проверки изменения только названия/назначений/связей для нерабочего окончания и нулевого рабочего интервала.
- Консервативный конфликт требует повторного ввода → сохранять черновик до явного перечитывания, не скрывать причину блокировки.
- PBT-092 уже фиксирует превышение бюджета на базовом develop → бюджет 400 мс не менять, выполнить целевой сценарий добавления по прежней методике, результат и ограничения указать явно; отдельную оптимизацию не прятать в 087.
