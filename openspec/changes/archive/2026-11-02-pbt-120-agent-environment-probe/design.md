# Design — PBT-120

Исследование без продуктового поведения (`skip_specs: true`). Технические решения фиксируются здесь; наблюдаемого поведения в specs не добавляется.

## D1. Единица знания и статусы

Каждое свойство среды фиксируется строкой таблицы со статусом:

| Статус | Значение |
| --- | --- |
| `подтверждено владельцем` | Сообщено владельцем как факт о его среде (исходная запись; сверка поведением — не обязательна) |
| `проверено` | Воспроизведено наблюдением по протоколу (владельцем во внутреннем клиенте или нами локально) |
| `неизвестно` | Ответ не получен или проверка недоступна; используется в планировании как неопределённость |
| `не поддерживается` | Установлено отсутствие свойства; влияет на выбор альтернатив |
| `решение владельца` | Выбран вариант пробы; этот статус не доказывает его техническую работоспособность |
| `план пробы` | Уточнение организации будущего эксперимента; выполнение и доступность среды ещё не подтверждены |

Стартовое состояние: `MCP поддерживается клиентом` = подтверждено владельцем (пример использования Playwright MCP); остальные строки — `неизвестно` до ответа. Предположения о поведении конкретных публичных клиентов не используются ни в одном статусе.

## D2. Состав анкеты — только необходимое для пробы PBT-121

Каждый вопрос анкеты привязан к решению, которое без него нельзя принять. Группы:

1. **Платформа клиента агента:** ОС и способ запуска клиента. Снимает выбор упаковки компонента (npm/Node против самодостаточного бинарника) и путей каталога очереди.
2. **Дашборд:** браузер, версия, вкладка или установленная PWA; корпоративная политика локальной сети. Снимает проверку канала HTTPS → loopback (Local Network Access, mixed content) и выбор места пробы (публичный сайт/локальная сборка).
3. **Конфигурация MCP в клиенте:** какие поля есть у описания сервера (команда/args/env, URL), можно ли добавить сторонний сервер и откуда. Снимает выбор транспорта компонента (stdio-кандидат по модели Playwright MCP) и источника установки.
4. **Инструкции/скилл:** поддерживает ли клиент пользовательские инструкции/скиллы, в каком виде. Снимает формат поставляемого скилла обслуживания очереди (PBT-129).
5. **Цикл и ожидание:** может ли агент обрабатывать задания по команде пользователя (минимум), есть ли длительный цикл/расписание; таймауты вызова инструмента. Снимает решение: ручной запуск как базовый режим, цикл — необязательное расширение.
6. **Источник:** есть ли у агента разрешённый инструмент чтения выбранной доски/проекта (только факт, без имени системы и версии в отчёте). Снимает допуск к планированию PBT-130.
7. **Ограничения компании:** установка локального ПО, разрешённые источники пакетов, loopback-соединения, допустимое размещение дашборда. Снимает выбор способа распространения (PBT-131) и сборки без аналитики (PBT-123).

Вопросы, не влияющие на пробу 121 (единицы спринта, история, семантика Done, формат очереди), в анкету не входят — это PBT-122+.

## D3. Целевая среда и организация пробы

- **Целевая среда пробы:** macOS — та же основная машина владельца, где работает внутренний клиент агента.
- **Способ пробного запуска компонента (PBT-121):** выбран кандидат `npx`/npm-пакет. Работа Playwright MCP подтверждает поддержку MCP, но не способ запуска именно этого сервера. Поля конфигурации, наличие нужного runtime и запуск нашего компонента проверяются в PBT-121. Бинарник остаётся кандидатом альтернативы при выявленном препятствии.
- **Место пробы 121:** отдельная экспериментальная HTTPS-страница с синтетическими данными, сопряжением и кнопкой запроса. Она использует реальный сервис документов платформы и отдельное тестовое хранилище. Действующий публичный сайт проекта остаётся целевым окружением будущей интеграции, но пока не содержит функций стенда.
- **Браузер пробы:** Chrome, обычная вкладка (базовый случай канала; PWA-режим — позже, отдельным решением).

Выбор macOS, Chrome/вкладки и кандидата `npx` сохранён по зафиксированным ответам владельца от 02.11.2026. Размещение отдельного стенда уточнено при ревью: конкретный HTTPS-origin, способ предоставления страницы и пакетного артефакта определяются в design PBT-121 до живого запуска. Подготовка артефакта не требует его публикации в npm; локальный пакет — допустимый кандидат.

Публичный Release и изменение production-сайта не являются шагами протокола. Если выбранное размещение требует внешней публикации, она оформляется отдельно в рамках PBT-121 до пробы. Локальная сборка пригодна для предварительной диагностики, но успешный обмен из localhost не заменяет проверку выбранного HTTPS-origin. Результат на экспериментальном origin не доказывает автоматически совместимость production-origin; адрес, версия браузера и ограничения фиксируются в отчёте пробы.

## D4. Ручной запуск — база, цикл — необязательное расширение

Обработка одного запроса по явной команде пользователя считается достаточным режимом первой версии (владелец запускает агента; агент берёт одно задание). Отсутствие длительного цикла/расписания не блокирует интеграцию и не считается отрицательным результатом пробы; оно лишь определяет, что скилл PBT-129 описывает одношаговую обработку. Обратное (цикл есть) расширяет, но не меняет архитектуру очереди.

## D5. Граница работ 120 и 121

В 120 владелец выполняет только действия без нашего сервера: отвечает на анкету и делает тривиальные наблюдения в клиенте — какие поля конфигурации MCP существуют, какие инструменты уже доступны (только имена), наблюдаемые таймауты. Подключение синтетического MCP-сервера, сквозной обмен и браузерный канал — протокол пробы PBT-121, который готовится здесь как согласованная инструкция, но выполняется в 121. Отчёт 120 не утверждает работоспособность обмена.

## D6. Обезличенный отчёт

`docs/research/PBT-120.md` по формату research-отчётов проекта: вопросы, таблица знаний со статусами, ответы анкеты (обезличенные: без названия клиента, компании, имён систем и версий, без токенов и URL внутренних систем), критерии перехода к 121 и зафиксированные блокеры/альтернативы. Недоступные проверки явно отмечаются `неизвестно`, а не пропускаются.

## D7. Подготовка PBT-121 и условия живой пробы

Для подготовки стенда достаточно:

1. Известна целевая ОС, поддержка MCP сообщена владельцем, выбран кандидат запуска компонента; непроверенные конфигурация и runtime явно отмечены.
2. Выбраны браузер/режим и задача размещения отдельного HTTPS-стенда; доступность конкретного origin ещё не объявляется доказанной.
3. Выбран ручной запуск одного задания; цикл может оставаться `неизвестно`.
4. Ограничения установки и loopback записаны с их фактическим статусом; неизвестное не трактуется как разрешение или запрет.

До живого запуска PBT-121 нужно определить фактическую конфигурацию клиента, способ предоставления компонента и HTTPS-страницы, зафиксировать версии браузера/runtime и применимые ограничения установки/сети. Эти вопросы проверяются в PBT-121, а не откладываются до упаковки PBT-131. При известном запрете установка/соединение не выполняются до выбора допустимого варианта.

Возможность начать подготовку стенда не означает, что условия его живого запуска уже выполнены. Если запуск компонента или канал не работают, фиксируем причину и рассматриваем альтернативу. Бинарник, локальная сборка или расширение не объявляются заранее работоспособными и разрешёнными; изменение подхода согласуется с владельцем.

## Риски

- Анкета расширяется до исследования клиента — ограничитель D2: только свойства, необходимые для пробы 121.
- Владелец не может раскрыть свойство — легитимный ответ `неизвестно`; он не трактуется как поддержка.
- Смешение 120/121 (объявление обмена доказанным) — ограничитель D5; в отчёте обмен не утверждается.

## Приложение B. Наблюдения владельца в клиенте (для статуса «проверено»)

1. Открыть экран/файл конфигурации MCP клиента; перечислить поля описания сервера (без значений секретов).
2. Спросить агента, какие MCP-инструменты ему доступны сейчас; вернуть только имена инструментов.
3. Если в клиенте видны настройки таймаутов/лимитов — зафиксировать их наличие и величины (без снимков экрана).

## Приложение C. Протокол пробы PBT-121 (готовится здесь, выполняется в PBT-121)

### C1. Подготовка среды

1. Зафиксировать фактические поля конфигурации MCP и проверить кандидат запуска компонента. Получить воспроизводимый пакетный артефакт и команды без корпоративных данных; публичная публикация пакета не предполагается.
2. Подготовить отдельную страницу стенда по D3; зафиксировать HTTPS-origin, версию сборки и браузера, режим вкладки, способ запуска компонента и применимые ограничения. В обычном production-дашборде функций стенда пока нет.
3. Использовать только синтетические документы в тестовом хранилище. Ограничить сервер loopback-интерфейсом, разрешёнными Host/Origin и явным сопряжением. Защиту браузера не отключать.

### C2. Автоматические проверки стенда с управляемым исполнителем

| Сценарий | Проверяемый результат |
| --- | --- |
| Полный обмен и reload | Запрос обработан, результат записан реальным сервисом документов и прочитан из хранилища после reload без повторной доставки исполнителем |
| Компонент недоступен / связь прервана | Есть диагностика; успех не показан, последние сохранённые данные не потеряны |
| Ошибка сохранения | Управляемая ошибка платформенного persistence не даёт сообщить успешное сохранение; после reload сохраняются прежние данные |
| Несопряжённый клиент / чужой Origin или Host | Чтение и изменение отклонены, тестовый документ не изменился |

Автоматические проверки и их артефакты фиксируются отдельно от внутреннего агента. Имитатор подтверждает поведение стенда, но не совместимость корпоративного клиента.

### C3. Живая проба владельца

1. Добавить компонент во внутренний клиент по фактической конфигурации; открыть экспериментальную HTTPS-страницу в Chrome и выполнить сопряжение.
2. Нажать «Обновить» синтетического запроса. По явной команде агент получает задание и возвращает синтетический результат; страница сообщает завершение сохранения.
3. Остановить обработку новых заданий, перезагрузить страницу и проверить сохранённые значения без нового запроса или повторной доставки результата.
4. Остановить локальный компонент, проверить диагностику недоступности и сохранность предыдущих данных. Зафиксировать поведение разрешения браузера на локальное соединение и наблюдаемые таймауты.
5. Вернуть обезличенный протокол по каждому шагу: ожидаемое/фактическое поведение, сработало/ошибка/не проверено, текст ошибки без секретов, версии компонента и браузера, режим, идентификатор тестовой сборки и origin стенда без внутренних адресов/токенов.

**Успех PBT-121:** автоматические сценарии C2 пройдены и полный путь C3 подтверждён внутренним агентом на выбранном HTTPS-origin, включая reload и отключение, без отключения защиты браузера. Невыполненный пункт остаётся непроверенным; отрицательный результат с установленной причиной допустим как итог исследования, но не как подтверждение совместимости. Проверка вкладки не объявляется проверкой установленной PWA.
