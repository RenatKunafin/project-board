# PBT-081 — проверка исправления

## Подтверждённая причина

Baseline: develop `65aba99`. План из двух задач, два проектных вида, один максимизирован. Реальный drag переносит первую задачу с 12–16.10.2026 на 14–20.10 (rev2→3). Обычный клик в поле поиска запускает сверку скрытого экземпляра и возвращает начало к 12.10 (rev4). Полный вывод и snapshot: `baseline-regression.md`.

При скрытии виджета сам PlanGanttWidget остаётся смонтированным, но его SVAR-чарт удаляется. apiRef скрытого виджета сохраняет старый стор, а planRef получает новый документ. Ранее любой mouseup запускал сравнение этих данных и мог трактовать рассинхронизацию как пользовательский жест. Простое восстановление соседей сразу после drag не воспроизводило дефект: их чарты уже пересоздавались с актуальными датами. Регресс включает обычный клик до восстановления.

## Исправление

Начало взаимодействия на полосе фиксирует владельца: экземпляр, ID задачи, API и ревизию. Capture mouseup/touchend сохраняет отпускание за пределами чарта. Сверяется только выбранная задача. Таймеры отменяются при завершении серии, размонтировании или смене документа; внешняя ревизия или другой API аннулируют старое наблюдение. Новый жест сначала фиксирует уже завершённый предыдущий ввод и отменяет его таймеры, чтобы быстрые изменения разных задач не терялись.

## Автоматические сценарии

`tests/e2e/shared-plan-gestures.spec.ts`:

1. Два общих вида, drag, скрытый сосед, клик после жеста, восстановление и reload.
2. Шесть общих видов, resize справа, каскад, скрытые соседи, клик, восстановление и reload.
3. Два вида, resize слева, сетка, клик, восстановление и reload.
4. Два видимых соседа, отпускание мыши вне чарта.
5. Внешняя редакция во время ожидающих сверок.
6. Закрытие владельца до финальной записи.
7. Переключение на импортированный документ до финальной записи.
8. Быстрые последовательные жесты по одной задаче.
9. Быстрые последовательные жесты по разным задачам.
10. Скрытие вкладки до финальной сверки сохраняет уже завершённый ввод.

Во всех изменяющих сценариях проверяются фактические даты и число редакций; в основных — неизменность другой задачи и стабильность после окна таймеров. Прежний набор plan-gantt (включая рабочий календарь, однодневную задачу, сводную полосу и отмену) также проверен.

Промежуточный запуск шести видов один раз превысил общий таймаут 30 с; причина этого замедления не установлена. Отдельный диагностический прогон с trace прошёл за 12 с без изменения production-кода; затем весь новый набор прошёл 9/9 последовательно. Первые ошибки подготовки теста (нестабильный nth после DOM-переноса при maximize, перекрытие стартовых окон в каскаде) исправлены стабильной привязкой к instanceId и подготовкой окон в сетке. Retry/skip не используются.

## Живой проход plan500

Chrome 155 через Playwright MCP, отдельный чистый browser context, production preview. Фикстура `tests/fixtures/gantt/plan-500.json` преобразована в native-формат той же схемой, что в PBT-058: `parallel` → `allowsParallel`, `resource.name` → `title`, добавлены `workingExceptions` и ID зависимостей. Импорт — через UI, затем через каталог открыты шесть проектных и четыре ресурсных вида одного документа. Один проектный вид максимизирован, фильтр «Задача 500», Дни.

После окна восстановления прокрутки реальный чарт прокручивается к t-500, elementFromPoint подтверждает полосу. Три переноса и три изменения левого края выполняются мышью на +96px (+2 дня). Для drag проверены привязка начала и сохранение рабочей длительности, для resize — дата начала и неизменный правый край. Каждый жест даёт одну ревизию, остальные 499 задач неизменны. После каждого жеста обычный клик в поиск и ожидание более 2 с не меняют документ. Reload сохраняет результат. Числа и даты — `live-plan500.json`, снимок — `live-plan500.png`.

Это проверка корректности исходного жестового сценария PBT-058, а не повтор полного performance benchmark: бюджеты/FPS здесь не измеряются, resize справа отдельно покрыт browser-регрессом на шести видах малого плана.
