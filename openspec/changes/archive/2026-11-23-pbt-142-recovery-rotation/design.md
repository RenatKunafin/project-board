# Design — PBT-142

## D1. Слоты и миграция

Набор слотов расширяется с двух до десяти: `FILES = ['project-board-recovery-a.json', …, 'project-board-recovery-j.json']`. Именование продолжает существующую латинскую серию; цифровые имена не вводятся, чтобы файлы прежней версии оставались частью набора без переименования и удаления.

Миграция не требуется и не выполняется: при первом запуске новой версии слоты a/b читаются как обычно (годные — с их поколениями), c–j отсутствуют и считаются свободными. Новые копии занимают свободные слоты по порядку, поэтому папка пользователя не меняется до первых сохранений. Обратная совместимость: при откате к прежней версии приложения она видит только слоты a/b — читает годной ту из них, у которой больше поколение. Если годные копии остались только в c–j, откатившаяся версия их не увидит; это принято, потому что откат приложения — нештатный сценарий, а файлы при этом не теряются.

## D2. Правило ротации

Целевой слот записи обобщает действующее правило двух слотов:

1. первый слот в состоянии `missing` или `invalid` (свободный) — как и сейчас, это чинит повреждённый слот и заполняет пустые;
2. если все слоты годны — слот с наименьшей генерацией.

Поколение нового снимка — `max(поколения годных слотов) + 1`, нумерация продолжается поверх существующих файлов. Итог: после заполнения всех десяти слотов каждый следующий снимок перезаписывает самую старую копию — «по очереди», старейшая первой. Атомарность записи (`createWritable` + `close`, проверка перечитыванием) и запрет уничтожать последнюю годную копию при отказе не меняются.

Блокировка при полном повреждении сохраняется с расширенным условием: если годных слотов нет и хотя бы один файл существует и негоден — запись запрещена, файлы не изменяются, статус `corrupt`. Пустая папка (все слоты `missing`) — не повреждение, первый снимок пишется в слот a.

## D3. Стоимость чтения

`readLatest` и `save` читают все слоты полностью (JSON, digest, десериализация полезной нагрузки). С десятью слотами чтение на сохранение растёт примерно в пять раз: копия — это все документы, единицы мегабайт, то есть десятки мегабайт чтения и сотни миллисекунд фоновой работы на сохранение. Сохранения редки (пауза 30 секунд после подтверждённых изменений, немедленные — только структурные операции), выполняются вне критического пути UI.

Альтернатива — облегчённое чтение только заголовка конверта на пути `save` (поколение без полной проверки) — отклонена для этой задачи: общий путь проверки уже существует, полное чтение подтверждает годность набора перед выбором цели, а экономия не требуется при фоновой частоте записей. Если живой контроль владельца покажет заметные задержки, вернуться к метаданным отдельной задачей.

## D4. Тексты и распознавание повреждений

- Store, отказ при полном повреждении: «Все файлы копий повреждены или неизвестного формата. Выберите другую папку; файлы не изменены.»
- Координатор: regex блокировки `/все файлы копий повреждены/i` (сейчас `/оба файла копий повреждены/i`) — сообщение об ошибке и впредь переводит статус в «файлы повреждены» и останавливает повторы.
- Стартовый диалог (`RecoveryStartup.tsx`), `damagedSlot`: «Часть файлов копий повреждена; доступна самая свежая годная копия.»
- Восстановление всегда предлагается из самой свежей годной копии — поведение не меняется; истории копий в UI нет (см. Non-goals).

## D5. Проверки

- Unit (`recovery-snapshot-store.test.ts`, MemoryDirectory): 12 последовательных сохранений — первые 10 заполняют слоты a–j по порядку, 11-й и 12-й перезаписывают слоты с наименьшими поколениями; миграция — два существующих годных файла продолжают нумерацию, новые уходят в c+; повреждение одного слота при годных остальных — восстановление из самой свежей, `damagedSlot`; повреждённый слот занимается следующей записью; все файлы повреждены — статус `corrupt`, запись отклонена, файлы не изменены; две вкладки под lock по-прежнему сериализуются (поколения без дыр).
- Обновить существующие unit-фиксации `directory.files.size` (2 → 10) и тексты ожиданий.
- e2e (`recovery-snapshots.spec.ts`, OPFS через заглушку `showDirectoryPicker`): после серии подтверждённых изменений и такта часов в папке фактические файлы копий; многократные сохранения дают не более 10 файлов; повреждемый файл не мешает восстановлению самой свежей годной копии.
- Живой контроль владельца: реальная папка ОС с накопленными копиями, консоль без ошибок.
- Полный набор testing.md перед PR; бюджеты производительности не меняются и не повторяются (путь планирования не затронут).

## D6. Риски и ограничения

- Рост чтения на сохранение — принят (D3); контроль по живому осмотру.
- Пользователь с огромным рабочим пространством получит 10-кратный объём папки копий (десятки МБ); допустимо для аварийного механизма, ординарная история в данных сайта (5 копий) не меняется.
- Десять слотов не решают возможную причину инцидента (например, прекращение записи копий после утраты разрешения или устаревший последний снимок); диагноз устанавливается отдельно по фактическим данным — задача не подменяет диагностику.
