# Design — PBT-028

## Context

Приложение — Vite 6 / React 18, Node 22.12; точка регистрации модулей — `widgets.ts`, восстановления документов — `main.tsx`. IndexedDB уже работает автономно. В `vite.config.ts` пока только React-плагин. Шрифты локальные; wx-icons вендорены PBT-073. Иконка топ-бара — LayoutDashboard. Имеющийся dist ориентировочно 2.1 МБ, наибольший JS около 1 МБ (это осмотр старого dist, не замер новой сборки).

Согласование подхода владельцем — 2026-10-22, текущая сессия. Технические детали ниже реализуют выбранный подход.

## D1. Генерация Service Worker

`vite-plugin-pwa@2.0.0` (MIT) — точный пин devDependency в `apps/project-board`. Метаданные тега подтверждают Vite 6 в peer range и Node >=20.19.0; транзитивные версии фиксирует lockfile. Стратегия `generateSW`: полный список ресурсов формируется сборкой, ручного списка хешированных чанков нет. Плагин и клиентский адаптер остаются внутри приложения.

Альтернативы: собственный SW — лишняя ответственность за ревизии и маршрутизацию; `injectManifest` — пока не нужен, специфических fetch-правил нет. Новая зависимость устанавливается после согласования подхода.

## D2. Полнота кэша и границы

- Precache включает HTML, JS, CSS, WOFF/WOFF2, SVG/PNG/ICO и манифест. Workbox runtime тоже локален. Проверка построенного списка и офлайн-сценарий обязательны: стандартный glob не гарантирует включение шрифтов.
- Лимит отдельного precache-файла 2 МиБ; его превышение должно останавливать сборку, а не молча исключать ресурс. Повышение лимита без разбора размера не планируется.
- Навигация внутри scope обслуживается кэшированным `index.html`. Ненавигационные запросы отсутствующих ресурсов не подменяются HTML. Никакого runtime-кэширования сторонних адресов.
- Scope и start URL согласованы с Vite base; текущий адрес — корень. Возможность размещения в подпути не требует выбора хостинга сейчас.
- SW регистрируется только в production, dev остаётся без SW. Кэши относятся к приложению и scope; не удаляем произвольные кэши origin.
- IndexedDB не копируется в Cache Storage. Подготовка офлайн-ресурсов не является подтверждением сохранения документов.

## D3. Манифест и оформление

Имя и short_name — `Project Board`, язык `ru`, display `standalone`, стабильный id в пределах base. Иконки PNG 192/512, отдельная maskable-иконка 512 и apple-touch-icon 180. Основа — существующий знак LayoutDashboard; без нового визуального бренда. Исходник и воспроизводимая генерация сохраняются в репозитории. Цвета иконок/manifest/theme-color выводятся из существующих токенов (преобразование в sRGB при генерации), без второй независимой палитры.

Установка через браузер: Chrome/Edge desktop согласно ADR PBT-002; Safari/macOS — доступный механизм платформы. Firefox остаётся поддерживаемым браузером приложения без обещания штатной установки. Собственная кнопка Install не вводится.

## D4. Готовность к офлайн-работе

Неблокирующий статус рядом с индикатором сохранения: «Подготовка офлайн…», «Готово к работе офлайн», «Офлайн-режим недоступен» при ошибке/неподдерживаемом окружении. Отдельное доступное имя, чтобы не нарушить существующие локаторы статуса сохранения. В dev статус не показывается.

Критерий готовности — успешная установка набора ресурсов и активный SW текущего scope; одного `navigator.onLine` недостаточно. Учитываются первая установка, повторный старт с существующим active/controller, отказ регистрации и неудачная установка (`redundant`). На повторном старте состояние определяется заново; localStorage-флаг готовности не используется. При ошибке приложение продолжает работать в доступной онлайн-сессии, инструкция предлагает повторное открытие при доступной сети.

Статус означает подготовленный запуск, а не вечную гарантию сохранности браузерного хранилища после его очистки. Очистка данных сайта отдельно описана в инструкции.

## D5. Граница обновлений

Режим `prompt`, `skipWaiting: false`: новая версия не вытесняет используемый SW. Первичная активация может принять текущую страницу через `clientsClaim`; она не перезагружает страницу. Клиент не вызывает принудительное обновление/перезагрузку. Если все окна закрыты, браузер может естественно активировать ожидающий SW; это штатный жизненный цикл. Кнопка применения обновления, сохранение перед ним и двухверсионные тесты — PBT-029. Нынешний `flushAll()` не считается достаточной гарантией ожидания записи и в этой задаче не изменяется.

## D6. Проверки

1. Контракт сборки: manifest, размеры/типы иконок, локальный SW, включение JS/CSS/шрифтов/иконок. Нет ресурсов стенда load-demo или исследовательских fixtures.
2. Chromium e2e: дождаться готовности и controller; создать данные, дождаться фактической записи. Закрыть все страницы, отключить сеть, открыть новую страницу того же контекста; проверить восстановление. Обычный HTTP-кэш отключить через CDP, SW не обходить.
3. Офлайн изменить существующий чек-лист, создать новый через каталог, проверить записи IndexedDB и повторное открытие. Проверить загрузку шрифтов и локальных иконок; оба вида Гантта — smoke на загрузку, без расширения сценариев редактирования.
4. Отрицательный сценарий: отказ установки обязательного ресурса в чистом контексте не приводит к ложной готовности; онлайн-приложение остаётся работоспособным. В отдельном чистом контексте первый запуск без сети не обещает доступность приложения.
5. Ручная установка через Chrome/Edge: правильные имя/иконка, отдельное окно, закрытие и запуск без сети. Запуск браузерного контекста не подменяет проверку установленного окна; результат и ограничения среды явно записываются.
6. Полный набор проекта: lint, typecheck, unit, build, browser на чистом preview, OpenSpec strict. Предсуществующие красные e2e исследуются по правилам AGENTS.md.

## D7. Документация и риски

Инструкция объясняет первый онлайн-запуск, критерий готовности, штатную установку и офлайн-сохранение. Гарантия относится к тому же origin/профилю при сохранённых данных браузера; смена адреса не переносит IndexedDB. Preview/localhost подходит для разработки, публикация требует HTTPS.

Риски: новый SW влияет на повторные e2e и кэширование старого dist — отдельные контексты и свежая сборка обязательны; ложная готовность от события регистрации — исключается проверкой активации; неполный glob — проверкой кэша и холодного запуска. При недоступной автоматизации системного меню установки ручной DoD остаётся незакрытым до реальной проверки.

## D8. Попутное исправление предсуществующего e2e

Общий прогон дал 127 pass / 1 fail (`dependencies.spec.ts:54`, ожидание «лаг 4»). Исходный develop `d748d83` извлечён через git archive в `/tmp/pbt-028-baseline`, собран без изменений PWA; тот же тест падает на том же ожидании. Исходники доменных пакетов не изменены. Корень виден в сценарии: после открытия редактора лага 2 тест сразу нажимает Enter, не вводя 4. Это детерминированный дефект теста, а не деградация среды, как предполагалось в исторических заметках AGENTS.md. Добавлен единственный пропущенный шаг `fill('4')`. Продуктовое поведение и assertions сохранены. Попутная правка явно включена в PR, отдельной продуктовой capability не требует.

## D9. Реализация и результаты

- Регистрация реализована нативным `navigator.serviceWorker.register` в `PwaStatus.tsx`, без virtual-модуля: жизненный цикл отслеживается напрямую, принудительное применение обновления не вызывается. Первая активация принимает страницы через clientsClaim, существующая активная версия продолжает обслуживать их при ожидании обновления.
- Цвета PWA и PNG/SVG генерируются Chromium из токенов и существующего знака Lucide (`npm run generate:pwa-assets`); копия лицензии включена в public/icons. Это производные статические файлы, не новая палитра. Импорт colors.json в Vite требует только resolveJsonModule в tsconfig приложения.
- В production-сборке precache 84 ресурса / 2043.50 КиБ; наибольший JS ~1072 КБ, ниже лимита отдельного файла 2 МиБ. Все 70 файлов assets (скрипт, стили, шрифты) сверены с реальными ключами Cache Storage; runtime Workbox локален. Версии существующих зависимостей при установке не изменились (267 новых записей lockfile).
- `npm run lint`, `npm run typecheck`, `npm test` — успешно; unit 468/468 (35 файлов). `npm run build` — успешно. Полный `npm run test:browser` после исправления D8 — **128/128**, включая 6 новых PWA-сценариев. Новых изменений продукта после этой сборки/прогона нет; позднее добавлены только инструмент проверки установки и документация.
- `openspec validate pbt-028-pwa-offline --strict`, `openspec validate --all --strict` — успешно (18 элементов).
- MCP Playwright, Chrome 155.0.8059.86: манифест без ошибок, installabilityErrors пуст; в чистом контексте reload без сети показывает три стартовых чек-листа и «Готово к работе офлайн». Консоль без ошибок; 4 предупреждения SVAR `_progressLinePoints` в исходном контексте с открытыми планами. Чистый офлайн-контекст и скриншот не используют документы рабочего профиля.
- `npm run verify:pwa-install`: настоящая установка Chrome/CDP во временном профиле, явный пользовательский выбор displayMode standalone, закрытие исходной страницы, запуск установленной записи при отключённой сети; подтверждены отдельное окно и `matchMedia('(display-mode: standalone)') === true`. JSON и скриншот — `screenshots/`. Установка и временный профиль удалены после проверки; основной профиль не затрагивался. CDP по умолчанию выбрал browser — это настройка пользователя в автоматизации, а не ошибка manifest (`display: standalone` подтверждён). Cleanup учитывает остающийся app shim macOS, только если он ссылается на собственный временный профиль проверки.
- Ограничение проверки установки: ручной проход по меню Chrome/Edge и отдельный запуск Edge в этой среде не выполнены. Воспроизводимый сценарий есть в `.docs/pwa.md`; автоматическая установка Chrome не подменяет утверждение о ручном тесте Edge. На ревью владельца остаётся проверка штатного меню; реализации установки и standalone-окна Chrome подтверждены.

## D10. Принятие

Владелец принял PR#56 сообщением «PR принят» 2026-10-22 после отчёта о проверках и явно указанного ограничения ручного меню Chrome/Edge. Приёмка зафиксирована с этим ограничением: фактическая проверка установки Chrome/CDP подтверждена, ручная проверка Edge не объявляется выполненной. Change архивируется с переносом требований в актуальные specs заключительным коммитом перед merge. Код после принятия не меняется.
