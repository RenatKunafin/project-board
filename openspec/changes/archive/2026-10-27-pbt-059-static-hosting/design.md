## Context

См. proposal.md. Возобновлённая feature/pbt-059-static-hosting fast-forward обновлена до develop833bab8. Исследовательские черновики от2026-10-23 заменяются текущим проектом. Провайдер GitHub Pages, публикация после merge в main и выхода GitHub Release выбраны владельцем2026-10-25. Видимость репозитория меняет владелец. При начале работы Pages не был включён. Владелец подтвердил переход в public; при реализации API подтвердил private:false, Pages включён с build_type:workflow/HTTPS, environment настроен для tags по правилу **/*.

## Goals / Non-Goals

Цель — выпуск выбранного коммита релиза на постоянный адрес и проверенный цикл установки/offline/обновления. В реализации остаются прежние SDK, схемы данных и пользовательский UI. Создание GitHub Release, продвижение develop в main и изменение публичности не выполняются как побочный эффект подготовки workflow.

## Decisions

### D1. Постоянный адрес и базовый путь

Адрес — https://renatkunafin.github.io/project-board/, base /project-board/. Публикуется только apps/project-board/dist. Локальный dev и обычные тесты сохраняют корневой base; release-сборка явно получает подпуть. Проверяются HTML/JS/CSS/fonts/icons, manifest id/start_url/scope, URL/scope sw.js и importScripts update-guard. Текущая регистрация уже использует import.meta.env.BASE_URL; её нельзя заменять абсолютным /sw.js. Живая установка обнаружила неверное разрешение id:'./': по стандарту его база — origin, и Chrome получал ID корня сайта. VitePWA integration.configureOptions задаёт id по окончательному config.base (с учётом CLI); root-идентичность сохраняется, Pages получает /project-board/. Тест проверяет также обработанный Chrome manifest.id, а не только сырой JSON.

Альтернатива — отдельный домен с base /. Сейчас не нужна, так как выбран стандартный Pages-адрес проекта. Origin сохраняется при дальнейших выпусках; данные localhost автоматически на github.io не переносятся, подпути одного origin не изолируют IndexedDB.

### D2. Триггер и исходники выпуска

Workflow .github/workflows/deploy-pages.yml запускается только на release с types:[published]. Push, merge в main, создание тега и draft-релиз сами по себе не деплоят. Событие published включает обычные релизы и опубликованные pre-release; отдельного исключения pre-release владелец не задавал.

Checkout выполняется по тегу события, фиксируется фактический commit SHA. Проверяется git ancestry этого SHA относительно актуального origin/main; одного target_commitish в метаданных недостаточно. Коммит, не входящий в main, отклоняется до deployment. Пересборка всегда использует тот же тег/lockfile; журналы содержат тег, SHA, инструменты и URL.

Проверки и сборка выполняются для этого SHA в workflow релиза. CI для PR/push в main должен проверять продвижение ветки, но сам сайт при этом не меняется. Альтернативы — автодеплой develop или main — отклонены владельцем выбранным порядком выпуска.

### D3. GitHub Pages и права

В Settings → Pages выбирается Source: GitHub Actions, deployment использует environment github-pages. Сборка имеет contents:read; deployment получает pages:write и id-token:write. Стандартного GITHUB_TOKEN достаточно; пользовательский токен в исходники/артефакт не добавляется. Environment должен разрешать tag refs релиза, иначе проверенный release-триггер будет заблокирован политикой веток.

Публикации сериализуются общей concurrency group без отмены уже выполняющегося deployment. Не обещается произвольная очередь всех опубликованных одновременно релизов: перед следующим выпуском нужно дождаться результата предыдущего. Проверка принадлежности тега main не заменяется отсутствием ограничений environment.

### D4. Ресурсы, кэш и состав артефакта

Workbox предварительно кэширует полный набор ресурсов. Переход проверяется из подготовленной предыдущей версии: её precache сохраняет текущую сессию до штатной активации обновления. Не обещаем бессрочную раздачу старых assets сервером после замены Pages-артефакта; это не требуется для проверяемой подготовленной сессии. Если реальные двухверсионные проверки потребуют удержания старых файлов, это отдельное уточнение решения до объявления перехода успешным.

Проверяются фактические CDN-заголовки HTML/sw.js/manifest/assets и обнаружение обновления. Не добавляем _headers как будто это конфигурация GitHub Pages. Ожидаемая задержка распространения релиза фиксируется в отчёте; не обещаем мгновенное обновление всех клиентов. Штатные prompt/flush/update guard сохраняются.

В артефакт не попадают examples, fixtures, .context, node_modules, исходные архивы. Используемые __projectBoard/storage-selftest не удаляются под видом публикации: они уже проверены PBT-060 и нужны существующим e2e. Документы пользователя остаются только в его IndexedDB.

### D5. Повтор и совместимый возврат

Неуспешный workflow можно повторить для того же release tag; сохранённые build-артефакты и журнал позволяют установить проверенный SHA. Время хранения Actions-артефакта задаётся явно:30 дней; их наличие не заменяет Pages CDN-проверку.

Возврат старой совместимой версии — новый Release с новым тегом на выбранном прежнем коммите из main. Новый тег не переписывает уже опубликованный. Откат файлов не откатывает локальные данные; допускается только версия, совместимая с текущими схемами. Guard будущих версий сохраняется; очистка пользовательских данных не используется как способ отката. Новый Release требует отдельного поручения владельца, workflow его самостоятельно не создаёт.

### D6. Проверки и последовательность завершения

Сначала реализуются workflow/base/инструкция и проходят локальные проверки: repository/lint/typecheck/unit/build/OpenSpec, существующий browser-набор и целевые тесты production под /project-board/, включая два поколения PWA. Результат открывается одним PR PBT-059 в develop.

Живые проверки становятся возможны после включения public/Pages, merge в main и публикации релиза. Затем на постоянном URL проверяются установка, reload, сохранение, закрытие/холодный offline-запуск, обновление на второй релиз и совместимый возврат. Публикационные шаги не отмечаются завершёнными по одному локальному preview или зелёному CI.

Для059 выбранный владельцем порядок main → Release требует публикационной приёмки после merge кода. Поэтому в этом плане change остаётся активным до реальных проверок сайта; после них архив/spec sync фиксируется документальным коммитом, а реестр получает Done. Это явное исключение из обычной архивации до merge, вызванное зависимостью внешней приёмки от релиза. Архивация незакрытых проверок и Done сразу после добавления workflow не допускаются.

## Risks / Trade-offs

- Тег на коммите вне main → проверка реальной ancestry до deployment.
- Environment допускает только branch main, но release ref является тегом → разрешить соответствующие tags и проверить реальный запуск.
- Неверный подпуть/импорт update-guard → production-проверка всех URL, offline и двух поколений сборки под тем же base.
- Задержка CDN/обновления → фиксировать реальные заголовки и SHA версии, проверять смену версии без очистки данных.
- Старые данные несовместимы с откатом → проверка схем и guard, не обещать автоматический откат миграций.

## Migration Plan

1. Владелец переводит репозиторий в public; настраиваются Pages Actions и environment.
2. Код PBT-059 проходит PR в develop, затем проверенная версия продвигается в main.
3. По отдельному поручению публикуется Release на теге из main; workflow выполняет проверки и Pages deployment.
4. На опубликованном адресе проверяется первая версия и следующий release; отчёт содержит URL/SHA/журнал/ограничения.
5. После реальной публикационной приёмки закрываются оставшиеся пункты, задача архивируется и отмечается Done.
