## Context

SDK v0 ([ADR PBT-002](../../docs/adr/PBT-002.md), ADR-6.3) обязан предоставлять «работу с документами и уведомления об изменениях». Паттерн разделения контракт/реализация отработан в PBT-006 (widget-sdk — типы, dashboard — исполнение). Схема полей документа — решения 15.2; модель состояния 15.4: операция → пересчёт → уведомления → запись (запись появится в PBT-009). Проверка `revision` — согласованное предложение 15.4, здесь становится контрактом.

## Goals / Non-Goals

**Goals:**

- Контракт документов в SDK и in-memory реализация в dashboard, проходящая все сценарии спецификации.
- Синхронные уведомления подписчиков после фиксации обновления.
- Отдельное хранилище viewSettings по экземпляру.

**Non-Goals:**

- IndexedDB, автосохранение, конфликты между вкладками браузера (PBT-009/PBT-010).
- Каталог документов и операции переименования/удаления (PBT-025); здесь только create/get/update/subscribe + viewSettings.
- Схема содержимого чек-листа (PBT-008) и генерики под типы документов (появятся при первом модуле).

## Decisions

- **Контракт в SDK, реализация в dashboard** — как реестр виджетов. SDK экспортирует типы (`ManagedDocument`, `DocumentContent = unknown`, `DocumentConflictError`, `DocumentChangeHandler`, `DocumentSubscribe`/`Unsubscribe`) без runtime-зависимостей. Сервис — интерфейс `DocumentService` и фабрика `createDocumentService()` в dashboard.
- **`expectedRevision` — обязательный параметр обновления.** `update(documentId, expectedRevision, nextContent)` без «update-or-create» семантики: конфликт — `DocumentConflictError` с текущей редакцией в поле. Это делает гонки видимыми уже на этом слое (15.4), PBT-010 добавит retry-политику автосохранения.
- **Синхронные уведомления.** Подписчики вызываются в момент `update`, после фиксации редакции, в порядке подписки. Обработчик получает копию документа (иммутабельные снапшоты: `ManagedDocument` экспонируется как `readonly`-структура, содержимое не клонируется глубоко — модуль отвечает за иммутабельность своего content). Отсутствие асинхронности упрощает тесты и рассуждения; очередь появится при необходимости (PBT-027).
- **ViewSettings — отдельная карта** `Map<viewSettingsKey, settings>` с ключом `widgetInstanceId`. Доступ: `getViewSettings(key)` / `setViewSettings(key, settings)` на сервисе; уведомлений не порождают (требование спецификации). Изоляция ключей по экземпляру — контракт уровня ключа.
- **Создание документа — `create(input)`.** Сервис генерирует `id` (v4 uuid через `crypto.randomUUID`), принимает `moduleId`, `documentType`, `schemaVersion`, `content`; проставляет `revision: 1`, метки времени. Формат id — деталь реализации, не контракта.
- **Без генериков в этом change.** `content: unknown` — модуль кастует у себя. Генерик-фасады (`defineDocumentService<S>`) появятся в PBT-008, когда станет известна реальная форма содержимого чек-листа — избегаем преждевременной типизации.

## Risks / Trade-offs

- [Синхронные обработчики могут вызвать реентерабельный update внутри уведомления] → документируем и защищаем: обновление во время доставки уведомлений того же документа отклоняется конфликтом редакции; глубже — не требуется первой версии.
- [Копии документа в уведомлениях не глубоки] → содержимое принадлежит модулю; при необходимости иммутабельных структур модуль строит их сам (для чек-листа PBT-008 выберет frozen-структуры).
- [In-memory реализация может «протечь» в продуктовый код] → контракт остаётся в SDK, PBT-009 заменит фабрику без смены потребителей; внедрение зависимости через пропс/аргумент (как реестр в main.tsx).

## Open Questions

- Нет: конфликт редакций уже согласован как локальная защита целостности (15.4); политики повтора — PBT-010.
