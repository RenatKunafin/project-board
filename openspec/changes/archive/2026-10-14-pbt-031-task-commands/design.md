# Design — PBT-031: операции над задачами и ручными датами

## Context

Существующая база: модель плана v1 `plan-document.ts` (иммутабельные readonly-структуры, фабрика, строгий `parsePlanContent`), арифметика `working-calendar.ts` (`isWorkingDay`, `nextWorkingDay`, `addWorkingDays`, `workingDaysBetween`; ISO-даты, UTC-полдень против DST), правила ADR PBT-003 A1–D7, SDK-контракт записи `DocumentService.update(documentId, expectedRevision, nextContent)`. UI-потребителей у плана ещё нет — только заглушка PBT-030. Все операции должны быть чистыми функциями над `PlanContent` без знания о React и UI-библиотеках (ADR-3 PBT-017, ESLint-границы ADR-3 PBT-002).

## Goals / Non-Goals

**Goals:** единый доменный слой операций над задачами; атомарные отклонения с кодами причин; семантика дат A2–A6; контракт очистки ссылок при удалении; `prevWorkingDay` в календаре; автотесты на каждое правило.

**Non-Goals:** операции над зависимостями/ресурсами/группами/недоступностями; проверка нарушений FS (PBT-035); интеграция с `DocumentService` в виде SDK-хелпера (D7); UI.

## Decisions

### D1. Единый путь команд: чистые операции + диспетчер

`packages/gantt/src/plan-commands.ts`. Два уровня:

- Ядро — чистые функции: `createTask(plan, input)`, `updateTask(plan, taskId, patch)`, `setTaskDates(plan, taskId, { start, end })`, `moveTask(plan, taskId, newStart)`, `setTaskDuration(plan, taskId, durationDays)`, `deleteTask(plan, taskId)`.
- Диспетчер — `applyPlanCommand(plan, command: PlanCommand): PlanCommandResult`, где `PlanCommand` — дискриминированное объединение с полями тех же команд. Диспетчер делегирует функциям.

Результат — объединение:

```text
PlanCommandResult =
  | { ok: true; plan: PlanContent }
  | { ok: false; error: PlanCommandError }
```

Обоснование: «единый путь команд» из карточки выполняется буквально — потребители (форма, drag, ресурсный вид) строят команды одного вида и получают один тип результата; команды — простые объекты, пригодные для сериализации (если PBT-062 история будет принята, слой не придётся переделывать). Разделение «даты» и «прочих полей» на разные команды осознанное: у `setTaskDates` / `moveTask` / `setTaskDuration` семантика A2/A3/A4 различается, generic-обновление её размывало бы.

Альтернатива «отдельные функции без диспетчера» отклонена: оставляет потребителям выбор точки входа и не даёт единого типа результата. Альтернатива «класс PlanDocument с методами» отклонена: против иммутабельных структур и чистых операций (правила реализации AGENTS.md).

### D2. Коды отклонений — отдельная таксономия от PlanIssue

`PlanCommandError { code: PlanCommandErrorCode, message: string }`; коды: `unknown-task`, `unknown-group`, `unknown-resource`, `unknown-work-type`, `inverted-interval`, `invalid-duration`.

`PlanIssue` (валидатор чтения PBT-030) описывает повреждённые данные с `path` — это диагностика формата; `PlanCommandError` — отклонение легитимной операции пользователя с человеческим сообщением. Смешение сломало бы контракт валидатора и потребовало бы `path`, которого у операций нет. Атомарность: функция сначала проверяет все условия, затем строит новый план; при отклонении исходный план не возвращается и не изменяется (DoD «отклоняется целиком»).

### D3. Ручной ввод дат (A3) и перенос (A2) — разные команды

- `setTaskDates` — ручной ввод A3: даты сохраняются как введены, включая нерабочие дни; проверяется только `end ≥ start` (иначе `inverted-interval`). Рабочая длительность — производная, может быть 0 (A6).
- `moveTask` — перенос A2: рабочая длительность `N = workingDaysBetween(start, end)` сохраняется. Направление привязки нового начала — по сравнению `newStart` с текущим началом: вперёд (или равно) → `nextWorkingDay`-семантика, назад → `prevWorkingDay`-семантика (ближайший рабочий день в сторону переноса). После привязки `newEnd = addWorkingDays(newStart, N − 1)` — новое начало всегда рабочий день, формула универсальна.
- Соседние и связанные задачи не трогаются ни одной из команд (правило раздела 7 решений; C5 — подсветка нарушений, не перенос, придёт в PBT-035).

Вырожденный случай N = 0 (задача целиком в нерабочих днях, A6): правило A2 «сохранить рабочую длительность» вырождается; привязка начала к рабочему дню дала бы длительность 1. Решение (утверждено владельцем 2026-10-14, **вариант A**) — перенос с сохранением календарной длины интервала без привязки: `newEnd = newStart + (старая календарная разница)`, длительность остаётся 0. Отклонённые альтернативы: запрет drag нулевых задач (ломает UI без причины) и привязка с превращением 0 в 1 раб. день (против A6). Направление привязки и длительность считаются по текущим датам задачи; сравнение дат — лексикографическое (ISO-строки).

### D4. Ввод длительности (A4): формула окончания

`setTaskDuration` — целое ≥ 1, иначе `invalid-duration` (A4 «минимум 1 при создании» толкуем как правило ввода длительности; нулевая длительность достижима только ручным вводом дат A3/A6). Окончание — N-й рабочий день, считая начало:

```text
if isWorkingDay(start) and N = 1 → end = start
otherwise                        → end = addWorkingDays(start, N − 1)
```

Для рабочего начала `addWorkingDays(start, N − 1)` даёт N-й рабочий день включительно (пример A4: пн 12.10, N=7 → вт 20.10). Для нерабочего начала первый рабочий день после него считается днём 1, и `addWorkingDays(start, N − 1)` также даёт день N (`addWorkingDays(x, 0) = nextWorkingDay(x)` — первый рабочий после нерабочего). Формула покрывает оба случая одной веткой, особый случай нужен только чтобы `N=1` при рабочем начале не сдвигал окончание на следующий день.

Начало при вводе длительности не меняется (даже если нерабочее — было введено пользователем, A3-совместимо); меняется только окончание.

### D5. `createTask`, `updateTask` и устойчивые ID

- `createTask(input: { title, start, end, groupId?, assigneeIds?, workTypeIds? })`: id генерируется `crypto.randomUUID()` (как в чек-листе и фабрике); задача добавляется в конец `tasks`; проверяются `end ≥ start` и существование ссылок (`unknown-group` / `unknown-resource` / `unknown-work-type`). Рабочая длительность при создании может быть 0 (валидация дат, не ввода длительности; A6-совместимо). Переопределение id при создании не даётся — потребность появится в импорте `.gantt` (PBT-052), расширение отдельным решением.
- `updateTask(patch: { title?, groupId?, assigneeIds?, workTypeIds? })`: отсутствующее свойство патча — поле не меняется; присутствующее свойство — заменяется, включая явный сброс (`groupId: undefined` выводит задачу из группы; пустой массив `assigneeIds` снимает все назначения). `id` задачи изменить нельзя — DoD «сохраняют устойчивые ID».
- Даты через `updateTask` не меняются — только команды D3/D4.

### D6. Удаление: контракт очистки ссылок

`deleteTask`: удаляется сама задача и **все зависимости, в которых она участвует** (`fromTaskId` или `toTaskId`) — зависимость с несуществующим концом не прошла бы `parsePlanContent` (`unknown-reference`), поэтому оставлять её нельзя. Группы, ресурсы, типы работ и недоступности **не трогаются**: без удаляемой задачи они остаются осмысленными.

Общий принцип для последующих задач (фиксируется в design, реализуется по мере появления операций): удаление сущности каскадно чистит только связи, существование которых без неё невалидно по валидатору чтения; справочники и независимые сущности сохраняются. Так, будущий `deleteResource` (PBT-033+) вычистит `assigneeIds` задач и недоступности ресурса, но не задачи.

Альтернатива «запрет удаления при ссылках» отклонена: нет требования, ухудшает UX и создаёт порядок ручной разборки графа перед каждым удалением.

### D7. Интеграция с DocumentService — паттерн применения, хелпер позже

Ядро операций не знает о `DocumentService`. Паттерн для будущих потребителей (форма, drag, ресурсный вид): прочитать документ → `parsePlanContent` → `applyPlanCommand` → при `ok` записать `plan` через `documentService.update(documentId, revision, nextContent)`; при отклонении — показать `PlanCommandError`, записи нет. SDK-хелпер (типа `usePlanCommands`) **не строится в этой задаче**: нет ни одного UI-потребителя, а правило «не создавать абстракцию без потребителя» и границы карточки не позволяют. Первый потребитель (PBT-037/038) либо подтвердит паттерн, либо оформит хелпер. Единственность пути обеспечивается экспортом операций из `packages/gantt` и ревью потребителей.

### D8. `prevWorkingDay` в рабочем календаре

`moveTask` назад требует `prevWorkingDay(date)` — симметрично `nextWorkingDay` (шаг назад, пропуск нерабочих, учёт исключений). Добавляется в `working-calendar.ts` (модуль PBT-013) и в интерфейс `WorkingCalendar` ( frozen-объект). Изменение интерфейса — обратно совместимое расширение; delta spec `working-calendars` отражает. Рабочая длительность считается существующей `workingDaysBetween`; календарь создаётся один раз на вызов операции из `plan.calendar` (не на задачу — 500 задач не должны 500 раз строить Set'ы).

## Risks / Trade-offs

- **Вырожденный перенос N=0 (D3):** правило не покрыто ADR PBT-003 — утверждено владельцем 2026-10-14 (вариант A); при пересмотре правится ветка `moveTask` и один сценарий спеки.
- **Формула D4 в двух ветках:** особый случай `N=1` при рабочем начале может показаться избыточным (можно нормировать `addWorkingDays`), но изменение арифметики PBT-013 шире, чем нужно, и затрагивает прошедшую проверку capability — оставляем ветку в операции.
- **Порядок задач при создании (в конец):** представление сортирует само (PBT-037), поэтому фиксировать позицию вставки сейчас не нужно; если форма захочет «вставить после задачи» — отдельное расширение.
- **Команды без истории:** сериализуемость заложена, но undo/redo — Proposed (PBT-062–063); ничего лишнего не строим.

## Migration Plan

Не требуется: формат плана v1 не меняется, только добавляются чистые функции; схема БД и SDK не затронуты.
