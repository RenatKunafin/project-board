## Context

Причина — [proposal.md](proposal.md). ResourceCatalogDialog вызывает applyCatalogCommand в PlanGanttWidget, который немедленно записывает каждую команду через useTaskForm.commitPlan с ретраем. PlanDialog PBT-085 уже обеспечивает верхний слой, visible/owner lifecycle и внутреннюю прокрутку. PlanCalendarSection хранит локальный ввод диапазонов. SDK предоставляет синхронные get/update с expectedRevision.

## Goals / Non-Goals

**Goals:** четыре раздела и единая транзакция настроек, сохранность незавершённого ввода, безопасное отклонение устаревшего снимка, прежние правила ядра.

**Non-Goals:** автоматический merge чужих изменений, долговременное хранение черновика, SDK/БД/зависимости пакетов, обновление формы задачи и прочих панелей.

## Decisions

### D1. Снимок и локальные операции

Диалог фиксирует исходные plan/revision при открытии. Валидные действия добавления, удаления, параллельности, недоступностей и календаря применяются чистыми командами к локальному плану через существующий applyPlanCommand; дублирующий диспетчер в компоненте вида удаляется. Имена редактируются в строках через отдельные строковые буферы, допускающие пустое значение во время ввода; при сохранении они валидируются существующими updateResource/updateWorkType, ID сохраняются.

Все четыре панели остаются смонтированными с hidden для неактивных: это сохраняет локальные ошибки и незавершённые значения. Ввод календарных диапазонов становится контролируемым состоянием диалога. Счётчики производные от черновика; календарь считает явно заданные нерабочие даты и исключения. По умолчанию открыт раздел исполнителей.

Альтернатива — хранить весь ввод в документе/SDK — нарушает отмену. Размонтирование панелей потребовало бы лишнего восстановления состояния.

### D2. Сохранение и незавершённое добавление

«Добавить» отдельно подтверждает новую запись только в черновик; Enter в строке добавления действует так же. Общая кнопка «Сохранить» валидирует все имена, включая скрытые разделы. Неподтверждённое добавление/редактирование периода или диапазона не отбрасывается: сохранение блокируется, открывается соответствующий раздел с предложением завершить действие либо очистить ввод. Имена существующих записей не требуют отдельного Enter.

После подготовки всего валидного плана выполняется одна SDK update с зафиксированной expectedRevision; оба вида обновляются по подписке. Сохранение без изменений закрывает диалог без новой редакции. Частичная запись недопустима.

### D3. Конкурентная правка и закрытие

Внешняя новая revision показывает предупреждение и блокирует сохранение прежнего снимка. Кнопка «Перечитать план» явно отбрасывает черновик после подтверждения и открывает актуальный снимок. Перед записью заново читается get; отсутствие документа даёт ошибку, а не fallback к старому содержимому. update вызывается с исходной revision и без автоматического ретрая. Исключения SDK показываются в открытом диалоге.

Выбран консервативный конфликт всего снимка, включая переименование метаданных: автоматический replay/rebase может неверно перенести удаление ссылок или потерять чужую правку. Эту сложность не вводим в UX-задачу.

Закрытие крестиком, Escape и «Отмена» при изменениях или незавершённом вводе требует подтверждения отказа от черновика. Используется native confirm по существующему контракту подтверждений удаления в модуле. PlanDialog получает необязательный локальный onBeforeClose, чтобы отказ не закрывал нативный dialog; остальные панели не меняют поведения. Скрытие владельца сохраняет черновик без вопроса, удаление/смена документа и unmount освобождают его по PBT-085.

### D4. Навигация и визуал

Оболочка wide896px PBT-085. Слева190px — четыре кнопки разделов с иконками/счётчиками, справа — прокручиваемая активная панель; header/footer неподвижны. При ширине экрана менее720px навигация горизонтальная. Поля имён в строках, Trash2 с aria-label/title, отдельное добавление, флаг «Можно параллельно»; календарь разделён на неделю, нерабочие даты и рабочие исключения. Периоды сохраняют текущий смысл отсутствий/отпусков и включительность дат.

### D5. Удаление и целостность

Подтверждение удаления исполнителя объясняет снятие назначений и удаление его недоступностей, типа работ — снятие типа и правило непараллельности по умолчанию; последствия применяются после общего сохранения. Операции удаления сейчас реконструируют задачу из неполного набора полей: поправить копирование так, чтобы группа и дополнительные поля сохранялись. Это необходимо для контракта сохранности задач при редактировании справочников; тест проверяет реальные связи/дополнительные поля, не способ реализации.

## Risks / Trade-offs

- Старая автоматическая запись закреплена UI-тестами → обновить действия навигации/сохранения, сохранив проверки настоящих данных, календаря и связей.
- Скрытый неполный ввод легко потерять → панели keep-mounted, проверка всех буферов перед записью, переход к проблемному разделу.
- Новый guard закрытия может повлиять на другие диалоги → необязательный callback, существующая последовательность освобождения фокуса сохраняется; целевые проверки PBT-085.
- Конфликт полного снимка требует повторного ввода → явное перечитывание, старый черновик сохраняется до выбора пользователя.

## Migration Plan

Миграций данных нет. Проверить сохранение/отмену и конфликт в двух видах, большие справочники, узкий экран, поля и назначения после reload. Обязательные проверки проекта и живой браузер; текущий механизм PWA/жестов/производительности не меняется. PR только в develop, архивирование после принятия.
