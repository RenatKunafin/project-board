# Design — PBT-052 Парсер OnlineGantt `.gantt`

## Context

Ядро плана v1 (`plan-document.ts`), календарная арифметика (`working-calendar.ts`) и образец диагностики конверта (`native-plan-format.ts`, PBT-050) существуют. Вход — файлы OnlineGantt `.gantt`: JSON с `data[]` (записи с опциональной вложенностью `subtasks`), справочником `resources[]` и настройками `advanced` (таймзона, рабочая неделя, праздники, почасовое расписание, колонки). Разобраны два рабочих примера:

- `diagramm.gantt` — плоский: 47 записей, 9 ресурсов; 16 отпуск-строк без назначений.
- `Online Gantt 20261016.gantt` — иерархический: 49 записей, из них 2 контейнера («Отпуск» = 16 подзадач, «ОКАД» = 16) и 47 листьев-задач; тот же справочник из 9 ресурсов. Даты/`Duration` контейнеров — охват подзадач (производные исходника).

Общие подтверждённые свойства обоих файлов: `StartDate` всегда `T05:00Z` (08:00 MSK), `EndDate` всегда `T14:00Z` (17:00 MSK **включительного** последнего дня: отпуск 31.08–11.09 с `Duration: 10` — ровно 10 рабочих дней пн–пт); `Predecessor` вида `15FS` / `7FS+14 days`, отсутствует в двух формах — `null` и `""`; `TaskID` уникальны в пределах файла **на всех уровнях вложенности**, ссылки предшественников глобальны (задачи из разных контейнеров); `unit` всегда 100, `Progress` всегда 0, непустые `info` — простой HTML. В `tests/fixtures/gantt/reference-gantt.ts` есть fixtures-only конвертер PBT-012 с явным запретом наследования без ревью — решения ниже приняты независимо, совпадения приёмов (`sv-SE`-локаль, префикс `t-`) переосмыслены.

## Goals / Non-Goals

Goals: чистая детерминированная функция разбора в `PlanContent` без расширения схемы; двухуровневая диагностика (отказ файла / предупреждение записи); отчёт импорта для предпросмотра PBT-053; DoD карточки покрыт тестами.

Non-Goals (сверх proposal): валидация семантики OnlineGantt за пределами нужного для плана (не проверяем `columns`, не воспроизводим UI-настройки); кэширование и потоковое чтение; обработка нескольких планов в одном файле (формат её не предусматривает).

## Decisions

### D1. Контракт разбора: `ok` с планом и отчётом либо отказ

```ts
parseOnlineGanttFile(text: string, options?: { title?: string }):
  | { ok: true;  payload: { title: string; content: PlanContent; report: OnlineGanttImportReport } }
  | { ok: false; issues: readonly OnlineGanttIssue[] }
```

- **Фатальный уровень** (`ok: false`, коды `invalid-json` / `invalid-structure`, формат записи — код/путь/сообщение, по образцу `PlanFileIssue`): не-JSON; верхний уровень не объект; `data`/`resources` не массивы. Частичный план не выдаётся.
- **Уровень предупреждений** (в `report.warnings`, импорт продолжается): дефекты отдельных записей (даты, дубли ID, битые ссылки, неподдержанные типы связей) и неперенесённые поля. Основание: вход — чужой формат вне нашего контроля, из него извлекается максимум, а все изъяны видны пользователю в предпросмотре PBT-053 до применения. Это осознанное отличие от строгого «всё или ничего» собственного формата (PBT-050), где вход создаётся нашим приложением.
- Результат `ok: true` обязан проходить `parsePlanContent` (инвариант: парсер не может произвести невалидный план; например, пропуск записи убирает и её зависимости). Отказ `parsePlanContent` после конвертации — внутренняя ошибка парсера, покрывается тестом на инвариант.
- Вход не мутирует; функция чистая, без I/O — чтение файла делает PBT-053.

### D2. Конвертация дат: таймзона файла, резерв — сдвиг, затем UTC

Приоритет: `advanced.timezone` (имя IANA, `Intl.DateTimeFormat` с локалью `sv-SE` даёт `YYYY-MM-DD` — приём, устойчивый к DST) → `advanced.timezoneOffset` (минуты со знаком JS: `-180` = UTC+3; сдвиг метки на `-offset` минут и взятие UTC-даты) → UTC + предупреждение `unknown-timezone`. Некорректное имя пояса (исключение `RangeError`) — как отсутствие, с предупреждением. Календарная дата берётся для `StartDate`, `EndDate` и обеих меток каждого праздника.

### D3. Даты записей и сверка длительности

`StartDate` → `start`, `EndDate` → `end` (включительное окончание — семантика примера подтверждена счётом рабочих дней). Поле `Duration` — производное исходника и в план не переносится (источник истины — даты, решения §15.3), но используется как **проверочный сигнал**: после построения календаря `workingDaysBetween(start, end)` сравнивается с `Duration` записи; расхождение — предупреждение `duration-mismatch` (ловит файлы с иной семантикой конца или сбитым поясом). `DurationUnit` ≠ `day` — предупреждение `unsupported-duration-unit`, запись не пропускается. Невалидная метка или несуществующая дата — предупреждение `invalid-task-date`, запись пропускается; `end < start` — предупреждение `inverted-interval`, запись пропускается.

### D4. Идентификаторы и коллизии

Задачи: `t-<TaskID>` (исходный ID восстановим; префикс исключает пересечения с ID ресурсов и зависимостей). Ресурсы: `resourceId` файла (в примере совпадает с названием; непустая строка проходит модель). Зависимости: `dep-<from>-<to>` (дубли пар с одинаковым лагом не создаются — идемпотентность; пара с другим лагом — предупреждение `duplicate-dependency-pair`, вторая пропускается). Дубли `TaskID` — первый входит в план, повторный пропускается с предупреждением `duplicate-task-id` (его зависимости и назначения теряют смысл и тоже пропускаются с предупреждениями об отсутствующей задаче). Дубли `resourceId` — аналогично. `projectStartDate`/`projectEndDate` не используются (в примере `null`, диапазон — производный).

### D5. Строки `Predecessor`

Отсутствие предшественника выражается двумя формами — `null` и `""`; обе трактуются как «нет» (без предупреждений). Разбивка непустой строки по `,` и `;` (в примерах предшественники одиночные; перечисление — гипотеза формата, неподдержанная форма даст предупреждение, а не молчание). Каждый элемент: `<id>FS` → лаг 0; `<id>FS+<N> day|days` → лаг N. Идентификаторы в строках — глобальные `TaskID` файла (ссылки разрешаются поверх границ контейнеров, D10). Пропуски с предупреждением и кодом причины: тип не FS (`unsupported-dependency-type`), нецелый/отрицательный лаг (`invalid-dependency-lag`, C2 ADR PBT-003), лаг в часах (`invalid-dependency-lag`), `id` не число или ссылка на отсутствующую/пропущенную задачу (`unknown-predecessor`). Зависимости на самого себя — пропуск (`invalid-dependency`): самоссылка в ядре запрещена (C4), в импорте она лишь диагностируется. Ссылка на запись-контейнер (группу) — `unknown-predecessor` с пояснением: в модели графе зависимостей группы не участвуют (C3).

### D6. Календарь и неперенесённые настройки

`advanced.workWeek` (имена дней `Monday…Sunday`) → `workingDays` (1–7, пн = 1); пустая неделя — `[1,2,3,4,5]` с предупреждением? Нет: пустая неделя означает не-календарь — предупреждение `invalid-calendar` и рабочая неделя по умолчанию `[1..5]` (модель требует непустой календарь). `holidays[].from/to` — календарные даты по D2, диапазон `from..to` включительно (в примере `from == to`); пересечение с `workingExceptions` в импорте не возникает (в модели их задаёт PBT-044). `workTime`, `columns`, `zoomLevel`, `dateFormat`, `timeFormat`, `firstDayOfWeek`, `dependencyConflict` — сводка «неперенесённые настройки» одной записью отчёта на каждую категорию (без перечисления каждой строки — иначе отчёт шумит; счётчики не нужны, состав категорий фиксирован).

### D7. Политика дополнительных полей

- `unit` → доп. поле задачи `assigneeUnits?: Record<resourceId, number>` (ADR PBT-003 D3 «сохраняется в данных»; прямое место назначения, отсутствие у ресурса — просто нет записи). Доп. поля переживают `parsePlanContent` и round-trip собственного формата (passthrough PBT-050).
- `info` → доп. поле задачи `notes?: string`: текст, извлечённый из HTML мини-извлекателем (теги вырезаются; `<br>`, `</p>`, `</li>` — перевод строки; базовые сущности `&amp; &lt; &gt; &quot; &#39; &nbsp;` декодируются). Не DOMParser: пакет не зависит от DOM; разметка примеров простая. Ограничение зафиксировано в Risks. Запись в отчёте не создаётся (массовая операция, политика документирована здесь и в спеке).
- `color`, `Progress` — не переносятся (модель их не использует; прогресс задач — незапланированная идея PBT-067): сводная запись отчёта «неперенесённые поля записей» с перечнем полей и числа затронутых записей.
- `TaskID` — в `id` задачи (D4); `TaskName` — `title`; при пустом названии — предупреждение, запись импортируется с названием как есть, если строка непустая… пустое название нарушает `parsePlanContent`? Проверка: `titleCheck` требует `typeof === 'string'` — пустая строка проходит валидацию модели. Импортируем как есть, без предупреждений (исходник — источник имён).

### D8. Название плана

Файл названия не содержит. `options.title` задаёт PBT-053 (из имени файла или поля предпросмотра); дефолт — `Импорт OnlineGantt`. В `payload.title` — для создания документа (по контракту `PlanFilePayload`-подобной формы, потребитель — PBT-053).

### D9. Расположение, тесты, эталоны

Модуль `packages/gantt/src/onlinegantt-parser.ts` + `onlinegantt-parser.test.ts` (инлайн-входы: несколько предшественников, вложенность `subtasks`, все виды предупреждений, фатальные случаи, инвариант `parsePlanContent`). Тесты обоих рабочих файлов — эталонные копии в `tests/fixtures/gantt/` (`diagramm.reference.gantt` — уже есть; `onlinegantt-20261016.reference.gantt` — копия второго примера) с тестами рядом (паттерн PBT-050: фикстурный тест вне tsconfig пакетов, импорт из `packages/gantt/src`). Проверки DoD: файл 1 — 47 задач, 9 ресурсов, групп нет, 16 строк без назначений остаются задачами, лаги 0/14/1; файл 2 — 2 группы («Отпуск» ×16, «ОКАД» ×16), 47 задач, 9 ресурсов, зависимость через границу контейнеров (`55FS`... в файле 2: `БЧ-АНЛ-ANDR` → `17FS+25 days`, где 17 — внутри «ОКАД»), праздник `2026-11-04`, `unit` в `assigneeUnits`. Зависимостей не вводится.

### D10. Иерархия `subtasks` → группы

Обход `data` рекурсивный. Запись с непустым `subtasks` → **группа**: `id = g-<TaskID>`, `title = TaskName`, `parentId` — контейнер уровнем выше (если есть); её `StartDate`/`EndDate`/`Duration` — производные охвата исходника и не читаются (сводные границы вычисляет модель, B2 ADR PBT-003). Запись без `subtasks` → задача (D3–D4) с `groupId` ближайшей группы. Глубина вложенности не ограничивается парсером (в примерах 2 уровня; модель групп — произвольная вложенность, ядро PBT-032). Пространство `TaskID` общее для всех уровней (подтверждено примерами): карта `TaskID → задача|группа` одна; повторный ID любого вида пропускается целиком со своим поддеревом с предупреждением `duplicate-task-id`. Назначения или предшественники у контейнера (в примерах не встречаются) — предупреждения `group-assignments-dropped` / `group-predecessor-dropped`, контейнер всё равно становится группой: группа в модели не имеет ни назначений, ни места в графе зависимостей (C3). Запись с `subtasks: []` в группу не превращается — импортируется задачей (пустые контейнеры в примерах не встречаются; выдумывать пустую группу по пустому массиву нечестно).

## Risks / Trade-offs

- [Семантика `EndDate` подтверждена двумя примерами] → сверка `Duration` с рабочими днями (D3) даёт предупреждение на файлах с иной семантикой конца/сбитым поясом; пользователь видит это в предпросмотре PBT-053 до применения.
- [Группа из `subtasks` — вывод по косвенному признаку (непустой массив), формат не документирован] → подтверждено двумя реальными файлами; назначения/предшественники контейнера не теряются молча (предупреждения D10); поведение на `subtasks: []` зафиксировано явно.
- [Формат не документирован производителем] → независимая сверка с оригинальным инструментом (метод контроля владельца, 2026-10-16): файл `Online Gantt 20261016.gantt` открыт на `onlinegantt.com/#/gantt` — инструмент интерпретирует записи с `subtasks` как сворачиваемые контейнеры (вложенность подтверждена), даты показывает включительно (27.07–31.07 при `Duration: 5`), строки зависимостей и ресурсы — как в файле, notes — текстом (скриншот `screenshots/onlinegantt-reference-opened.png`). Этот же приём — контроль результата PBT-053: импортированный файл открывается в оригинале и в нашей системе, сравниваются группы, даты, зависимости, ресурсы.
- [Разделитель нескольких предшественников — гипотеза] → неразобранный элемент строки всегда даёт предупреждение с исходным текстом (нет молчаливых потерь); при реальном файле с иным синтаксисом диагностика укажет на него.
- [Мини-извлекатель HTML может потерять экзотическую разметку] → политика зафиксирована (текст без разметки), тесты на типовых случаях примера; полный HTML-парсер — вне границы (новая зависимость ради двух записей примера).
- [Двухуровневая диагностика шире образца PBT-050] → отличие мотивировано чужим входом; критерии «фатально/предупреждение» перечислены явно (D1), чтобы PBT-053 не додумывал.

## Migration Plan

Новый модуль без изменения существующих контрактов; миграция не требуется. Откат — удаление модуля с тестами.
