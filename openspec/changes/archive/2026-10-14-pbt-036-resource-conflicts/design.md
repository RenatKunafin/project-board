# Design — PBT-036: конфликты ресурсов и отпусков

## Context

База: модель v1 с `tasks[].assigneeIds?` / `tasks[].workTypeIds?` и `unavailability: [{ id, resourceId, start, end }]`; арифметика PBT-013 (`isWorkingDay`, календарь из `plan.calendar`); прецедент диагностики `dependencyViolations` (PBT-035: чистая функция, календарь один раз на вызов, защитный пропуск повреждённых рёбер, сообщения на русском). Правила ADR PBT-003: D1 (несколько назначений, конфликт по каждому ресурсу), D2 (задачи без назначений не участвуют), D3 (проценты не влияют), D4 (задача без типа — непараллелизуемая), D6 (пересечения по рабочим дням; отпуск на нерабочих днях не конфликтует; действует и для параллелизуемых), правило 11.3 (конфликтуют пересекающиеся работы, обе запрещающие параллельность; таблица: Разработка+Разработка — конфликт, Разработка+ПСИ и ПСИ+ПСИ — допустимо), раздел 12 (пересечение работы с отпуском — конфликт всегда, исправляет менеджер).

## Goals / Non-Goals

**Goals:** чистая `resourceConflicts(plan)` с двумя видами конфликтов; матрица 11.3 включая D4; рабочие дни как мера пересечения (D6); диагностика без дублей пар; даты неизменны.

**Non-Goals:** исправление конфликтов, проценты загрузки (D3), UI (PBT-046/047), команды (ядро операций завершено).

## Decisions

### D1. Два вида конфликтов — дискриминированное объединение

```text
ResourceConflict =
  | { kind: 'parallel-work'; resourceId; firstTaskId; secondTaskId;
      intervalStart; intervalEnd; message }
  | { kind: 'unavailability'; resourceId; taskId; unavailabilityId;
      intervalStart; intervalEnd; message }
```

Объединение вместо одного плоского типа: у видов разный состав участников (пара задач против задачи и периода), опциональные поля размывали бы контракт. Порядок выдачи: сначала все `parallel-work` (перебор ресурсов, внутри — пары задач в порядке массива `tasks`), затем все `unavailability` (перебор недоступностей, внутри — задачи в порядке массива); детерминировано для сравнения и тестов.

Интервал контакта: календарное пересечение `[max(starts), min(ends)]`, суженное до рабочих дней — `intervalStart`/`intervalEnd` это первый и последний рабочий день пересечения. Если в пересечении нет ни одного рабочего дня — конфликта нет (D6: пересечения учитываются по рабочим дням, обе непараллелизуемые работы в общий нерабочий день не конфликтуют).

### D2. Многотипные задачи: консервативный критерий (утверждено владельцем)

ADR PBT-003 фиксирует правило для задач с одним типом и «задача без типа — непараллелизуемая» (D4); случай задачи с несколькими типами (формат v1 допускает `workTypeIds` массив) не определён.

**Вариант A (утверждён владельцем 2026-10-14):** работа параллелизуема, только если **все** её типы разрешают; отсутствие типов — непараллелизуема (D4). Эквивалентно: работа непараллелизуема, если нет типов или хотя бы один тип с `allowsParallel: false`.

Основание: преемственность консервативного духа D4 (в ADR отклонён «пропускающий» вариант как «консервативно пропускала бы реальные конфликты»). Задача с типами [Разработка, ПСИ] содержит непараллелизуемую разработку — конфликтовать с другой разработкой обязана. Пропуск такого конфликта при варианте B — скрытая потеря диагностики.

Отклонённая альтернатива — **вариант B** (параллелизуема, если хотя бы один тип разрешает): матрица [Разработка+ПСИ] и [Разработка,ПСИ]+Разработка дала бы разные вердикты при одинаковой фактической занятости.

Матрица при варианте A: Разработка+Разработка → конфликт; Разработка+ПСИ → нет; ПСИ+ПСИ → нет; без типа+без типа → конфликт (D4); без типа+Разработка → конфликт (обе запрещают); без типа+ПСИ → нет; [Разработка,ПСИ]+Разработка → конфликт; [Разработка,ПСИ]+ПСИ → нет.

### D3. Алгоритмы: перебор пар и работа × недоступность

**Работа × работа:** группировка назначений по ресурсу (задача × `assigneeIds` — D1, конфликт по каждому ресурсу; задачи без назначений не участвуют — D2); для каждого ресурса пары (i < j) по порядку массива `tasks` (без дублей пар по построению, DoD-4); конфликт ⇔ обе работы непараллелизуемы (D2) И пересечение календарных интервалов непусто И содержит ≥ 1 рабочий день.

**Работа × недоступность:** для каждой недоступности — задачи с её ресурсом в назначениях; конфликт ⇔ пересечение с работой содержит ≥ 1 рабочий день; **параллельность типов игнорируется** (раздел 12: правило распространяется и на ПСИ). Отпуск, целиком лежащий в нерабочих днях, даёт пустое рабочее пересечение с любой работой — конфликта нет (D6).

Оценка сложности O(Σ по ресурсам |задачи|² + |недоступности| × |задачи|) — при целевой нагрузке (сотни задач, десятки назначений на ресурс) приемлемо; кэширование и инкрементальность — вопрос представлений (PBT-047), не ядра. Ресурс недоступности, отсутствующий в справочнике, пропускается защитно (повреждённые данные — ответственность валидатора чтения, прецедент PBT-035 D2).

### D4. Диагностика и неприкосновенность дат (DoD-4/5)

`message` на русском называет обе работы (или работу и отпуск), ресурс и причину («обе запрещают параллельность» / «работа пересекается с периодом недоступности»). Функция чистая: не мутирует план, календарь создаётся один раз; «пересчёт после правки календаря/назначения/типа не меняет исходные даты» (DoD-5) достигается чистотой и подтверждается тестами на тот же план до/после диагностик и правок.

### D5. Границы и экспорт

`plan-conflicts.ts` — типы `plan-document.ts` + `working-calendar.ts`, без React и UI-библиотек. `PlanCommand` не расширяется (команд нет). Экспорт из `index.ts`.

## Risks / Trade-offs

- **Многотипные задачи (D2) — правило не зафиксировано в ADR:** вариант A утверждён владельцем 2026-10-14; при пересмотре правится предикат `isParallelAllowed` и табличные тесты.
- **Квадратичный перебор пар на ресурс** — осознанно: типичный ресурс имеет единицы–десятки работ; при обнаружении деградации на PBT-058 порогами ADR-7 оптимизация станет отдельной задачей.
- **Два вида конфликтов в одном списке** — потребители фильтруют по `kind`; единая точка вызова проще для PBT-046, чем две функции.

## Migration Plan

Не требуется: формат v1 не меняется; только чистая функция диагностики.
