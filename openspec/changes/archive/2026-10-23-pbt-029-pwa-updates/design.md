# Design — PBT-029

## Context

Подход согласован владельцем сообщением «делаем» 2026-10-22; реализация начинается после этого согласования.

База — develop после merge PR#56. PWA использует `vite-plugin-pwa@2.0.0`, generateSW, prompt, skipWaiting false и clientsClaim true. `PwaStatus.tsx` регистрирует SW нативно и показывает только офлайн-готовность. Документы сохраняются платформенным сервисом с задержкой 250 мс; workspace — полным снапшотом через App с задержкой 300 мс; настройки экземпляров — отдельными асинхронными записями `WorkspaceStore.saveViewSetting`.

Обнаруженные границы текущего кода:

- `flushAll()` ждёт `flushDocument()`, но при `entry.inFlight` тот возвращает управление сразу; отложенные повторы и следующая запись тоже не входят в возвращённое ожидание.
- Ошибка записи переводится в статус/повтор, а не в отклонение `flushAll()`: простого await недостаточно для разрешения reload.
- В catch записи `entry.pending = document` может затереть более новую pending-редакцию, появившуюся во время await. Исправление требуется для гарантии сохранения актуальных данных.
- Сохранение workspace и настроек сейчас вызывается без общего await; одного агрегатного статуса документов недостаточно.
- Семантика конфликта уже задана: сервис перечитывает актуальную запись хранилища и сообщает conflict. Эта задача блокирует обновление при конфликте, не вводя новую систему разрешения конфликтов.

## D1. Обнаружение и UI (согласовано)

Расширить клиент PWA с выделением логики жизненного цикла из представления. `registration.waiting` учитывается как при старте, так и после updatefound/statechange. Офлайн-готовность остаётся отдельным статусом. Уведомление «Доступна новая версия» содержит «Обновить» и «Позже»; отложенное уведомление можно снова открыть действием в топ-баре, пока версия ожидает. Текущая работа и формы при появлении уведомления не меняются.

Регистрация при запуске уже проверяет SW. Дополнительный `registration.update()` — при возвращении видимости/фокуса и событии online, с ограничением не чаще одного раза в минуту и защитой от параллельных вызовов; периодическая проверка раз в час, только в видимой онлайн-странице. Ошибка проверки сети не отменяет уже готовый офлайн-кэш и не считается доступным обновлением.

Нажатие «Обновить» открывает подтверждение: «Приложение перезапустится. Сначала сохраните изменения в открытых формах. Документы и расположение окон будут сохранены перед обновлением». Кнопки «Отмена» и «Обновить». Неподтверждённый текст формы не считается сохранённым документом; автоматически применять формы модулей платформа не умеет. Отмена не вызывает сохранение/активацию/reload.

После подтверждения диалог становится блокирующим («Сохранение…», затем «Обновление…»), повторное нажатие и Escape отключены. Собственные фоновые callbacks сохранения учитываются ожиданием. Это не отменяет уже начатые записи или завершение отложенного жеста: они входят в сохраняемое актуальное состояние.

## D2. Подтверждение записи документов (согласовано)

Усилить существующий платформенный `AutosavingDocumentService.flushAll(): Promise<void>`: завершение означает, что все операции, вошедшие в подготовку, подтверждены хранилищем и нет pending/in-flight/retry. Выполняющаяся запись представляется Promise; flush присоединяется к ней, снимает задержки очереди и дренирует последующие редакции. Параллельные flush не создают конкурирующие записи одного документа. Отложенный повтор не подменяет более новую pending-редакцию устаревшим содержимым.

При исчерпании текущих ограниченных повторов или conflict явное ожидание отклоняется диагностикой. Фоновое автосохранение сохраняет существующие статусы и ограниченные повторы, без необработанных rejection. `pagehide` остаётся best effort и явно обрабатывает отказ flush; нельзя считать pagehide гарантией завершения IndexedDB.

Выполняющиеся async-удаления документов также учитываются перед разрешением обновления: reload не должен прервать delete. При ошибке delete обновление не применяется. Это ограниченная координация существующих операций, без новых правил каталога. Для сервиса без persistence уточнить поведение: обновление не получает ложное подтверждение долговременного сохранения; основное приложение всегда использует store.

Существующий SDK `DocumentService` модулей не меняется: усиление относится к платформенному сервису. Корректировка реализации очереди и тестов входит в PBT-029, поскольку напрямую обеспечивает её DoD.

## D3. Рабочее пространство и настройки (согласовано)

У `WorkspaceStore` — последовательная цепочка завершения всех save/saveViewSetting и явная финальная запись актуального снапшота и всех настроек экземпляров перед обновлением. Старый снапшот, начатый раньше, не может зафиксироваться после финального. Финальная запись workspace/settings транзакционная; ошибка возвращается вызывающему, актуальное состояние в памяти сохраняется для повторной попытки. Новая схема БД не нужна.

App предоставляет клиенту обновления `prepareForUpdate()` через внутренний callback (не SDK): снимает таймер workspace, дожидается очередей, пишет актуальные snapshotRef/viewStatesRef и ждёт документы. После асинхронных этапов ещё раз проверяет актуальность refs/редакций, если завершившийся callback добавил изменение. UI заблокирован до подтверждения завершения, затем только отправляется запрос активации. Все записи настроек получают обработку ошибок; фоновые ошибки не маскируются как успешная подготовка.

Не требуется общая транзакция документов и workspace: если один этап записался, а следующий завершился ошибкой, страница не перезагружается. Следующая попытка дописывает актуальное состояние. Гарантия — подтверждены все этапы перед активацией.

## D4. Согласованная политика нескольких окон и активация

**Согласовано: применять обновление при одном открытом окне приложения.** В ожидании могут оставаться любые окна, включая установленную PWA, но активация по кнопке блокируется, пока открыты другие окна/вкладки того же origin и scope. Сообщение: «Закройте другие окна Project Board и повторите обновление». Другие окна не закрываются программно и не перезагружаются.

Альтернатива — межоконный протокол согласия, блокирования ввода и сохранения всех сессий, включая независимые черновики. Это существенно расширяет задачу; предлагается оставить для отдельного решения. Одно лишь BroadcastChannel-число окон ненадёжно: фоновые/старые страницы могут не отвечать.

Список клиентов запрашивается у ожидающего SW через MessageChannel: `clients.matchAll({type:'window', includeUncontrolled:true})`, затем фильтр по фактическому scope. includeUncontrolled нужен, потому что ожидающий worker ещё не управляет старой страницей. Учитываются обычные вкладки, установленное окно и технический маршрут в том же scope. Проверка проводится до подготовки сохранения и ещё раз непосредственно обработчиком запроса активации. Ответы коррелируются с текущим waiting worker; таймаут/исчезновение waiting/замена новой версией не разрешают безусловный reload.

Для проверки клиентов и условного skipWaiting добавить небольшой локальный versioned-скрипт в generateSW `importScripts`. Обработчик запроса активации снова проверяет, что клиент один и это отправитель, затем вызывает skipWaiting. Не использовать сетевое перечисление окон из UI. Версию вспомогательного скрипта привязывать к сборке (хешированный ресурс), чтобы новая публикация не меняла код уже установленного SW.

Перезагрузка выполняется однократно по controllerchange только в инициировавшем её окне и после успешной подготовки. Первая установка SW и незапрошенная смена controller не вызывают автоматический reload. Отмена доступна до отправки активации; после отправки нельзя обещать отмену браузерной активации. Ошибка/таймаут подготовки до активации оставляет рабочую сессию доступной; ошибка активации показывается отдельно, сохранённые данные уже подтверждены.

Ограничение платформы: новую вкладку технически можно открыть одновременно с активацией; проверки снижают этот риск, но не являются атомарной блокировкой создания окон браузером. Фоновая смена SW не должна заставлять такие окна автоматически перезагружаться; пользовательская инструкция просит оставлять одно окно до завершения обновления. Полная межоконная блокировка потребует отдельного протокола. Кроме того, приложение не предотвращает принудительный reload/закрытие пользователем через браузер.

## D5. Две сборки и миграции (согласовано)

E2E-сервер отдаёт A и затем B по одному origin/scope; `sw.js`, HTML и manifest — без длительного HTTP-кэша. Обе сборки имеют реально различающиеся хеши ресурсов и SW, проверяемые маркеры версии. Старые статические ресурсы остаются на сервере во время перехода, как рекомендуется для безопасного deployment; новая навигация после принятия обслуживается новым precache. Собственные caches origin не очищаются целиком.

Обычная product-сборка не содержит тестовых схем/модулей/endpoint переключения. Для двухверсионной проверки миграций — отдельный fixture-конфиг сборки: добавочный тестовый модуль регистрирует документ схемы 1 в A и 2 с чистой миграцией в B, используя настоящий SDK, registry, restoreAll и IndexedDB. Подмена только точки комплектации через тестовый Vite-плагин; производственные типы виджетов сохраняются. Это проверяет реальное восстановление после обновления, не утверждая, что у рабочих checklist/plan существовал выдуманный старый формат. Позитивные/негативные тесты миграций PBT-026 сохраняются.

Сценарий: A → документ fixture v1 + реальные чек-лист/план, вкладки/каскад/настройки → публикация B → видимое уведомление без reload → правка непосредственно перед подтверждением → ожидание записи → B восстанавливает реальные документы и layout, fixture мигрирует в v2 однократно → закрытие окон → B открывается без сети с документами и ресурсами своей версии. Проверить реальный Cache Storage и принадлежность загруженных ресурсов B; список не ограничивать маркером версии.

Первый rollout **PBT-028 → PBT-029** отличается: загруженный JS PBT-028 не умеет показывать обновление. Никакая новая сборка не добавит кнопку в старую открытую страницу. Инструкция первого перехода: дождаться «Сохранено», закрыть все окна/вкладки приложения, открыть снова после штатной активации браузером. Не обещаем программную гарантию flush из ещё не обновлённого кода PBT-028. Проверить этот путь отдельно на настоящем baseline PBT-028; основной управляемый A → B тест использует клиент обновлений в обеих версиях.

## D6. Проверки и границы объёма

- Unit очереди: flush во время in-flight; новая редакция во время записи/повтора; сохранение всех документов; параллельные flush; исчерпание повторов; conflict; ожидание delete и ошибка удаления. Проверять подтверждённое содержимое и момент завершения Promise, а не только флаги реализации.
- Workspace: отложенный старый save и настройка не обгоняют финальное сохранение; ошибка транзакции запрещает разрешение reload; повтор сохраняет последние refs.
- Browser A/B: обнаружение, «Позже», отмена, правка в момент обновления, ошибка/задержка записи, восстановление после ошибки, две вкладки (отказ без reload), их закрытие и успешный повтор, миграция fixture, холодный офлайн B. Начальная активация не перезагружает страницу.
- Время ожидания подготовительного сохранения ограничено (предлагается 15 с); превышение сообщает об ошибке и не разрешает активацию. Операции IndexedDB могут завершиться позже; это не отменяется таймаутом. Каждая попытка имеет отдельный token, поздний результат старой попытки не вызывает reload.
- MCP Playwright — живой UI и консоль отдельно от полного e2e; скриншоты уведомления/ошибки/успеха в `change/screenshots/`.
- Перед PR: lint, typecheck, unit, свежий build, browser на чистом preview, целевые двухверсионные проверки и OpenSpec strict. Новые библиотеки не планируются.
- Если надёжная координация требует отдельного самостоятельного результата, вернуться к декомпозиции до расширения PR. Предлагаемый объём — завершение записи и применение обновления как единый сценарий PBT-029.

## D7. Фактическая реализация и проверки (2026-10-23)

- `PwaStatus` управляет уведомлением, подтверждением и ошибкой. Протокол сообщений и ожидание controllerchange выделены в `pwa-update.ts`. Первый controllerchange не вызывает reload; загрузка новой версии выполняется только после успешного пользовательского сценария. Корреляция попытки обеспечена отдельным MessageChannel и локальным await с таймаутом: после отказа порт закрывается, controllerchange-listener снимается. Дополнительный числовой token не понадобился; позднее завершение сохранения не выполняет UI-активацию (проверено браузером).
- `pwa/update-guard.ts` содержит source локального SW-обработчика. Vite вычисляет SHA-256 и выпускает его как хешированный asset, подключённый через importScripts; runtime-зависимости не добавлялись. Обычный build не содержит `update-fixture` или тестовую комплектацию.
- Платформенный flushAll присоединяется к Promise существующей записи, дренирует следующие редакции и ограниченные повторы; отказ виден вызывающему. Ошибка перечитывания конфликта переводит документ в error и сохраняет pending. Удаление ждёт предыдущий put, учитывается общим ожиданием; update/rename в процессе удаления отклоняются, чтобы новая правка не исчезла вместе с записью. Платформенный flush workspace записывает снимок и view settings в одной транзакции после предыдущих save; callbacks получают обработку ошибок.
- `prepareForUpdate` использует стабильные refs, снимает debounce и повторяет фиксацию, если завершившийся callback изменил состояние во время await. Ref настроек обновляется иммутабельно для обнаружения таких изменений. Схема БД и SDK модулей не менялись.
- В тестовом Vite-плагине нужен `enforce: pre`: обычный resolver успевал разрешить production widgets до тестового перехвата. Исправлен сам стенд; A/B теперь содержат разные хешированные JS и реальные схемы fixture 1/2. Метка HTML проверяется вместе с кодом, документом и Cache Storage, не подменяет проверку обновления.
- Baseline PBT-028 — настоящий git archive `c3494ba`, с aliases на его собственные пакеты и теми же установленными версиями зависимостей. На macOS root временной директории нормализуется через realpath (иначе Vite смешивает /var и /private/var); workspace node_modules подключаются отдельно. При естественной активации тест ждёт activate именно нового worker, затем activated, а не исчезновение waiting у старого.
- Задержка записи проверена настоящей IDB-транзакцией: дополнительные запросы держат её открытой до освобождения gate. Перехват transaction после инициализации Dexie не годится, поскольку внутренний слой уже захватил API. Подтверждены 15-секундный таймаут, отсутствие позднего reload после завершения записи и успешный явный повтор.
- `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` — успешно. Unit: **480/480**, 36 файлов (+12 к develop). Production precache: 85 записей, ~2052 КиБ. Новых литеральных цветов/внешних runtime-ресурсов нет.
- `npm run test:browser` на свежем build и свободном preview: **128/128**. Отдельный двухверсионный прогон `playwright.pwa.config.ts`: **8/8**, включая реальный план, свежую правку, настройки/каскад, миграцию в schemaVersion 2, отсутствие старого A-only JS в Cache Storage, холодный B без сети; откладывание/отмена; ошибки documents/tabs/settings и повтор; соседнее окно; таймаут in-flight; первый переход с PBT-028. Полная команда воспроизведения — `npm run test:pwa-updates` (сборка fixtures + прогон).
- MCP Playwright, Chrome 155.0.8059.86: A → уведомление → подтверждение → блокировка при втором окне → закрытие второго → повтор → B. **0 ошибок и 0 предупреждений консоли**, скриншоты в screenshots/. Документы пользователя не использовались: отдельный тестовый origin localhost:4184 со стартовыми чек-листами.
- OpenSpec strict change/all — **19/19**. После проверок изменялись только документация и отступы Vite-конфига, поведение не менялось. Change остаётся активным до принятия PR.
