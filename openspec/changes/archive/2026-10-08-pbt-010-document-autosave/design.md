## Context

Две половины сохранения готовы по отдельности: синхронный `DocumentService` (PBT-007) и асинхронный `DocumentStore` на Dexie (PBT-009) — контрактно они не связаны. Схема состояния 15.4 решений: операция → пересчёт → уведомление → запись; запись после завершённой операции; защита `revision`. DoD карточки требует очередь, состояние «сохранено/сохраняется/ошибка», восстановление после перезапуска и конфликт двух окон.

## Goals / Non-Goals

**Goals:**

- Очередь автосохранения per-document внутри сервиса: debounce, последняя редакция, правильный порядок.
- Состояния `saved / saving / error / conflict` с подпиской для UI; retry при техническом сбое; перечитывание при конфликте.
- Восстановление при старте (`restoreAll`) и bootstrap приложения: чек-лист переживает перезагрузку.
- Индикатор состояния сохранения в оболочке.

**Non-Goals:**

- Слияние/merge конфликтующих правок (CRDT/OT), выборочное сохранение, ручные «Сохранить/Отменить» кнопки.
- Координация нескольких вкладок через BroadcastChannel/storage events (первая версия — конфликт разрешается перечитыванием).
- Сохранение viewSettings (настройки представления остаются в памяти; персистентность настроек — вне первой версии).
- Каталог документов (PBT-025): восстановление возвращает все документы, приложение использует первый чек-лист.

## Decisions

- **Store — опциональная зависимость сервиса.** `createDocumentService({ store, saveDelayMs = 250 })`. Без store сервис ведёт себя как раньше (все тесты PBT-007 сохраняются). Имя БД приложения: `project-board`.
- **Очередь per-document, единая для всех представлений.** Состояние очереди: `{ pending: ManagedDocument | null, lastSavedRevision: number | number-0, inFlight, timer }`. `update()` кладёт `pending` (всегда последняя редакция) и перезапускает debounce-таймер (`saveDelayMs`, fake timers в тестах). DoD-5 выполняется конструктивно: очередь принадлежит документу, не представлению.
- **`lastSavedRevision`:** 0 до первой успешной записи (новый документ), затем — редакция последнего подтверждённого store-сохранения. Flush вызывает `store.save(document, lastSavedRevision)`; `DocumentConflictError` → ветка конфликта; `PersistenceError` → retry.
- **Retry при техническом сбое:** до 3 попыток (задержки 250→500→1000 мс), затем состояние `error` (очередь сохраняет последнюю редакцию). Следующая операция перезапускает flush. Между попытками и при успешной записи состояния: `saving` → `saved`.
- **Конфликт → перечитывание.** `store.get(documentId)` → если найден: заменить память, `revision` = хранимая, уведомить подписчиков, `lastSavedRevision` = хранимая, состояние `conflict`; несохранённый pending отбрасывается (правка устаревшей стороны теряется — выбранное разрешение, индикатор виден). Если не найден (документ удалён из другого окна): документ удаляется из памяти, состояние `conflict` (сценарий удаления — PBT-025 уточнит).
- **`restoreAll()`:** `store.listAll()` → записать в память без уведомлений (подписчиков ещё нет) → вернуть список. Приложение: async bootstrap в `main.tsx` — восстановить, затем гарантировать наличие одного чек-листа (`listByModule('checklist')` пуст → `create`), рендер.
- **Индикатор:** `subscribeSaveState(documentId, handler)` + `getSaveState(documentId)`; состояние `undefined` до первой операции (не показываем ничего); `App` — бейдж под заголовком: «Сохранено» / «Сохраняется…» / «Ошибка сохранения» / «Обновлено из другого окна».
- **Конфликт в unit-тестах:** FakeStore (Map + переключаемое поведение: `failNext`, `staleRevision`) — без fake-indexeddb; интеграция с реальным Dexie покрывается e2e двух страниц.

## Risks / Trade-offs

- [Потеря несохранённых правок второго окна при конфликте] → выбранное разрешение задокументировано (хранилище = истина, индикатор «Обновлено из другого окна»); merge/CRDT — вне первой версии, возврат к вопросу при реальных жалобах.
- [Debounce 250 мс задерживает durable-запись] → осознанно (решения 15.4: запись после завершённой операции, не каждое движение); при закрытии вкладки незаписанное может пропасть — приёмлемо для v1, `flush on beforeunload` добавим при интеграции PWA (PBT-028).
- [Bootstrap-загрузка делает старт асинхронным] → рендер после `restoreAll` (оболочка статична до этого); для первой версии достаточно.
- [Документ чек-листа создаётся один при старте] → приближение до каталога PBT-025; несколько списков пока не создать из UI (ограничение фиксируется в карточке).
