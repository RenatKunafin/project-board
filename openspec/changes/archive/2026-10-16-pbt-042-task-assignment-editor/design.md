# Design — PBT-042 Task assignment editor

## Context

Ядро PBT-034: `assignResource`/`unassignResource`/`assignWorkType`/`unassignWorkType` — идемпотентные множества (`assigneeIds`/`workTypeIds`); `createTask` принимает множества при создании; `updateTask` патчит множества (присутствие свойства = замена целиком, `[]` = снять все). Справочники с редакторами — PBT-041. Форма задачи — TaskEditorDialog (PBT-038), submit → `createTask`/`updateTask`+`setTaskDates` в `submitTaskForm`.

## Goals / Non-Goals

- Goals: назначение/замена/снятие исполнителей и типов в карточке задачи без изменения сроков; отображение назначений в таблице; только справочники текущего плана; несколько исполнителей без дублирования строк.
- Non-Goals: см. proposal.

## Decisions

### D1. Чекбоксы множеств в форме задачи

Секции «Исполнители» и «Типы работы»: чекбоксы по справочникам плана (модель — множества, D1 ADR PBT-003). Состояние формы — выбранные id (инициализация из задачи при редактировании, пусто при создании); submit присылает полные списки — семантика «замена множества». Пустой список при редактировании → патч `[]` → ядро снимает все назначения и убирает поле (PBT-034: опустевший массив убирается). Если справочник пуст — плейсхолдер со ссылкой на кнопку «Справочники» (текст, не ссылка-действие: v1).

Альтернатива «мультиселект»/«теги» отклонена: чекбоксы явнее при десятках записей и не требуют нового компонента.

### D2. Даты не затрагиваются

Назначения проходят тем же submit-путём: `createTask(...)` с множествами; редактирование — `updateTask` (title/groupId/множества) + `setTaskDates` (даты формы, как в PBT-038). Контракт ядра: команды назначения не меняют даты (тесты PBT-034); e2e фиксирует даты до/после.

### D3. Колонки таблицы

Колонки «Исполнители» (имена через запятую из `assigneeIds` по справочнику) и «Типы» (названия типов); пусто → «—» (DoD «неназначенная отображается явно»). Одна строка на задачу независимо от числа исполнителей (DoD «без дублирования» — дублирование строк характерно ресурсному виду, PBT-047). Чтение — из `planRef` (актуально при перерисовке строки, прецедент колонки «Раб. дни»).

### D4. Только справочники текущего плана

Чекбоксы строятся из `plan.resources`/`plan.workTypes` документа формы; id из чужого плана невозможны по построению (в select/чекбокс попадают только существующие записи; при гонке удаления ядро вернёт `unknown-resource` — alert формы).

## Risks / Trade-offs

- Чекбоксы при сотнях ресурсов потребуют прокрутки в диалоге — целевой объём плана (несотни задач, единицы–десятки ресурсов) приемлем; виртуализация — при претензиях.
- Колонки «Исполнители»/«Типы» сужают чарт — суммарная ширина таблицы растёт; гриду доступна горизонтальная прокрутка (наблюдение PBT-037).

## Migration Plan

Схема не меняется; множества уже в модели v1. Новая поверхность формы и таблицы.

## Open Questions

Нет — развилок, требующих владельца, не выявлено; серия автономна (директива владельца).
