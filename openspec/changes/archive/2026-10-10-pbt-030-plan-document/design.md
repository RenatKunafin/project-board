# Design — PBT-030: документ плана и регистрация модуля

## Context

Ядро разблокировано (ADR PBT-017). Существующая база: `widget-sdk` (DocumentService, defineWidgetType с documentSupport), чек-лист как эталонный модуль, арифметика календаря PBT-013 (`createWorkingCalendar`, ISO-даты `YYYY-MM-DD`, Weekday 1–7), fixtures-формат PBT-012 (`tests/fixtures/gantt/`), правила ADR PBT-003 (A1–D7). Схема хранения — одна запись на документ (ADR PBT-002 ADR-5), содержимое непрозрачно для сервиса.

## Goals / Non-Goals

**Goals:** типизированный формат плана v1; фабрика пустого плана; валидатор чтения с диагностикой; регистрация модуля через SDK; подключение в комплектацию; delta spec `planning-documents`.

**Non-Goals:** операции (PBT-031), отображение (PBT-037+), миграции (PBT-026), импорт (PBT-052+).

## Decisions

### D1. Формат v1 — расширение fixtures-формата PBT-012

Продуктовый `PlanContent` наследует состав контрольного формата (осознанно: перенос golden-фикстур в тесты ядра станет тривиальным, см. PBT-031+):

```text
PlanContent {
  title?: string                       // задаётся каталогом, как у чек-листа
  calendar: { workingDays: Weekday[1..7], holidays: ISO[], workingExceptions: ISO[] }
  workTypes:  [{ id, title, allowsParallel }]
  resources:  [{ id, title }]
  groups:     [{ id, title, parentId? }]         // parentId отсутствует у корневых
  tasks:      [{ id, title, groupId?, start, end, assigneeIds?, workTypeIds? }]
  dependencies: [{ id, fromTaskId, toTaskId, lagDays }]
  unavailability: [{ id, resourceId, start, end }]
}
```

Даты — календарные ISO `YYYY-MM-DD` без времени суток; окончание включительно (A1); `lagDays` — целое ≥ 0 (C2); задача без типа — непараллелизуемая на уровне проверок ядра (D4), в данных флаг не нужен. Назначения — `assigneeIds` внутри задачи (несколько, D1): плоские ссылки проще для валидации и импорта `.gantt`; отдельная таблица назначений — усложнение без требования первой версии. Все структуры `readonly`, операции будущих задач возвращают новый объект (иммутабельность, как в workspace/checklist).

### D2. Валидация чтения — диагностика вместо молчаливого fallback

`parsePlanContent(value: unknown): PlanValidationResult`:

- `{ ok: true, plan: PlanContent }` — документ прошёл все проверки;
- `{ ok: false, issues: PlanIssue[] }` — `PlanIssue { code, path, message }`, коды: `invalid-structure`, `invalid-date`, `invalid-weekday`, `invalid-lag`, `duplicate-id`, `unknown-reference`, `circular-group`, `inverted-interval`, `empty-calendar`.

Отличие от `parseChecklistContent` (молча заменяет на пустой список) осознанное: DoD требует «повреждённые данные не становятся рабочим документом без диагностики»; план — дорогое в восстановлении содержание, молчаливая подмена недопустима. Потребители (заглушка, будущие представления) получают вариант с ошибкой и показывают диагностику. Проверки: структура и типы; форматы дат; weekday 1–7; целостность ссылок (groupId/assigneeIds/workTypeIds/зависимости/resourceId/parentId); уникальность id внутри коллекций; отсутствие циклов групп; `end ≥ start`; календарь без единого рабочего дня отклоняется (консистентно с `createWorkingCalendar`).

### D3. Фабрика пустого плана

`createPlanContent(title?): PlanContent` — календарь пн–пт (1–5), пустые коллекции, `crypto.randomUUID()` для генерируемых id (как в чек-листе). В `documentSupport.createContent` передаётся название каталога. `schemaVersion: 1` живёт в оболочке документа (как у чек-листа); дубль в контенте не нужен — миграции (PBT-026) читают оболочку.

### D4. Регистрация модуля и временная заглушка

`createGanttModule(): { widgetTypes: [...] }` по образцу `createChecklistModule()`:

- тип: id `plan`, title «План», `documentSupport: { moduleId: 'gantt', documentType: 'plan', schemaVersion: 1, createContent }`;
- component — `PlanPlaceholderWidget`: показывает название документа из контента и состояние «представление Гантта готовится (PBT-037)», при `parse` с ошибками — список диагностики. Заглушка осознанная: даёт каталогу тип и проверяет сквозной путь документ↔SDK без преждевременного UI; заменяется в PBT-037;
- `sizeConstraints: { minWidth: 3, minHeight: 3 }` (стартовые значения, уточнятся представлениями).

### D5. Подключение в комплектацию

`apps/project-board/src/widgets.ts`: `[...createChecklistModule().widgetTypes, ...createGanttModule().widgetTypes]`. Никакого кода платформы не меняем: создание, автосохранение, восстановление, подписки — готовые сервисы PBT-007/009/010. Сквозная проверка DoD — e2e: создать «План» через каталог → перезагрузка → документ восстановился → открыть второй экземпляр того же плана.

### D6. Границы зависимостей

`packages/gantt` не импортирует SVAR/RCT/dayjs (ADR-3 PBT-017, DoD-5) — только `widget-sdk` + react для заглушки (по образцу checklist). Арифметика PBT-013 остаётся отдельным модулем; валидатор не строит `createWorkingCalendar`, лишь сверяет правила данных. Экспорт `packages/gantt/src/index.ts` дополняется моделью и модулем (сейчас экспортируются только константы).

### D7. Обобщение рендера панелей приложения (найдено при реализации)

Вертикальный срез PBT-011 рендерил **все** панели как ChecklistWidget: `PaneInstance` не хранил тип, а выбор компонента был жёстким. DoD «план открывается в зарегистрированном виджете» без этого невыполним (план открывался как чек-лист). Правка приложения: `PaneInstance` хранит `typeId`; рендер берёт компонент из реестра (`lookup.component` c WidgetProps), для незарегистрированного типа — `UnknownWidgetType`. Платформа и SDK не затронуты; существующие e2e чек-листа проходят без изменений. Попутно исправлены два флаки-теста `shell.spec.ts` (strict-mode violation: текст документа искался глобально, хотя он виден в двух экземплярах одного документа; воспроизводилось на чистом `develop` до изменений).

## Risks / Trade-offs

- **Embedded `assigneeIds` vs таблица назначений:** при будущих требованиях (частичная загрузка, интервалы назначения) потребуется миграция v2 — принято сознательно, первая версия правила конфликтов не использует проценты (D3 ADR PBT-003).
- **Заглушка в каталоге:** пользователь может создать план, не увидев ничего, кроме названия — приемлемо на стадии ядра, помечено текстом заглушки со ссылкой на задачу.
- **Строгий валидатор может отвергнуть будущие легитимные варианты** (например, перевёрнутый интервал): обработаются при реальных сценариях PBT-031+ как расширение правил, не слом — `ok: false` с явным кодом вместо падения.
- **Фикстуры-формат остаётся тестовым:** совпадение по смыслу, но не гарантия идентичности; продуктовый импорт `.gantt` (PBT-052) пишет в продуктовый формат.
