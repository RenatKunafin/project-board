## Context

Карточка PBT-084 (.context/tasks/PBT-084.md) и раздел 6 «P2 — цвет задачи как данные плана» обновлённого прототипа (MVP-DESIGN-TASKS.md, 2026-10-26) с готовой реализацией референса: `src/lib/task-colors.ts` (палитра, проверка, генерация правил), `TaskColorPicker.tsx` (кружки и портальное меню), применение в `SvarGanttChart.tsx` / `ResourceTimelineChart.tsx` / `DemoTaskForm.tsx`.

Текущее состояние репозитория:

- `PlanTask` (`plan-document.ts`) не имеет цвета; опциональные поля валидируются отдельно (образец «как для каталогов» — assigneeIds/workTypeIds с проверкой ссылок).
- Проектный вид — SVAR Gantt 2.8.0 (ADR-1 PBT-017): полоса `.wx-bar.wx-task` красится публичными CSS-переменными `--wx-gantt-task-color/-fill-color/-border-color`, у полосы атрибут `data-task-id`; `taskTemplate` замещает стандартный рендер — не используется.
- Ресурсный вид — React Calendar Timeline 0.30.0-beta.19 (ADR-2 PBT-017): адаптер красит элементы инлайн-стилями, конфликт имеет собственную подсветку (`rtl-item--conflict`).
- PlantUML (`plantuml-export.ts`): окраска `[alias] is colored in Color/Color`, именованные цвета этапов по маркерам названия (техдолг с TODO); целевой рендер 1.2026.9beta4 поддерживает hex `#rrggbb`.
- OnlineGantt `.gantt`: цвет сейчас перечисляется в отчёте непереносимого.
- Семантика дат/жесты — ADR PBT-003/PBT-017: не меняются.

## Goals / Non-Goals

Goals: ручной цвет задачи как данные плана (идентификатор конечной палитры), «Авто» как отсутствие значения; выбор в общей форме и быстрая смена правым кликом в обоих видах; отображение генерируемыми CSS-правилами; сохранение командами, в round-trip и экспорте PlantUML; конфликт/отпуск — собственные маркеры.

Non-Goals: hex в документе и произвольный picker, цвет групп, цвет по типу работы, влияние на семантику и жесты, смена версии схемы.

## Decisions

### D1. Палитра референса: десять идентификаторов + «Авто» (переносится как есть)

Состав и порядок — из `src/lib/task-colors.ts` референса: sapphire `#3186E9` (Сапфир), turquoise `#1DBCB5` (Бирюза), jade `#2FC183` (Нефрит), lime `#BEBF28` (Лайм), ochre `#EAB532` (Охра), pumpkin `#F3821D` (Тыква), coral `#F05653` (Коралл), rose `#E266A7` (Роза), plum `#9F5DCB` (Слива), steel `#8B9AAB` (Сталь). Ровно десять значений плюс «Авто»; имена/порядок — предмет решения MVP (изменение состава — без смены схемы, но с расширением списка и валидации). Hex-значения палитры известны генератору PlantUML — экспорт пишет hex (D6), что и даёт требуемую владельцем совместимость с PlantUML.

### D2. Значение в документе: идентификатор палитры, валидация известности (по прототипу)

`PlanTask.color?: string` — id из палитры; отсутствие поля — «Авто» (accent темы). Валидация при чтении — как для каталогов: неизвестное значение отклоняется с диагностикой `invalid-structure` (место+причина), без молчаливого сброса. Hex и CSS-строки в документе запрещены (не формат данных). Схема v1 и формат файла v1 не меняются: поле опциональное, старые документы читаются без изменений. Отличие от ранее предложенного hex-подхода: модель конечна и самодостаточна — неизвестное значение не «отображается как есть», а диагностируется (решение прототипа, принято владельцем 2026-10-26).

### D3. Отображение: генерируемые CSS-правила по идентификатору задачи (механизм референса, уточнён живым осмотром)

Единая функция в духе `barColorRules(attr, tasks, declarations)`: только задачи с валидным `color` И идентификатором, безопасным для селектора (`/^[A-Za-z0-9_-]+$/`), получают правило `[attr="…id…"]{…}`; остальные — «Авто». Пользовательский CSS в библиотеку не передаётся.

- Проектный вид (SVAR): атрибут `data-task-id` с префиксом `:` (контракт 2.8.0); фон — `color-mix(in oklch, HEX 80%, #000)`, заливка прогресса и рамка — полный HEX. Уточнение по живому осмотру владельца 2026-10-26: mix референса с поверхностью темы (45% + `--surface` с hue 250°) искажал оттенок тёплых цветов в oklch — «Тыква» становилась фиолетовой; mix с чёрным сохраняет оттенок и спокойную глубину тёмной темы. Жесты, выделение, hover, связи — штатные (рендер не трогаем, ADR-2 PBT-017).
- Ресурсный вид (RCT): инлайн-стиль элемента дорожки с тем же затемнением фона и рамкой HEX; конфликт сохраняет собственную подсветку и приоритет; отпуска без изменений.

Правила мемоизируются по набору задач с цветом и вычисляются от **актуального** плана, минуя стабилизацию props SVAR (ownWrite): обновление `<style>` не перезаливает стор.

### D4. Приоритеты маркеров

Конфликт и отпуск — собственные маркеры: цвет задачи не означает проблему. Ресурсный вид: конфликт > ручной цвет > «Авто». Проектный вид: ручной цвет > «Авто»; сводные полосы групп не окрашиваются. Выделение/фокус/стрелки остаются читаемыми (рамка/эффекты библиотек сохраняются).

### D5. Импорт: несовпавший цвет — «Авто» (решение владельца 2026-10-26)

При любом импорте внешнего файла цвет устанавливается в «Авто», если нет совпадения со значениями палитры — ни по hex, ни по идентификатору:

- OnlineGantt `.gantt`: hex-цвет записи после нормализации регистра точно совпадает со значением палитры → соответствующий идентификатор; иначе — «Авто» (поле цвета отсутствует), остальное содержание импортируется. Отчёт непереносимого для прогресса и признака длительности сохраняется; цвет в отчёт не входит — его судьба задана правилом «Авто».
- Собственный формат: неизвестный идентификатор цвета нормализуется в «Авто» на шаге разбора, до полной валидации содержимого; остальные проверки без смягчения (повреждённые даты/ссылки по-прежнему отклоняют файл целиком).

Отличие от референса («неизвестный цвет отклоняется при импорте») — решение владельца: нормализация вместо отклонения, чтобы цвет не блокировал импорт остального содержания. Открытие документов каталога с неизвестным цветом — по-прежнему строгая диагностика (D2): прощающая нормализация действует только на пути импорта файлов.

### D6. PlantUML: hex палитры, приоритет над этапами

Задача с цветом экспортируется `[alias] is colored in #rrggbb/#rrggbb`, где hex — значение палитры для её id; задачи без цвета — прежняя эвристика маркеров (TODO остаётся); легенда-комментарий этапов не меняется. Hex — родная форма целевого рендера PlantUML 1.2026.9beta4; фактический рендер контрольного файла — обязательная проверка (офлайн, у владельца; результат фиксируется в PR).

### D7. Схема и формат файла не меняются

`PLAN_SCHEMA_VERSION = 1`, `PLAN_FILE_FORMAT_VERSION = 1`; поле опциональное, round-trip дополнительных полей уже сохраняет содержимое. Миграция не нужна.

### D8. Форма задачи и быстрая смена (по референсу)

Форма (общий черновик PBT-087): fieldset «Цвет» с легендой — кнопка «Авто» (accent темы) и десять кружков (`aria-pressed`, выбран — галочка и обводка, доступные подписи). Мини-превью полосы из референса исключено по решению владельца 2026-10-26: выбранная задача сразу видна в диаграммах за формой. Изменение цвета — в общем черновике: единая операция документа, даты не меняются.

Быстрая смена: правый клик на полосе задачи в проектном и ресурсном видах → портальное меню (role=dialog) с теми же кружками; вне окна, поверх слоёв; закрытие Escape и кликом вне; координаты ограничены viewport. В проектном виде выбор — собственная запись документа с пометкой ревизии (механизм ownWrite жестов, D7 PBT-039): чарт не пересобирается, позиция прокрутки и свёрнутость групп сохраняются (устранение дефектов живого осмотра 2026-10-26 №2–3); полоса перекрашивается мгновенно реактивным `<style>`. Открытые представления того же плана обновляются подпиской. Правый клик по группе/пустому месту меню не открывает. Оговорка владельца 2026-10-26: при непредвиденной сложности реализации (например, бета RCT не даст корректное событие правого клика на элементе) быстрая смена выносится в отдельную задачу, а не форсируется в этом change.

## Risks / Trade-offs

- Атрибут `data-task-id`, переменные `--wx-gantt-task-*` и `--resource-color` — контракт на стыке CSS библиотек: пины версий уже зафиксированы (ADR-1/2 PBT-017); проверка цвета входит в объём возможного обновления.
- Объём PR на верхней границе ориентира 100–400 строк содержательного кода (палитра, форма, меню, два вида, переносы) — при превышении обсудить вынесение быстрой смены отдельно до реализации.
- color-mix(oklch) требует целевые браузеры проекта — уже используется в `gantt.css`, нового риска нет.

## Migration Plan

Не требуется (D7).

## Test Strategy

Unit: палитра (список, уникальность id/hex); валидация color (известный/неизвестный/отсутствие); команды и форма сохраняют цвет (изменение полей/дат/перенос/длительность/группа/создание с предшественниками), сброс — undefined; генерация правил (безопасный/небезопасный id, отсутствие правила для «Авто»); PlantUML (hex палитры, приоритет над этапом); round-trip идентификатора; OnlineGantt (совпадение → id, несовпадение → отчёт). E2E (production preview): выбор/сброс в форме; быстрая смена правым кликом в обоих видах; оба вида одного плана; независимые планы; жесты/изменения не сбрасывают цвет; reload и холодный офлайн; документ без цвета — «Авто»; файловый round-trip; предпросмотр PlantUML с hex; конфликтная полоса читается как конфликт. По прототипу: реальный сценарий на импортированном пользовательском плане, скриншоты 1024×778 и 1856×1269, сохранение геометрии/состояния окон, без подмены данных пользователя демо. Обязательный набор: lint/typecheck/unit/build/browser, verify:repository, openspec strict.
