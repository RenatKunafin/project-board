## Context

Сейчас приложение не содержит аналитического кода. Оно собирается локально, для обычной production-сборки и отдельно для GitHub Pages через `npm run build:pages`; service worker и PWA-подпуть должны продолжать работать без внешнего аналитического сервиса.

## Goals / Non-Goals

**Goals:**

- подключить счётчик `113967203` только в проверяемом Pages release;
- включить предоставленную владельцем конфигурацию Вебвизора временно, но вынести переключение в build-time флаг;
- не передавать в `dataLayer` данные приложения и не вводить цели/события;
- обеспечить безопасный no-op при ошибке загрузки внешнего скрипта;
- проверить сетевые запросы, SPA-поведение, PWA/offline и отсутствие дублей.

**Non-Goals:**

- аналитика действий внутри документов, названий задач, заметок, календарей и поисковых строк;
- формы, пользовательские цели, ecommerce-события и пользовательские идентификаторы;
- серверная аналитика или изменение IndexedDB/SDK-контрактов;
- постоянное включение Вебвизора: после текущего этапа он отключается тем же флагом.

## Decisions

1. **Release-only build-флаг.** Публикационный workflow передаёт `VITE_YANDEX_METRIKA_ENABLED=true`; обычный build, dev, preview и CI browser-сборки флаг не получают. Это надёжнее проверки только `import.meta.env.PROD`, потому что локальный preview тоже является production-сборкой.
2. **Идемпотентный загрузчик в composition root.** Скрипт добавляется один раз после старта приложения; повторный mount React StrictMode, service worker и восстановление workspace не должны создавать второй тег или второй initial hit.
3. **Параметры берутся из предоставленного кода, без `dataLayer`-пушей.** Сохраняются `webvisor`, `clickmap`, `trackLinks`, `ecommerce: "dataLayer"`, `referrer`, `url`, `accurateTrackBounce` и `ssr`; приложение не создаёт ecommerce-объекты. Вебвизор временный и отключается сменой release-флага/параметра перед следующим релизом.
4. **URL нормализуется.** В Метрику передаётся публичный origin + pathname/base без query/hash, чтобы случайные параметры не стали источником утечки. Навигационных страниц в SPA не вводим.
5. **Отсутствие consent UI в этом PR.** Владелец отвечает за опубликованное уведомление/политику обработки данных; PR фиксирует это как release checklist. Добавление интерактивного баннера согласия — отдельный scope, если он потребуется.

## Risks / Trade-offs

- [Вебвизор может записывать отображённый HTML и действия] → временное включение явно зафиксировано; перед следующим release-флагом выставляется false, а PR не добавляет цели или dataLayer-события.
- [Внешний скрипт блокируется] → загрузчик не бросает исключения и не участвует в bootstrap приложения; локальные данные сохраняются независимо.
- [Дубли из-за SPA/StrictMode] → глобальный guard по counter id и browser-тест с повторным монтированием/переключением интерфейса.
- [Запросы в тестах] → флаг отсутствует во всех CI/local build-командах, а e2e проверяет отсутствие `mc.yandex.ru`.
- [Правовая/организационная настройка] → перед публикацией владелец проверяет уведомление и настройки счётчика; в PR отделяются локальные проверки от post-release визита.

## Migration Plan

1. Добавить загрузчик и тесты на feature-ветке.
2. Включить `VITE_YANDEX_METRIKA_ENABLED=true` только в шаге Pages release.
3. После публикации проверить один network hit и тестовый визит в счётчике.
4. Для отключения Вебвизора выставить release-флаг false или изменить параметр в одном конфигурационном месте, пересобрать и опубликовать новую версию.
