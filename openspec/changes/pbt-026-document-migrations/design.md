# Design — PBT-026: версии БД и миграции документов

## Context

Два уровня версий согласованы (решения §15.5): версия схемы БД (Dexie-хранилища) мигрирует силами адаптера (PBT-024, spec «Расширение схемы сохраняет документы»), а `schemaVersion` содержимого — зона модуля-владельца; механизма нет. `restoreAll()` — единственная точка массового чтения хранилища. Guard «БД более новой версии» существует (`schema-version-unsupported`), но документы с будущим `schemaVersion` сегодня восстанавливаются и перезаписываются. Сервис документов не знает реестра виджетов (ADR-3) — прецедент встраивания на границе приложения: ленивое дополнение названия (PBT-025 D2, в `main.tsx`).

## Goals / Non-Goals

**Goals:** контракт миграций в SDK; пакетное преобразование при восстановлении одной транзакцией; однократность; `schemaVersion` ≠ `revision`; guard будущих версий (чтение без записи); диагностика сбоев без прерывания восстановления.

**Non-Goals:** миграции структуры БД, откаты версий, миграции по требованию, перенос ленивого дополнения названий в миграции (компромисс PBT-025 остаётся).

## Decisions

### D1. Контракт миграций в SDK, инъекция через фабрику сервиса

`DocumentMigration { from, to, migrate(content) }` — чистая функция, сбой — исключение. `WidgetDocumentSupport` дополняется опциональным `migrations`; актуальная версия — существующее `schemaVersion` дескриптора. Приложение (composition root) собирает поддержку `DocumentMigrationsSupport { moduleId, documentType, actualVersion, steps }` из определений виджетов и передаёт в `createDocumentService({ ..., migrations })` — сервис остаётся независимым от реестра (ADR-3, как `store`). Альтернатива «сервис читает реестр» отклонена: цикл зависимостей и нарушение границы.

### D2. Восстановление: классификация → цепочки → одна транзакция

`restoreAll()`: (1) `store.listAll()`; (2) каждый документ классифицируется по зарегистрированной поддержке: `actual` (пропуск), `outdated` (версия < актуальной — строится цепочка шагов `from → to`, разрыв цепочки = проблема, документ нетронут), `future` (версия > актуальной — read-only, D3), `unknown` (модуль/тип не зарегистрированы — не трогается, ограничение D4); (3) успешные цепочки применяются в памяти (новый объект с `schemaVersion: actual`, `revision` без изменений); (4) фиксация — новый `DocumentStoreLike.saveAll(entries)` одной транзакцией адаптера (Dexie `db.transaction('rw', documents, ...)`), `expectedStoredRevision` = хранимая редакция. Сбой `saveAll` → хранилище целиком в исходном состоянии. Сбой функции шага → документ исключается из фиксации, проблема остаётся, восстановление продолжается. Проблемы — `listRecoveryIssues(): DocumentRecoveryIssue[]` (`documentId`, модуль, тип, версии, причина) для приложения/каталога.

### D3. Guard будущих версий в операциях записи

`update`, `rename`, `delete` первыми проверяют зарегистрированную поддержку документа: если `schemaVersion` документа больше актуальной — `DocumentFutureVersionError` (новый класс SDK с фактической и актуальной версиями). Удаление блокируется наравне с записью: уничтожение данных, написанных более новым приложением, недопустимо (spec «Откат приложения сохраняет данные»). Чтение, подписка, отображение — разрешены. Для модулей без зарегистрированной поддержки guard не работает — такие документы сегодня и не редактируются полноценно; ограничение принимается.

### D4. Каталог: будущая версия видима и помечена

Строка документа с бейджем «Версия N — новее поддерживаемой»; кнопки записи (переименовать, удалить) не отображаются, открытие в виджете работает (чтение разрешено spec'ом; содержимое интерпретирует модуль — план покажет диагностику, чек-лист — пустой список). Проблемы миграций (разрыв цепочки, сбой шага) в UI первой версии не отображаются — API `listRecoveryIssues` доступен приложению (spec требует «доступна приложению», не каталогу).

### D5. Однократность и разделение `schemaVersion`/`revision`

После фиксации документ имеет `schemaVersion = actual` и при следующем `restoreAll` классифицируется `actual` — функции миграций не вызываются (тест — spy). `revision` миграцией не меняется: это номер пользовательской редакции данных, а миграция меняет формат представления — автосохранение после миграции не запускается (очередь не наполняется), `updatedAt` сохраняется.

### D6. Продуктовых миграций пока нет — фикстуры в интеграционных тестах

Все модули на версии 1: регистрируются пустые списки миграций (контракт включён, поведение — нулевое). Реальные цепочки и сбой проверяются тестовым модулем с фактическими структурами (v0: пункты без признака → v1: с `done` → v2: с меткой времени) на `fake-indexeddb`: старая фикстура → миграция → повторное открытие; сбой шага (бросающая функция на реальной структуре); будущая версия (запись с `schemaVersion: 99` в БД до старта) — по DoD без mock-only.

### D7. Попутный фикс: названия срез-документов по отсортированной позиции

E2E вскрыл нестабильность из PBT-011 D7: `ensureTwoChecklists` создавал оба документа в одну миллисекунду (совпадающие `createdAt`), названия присваивались по порядку создания, а возвращал — отсортированный порядок только при повторных запусках; при «перевороте» UUID после перезагрузки панели получали другие документы. Теперь недостающие документы создаются с временным названием, затем переименовываются по финальной отсортированной позиции («Список 1»/«Список 2»), и возвращаются `[sorted[0].id, sorted[1].id]` — соответствие «позиция ⇔ название» одинаково при каждом старте.

## Risks / Trade-offs

- **`saveAll` в обязательном контракте хранилища**: вторая реализация (`FakeStore`) обязана её реализовать; контракта немного, а атомарность без него недостижима. Обратная совместимость — новые методы контракта без дефолтов в частном пакете приемлемы.
- **Guard только для зарегистрированных модулей**: документы неизвестных модулей не защищены от записи; в текущей комплектации таких нет, риск отложен до появления внешних модулей (PBT-060 зафиксирует).
- **Миграции выполняются до поднятия UI**: длительность миграций при старте; объёмы — десятки документов, функции дешёвые; при сотнях — пересмотреть (порог PBT-058 не затрагивает).
- **`revision` не поднимается миграцией**: два документа после миграции и без неё неотличимы по `revision` — это и требуется (формат ≠ редакция); конфликтные сценарии не задействуют `schemaVersion`.
