# Design — PBT-055 Генератор PlantUML

## Context

Два источника требований к виду: **целевой пример владельца** `.context/examples/plant-uml-example.plantuml` («хочу таким же», 2026-10-16) и **референс-гайд** `.context/examples/SKILL (1).md` (приёмы формата: алиасы `as`, `requires/starts`, `is open`, `language ru`, цвет дня/диапазона, предупреждение о немоделируемости ресурсов). Живой спайк на официальном рендер-сервере (GET `/plantuml/svg/~0<deflate+base64u>`, версия **1.2026.9beta4** — закреплена как целевая) подтвердил: `Project starts` обязательна; `ends` включительный; `requires N days` считает незакрытые дни от старта (23.07 + 5 р.д. → 29.07, семантика A4 совпадает); кириллица/«»/— ок; **`[A] -> [B] : +N` — Syntax Error**; **`[`/`]` в названии ломают синтаксис**; `is colored in X/X`, `D is closed`, `D is open`, `D1 to D2 are colored in` работают.

## Goals / Non-Goals

Goals: генерация в стиле целевого примера (алиасы, requires+starts, палитра этапов, отпуска разделом, серые выходные, language ru, printscale); DoD покрыт unit-эталонами и рендер-сверкой.

Non-Goals (сверх proposal): вехи/выделенные даты; `on {Ресурс}`; caption-легенда; настройки профиля.

## Decisions

### D1. Контракт

```ts
serializePlanToPlantUml(plan: PlanContent): {
  readonly text: string;
  readonly report: readonly PlantUmlExportNote[];
}
interface PlantUmlExportNote { readonly topic: string; readonly message: string; }
```

Чистая, детерминированная. Пустой план (нет задач и отпусков): минимальная диаграмма c `Project starts` от первой даты праздника; если и календарь пуст по датам — якорь `2000/01/01` + заметка `empty-plan` (детерминизм важнее красоты пустой диаграммы).

### D2. Структура текста (по целевому примеру)

```
@startgantt
title <title плана | «План»>
language ru

Project starts <min(start задач, start отпусков) — YYYY/MM/DD>

saturday are closed            ← все дни недели вне workingDays
2026/11/04 is closed           ← праздники
2026/10/17 is open             ← рабочие исключения (переносимо!)

' ==== Цветовая схема по этапам ====   (комментарий-шапка палитры, как в примере)

-- <Группа (полный путь через « / »)> --
[<Название>] as [T15] requires <N> days
[T15] is colored in <Цвет>/<Цвет>
[T15] starts 2026/07/23

-- Отпуска --                  ← при наличии
[Отпуск: <Ресурс>] as [U3] requires <N> days
[U3] is colored in DarkGreen/DarkGreen
[U3] starts 2026/09/21

[T15] -> [T18]                 ← FS-связи по алиасам, после всех задач

' ==== Выходные — серые ====    (как в примере: заливка поверх closed)
2026/07/11 to 2026/07/12 are colored in lightgray
                               ← диапазоны сб-вс (и иных нерабочих дней недели)
                                 между min и max датой плана

printscale daily zoom 1
@enduml
```

- **Алиасы:** задачи `T<номер по порядку в документе>` (стабильно: порядок `plan.tasks`), отпуска `U<номер>`. Связи — только по алиасам: дубли названий безопасны (спека «Кодирование»). Человекочитаемое имя — в основной подписи, как в примере владельца; исполнители в подпись не добавляются (решение владельца 2026-10-16: строго как в целевом примере).
- **Длительность:** `requires N days`, N = `workingDaysBetween(start, end)` ядра (включительно) — рендер воспроизведёт даты при рабочих краях. **N = 0** (A6: интервал без рабочих дней) → задача выводится **вехей** `[Название] as [T7] happens 2026/07/18` (+ цвет этапа) — решение владельца 2026-10-16; валидность `happens` подтверждена референс-гайдом и проверяется рендер-сверкой. **Края полосы на нерабочих днях** (A3: ручной ввод в выходной): полоса рендера может лечь иначе → заметка отчёта `non-working-edge` по каждой такой задаче (даты всё равно выводим).
- **Горизонт H = [min(start задач, отпусков), max(end задач, отпусков)].** Праздники и рабочие исключения выводятся только внутри H (решение владельца 2026-10-16: меньше шума вне шкалы); выходные-заливка — по H (диапазоны сб–вс и иных нерабочих дней недели, склеенные по соседству, как в примере).
- **Пустые группы** — выводятся разделителем (структура плана видна; решение владельца 2026-10-16).
- **Связи:** `->` по алиасам; лаг ≠ 0 — заметка `lag`. `starts at` не используем: рендер пересчитал бы старт, а у нас ручной план с фактами (скилл-референс применяет `starts at` для моделирования занятости — это не наш случай).
- **Отпуска:** длительность аналогично (рабочие дни периода); старт на нерабочем — заметка.
- **Выходные lightgray:** перечисление диапазонов нерабочих дней недели (по умолчанию сб+вс, из календаря) между min/max датой плана включительно (до +1 месяца запаса не добавляем — горизонт плана). Диапазоны склеиваем по соседству (сб+вс одним диапазоном, как в примере).

### D3. Палитра этапов (константы из целевого примера)

Маркер (вхождение подстроки в название, регистронезависимо) → цвет: `АНЛ`→`LightSkyBlue`, `DEV`→`MediumPurple`, `ИФТ`→`Orange`, `ПСИ`→`Tomato`, `ТРЖ`→`LightGreen`; отпуск (периоды недоступности) → `DarkGreen`. Задача без маркера — без строки цвета (дефолт рендера). Комментарий-шапка со схемой — как в примере. Маркеры — консервативная эвристика владельца из его данных; замена/расширение палитры — правка констант этого модуля.

### D4. Кодирование названий

`[`→`(`, `]`→`)`, `:`→`—` (не ломает метки), `\r\n\t`→пробел; кириллица/«»/— как есть. Подпись отпуска: `Отпуск: <Ресурс>` (даты в названии не дублируем — они на шкале; в примере владелец вписывал месяц руками для различия дублей — у нас алиасы различают задачи, но подписи одинаковых отпусков одного ресурса останутся равными; допустимо, различие дат видно на шкале).

### D5. Отчёт

Пункты (только при наличии данных): `lag`, `summary-bar` (сводная полоса групп), `work-types`, `unit`, `conflicts`, `non-working-edge`, `empty-plan`. workingExceptions из отчёта исключены — переносятся `is open` (D2).

### D6. Тесты и рендер-верификация

- Unit `plantuml-export.test.ts`: эталон текста контрольного плана (с группами, связями с лагом, праздником, исключением, отпуском, маркерами этапов); кириллица/скобки; дубли названий + связи по алиасам; пустой план; выходные-диапазоны (в т.ч. граница min/max); детерминированность (двойной вызов).
- Рендер-верификация (DoD-5): контрольный текст — живой прогон на закреплённой версии (метод спайка), 200/без Syntax Error, даты и подписи в SVG; скриншот в `change/screenshots/`. В CI — только текстовые эталоны.
- Расположение: `packages/gantt/src/plantuml-export.ts`, экспорт из `index.ts`; зависимостей нет.

## Risks / Trade-offs

- **[Парные теги обязательны — найдено рендер-верификацией]** `@startgantt … @enduml` (смешанная пара — как в примере владельца `plant-uml-example.plantuml`, строка 280) стабильно валит рендер-сервер 500 без синтаксической диагностики; парный `@endgantt` рендерится. Генератор выдаёт только парные теги; замечание о примере владельца передано (файл стоит поправить у источника).
- [`requires` на старте/фине в нерабочий день даёт иную полосу] → заметка `non-working-edge`; точность приоритетна только для валидных по календарю планов (правило A3 — ручной ввод сохраняется, диаграмма — публикация).
- [Палитра по маркерам названия — эвристика] → палитра владельца из его данных; маркеры и цвета — константы модуля, замена без изменений контракта.
- [Диапазоны выходных раздувают текст на длинном горизонте] → горизонтом берём min/max плана (не год), диапазоны склеиваем; для плана-500 строк ~100 — приемлемо (пример владельца: 25 строк на полгода).
- [Целевая версия меняет синтаксис] → закреплена 1.2026.9beta4; при обновлении — повторный спайк.
- [Рендер-сервер нестабилен эпизодами (500 на всё)] → верификация повторами; артефакт карточки — PNG рендера `screenshots/reference-render.png` (эталон OnlineGantt: 47 задач, 3038×972, русская шкала).
