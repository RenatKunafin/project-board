Референс: `flexi-dashboard-hub/src/components/dashboard/GanttPrototype.tsx` (строки 55–58 — строка 2 тулбара), `WidgetFrame.tsx` (уголок ресайза), скриншоты `screenshots/redesign-ref/01`, `10`, `12-cascade-mode.png`. ## D2. Недельная семантика зума «Дни/Недели»

### D2.1 Механика шкалы (исследование дистрибутива)

- `IScaleConfig.unit` принимает `'week'` (`TLengthUnit` в gantt-store: minute…year). Дефолтный формат week-юнита — `«Week %w»` — переопределяется функцией.
- `IScaleConfig.format` — `(date: Date, next?: Date) => string`: `next` — начало следующей клетки. Подпись-диапазон «12–18 окт» строится по границам самой клетки (`next − 1 день` = последний день недели) — корректна при любом начале недели.
- Позиции полос остаются дневной точности: стор хранит `lengthUnitWidth` в днях (`cellWidth / дней_в_клетке`), `$x/$w` задач считаются от дат в днях — week-клетки не квантуют полосы по неделям (сверено по `resetScales`/`prepareTask` в gantt-store).
- **`highlightTime` для week-клеток не срабатывает**: в react-gantt сторож `if (C.unit !== "day" && C.unit !== "hour") return ""` — заливка нерабочих дней пропадёт. Текущая подсветка (`gantt-weekend`/`gantt-holiday` через `highlightTime`, PBT-073 D2) работает только по day-клеткам.

### D2.2 Конфигурация режимов

- **«Дни»**: `scales = [{unit:'month', format: «октябрь 2026 г.»}, {unit:'day', format: дд.мм}]`, `cellWidth = 48` (без изменений). Подсветка — текущий `highlightTime`.
- **«Недели»**: `scales = [{unit:'month', ...}, {unit:'week', step: 1, format: диапазон}]`, `cellWidth = WEEK_CELL_WIDTH = 112` — живая сверка (задача 1.2): ровно 16px/день, самая длинная подпись «28 сент – 4 окт» = 111px текста в клетке 112px — помещается; в окно чарта 1200px (широкий экран, таблица 712px) помещается ~10 недель ≈ 2.5 месяца. Месяц над недельными колонками рисуется SVAR автоматически, квантуясь по границам недель (500px = 5 недель — наблюдение).
- Форматтер диапазона — чистая функция в `zoom-utils.ts` (`formatWeekRangeLabel(start, next)`): «12–18 окт» в пределах месяца; «28 окт – 3 ноя» на стыке; «29 дек – 4 янв» на стыке годов; month short ru-RU, день без ведущего нуля. `next === undefined` (последняя клетка) — `next = start + 6 дней` (защита, по датам клетки). Unit-тесты табличные.
- `ZOOM_CELL_WIDTH` заменяется таблицей `ZOOM_SCALE = { days: {cellWidth:48}, weeks: {cellWidth:WEEK_CELL_WIDTH} }` + функция `zoomPxPerDay(zoom)` (days → 48; weeks → WEEK_CELL_WIDTH/7). Все потребители `ZOOM_CELL_WIDTH` (проп `cellWidth` чарта, `convertZoomScrollLeft`) переводятся на px/день.

### D2.3 Подсветка нерабочих дней в недельном режиме (собственный слой)

`highlightTime` непригоден (D2.1) — в режиме «Недели» рисуем слой сами (прецедент: слой нерабочих дней ресурсного вида, PBT-047/074):

- Абсолютный слой над областью чарта: `pointer-events: none` (жесты SVAR не затрагивает), `transform: translateX(-scrollLeft_трекаемый)` — трекинг прокрутки уже есть (PBT-073 D6: пассивный слушатель `.wx-chart`). Высота = высота чарта, ширина = полная ширина шкалы.
- Полосы слоя: один блок на подряд идущие нерабочие дни (выходные схлопываются в 2-дневные блоки, праздники — одиночные;_merge праздник+выходные подряд — по цвету праздника, различимость сохраняется). `left/width` — из px/день от даты начала шкалы; цветовые токены существующие `--color-gantt-weekend`/`--color-gantt-holiday`.
- **Привязка дня к x**: смещение первого дня шкалы. SVAR снапает `start` к началу недели (`getUnitStart`) — источник `_weekStart` — локаль i18n (дефолт прослеживается до date-fns `weekStartsOn`, по умолчанию 0 = воскресенье). Не угадываем: **нулевая дата слоя берётся из фактических клеток шкалы** — `api.getState()._scales.rows[последняя].cells[0].date` (контракт IApi подтверждён типами gantt-store), fallback — дата первой полосы задачи минус смещение до понедельника. Проверяется живой проверкой (computed left полосы задачи vs слой).
- **Риск «начало недели» (Пн vs Вс) — ЗАКРЫТ живой проверкой (2026-10-21)**: дефолт SVAR действительно Вс-старт (наблюдение «4–10 окт» = Вс–Сб, `_weekStart: 0` в сторе). Проверены пути: проп `_weekStart` — игнорируется (init-объект Gantt жёстко берёт локаль: `_weekStart: ze.weekStart` из `useContext(context.i18n)`); проп `i18n` — принимает React Context, не локаль. **Рабочее решение — Provider того же контекста**: `context.i18n` (runtime-экспорт `@svar-ui/react-core` 2.6.1, в типах отсутствует — изолированный адаптер `svar-locale.ts` с минимальным контрактом и деградацией на null), значение — `locale({ calendar: { weekStart: 1 } })`; кастомные значения побеждают дефолты (`extend(defaults, optional=true)` — семантика проверена вживую). Результат: недели Пн–Вс («28 сент – 4 окт», `_weekStart: 1`), зависимость `@svar-ui/react-core@2.6.1` добавлена в packages/gantt (точный пин, правило изоляции). Запасной `registerScaleUnit` не понадобился.
- **Слой подсветки — реализация упрощена против плана**: слой `.wx-gantt-holidays` существует и в week-режиме (пустой) и живёт внутри скролл-контента `.wx-area` — полосы инжектятся прямо в него (эффект в виджете, deps: зум/источник/диапазон), позиция и прокрутка наследуются, CSS-классы `gantt-weekend`/`gantt-holiday` уже оформлены (PBT-037/053). Никакого transform-трекинга не нужно. Блоки — подряд идущие дни одного вида (выходные парами 32px, праздник 16px — различимость сохранена); x/ширина из `scales.start` + `lengthUnitWidth` (16px/день), сверено с позициями полос задач (1056 = 66×16 ✓).
- Z-index слоя — под полосами задач (сверка computed вживую; при необходимости `z-index: 0` и поднятие слоя `.wx-gantt-holidays`-аналога не требуется — полосы SVAR рисуются выше фоновых слоёв шкалы).

### D2.4 Прокрутка и состояние

- Конверсия прокрутки при смене режима: `daysFloat = left / pxPerDay(from)` → `left' = daysFloat * pxPerDay(to)` — та же схема D6.5 PBT-073, база меняется с ширины клетки на px/день (для «Дней» значения совпадают). `convertZoomScrollLeft` переписывается на `zoomPxPerDay`, тесты обновляются (48↔100/7).
- `chartKey` (пересборка чарта при смене зума) — без изменений: смена режима меняет scales/unit, пересборка обязательна.
- Settings (`ganttZoom`) — без изменений: тот же ключ, переживание reload уже покрыто (PBT-073). Дефолт `'weeks'` сохраняется — теперь это недельные колонки.

### D2.5 e2e

- Новый: переключение «Недели» → в шкале видны подписи-диапазоны (регэксп «\d{1,2}–\d{1,2} [а-я]+»), полоса задачи начинается внутри недельной колонки по дате (дневная точность — сверка границ полосы с датой), подсветка выходного дня видна в недельном режиме; смена «Дни»↔«Недели» не сбрасывает позицию взгляда (та же левая дата в видимой области); reload в «Неделях» сохраняет режим.
- Существующие зум-тесты (подписи числа месяца в «Неделях») переписываются под новую семантику; тесты плотности (ширина клетки) — только для «Дней».

Отклонено: три строки шкалы месяц/неделя/день с скрытой дневной (лишний ряд, ломает `scaleHeight`); `{unit:'day', step:7}` (клетка-неделя с дневным юнитом: `highlightTime` красил бы всю неделю по её первому дню — дневная точность потеряна); плавный зум `zoom-scale` SVAR (вне решения владельца).

## D3. Каскад: клампинг окна в границы канваса

### D3.1 Корни (по коду; подтверждено живой проверкой)

1. **Resize не ограничен канвасом**: `bounds="parent"` react-rnd действует только на drag; `maxWidth/maxHeight` рендера — ограничения типа виджета (`cascadeSizeBounds`), не размеры канваса. Ресайз вправо/вниз уводит край окна за канвас.
2. **Восстановление из БД без проверки** (PBT-024): `areaOf` возвращает сохранённую геометрию как есть — записанная на большем экране позиция оказывается за краем текущего канваса; `overflow: hidden` канваса делает заголовок/кнопки недостижимыми. Путь воспроизведения: сохранить пространство с окном у правого края, сузить окно браузера, перезапустить.
3. **Сжатие канваса при жизни сессии** (ресайз окна браузера, разворот соседа) не переклампирует отображённые окна. Живая проверка: сжатие вьюпорта 1280→700 — окна №4/№5 стека (правый край 736) прижались к right=700 ✓ (после реализации; до неё оставались за краем).

### D3.2 Решение

- Чистая функция `clampCascadeArea(area, canvas, minSize)` в `cascade-layout.ts` (unit-тесты): позиция клампится в `0..max(0, canvas − размер)`; размер клампится к `min(minSize_типа…, canvas − позиция)`, но не ниже минимума типа; если минимум типа не влезает в канвас — окно в `0,0` с минимальным размером (достижимость важнее вписывания).
- `CascadeLayout` измеряет контейнер (`ResizeObserver` на `.cascade-layout`) → размер канваса в state; **клампинг на отображение** — каждая область проходит `clampCascadeArea` перед передачей в `Rnd`. Покрывает пути 2 и 3 без записей в БД (перезапись сохранённой геометрии на старте — Non-goal).
- **Клампинг на фиксацию**: `onDragStop`/`onResizeStop` клампят результат до `applyArea` — в раскладку (и далее в БД) попадает валидная геометрия; в сочетании с `bounds="parent"` на drag оба жеста не могут зафиксировать окно за краем.
- Сетку (RGL) не трогаем: у неё своя согласованность с сеточными координатами.

### D3.3 e2e

- Resize за правый/нижний край → край окна останавливается на границе канваса, окно управляемо.
- Восстановление за краем: сохранить окно у правого края → сузить viewport → reload → окно видно целиком, заголовок/кнопки достижимы.
- Существующие каскадные e2e (перенос, перекрытие, глубина) — зелёные без правок.

## D5. Риски

- **weekStart Вс/Пн** (D2.3) — ЗАКРЫТ: решение через `context.i18n.Provider` (детали в D2.3); резервный `registerScaleUnit` не потребовался.
- Слой подсветки и трекинг прокрутки: трекинг не нужен вовсе — полосы живут внутри скролл-контента SVAR (D2.3, упрощение); рассинхрон невозможен.
- `api.getState()._scales` — публичный тип `IApi.getState(): IData` (GanttScaleData: start/end/lengthUnitWidth) — используется только для чтения.
- Клампинг на отображение + `bounds="parent"` могут дать визуальный «подпрыг» окна при сжатии канваса — принимается (альтернатива — записи в БД на старте — отклонена).
- Синтетические mouse-события не активируют жести SVAR/react-rnd (проверено) — жестовые проверки только e2e с реальной мышью (покрыто: каскадные drag/resize и жестовые спеки плана идут в дефолтном недельном режиме).
