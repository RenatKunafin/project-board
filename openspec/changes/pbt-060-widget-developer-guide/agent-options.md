# Варианты унификации инструкций агентов

Владелец 2026-10-24 подтвердил общий объём уборки и сообщил об использовании разных агентов. Удаление всей .opencode как «неиспользуемой» больше не входит в согласованный план. Владелец одобрил вариант2 с правилами и навыками в .agents («Отлично, делаем»).

## Вариант 1. Один AGENTS.md

Все постоянные инструкции проекта — один компактный AGENTS.md; технические знания/руководства — docs/. Совместимые агенты читают файл напрямую, для остальных нужен небольшой загрузчик. Плюсы: минимум файлов и настройки. Ограничения: по мере роста инструкции снова становятся длинными и все разделы попадают в контекст независимо от задачи.

## Вариант 2. AGENTS.md + общие .agents/rules + тонкие адаптеры (рекомендация)

AGENTS.md — краткая обязательная точка входа: критические ограничения, карта правил и порядок их чтения. .agents/rules/workflow.md — задачи/ревью/OpenSpec/git; .agents/rules/code.md — архитектура/SDK/стиль; .agents/rules/testing.md — проверки/production/offline/артефакты. В docs/ — руководства, ADR и знания, а не дублирующие инструкции агента.

Специфичные конфиги содержат только механизм подключения общих файлов, без самостоятельной версии правил. При необходимости Claude использует импорт @AGENTS.md/общих rules, OpenCode — instructions в opencode.json, Cursor — AGENTS.md или короткий нативный loader. Для Codex обязательное чтение нужных файлов задаётся в AGENTS.md. Наличие папки rules само по себе не означает автозагрузку; критические ограничения остаются в общей точке входа.

Поддержку конкретных инструментов проверять по используемым версиям. Современный Claude Code умеет AGENTS.md напрямую при соответствующей настройке/встроенном плагине; импорт CLAUDE.md полезен для совместимости со старыми/ограниченными установками. Не добавлять адаптер для каждого существующего редактора без потребности.

Плюсы: один поддерживаемый набор правил, небольшой контекст, переносимость, простой review. Ограничения: несколько небольших конфигов загрузки и проверка ссылок/порядка применения. Проверить запуск каждого заявленного инструмента: он должен назвать прочитанные правила и обязательные команды проверок.

Существующие OpenSpec-команды/навыки — отдельный слой интерфейса инструментов. Сохранить нужные интеграции, сверить их с общим workflow; автоматически сгенерированные шаблоны не превращать вручную в независимый источник правил проекта.

## Вариант 3. Общий источник + генератор конфигов

Правила хранятся централизованно, скрипт создаёт необходимые нативные представления/загрузчики для поддерживаемых инструментов. CI проверяет, что сгенерированные файлы актуальны, вручную они не редактируются. Плюсы: воспроизводимость при большом числе инструментов и разных форматах. Ограничения: собственный генератор, шаблоны и дополнительное сопровождение. Для текущего репозитория это больше инфраструктуры, чем требуется варианту2.

## Общие границы

- Правила проекта, знания/документация, интерфейс команд и разрешения исполнения — разные слои. Глобальную память, токены, MCP и системные разрешения агентов не переносить в репозиторий в рамках этой задачи.
- Не создавать независимо редактируемые копии одинаковых правил в .claude/.cursor/.opencode/.codex.
- Поддерживаемый список инструментов и используемые версии уточнить при выборе адаптеров. Пустую универсальную «поддержку всех агентов» не обещать.
- Решение о варианте не меняет одобренные .docs→docs, удаление load-demo/архивных картинок и исходный результат руководства PBT-060.

## Размещение скиллов (предложение)

Канонический источник проектных скиллов — `.agents/skills/<skill-name>/SKILL.md` в репозитории. Рядом при необходимости scripts/, references/, assets/. Существующие OpenSpec-скиллы из .opencode/skills при реализации сначала проверить на переносимость и адаптировать к общему CLI/правилам, затем хранить в общем источнике. Постоянные требования остаются в AGENTS/rules; скиллы описывают выполняемые по задаче сценарии.

Официальные документы подтверждают нативное обнаружение .agents/skills у Codex, OpenCode и Cursor. Claude Code документирует .claude/skills; для него можно сделать относительные симлинки отдельных skill-каталогов на канонический источник, без самостоятельно редактируемых копий. При несовместимой среде потребуется проверенный адаптер/генерируемое представление. Проверка каждого используемого агента включает обнаружение скилла и отсутствие дубликатов/расхождений. Поддержка всех собственных полей frontmatter/спецвозможностей разных агентов автоматически не предполагается.

Личные/установленные глобально навыки владельца остаются в пользовательских директориях. В репозиторий входят только проектные навыки; `.opencode/commands` и другие интерфейсы slash-команд сохраняются лишь там, где нужны инструменту.

- https://opencode.ai/docs/skills/
- https://cursor.com/docs/skills

## Размещение правил рядом со скиллами (предложение владельца)

Рекомендуем `.agents/rules/` вместо отдельной rules/ в корне. В корне остаётся AGENTS.md — обнаруживаемая точка входа с критическими ограничениями и явным порядком чтения .agents/rules. Полной универсальной схемы всех подпапок .agents не предполагаем: Agent Skills задаёт формат skill-каталога/SKILL.md, а обнаружение/активация rules остаётся зависимым от агента. Antigravity уже использует .agents/rules, но со своим frontmatter/trigger; стандартизация общих rules обсуждается в открытом proposal agentsmd/agents.md#179. Нативные настройки подключают одни исходные файлы, а не самостоятельные копии правил.
