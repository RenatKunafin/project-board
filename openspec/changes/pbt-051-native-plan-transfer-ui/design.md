# Design — PBT-051 Native plan transfer UI

## Context

PBT-050 дала чистый контракт формата (`serializePlanFile`, `deserializePlanFile`, `planFileName`) без UI. Виджет плана работает с документом через `documentService` (подписка + `update` с ретраем ревизии); платформа имеет механизм перепривязки экземпляра к документу (`replacePaneDocument`, прецедент «замена недоступного документа» PBT-025), но SDK его не отдаёт. Каталог документов перечитывает `listDocuments()` при рендере App; структурные операции будят его через `bumpDocumentsVersion`.

## Goals / Non-Goals

- Goals: скачать план файлом; открыть файл плана с валидацией до сохранения; импорт всегда новый независимый документ; импортированный план сразу открыт в окне; каталог отражает оба плана.
- Non-Goals: см. proposal.

## Decisions

### D1. Место UI — тулбар плана

Кнопки «Экспорт» и «Импорт…» в тулбаре `PlanGanttWidget` (ряд «+ Задача / + Группа / Настройки плана / Проблемы»), стиль существующий `plan-gantt__add-button`; data-атрибуты `data-export-plan`, `data-import-plan`, `data-import-plan-input` для e2e. Кнопки активны при выбранном документе (в состоянии «документ не выбран» тулбар не рендерится — вне границ). Уточнение по итогам отладки: кнопки компактные иконочные (`📤`/`📥`, aria-label «Экспорт плана»/«Импорт плана», класс-модификатор `plan-gantt__icon-button` с `line-height: 1; height: 28px`) — эмодзи выше текста 13px, без ограничения ряд тулбара растёт и сдвигает чарт (наблюдение бисекта: двойной клик по нижней строке попадал в соседнюю строку).

### D2. Экспорт — скачивание клиентскими средствами

`serializePlanFile({ title: document.title, content: plan })` → `Blob([json], {type: 'application/json'})` → временный `URL.createObjectURL` → `a.download = planFileName(new Date())` → `click()` → `revokeObjectURL`. Название плана — из метаданных документа (каноническое место, PBT-025). DOM-код — в виджете (UI-слой): доменный модуль формата PBT-050 остаётся чистым (без Node/DOM API). Экспорт отправляет `plan` (валидный, после `parsePlanContent`), а не сырой `document.content` — файл всегда валиден по построению.

### D3. Импорт — валидация до сохранения

Скрытый `<input type="file" accept=".json,application/json">`; клик по кнопке вызывает `input.click()`. `onChange` → `file.text()` → `deserializePlanFile(text)`:
- **ok** → `documentService.create({ moduleId: PLAN_MODULE_ID, documentType: PLAN_DOCUMENT_TYPE, schemaVersion: PLAN_SCHEMA_VERSION, title, content })` → `switchDocument(created.id)`. Создание после валидации — частичный документ невозможен (DoD-2).
- **fail** → inline-область под тулбаром (`role="alert"`, `data-import-plan-result`): коды и сообщения конверта, при `plan-invalid` — полный перечень `details`. Документ не создаётся.
- **отмена** (диалог закрыт без выбора) — события `change` нет, состояние не меняется (DoD-4).
- `input.value = ''` после чтения: повторный выбор того же файла снова срабатывает.

### D4. Открытие импортированного плана — SDK `switchDocument`

Развилка:
- **A (принято):** SDK получает `WidgetProps.switchDocument?: (documentId: string) => void`; `WidgetPane` передаёт `(id) => handlers.current.replacePaneDocument(instanceId, id)`. UX «открыл файл — работаю с ним»; перерендер App происходит от смены `panesByTab` (существующий `bumpDocumentsVersion` внутри `replacePaneDocument`) — каталог показывает оба документа; подпись окна пересчитывается из актуального документа (`windowTitleOf`); прежний план остаётся в каталоге. Прецедент расширения SDK опциональным хендлером: `updateSettings` (PBT-049, ADR-6.4 PBT-002 «расширения контракта — новыми решениями»).
- Отклонено: открытие нового экземпляра платформой — большее вторжение в платформу (SDK «запросить окно» не существует), старое окно теряет смысл; отказ от открытия (только каталог) — слабый UX, не соответствует сценарию переноса.

### D5. Повторный импорт — политика PBT-050 без диалогов

Каждый импорт создаёт новый документ: совпадение названий допустимо (независимость планов); перезаписи нет — подтверждения «заменить?» не нужны (DoD-3 «не перезаписывает другой план неожиданно» выполняется по построению). Текущее окно переключается на последний импортированный.

### D6. Delta `document-management` — создание документа модулем

Наблюдаемое поведение платформы: документ, созданный модулем через сервис во время работы (импорт), появляется в каталоге без перезапуска и восстанавливается после него. Требование формулируется модульно-нейтрально (гарантия каталога, не план-специфика). Переключение окна на документ — поведение импорта, описывается в `plan-transfer` (механизм переиспользует перепривязку; новое требование `widget-windows` не вводится — capabilities карточки).

### D7. E2E (`tests/e2e/plan-transfer.spec.ts`)

- **Перенос между контекстами (DoD-1):** контекст A — создать план через каталог, добавить задачу, «Экспорт» → `page.waitForEvent('download')` → `download.path()`; контекст B (`browser.newContext()`) — «Импорт…» → `setInputFiles(path)` → проверить: заголовок окна = название из файла, счётчик задач, каталог содержит план.
- **Битый файл (DoD-2):** импорт обрезанного JSON → `data-import-plan-result` с диагностикой, каталог без новых документов.
- **Двойной импорт (DoD-3):** тот же файл дважды → два документа с одинаковым названием в каталоге, окно на последнем.
- Экспорт в headless Chromium: download API поддержан; файл существует и парсится (`JSON.parse` в тесте).

## Risks / Trade-offs

- `switchDocument` — третье опциональное расширение SDK (после `onResize`/`updateSettings`): рост поверхности контракта компенсируется общей реализацией на `replacePaneDocument` и будущим переиспользованием (PBT-054 «преобразование отпусков импорта» ляжет сюда же).
- Скачивание и выбор файла в jsdom не тестируются (unit) — покрывается e2e на прод-сборке; хелпер скачивания — три строки DOM-кода.
- DoD-5 (офлайн) отложен до PBT-028/029: используемые API клиентские, PWA-слой не влияет на поведение переноса; зафиксировано в proposal.
- Диалог выбора файла — нативный, браузерными стилями не управляем: сценарии e2e идут через `setInputFiles`/`filechooser`, не через клики по системному диалогу.
- Локальная тестовая среда деградирует (развитие разбора 2026-10-15): в параллельных прогонах плавающий набор красных SVAR-спек — {dependencies, plan-gantt ×3} на develop и {conflicts:115, plan-groups:94, resource-timeline:184} на ветке; бисект-нестабильность (одиночные и малогрупповые прогоны стабильно зелёные на обеих ветках; на develop с одним только тест-файлом без правок кода краснеет 8). Меры в этой задаче: компакт-класс кнопок (тулбар не растёт — убран реальный сдвиг геометрии) и паузы стабилизации 600 мс после записи контрольных данных перед жестами в трёх существующих спеках (комментарии с причиной в спеках). SVAR пересобирает представление по ревизии (PBT-037) — жест в переходный DOM попадает в соседнюю строку; при деградации среды окно гонки шире паузы.

## Migration Plan

Схема БД не меняется. Новое поведение — только UI-кнопки и SDK-хендлер; старые установки получают кнопки тулбара без миграций данных.

## Open Questions

Нет — места кнопок, политика импорта и открытие импортированного плана зафиксированы в design; развилка D4 решена рекомендацией A (переключение текущего окна).
