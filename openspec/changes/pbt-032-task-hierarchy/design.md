# Design — PBT-032: иерархия и сводные сроки групп

## Context

База после PBT-031: `plan-commands.ts` — чистые операции над задачами + диспетчер `applyPlanCommand` с объединением `PlanCommand` и кодами отклонений (`unknown-task/group/resource/work-type`, `inverted-interval`, `invalid-duration`); модель v1 хранит `groups: [{ id, title, parentId? }]` и `tasks: [{ id, title, groupId?, start, end, ... }]`; валидатор чтения `parsePlanContent` уже отклоняет self-parent, неизвестного родителя и циклы групп (`circular-group`). Правила блока B ADR PBT-003: B1 (пустые группы разрешены, сводная отсутствует), B2 (сводная — вычисляемое отображение min/max, не перетаскивается), B3 (перенос задач и подгрупп между группами, своя сводная пересчитывается), B4 (раскрытие — на уровне виджета, вне документа). Валидатор гарантирует целостность структуры при чтении; операции обязаны её не ломать.

## Goals / Non-Goals

**Goals:** команды create/update/delete группы в едином `PlanCommand`; отклонение циклов (включая «в собственного потомка») без изменения документа; сводные границы как чистая функция; контракт удаления с сохранением содержимого; гарантии порядка; тесты дерева, порядка, циклов, пустых групп, обновления сводных.

**Non-Goals:** позиционное переупорядочивание и drag дерева (PBT-040), состояние раскрытия (B4, виджеты), сводные полосы в UI (PBT-037), прочие разделы плана (PBT-033–036).

## Decisions

### D1. Команды групп — расширение единого `PlanCommand`

`packages/gantt/src/plan-hierarchy.ts` — операции и вычисления; `plan-commands.ts` — расширение объединения `PlanCommand` вариантами `createGroup` / `updateGroup` / `deleteGroup` и диспетчера (делегирование). Единый путь команд PBT-031 сохраняется: потребители строят команды одного вида и получают один `PlanCommandResult`.

```text
PlanCommand += 
  | { type: 'createGroup'; input: { title: string; parentId?: string } }
  | { type: 'updateGroup'; groupId: string; patch: { title?; parentId? } }
  | { type: 'deleteGroup'; groupId: string }
```

Семантика `updateGroup` по образцу `updateTask`: отсутствующее свойство — не менять; присутствующее — заменить, включая `parentId: undefined` (вынос на корень). Переименование и перенос — одна команда с разными полями патча; в design намеренно: оба действия меняют однострочные поля группы, дублировать команду ради имени — лишнее.

Код ошибки дополняется: `'circular-group'` (перенос в себя или в собственного потомка). Таксономия остаётся отдельной от `PlanIssue` (решение D2 PBT-031); имя кода совпадает с кодом валидатора осознанно — одна и та же сущность нарушения.

Альтернатива «отдельный `GroupCommand` + второй диспетчер» отклонена: два пути — против цели единого пути из карточки PBT-031.

### D2. Удаление группы: перенос прямых потомков к родителю (утверждено владельцем)

Правила B ADR PBT-003 не определяют удаление группы. Контракт очищения ссылок D6 PBT-031 («чистятся только сущности, невалидные без удаляемой») продолжается, но здесь содержимое остаётся валидным и без группы — вопрос в том, куда оно попадает.

**Вариант A (утверждён владельцем 2026-10-14):** прямые потомки (подгруппы с `parentId = G` и задачи с `groupId = G`) перепривязываются к родителю `G`; у корневой `G` — к корню плана. Задачи глубже (в подгруппах) не трогаются. Зависимости, ресурсы, типы, недоступности не изменяются.

Основания: безопасность данных (одно действие не может массово удалить задачи с их зависимостями); прецедент ADR PBT-002 ADR-7 — удаление контейнера (вкладки) не удаляет содержимое (документы); сводная родителя корректно пересчитывается (поддерево остаётся в нём целиком).

Отклонённые альтернативы: **вариант B** — каскадное удаление поддерева с зависимостями (массовая потеря данных одной операцией, аналогов в согласованных решениях нет); **вариант C** — запрет удаления непустой группы (ручная разборка дерева перед каждым удалением, против прецедента ADR-7).

### D3. Циклы: отклонение без изменения документа

`updateGroup` с присутствующим `parentId` проверяет по порядку: `unknown-group` (сам groupId или новый parentId не существует); `parentId === groupId` → `circular-group`; иначе подъём по цепочке родителей от нового parentId — встреча groupId → `circular-group` (перенос в собственного потомка, DoD-2; покрывает и самоперенос). Проверка полная, подъём конечен (валидатор чтения исключает циклы во входных данных). Отклонение возвращает документ без изменений — атомарность PBT-031.

`createGroup` проверяет только существование parentId (`unknown-group`): новая группа потомком быть не может. Перенос задачи (`updateTask` c `groupId`) уже покрыт PBT-031 (`unknown-group`); вынос задачи на корень — `groupId: undefined`.

### D4. Порядок элементов: гарантии операций, без позиционных команд

Порядок внутри группы определяется порядком появления элементов в массивах `groups` / `tasks` (внутри одной группы). Гарантии операций: `createTask` / `createGroup` добавляют в конец массива (уже так в PBT-031); перенос группы (`updateGroup.parentId`) и задачи (`updateTask.groupId`) перемещают элемент в конец его массива — порядок в старой группе не «дырявится», в новой — детерминирован (в конец). Удаление группы не меняет относительного порядка остальных. Отдельные команды «вставить после X» не строятся: первый реальный потребитель — drag дерева (PBT-040), позиционные операции оформляются там (правило «не строить абстракцию без потребителя», прецедент D7 PBT-031). Тесты порядка: стабильность массивов при неизменных операциях, перемещение в конец при переносе, отсутствие дублей.

### D5. Сводные границы — чистая функция, не хранится

`groupSummaryBounds(plan, groupId): { start: string; end: string } | undefined` — рекурсивный обход поддерева группы: min `start` и max `end` по всем вложенным задачам (включая подгруппы любой глубины). `undefined` для пустой группы (B1) — сводная полоса отсутствует. В документе не хранится (источник истины — даты задач, ADR-5 PBT-002; «производные значения вычисляются»); «обновляются после изменения» (DoD-3) достигается пересчётом потребителем после любой команды — тестом подтверждается на `setTaskDates` и переносе между группами. Сравнение дат — лексикографическое по ISO-строкам (инвертированные интервалы исключены операциями и валидатором). Сложность O(размер поддерева) — при целевом объёме (несколько сотен задач) несущественно; кэширование — вопрос представления (PBT-037), не ядра.

Помощники: `childGroups(plan, groupId)` / `childTasks(plan, groupId)` — прямые потомки; экспортируются — пригодятся PBT-037/040 и сокращают дублирование.

### D6. Границы зависимостей

`plan-hierarchy.ts` импортирует только типы `plan-document.ts` и `working-calendar.ts` — без React, без UI-библиотек (ADR-3 PBT-002, ADR-3 PBT-017). `plan-commands.ts` импортирует `plan-hierarchy` (одно направление, без циклов). Экспорт нового модуля из `index.ts`.

## Risks / Trade-offs

- **Удаление группы — правило не покрыто ADR PBT-003:** вариант A утверждён владельцем 2026-10-14; при пересмотре правится `deleteGroup` и сценарий спеки, контракт D6 остаётся каркасом.
- **Перенос в конец при групповом переносе:** теряется «положение» элемента среди соседей старой группы (оно и не сохранялось явно); PBT-040 при потребности добавит позиционные команды — это расширение, не слом.
- **`updateGroup` объединяет переименование и перенос:** одна команда с двумя смыслами чуть шире, чем «одна команда — одно действие»; принято ради симметрии с `updateTask` и без дублирования кода валидации патча.

## Migration Plan

Не требуется: формат v1 не меняется (группы уже в модели); только чистые функции и расширение объединения команд.
