## Context

Причина изменения описана в [proposal.md](proposal.md). Границы задаёт [ADR PBT-002](../../../docs/adr/PBT-002.md); публичный SDK экспортирует только корень пакета. Используются ESLint 9 flat config и typescript-eslint. В tsconfig нет aliases/paths; Vite также не задаёт алиасы пакетов. Новая зависимость для проверки не нужна.

## Goals / Non-Goals

**Goals:** проверять одинаковую политику независимо от синтаксиса импорта и расположения файла, автоматически охватывать новые модули, давать понятную диагностику без влияния на production.

**Non-Goals:** полноценный TypeScript/bundler resolver, контроль всех транзитивных зависимостей npm, изоляция недоверенных плагинов, новые ограничения на обычные внешние библиотеки виджетов и изменение графа ADR.

## Decisions

### D1. Одно локальное правило вместо пересекающихся списков

Подключить `project-board/package-boundaries` через локальный ESLint plugin в `scripts/eslint/`. Оно проверяет межпакетные связи и Dexie одновременно. Отдельные определения `no-restricted-imports` удалить: последующие flat config объекты заменяют параметры предыдущего определения того же правила. Новых npm-пакетов нет.

Альтернативы: только объединить core-паттерны недостаточно для нормализованных относительных путей и динамического import(); универсальный сторонний boundary-plugin с resolver добавляет зависимость и настройку сверх задачи. Основание: [объединение правил ESLint](https://eslint.org/docs/latest/use/configure/rules), [область no-restricted-imports](https://eslint.org/docs/latest/rules/no-restricted-imports).

### D2. Политика пакетов

При загрузке конфига собрать имена и корни пакетов из package.json в `packages/*`, `examples/*`, `apps/*`. SDK и dashboard — специальные роли; остальные packages/examples — предметные модули по умолчанию, apps — composition roots. Новое приложение/модуль не требует списка собственных имён в правиле. Неизвестный `@project-board/*` из модуля/SDK/платформы не становится разрешённым внешним импортом.

Разрешены собственные внутренние импорты. Модулям и платформе разрешён публичный `@project-board/widget-sdk`; глубокие и относительные обращения к внутренностям SDK запрещены. SDK не зависит от других пакетов проекта; модули не зависят от dashboard, соседей, apps и корневых внутренних helpers. Dashboard не зависит от предметных пакетов. Относительный выход за собственный пакет не считается внешней npm-библиотекой. Composition roots и интеграционные тесты вне пакетов могут собирать приложение.

Dexie и его подпути запрещены везде за исключением адаптера платформы. SDK дополнительно не импортирует используемые UI-семейства: `@svar-ui/*`, `react-calendar-timeline`, `react-grid-layout`, `react-rnd`, `lucide-react`, `react-dom`. React-типы публичного контракта и Vitest в тестах остаются допустимыми. Список UI-семейств явный: это не универсальный определитель произвольной UI-библиотеки; новая библиотека требует ревью зависимостей и при необходимости обновления списка.

### D3. Статически известные пути

Одинаково обрабатывать import/export, type-only import/export и import-type выражения, literal import(), CommonJS require/import-equals. Для относительных/абсолютных путей использовать нормализацию относительно файла, для workspace — сопоставление с package.json и границей имени. Не выполнять импортируемый код и не загружать npm-модули для разрешения путей. Затенённый пользовательский `require` не трактовать как загрузчик.

Вычисляемые runtime пути не резолвятся и не объявляются проверенными. Если появятся aliases/paths, их поддержку нужно явно добавить; текущая конфигурация их не использует. Не допускать обхода ссылкой из модуля на корневой файл, который затем реэкспортирует запрещённый пакет.

### D4. Проверка наблюдаемого поведения инструмента

Тесты через установленный ESLint загружают настоящий config, проверяют его эффективное правило и lintText по реальным/временным путям пакетов. Матрица включает запрещённые и разрешённые связи, разные синтаксисы, относительную нормализацию, глубокие пути, учебный виджет и новый модуль с отличающимся именем package.json. Временная структура удаляется. Отсутствие диагностики парсера не считается успешной проверкой запрещённого импорта.

Полный lint текущего репозитория не должен требовать ослабления границ. При находке действительной архитектурной связи описать её и выбрать устранение явно, без незаметного предметного рефакторинга.

## Risks / Trade-offs

- Собственное правило требует сопровождения → ограничить его политикой ADR и статически известными путями, закрепить поведенческими тестами.
- Новый пакет может не попасть в инвентарь → классификация по общим директориям и тест добавления нового package.json; ESLint должен перечитать config после добавления пакета.
- Нельзя гарантировать все обходы линтера/динамические вычисления → проверка архитектуры не является sandbox; не заявлять поддержку неразрешаемых путей.
- Изменение инструмента может нарушить чистое подключение нового виджета → проверить учебный модуль в составе целевых lint-тестов и существующую команду чистого подключения перед PR.

## Migration Plan

Изменяются только tooling, тесты и руководство. Существующие CI-команды подхватывают правило без дополнительной настройки. Миграций данных/SDK нет. Откат — возврат изменения инструмента через обычный PR; production-данные и выпуск сайта не затрагиваются.
