# plan-transfer Specification

## Purpose

Перенос одного плана в файл и обратно: версионированный собственный формат полного переноса (конверт с маркером формата, версией формата, названием плана и версией содержимого), сериализация, полная валидация при десериализации со структурированной диагностикой, отклонение будущих версий и политика независимого импорта (файл всегда создаёт новый план; идентификаторы сущностей не связывают планы). Семантика дат — ADR PBT-003: календарные даты ISO, окончание включительно. UI импорта и экспорта — `document-management`/представления; эта capability определяет формат и его проверки.

## Requirements

### Requirement: Экспорт полного плана в файл

Модуль планирования SHALL сериализовать план в текстовый JSON-файл собственного формата, включающий маркер формата, версию формата, название плана и полное содержимое: рабочий календарь, типы работ, ресурсы, вложенные группы, задачи, FS-зависимости и периоды недоступности. Производные значения (сводные сроки групп, длительности в рабочих днях, диагностики конфликтов) MUST NOT включаться в файл. Файл MUST быть пригоден для чтения в текстовом редакторе.

#### Scenario: Полный план переносится целиком

- **GIVEN** план со всеми разделами: календарём с праздником, двумя типами работ, ресурсами, вложенными группами, задачами с назначениями, FS-зависимостью с лагом и периодом недоступности
- **WHEN** план сериализуется в файл
- **THEN** файл содержит название плана и все перечисленные данные без потерь

#### Scenario: Производные значения не попадают в файл

- **GIVEN** план с группой, имеющей сводный интервал, и задачей с рабочей длительностью
- **WHEN** план сериализуется в файл
- **THEN** файл не содержит вычисленных сводных сроков, рабочих длительностей и диагностик конфликтов

### Requirement: Импорт файла с валидацией

Модуль SHALL десериализовать файл собственного формата с полной проверкой до выдачи плана: корректность JSON, наличие и типы полей конверта, совпадение маркера формата, поддержка версии формата и версии содержимого, валидность содержимого плана. Неизвестный идентификатор цвета задачи SHALL нормализоваться в автоматический цвет на шаге разбора; остальные проверки смягчения не имеют. Повреждённый или чужой файл MUST NOT выдаваться за план: результат SHALL содержать перечень диагностических сообщений с кодом, местом и причиной; входные данные MUST NOT изменяться. Проверка содержимого SHALL повторять полную валидацию плана при чтении, включая структуру, форматы дат, уникальность идентификаторов, внутренние ссылки и циклы групп.

#### Scenario: Повреждённый JSON даёт диагностику

- **GIVEN** текст файла обрезан и не является корректным JSON
- **WHEN** выполняется десериализация
- **THEN** результат содержит диагностику синтаксической ошибки JSON
- **AND** план не создаётся

#### Scenario: Чужой формат распознаётся

- **GIVEN** файл с маркером формата, не совпадающим с маркером приложения
- **WHEN** выполняется десериализация
- **THEN** результат содержит диагностику неизвестного формата
- **AND** содержимое файла не интерпретируется как план

#### Scenario: Невалидное содержимое даёт полный перечень проблем

- **GIVEN** файл формата приложения, содержимое которого ссылается на несуществующую группу и содержит цикл вложенности групп
- **WHEN** выполняется десериализация
- **THEN** результат содержит диагностику обеих проблем с указанием места
- **AND** план не создаётся

#### Scenario: Валидный файл выдаёт план с названием

- **GIVEN** файл формата приложения с корректным содержимым и названием плана
- **WHEN** выполняется десериализация
- **THEN** результат содержит план, эквивалентный содержимому файла, и название для создаваемого документа

#### Scenario: Неизвестный цвет файла нормализуется в автоматический

- **GIVEN** файл формата приложения с задачей, цвет которой — неизвестный палитре идентификатор
- **WHEN** выполняется десериализация
- **THEN** план создаётся, задача без ручного цвета, остальное содержимое задачи сохранено
- **AND** файл с повреждённой датой в той же задаче по-прежнему отклоняется с диагностикой

### Requirement: Отклонение будущей версии формата

Файл с версией формата или версией содержимого больше поддерживаемой SHALL отклоняться с диагностикой о несовместимости: файл создан более новой версией приложения. Данные файла MUST NOT интерпретироваться как план частично и MUST NOT уничтожаться.

#### Scenario: Файл будущей версии не импортируется

- **GIVEN** файл с версией формата больше поддерживаемой
- **WHEN** выполняется десериализация
- **THEN** результат содержит диагностику несовместимой версии
- **AND** план не создаётся, файл остаётся доступным без изменений

### Requirement: Импорт создаёт независимый план

Десериализованный файл SHALL использоваться только для создания нового независимого документа плана: замена содержимого существующего плана файлом в этой версии формата не поддерживается. Идентификаторы сущностей внутри плана SHALL сохраняться из файла, а ссылки между сущностями SHALL оставаться внутренними для содержимого плана. Совпадение идентификаторов или названий сущностей разных планов MUST NOT создавать связи между планами.

#### Scenario: Два импорта одного файла дают независимые планы

- **GIVEN** один файл формата приложения, импортированный дважды
- **WHEN** содержимое одного из полученных планов изменяется
- **THEN** содержимое второго плана остаётся без изменений
- **AND** совпадающие внутренние идентификаторы сущностей не связывают планы

### Requirement: Round-trip без потерь

Последовательные сериализация и десериализация плана SHALL восстанавливать название и все разделы содержимого без изменений, включая поддержанные дополнительные поля внутри сущностей содержимого и ручной цвет задач (идентификатор палитры либо его отсутствие). Повторный экспорт десериализованного плана SHALL давать эквивалентный файл без смены версии формата.

#### Scenario: Round-trip контрольного плана

- **GIVEN** план со всеми разделами модели
- **WHEN** план сериализуется в файл и десериализуется обратно
- **THEN** название и все разделы содержимого эквивалентны исходным

#### Scenario: Дополнительное поле сохраняется при переносе

- **GIVEN** файл, в содержимом которого у задачи присутствует неизвестное приложению поле
- **WHEN** файл десериализуется и результат сериализуется снова
- **THEN** дополнительное поле задачи сохраняется в полученном файле

#### Scenario: Ручной цвет сохраняется в round-trip

- **GIVEN** план с задачами, у части задан ручной цвет, у части он отсутствует
- **WHEN** план экспортируется в файл и импортируется обратно
- **THEN** идентификаторы цветов и отсутствие поля у неокрашенных задач сохраняются точно, версия формата не меняется

### Requirement: Экспорт плана из интерфейса

Представление плана SHALL предоставлять команду экспорта: текущий план сериализуется в файл собственного формата с названием плана из метаданных документа и скачивается под именем по шаблону `pb-plan-YYYY-MM-DD_HH-mm-ss.json`. Экспортированные данные SHALL соответствовать формату, действующему на момент экспорта; производные значения в файл не включаются.

#### Scenario: Экспорт текущего плана скачивает файл

- **GIVEN** открыт план с задачами, группами и календарём
- **WHEN** пользователь выполняет команду экспорта
- **THEN** браузер скачивает файл формата приложения
- **AND** содержимое файла соответствует текущему содержимому документа

#### Scenario: Имя файла по шаблону

- **GIVEN** открыт план «ОКАД»
- **WHEN** пользователь выполняет команду экспорта
- **THEN** предлагаемое имя файла имеет вид `pb-plan-YYYY-MM-DD_HH-mm-ss.json`

### Requirement: Импорт файла из интерфейса

Представление плана SHALL предоставлять команду импорта, открывающую браузерный диалог выбора файла. Выбранный файл SHALL полностью валидироваться до создания документа; при успехе создаётся новый независимый документ плана с названием из файла, при отказе — пользователю показывается перечень диагностических сообщений по месту команды, и документ MUST NOT создаваться. Отмена выбора файла в диалоге MUST NOT изменять данные.

#### Scenario: Валидный файл создаёт план и открывается в окне

- **GIVEN** пользователь выбрал корректный файл формата приложения с названием «ОКАД»
- **WHEN** импорт выполняется
- **THEN** создаётся документ плана с названием «ОКАД», доступный в каталоге
- **AND** окно, из которого выполнен импорт, отображает импортированный план
- **AND** план, открытый в окне до импорта, остаётся доступным в каталоге

#### Scenario: Повреждённый файл даёт диагностику без документа

- **GIVEN** пользователь выбрал обрезанный JSON-файл
- **WHEN** импорт выполняется
- **THEN** пользователь видит диагностику с указанием причины
- **AND** каталог не содержит нового документа

#### Scenario: Отмена выбора файла ничего не меняет

- **GIVEN** открыт диалог выбора файла
- **WHEN** пользователь закрывает диалог без выбора
- **THEN** содержимое и каталог остаются без изменений

### Requirement: Повторный импорт создаёт независимый план

Повторный импорт того же файла SHALL создавать ещё один независимый документ: ранее созданные планы MUST NOT перезаписываться или изменяться; окно, из которого выполнен импорт, SHALL отображать последний импортированный план.

#### Scenario: Два импорта одного файла

- **GIVEN** один файл формата приложения импортирован дважды
- **WHEN** пользователь просматривает каталог
- **THEN** каталог содержит два независимых документа с названием из файла
- **AND** окно импорта отображает последний импортированный план, ранее созданные планы без изменений

### Requirement: Разбор файла OnlineGantt `.gantt` в план с отчётом

Модуль планирования SHALL разбирать файл OnlineGantt `.gantt` (JSON с плоским списком записей `data` и справочником `resources`) в содержимое документа плана: задачи с датами и назначениями, ресурсы, FS-зависимости и рабочий календарь. Результат успешного разбора SHALL включать отчёт импорта — перечень предупреждений о неперенесённых или преобразованных данных и сводку (задачи, ресурсы, зависимости). Записи без назначенных ресурсов SHALL импортироваться как обычные задачи: автоматическое распознавание отпуска или иного смысла по названию не выполняется, преобразование — явное действие пользователя (PBT-054).

#### Scenario: Рабочий пример разбирается целиком

- **GIVEN** рабочий файл примера с 47 записями, 9 ресурсами, назначениями и строками зависимостей
- **WHEN** выполняется разбор файла
- **THEN** результат содержит 47 задач, 9 ресурсов, назначения и зависимости с лагами
- **AND** отчёт импорта содержит сводку без критических проблем

#### Scenario: Плоский файл без групп

- **GIVEN** файл `.gantt` без вложенности записей
- **WHEN** выполняется разбор файла
- **THEN** план не содержит групп; группировка остаётся ручной операцией пользователя

#### Scenario: Отпуск-строки остаются задачами

- **GIVEN** файл с записями без назначенных ресурсов, названия которых похожи на отпуска
- **WHEN** выполняется разбор файла
- **THEN** эти записи импортируются обычными задачами без назначений
- **AND** отчёт не помечает их как отпуска и не изменяет их назначения

### Requirement: Иерархия записей файла переносится в группы

Разбор SHALL переносить вложенность записей файла (подзадачи контейнера) в группы плана: запись с подзадачами становится группой, вложенные записи — задачами или подгруппами этой группы, рекурсивно на любую глубину. Даты, длительность, назначения и предшественники записи-контейнера — производные исходного инструмента и MUST NOT переноситься в план; сводная полоса группы вычисляется моделью плана. Идентификаторы записей SHALL быть уникальны в пределах файла на всех уровнях вложенности: ссылки предшественников разрешаются в общем пространстве идентификаторов файла.

#### Scenario: Контейнеры становятся группами

- **GIVEN** файл с двумя контейнерами «Отпуск» и «ОКАД», содержащими подзадачи, и задачами вне контейнеров
- **WHEN** выполняется разбор файла
- **THEN** план содержит две группы с вложенными задачами и задачи без группы на верхнем уровне
- **AND** даты и длительность контейнеров не попадают в план: сводная полоса групп вычисляется из вложенных задач

#### Scenario: Зависимость через границу контейнера

- **GIVEN** задача внутри одного контейнера со строкой предшественника, ссылающейся на задачу внутри другого контейнера
- **WHEN** выполняется разбор файла
- **THEN** зависимость создаётся между этими двумя задачами

#### Scenario: Контейнер с назначениями не переносит их молча

- **GIVEN** запись-контейнер с назначенными ресурсами
- **WHEN** выполняется разбор файла
- **THEN** контейнер становится группой без назначений
- **AND** отчёт импорта содержит предупреждение о неперенесённых назначениях контейнера

### Requirement: Конвертация дат по часовому поясу плана

Разбор SHALL преобразовывать временные метки UTC файла в календарные даты `YYYY-MM-DD` по часовому поясу плана из настроек файла. Дата окончания записи SHALL браться из метки последнего рабочего дня как включительная. При отсутствии или некорректности имени часового пояса SHALL применяться числовой сдвиг из настроек файла; при отсутствии обоих — UTC с предупреждением в отчёте.

#### Scenario: Даты не сдвигаются из-за UTC

- **GIVEN** запись с началом `2026-08-31T05:00:00.000Z` и окончанием `2026-09-11T14:00:00.000Z`, часовой пояс плана `Europe/Moscow`
- **WHEN** выполняется разбор файла
- **THEN** задача получает даты `2026-08-31` и `2026-09-11` с включительным окончанием

#### Scenario: Праздник попадает в календарную дату пояса

- **GIVEN** праздник с меткой `2026-11-03T21:00:00.000Z` и часовой пояс плана `Europe/Moscow`
- **WHEN** выполняется разбор файла
- **THEN** календарь плана содержит праздник `2026-11-04`, а не `2026-11-03`

#### Scenario: Отсутствие пояса даёт предупреждение

- **GIVEN** файл без настроек часового пояса
- **WHEN** выполняется разбор файла
- **THEN** даты преобразуются по UTC
- **AND** отчёт импорта содержит предупреждение об отсутствии пояса

### Requirement: FS-зависимости с задержкой из строк предшественников

Разбор SHALL преобразовывать строки предшественников в FS-зависимости задачи: запись без задержки — лаг 0, записи `+N day`/`+N days` — лаг N рабочих дней. Строка с несколькими предшественниками SHALL давать по одной зависимости на каждого. Задержка, выходящая за рамки целых неотрицательных дней, и неподдержанные типы связей (не FS) MUST NOT давать зависимость: в отчёте перечисляется причина пропуска.

#### Scenario: Нулевой и ненулевой лаг

- **GIVEN** записи со строками предшественников `15FS` и `7FS+14 days`
- **WHEN** выполняется разбор файла
- **THEN** создаются зависимости с лагом 0 и 14 рабочих дней соответственно

#### Scenario: Несколько предшественников у одной записи

- **GIVEN** запись со строкой предшественников из двух ссылок FS
- **WHEN** выполняется разбор файла
- **THEN** создаётся две зависимости на эту запись

#### Scenario: Неподдержанный тип связи пропускается с предупреждением

- **GIVEN** запись со строкой предшественника `7SS`
- **WHEN** выполняется разбор файла
- **THEN** зависимость не создаётся
- **AND** отчёт импорта содержит предупреждение о неподдержанном типе связи

### Requirement: Рабочий календарь из настроек файла

Разбор SHALL переносить рабочую неделю файла в рабочие дни календаря плана и праздники — в календарь плана с конвертацией по часовому поясу. Почасовое рабочее время (`workTime`) и настройки отображения (колонки, масштаб, форматы) MUST NOT переноситься в план и SHALL перечисляться в отчёте импорта как неперенесённые.

#### Scenario: Рабочая неделя и праздники переносятся

- **GIVEN** файл с рабочей неделей понедельник–пятница и праздником 4 ноября
- **WHEN** выполняется разбор файла
- **THEN** календарь плана содержит рабочие дни 1–5 и праздник `2026-11-04`

#### Scenario: Почасовое расписание перечислено в отчёте

- **GIVEN** файл с настройкой рабочего времени `08:00–12:00, 13:00–17:00`
- **WHEN** выполняется разбор файла
- **THEN** план не содержит почасового расписания
- **AND** отчёт импорта перечисляет эту настройку как неперенесённую

### Requirement: Политика дополнительных полей импорта

Разбор OnlineGantt SHALL документированно распоряжаться полями файла вне модели плана без молчаливой потери: процент загрузки назначения (`unit`) сохраняется в данных плана и не влияет на проверки; примечания (`info`) сохраняются как текст без HTML-разметки; цвет записи переносится в ручной цвет задачи только при точном совпадении его hex-значения (после нормализации регистра) со значением палитры цветов проекта, при отсутствии совпадения устанавливается автоматический цвет; прогресс и признак длительности не переносятся и перечисляются в отчёте; исходный идентификатор записи восстановим из идентификатора задачи.

#### Scenario: Загрузка назначения сохраняется без влияния на проверки

- **GIVEN** файл с назначением `unit: 100`
- **WHEN** выполняется разбор файла
- **THEN** назначение сохраняется в данных плана вместе с загрузкой
- **AND** проверки конфликтов не учитывают загрузку (правило ADR PBT-003 D3)

#### Scenario: Примечание сохраняется текстом

- **GIVEN** файл с примечанием записи в формате HTML
- **WHEN** выполняется разбор файла
- **THEN** примечание сохраняется как текст без тегов и не исполняется как разметка

#### Scenario: Цвет записи совпадает с палитрой и переносится

- **GIVEN** файл с цветом записи `#3186E9`
- **WHEN** выполняется разбор файла
- **THEN** задача получает ручной цвет `sapphire`

#### Scenario: Непереносимые поля перечислены

- **GIVEN** файл с цветом записи `#123456`, не входящим в палитру, и с полями прогресса у записей
- **WHEN** выполняется разбор файла
- **THEN** задача импортируется без ручного цвета (автоматический цвет), план не содержит прогресса
- **AND** отчёт импорта перечисляет неперенесённый прогресс и признак длительности

### Requirement: Диагностика повреждённого входа

Разбор MUST NOT выдавать повреждённый файл за план: некорректный JSON и отсутствие обязательных разделов дают отказ с перечнем диагностик без частичного плана. Дефект отдельной записи (некорректная дата, перевёрнутый интервал, дублирующийся идентификатор, ссылка предшественника на отсутствующую запись) SHALL давать предупреждение в отчёте с пропуском затронутой записи или связи; остальной план импортируется. Входные данные MUST NOT изменяться.

#### Scenario: Некорректный JSON даёт отказ

- **GIVEN** текст, не являющийся корректным JSON
- **WHEN** выполняется разбор файла
- **THEN** результат содержит диагностику синтаксической ошибки
- **AND** план не создаётся

#### Scenario: Дефектная запись пропускается с предупреждением

- **GIVEN** файл, где одна запись ссылается на отсутствующий идентификатор предшественника
- **WHEN** выполняется разбор файла
- **THEN** эта связь не создаётся и перечислена в отчёте
- **AND** остальные записи и связи импортируются

### Requirement: Импорт файла OnlineGantt из интерфейса с предпросмотром

Команда импорта плана SHALL принимать файлы OnlineGantt `.gantt` наряду с файлами собственного формата: выбранный `.gantt` SHALL полностью разбираться до каких-либо изменений данных, а результат показываться в предпросмотре — создание документа выполняется только явным применением. Применение SHALL создавать новый независимый документ плана с названием из предпросмотра и переключать окно, из которого выполнен импорт, на новый план; ранее созданные планы MUST NOT изменяться. Критические ошибки разбора (некорректный JSON, отсутствие обязательных разделов) MUST блокировать применение: пользователю показывается перечень диагностик по месту команды, диалог предпросмотра не открывается, документ не создаётся. Отмена предпросмотра и неуспешный импорт MUST NOT изменять данные и каталог.

#### Scenario: Рабочий файл проходит предпросмотр и импортируется

- **GIVEN** пользователь выбрал в команде импорта эталонный файл `.gantt` с 47 задачами и 9 ресурсами
- **WHEN** предпросмотр открыт и пользователь применяет импорт
- **THEN** создаётся документ плана с задачами, группами, ресурсами и зависимостями из файла
- **AND** окно, из которого выполнен импорт, отображает импортированный план
- **AND** план доступен в каталоге документов и открывается в ресурсном представлении с теми же данными

#### Scenario: Отмена предпросмотра ничего не меняет

- **GIVEN** открыт диалог предпросмотра разобранного файла
- **WHEN** пользователь отменяет импорт или закрывает диалог
- **THEN** каталог и содержимое текущих планов остаются без изменений

#### Scenario: Критическая ошибка даёт диагностику без документа

- **GIVEN** пользователь выбрал файл, не являющийся корректным JSON
- **WHEN** выполняется разбор
- **THEN** пользователь видит перечень диагностик по месту команды импорта
- **AND** диалог предпросмотра не открывается и документ не создаётся

#### Scenario: Повторный импорт создаёт независимые планы

- **GIVEN** один файл `.gantt` импортирован дважды с применением
- **WHEN** пользователь просматривает каталог
- **THEN** каталог содержит два независимых документа, содержимое первого не изменилось

### Requirement: Состав предпросмотра импорта

Предпросмотр SHALL показывать до применения: сводку разбора (число задач, групп, ресурсов, зависимостей и задач без исполнителя), перечень предупреждений отчёта импорта с причинами (пропущенные записи и связи, неперенесённые поля и настройки) и редактируемое название создаваемого плана. Задачи без исполнителя SHALL быть помечены как требующие ручного решения (назначение исполнителя или преобразование в период недоступности) и MUST NOT удаляться или скрываться автоматически; пометка выставляется по отсутствию исполнителя, а не по названию записи. Примечания исходного файла SHALL отображаться как текст без исполнения HTML-разметки.

#### Scenario: Сводка и предупреждения видны до применения

- **GIVEN** файл с предупреждениями отчёта (неперенесённые настройки, поля записей)
- **WHEN** открывается предпросмотр
- **THEN** сводка показывает количества задач, групп, ресурсов и зависимостей
- **AND** предупреждения перечислены с указанием причины

#### Scenario: Задачи без исполнителя помечены как ручные решения

- **GIVEN** файл с задачами без назначенных ресурсов
- **WHEN** открывается предпросмотр
- **THEN** эти задачи перечислены с пометкой о ручном решении
- **AND** после применения они остаются в плане обычными задачами

#### Scenario: Примечание отображается текстом

- **GIVEN** файл с HTML-примечанием у задачи
- **WHEN** открывается предпросмотр
- **THEN** примечание показано как текст без тегов и не исполняется как разметка

### Requirement: Явный выбор ресурса при преобразовании импортированных строк

При преобразовании импортированной строки без исполнителя в период недоступности ресурс SHALL определяться только явным выбором пользователя из справочника плана: значение MUST NOT предугадываться по названию записи или иным данным строки. Список предлагаемых ресурсов — справочник текущего плана; при пустом справочнике преобразование предлагает сначала создать ресурсы.

#### Scenario: Неоднозначное имя не влияет на выбор

- **GIVEN** импортированная строка «ОТПУСК-DEV-iOS» и два ресурса «iOS-разработчик» и «iOS-разработчик 2»
- **WHEN** пользователь открывает преобразование и выбирает «iOS-разработчик 2»
- **THEN** период недоступности создаётся именно для выбранного ресурса
- **AND** выбор ресурса изначально пуст: подсказки из названия строки нет

#### Scenario: Пустой справочник подсказывает создать ресурсы

- **GIVEN** задача без исполнителей в плане без ресурсов
- **WHEN** пользователь открывает преобразование
- **THEN** диалог сообщает об отсутствии ресурсов и не предлагает применения
