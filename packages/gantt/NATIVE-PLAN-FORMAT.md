# Формат файла плана Project Board (v1)

Собственный формат переноса одного плана: файл содержит план целиком — задачи,
группы, зависимости, ресурсы, типы работ, рабочий календарь и периоды
недоступности. Файл текстовый JSON, пригоден для чтения в редакторе.

- Модуль формата: `packages/gantt/src/native-plan-format.ts`
- Эталонный файл: `tests/fixtures/gantt/native-plan-sample.json`
- Семантика дат: календарные даты `YYYY-MM-DD` без времени суток; окончание
  задачи **включительно** (задача «пн 12.10 – пт 16.10» включает пятницу);
  длительность в рабочих днях считается приложением из календаря.

## Структура файла

```json
{
  "format": "project-board-plan",
  "formatVersion": 1,
  "title": "Название плана",
  "schemaVersion": 1,
  "content": { … }
}
```

| Поле | Смысл |
| --- | --- |
| `format` | Маркер формата. Файлы с другим маркером не импортируются |
| `formatVersion` | Версия **формата файла**. Версии больше поддерживаемой приложением отклоняются |
| `title` | Название плана; при импорте становится названием документа |
| `schemaVersion` | Версия **содержимого** (модели плана). Должна совпадать с поддерживаемой приложением |
| `content` | Содержимое плана: `calendar`, `workTypes`, `resources`, `groups`, `tasks`, `dependencies`, `unavailability` |

`formatVersion` и `schemaVersion` — разные оси: первая меняется при изменении
оболочки файла, вторая — при миграции самой модели плана.

## Разделы `content`

- `calendar`: `workingDays` (целые 1–7, пн–вс), `holidays`, `workingExceptions` — ISO-даты.
- `workTypes`: `id`, `title`, `allowsParallel`.
- `resources`: `id`, `title`.
- `groups`: `id`, `title`, опциональный `parentId` (произвольная вложенность, циклы недопустимы).
- `tasks`: `id`, `title`, опциональные `groupId`, `assigneeIds`, `workTypeIds`; `start`, `end` — ISO-даты, окончание включительно.
- `dependencies`: `id`, `fromTaskId`, `toTaskId`, `lagDays` (целое ≥ 0, рабочие дни; связь «окончание → начало»).
- `unavailability`: `id`, `resourceId`, `start`, `end` (включительно).

Все ссылки — внутренние для `content` (ссылки только на сущности того же файла).

## Импорт и идентификаторы

Импорт файла всегда создаёт **новый независимый план**; замена содержимого
существующего плана не поддерживается. Идентификаторы сущностей сохраняются
из файла. Совпадение идентификаторов или названий сущностей разных планов не
создаёт связей: планы независимы, ссылки резолвятся внутри своего содержимого.

## Диагностика

Десериализация валидирует файл полностью и при проблеме отдаёт перечень
сообщений (код, место, причина) вместо частичного плана:

| Код | Причина |
| --- | --- |
| `invalid-json` | Текст не является корректным JSON |
| `invalid-envelope` | Нарушена структура конверта (не объект, отсутствуют/неверные поля, неподдерживаемая `schemaVersion`) |
| `unknown-format` | Маркер `format` не совпадает с форматом приложения |
| `unsupported-future-version` | `formatVersion` больше поддерживаемой: файл создан более новой версией приложения |
| `plan-invalid` | Содержимое не прошло валидацию плана; поле `details` содержит полный перечень (`unknown-reference`, `circular-group`, `inverted-interval`, …) |

Файл будущей версии не читается частично и не повреждается — данные
остаются пригодными для более новой версии приложения.

## Имя файла

Экспорт предлагает имя по шаблону `pb-plan-YYYY-MM-DD_HH-mm-ss.json`
(локальное время; утилита `planFileName`). Имя файла — конвенция генерации:
приложение принимает файл с любым именем.

## Ограничения v1

- Неизвестные поля внутри `content` сохраняются при переносе, но не имеют
  гарантий: смена `formatVersion` может их отбросить.
- Миграции устаревших версий формата отсутствуют (v1 — первая версия).
- Производные значения (сводные сроки групп, рабочие длительности, конфликты)
  в файл не входят — приложение вычисляет их из содержимого.
