# ADR PBT-017 — Компоненты Гантта и границы адаптеров

- **Дата:** 2026-10-10
- **Статус:** Принято (ревью владельца 2026-10-10: выбор компонентов, стратегия жестов, судьба стендов, пороги PBT-058; развилки change `pbt-017-gantt-components-decision`)
- **Затрагивает:** PBT-030–PBT-036 (ядро планирования), PBT-037–PBT-049 (представления и редакторы), PBT-047/PBT-048 (ресурсный вид), PBT-058 (итоговая проверка производительности)
- **Основания:** [PBT-014](../research/PBT-014.md) (спайк SVAR) · [PBT-015](../research/PBT-015.md) (спайк RCT) · [PBT-016](../research/PBT-016.md) (замеры нагрузки) · правила [ADR PBT-003](PBT-003.md)
- **Связанные решения:** [ADR PBT-002](PBT-002.md) (стек и границы; компоненты Гантта оставлены кандидатами — этот ADR закрывает развилку)

## Контекст

Требования к представлениям зафиксированы в решениях §13: проектное — задачи, вложенные группы, сроки и зависимости с ручным редактированием; ресурсное — компактные дорожки исполнителей с укладкой пересечений и анализом занятости. Правила редактирования — ADR PBT-003 (A1–D7): включительное окончание, рабочая длительность, ручной режим без автопереноса, конфликты по параллельности типов работ. Целевая нагрузка — несколько сотен задач и до 10 виджетов (§20).

Три исследования проверили кандидатов и дали вывод «подходит с ограничениями» для обоих представлений; нагрузочный прототип подтвердил совместимость библиотек в одном бандле и запас по целевым сценариям. Этот ADR переводит кандидатов в решения, фиксирует версии и распределяет ответственность между ядром, адаптерами и библиотеками.

## Решения

### ADR-1. Проектное представление: SVAR React Gantt 2.8.0 (MIT)

Принимается открытая редакция `@svar-ui/react-gantt@2.8.0` (peer React ≥18, совместим с 18.3). Основания: стабильный публичный API; дерево задач со сводными полосами и сворачиванием; отрисовка FS-связей; форма редактирования `Editor`; подсветка нерабочих дней `highlightTime`; отсутствие в открытой редакции рабочих календарей и автопланирования (PRO) — что в нашем случае не ограничение, а соответствие согласованному ручному режиму: даты не пересчитываются скрыто, зависимые не двигаются. Отклонено: Frappe Gantt (слабее по произвольной вложенности и свимым группам), собственный рендер проектного вида (дерево, связи, форма и масштабирование — значительный объём без выигрыша), коммерческие редакции SVAR (против предпочтения open-source; платные возможности не нужны по согласованному поведению).

### ADR-2. Ресурсное представление: React Calendar Timeline 0.30.0-beta.19 (MIT, точный пин)

Принимается `react-calendar-timeline@0.30.0-beta.19` — TS/React 18–19 линия (peer `dayjs`, `interactjs`). Основания: компактные дорожки с укладкой пересекающихся задач (`stackItems`); встроенная виртуализация элементов; отпуск — элемент дорожки ресурса (D1/D6); лента занятости ресурса как union-интервалов назначений (суть референса: когда занят, где окна); день-точность собственным снапом; подтверждённый resize контейнера. Меры по бете: точный пин версии; обновления — отдельная осознанная операция; API жестов изолируется в единственном модуле адаптера; план Б при поломке беты — собственный рендер дорожек (укладка, виртуализация), оформляется новой PBT-задачей до PBT-047. Жесты в ресурсном виде — вспомогательная возможность (PBT-048); основная роль вида — анализ загрузки, основное редактирование сроков — проектный Гантт.

### ADR-3. Ядро планирования независимо от библиотек отображения

Источник истины — документ плана собственного ядра (PBT-030+). Ядро и только ядро: хранит календарные даты с включительным окончанием (A1); считает рабочую длительность и длительности ввода в рабочих днях (A4–A6); вычисляет сводные полосы групп (B2 — min начала / max окончания вложенных); проверяет FS-зависимости и циклы (C1–C5); определяет конфликты ресурсов по параллельности типов работ и отпускам (D1–D7); владеет арифметикой рабочего календаря (модуль PBT-013). Библиотекам отводятся отображение и первичный ввод жестов; их производные значения (календарная `duration` SVAR, пересчитанные сводной SVAR) не попадают в документ.

### ADR-4. Адаптеры представлений

- **Адаптер проектного вида** (`план ↔ SVAR ITask/ILink`): при передаче — окончание +1 календарный день (включительное → исключительное), FS — `type: "e2s"`, лаг — из документа; при чтении из компонента — окончание −1 день; `getTask` нормализуется (несимметрия сводных). Колонка «Длительность» SVAR заменяется своей (рабочие дни).
- **Адаптер ресурсного вида** (`план ↔ RCT groups/items`): ресурсы → группы; назначения → элементы на дорожке каждого ресурса (D1); неназначенные задачи не отображаются (D2); отпуск → элемент недоступности без жестов; границы дня — полночь начала / полночь дня после включительного окончания; снап к суткам — свой код.
- Конвертация включительного окончания локализована в адаптерах; ядро и адаптеры живут в `packages/gantt`; спайковый код напрямую не переносится — продуктовые адаптеры пишутся с нуля по схемам отчётов.

### ADR-5. Стратегия жестов

- **SVAR:** данные передаются в `Gantt` один раз; источник отображения — стор SVAR; контролируемые props не обновляются в окне жеста. После `mouseup`/`touchend` план сверяется со стором (серия 80/450/1000 мс), к факту применяются правила ядра, исправленные даты записываются `api.exec('update-task')`. Режим жеста определяется дельтами дат: сдвиг обоих краёв — drag (A2, привязка начала к рабочему дню в сторону переноса); изменение одного края — ручной ввод (A3, дата как введена). Payload `update-task` как источник данных не используется (ненадёжен). Резервная стратегия при сбоях на продуктовых сценариях — блокировка действий (`return false`) с полным собственным применением. Перехватчики служебных запретов (drag сводной — `drag-task` → `return false` для summary) вешаются с защитой от дублей (StrictMode) и переустановкой при пересоздании bus.
- **RCT:** жест доступен после клика-выделения; факт применяется после `mouseup` по той же схеме «факт → правила ядра → применение» (`onItemDrag` с `eventType: move|resize`).

### ADR-6. Судьба исследовательских стендов

- `apps/gantt-spike`, `apps/resource-timeline-spike` — удалить отдельным хаускипинг-PR сразу после merge этого ADR: решение принято, стенды своё отработали; схемы адаптеров сохранены в отчётах PBT-014/015 и git-истории. Удержание мёртвых стендов до PBT-037 — риск рассинхронизации с продуктовым кодом.
- `apps/load-demo` — сохранить до PBT-058 (итоговая проверка производительности по утверждённым порогам и сценариям PBT-012), удалить в релизной зачистке.

### ADR-7. Пороги производительности для PBT-058

Утверждаются кандидаты отчёта PBT-016 (окружение: активная вкладка Chromium, macOS):

| Метрика | Порог |
| --- | --- |
| Монтирование 10 виджетов (план-500) | ≤ 1000 мс |
| Переключение набора из 10 панелей | ≤ 500 мс |
| Добавление задачи (план-500) | ≤ 400 мс |
| Запись плана-500 в IndexedDB | ≤ 700 мс |
| Прокрутка таймлайна | ≥ 30 FPS (видимая вкладка, ручная проверка) |

## Последствия

- Разблокируются PBT-030+ (ядро) и PBT-037+/PBT-047+ (представления); адаптеры пишутся с нуля в `packages/gantt` по границам ADR-4.
- Ограничения библиотек становятся контрактом адаптеров; нарушения семантики ADR PBT-003 библиотекой недопустимы по построению (правила применяет ядро).
- Позиции §19 `.context/project-decisions.md` (SVAR, RCT) переводятся из «кандидатов» в «решения» со ссылкой на этот ADR.
- Пороги ADR-7 становятся критериями PBT-058.
- После merge: хаускипинг-PR удаляет `apps/gantt-spike` и `apps/resource-timeline-spike` (ADR-6).

| Вопрос | Отклонено | Причина |
| --- | --- | --- |
| Проектный вид | Frappe Gantt (MIT) | Слабее по произвольной вложенности и свимым группам (отбор §19) |
| Проектный вид | Собственный рендер | Дерево, связи, форма, масштабирование — большой объём без выигрыша |

| Ресурсный вид | Собственный рендер сразу | Укладка, виртуализация и лента занятости уже решены RCT; дороже без выигрыша в первой версии (остаётся планом Б) |
| SVAR PRO-редакция | Коммерческие календари/автопланирование | Против предпочтения open-source; платные возможности противоречат ручному режиму |

| Жесты SVAR | Payload `update-task` как данные | Содержит старые даты в части прогонов; зависит от порядка событий мыши |
