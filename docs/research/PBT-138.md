# PBT-138 — Потеря данных при аварийном завершении браузера (фаза 1: диагностика)

- **Дата:** 2026-11-09
- **Тип:** Исследование (фаза 1); митигация — отдельное решение
- **Change:** `pbt-138-crash-persistence` (skip_specs)
- **Ветвь:** `feature/pbt-138-crash-persistence` → PR в `develop`
- **Источник:** сообщение владельца: при экстренном выходе из браузера (kill процесса) «стирается всё», восстановление из бэкапа вручную

## Вопросы

1. Воспроизводится ли полная потеря данных при `kill -9` Chrome?
2. Каков механизм: повреждение/удаление БД браузером, потеря «хвоста» коммитов или что-то в приложении?
3. Что именно теряется и что остаётся?

## Стенд

- `tests/persistence-crash/diagnose.mjs` — серии kill-тестов: чистый профиль Chrome 156 (channel `chrome`), production preview (`npm run build` + preview 4173), создание чек-листов через UI, `kill -9` всех процессов профиля, перезапуск, подсчёт выживших окон + снимок `chrome://indexeddb-internals` + каталог LevelDB.
- Серии: A — kill в покое (7×); B — kill во время активной записи пунктов (7×); C — kill на грани debounce 350 мс (6×); D — тяжёлая БД (20 документов × 30 пунктов) + kill во время записи (5×).
- `tests/persistence-crash/control.mjs`, `localize.mjs` — контрольные эксперименты (graceful close vs kill) и пошаговая локализация с прямыми снимками IndexedDB из страницы (`tabs`/`widgetInstances`/`settings`/`documents`).

## Результаты

| Серия | Итог |
| --- | --- |
| A: kill в покое | 7/7 выжило |
| B: kill во время записи (малый объём) | 7/7 выжило |
| C: kill на грани debounce | 6/6 выжило |
| D: тяжёлая БД + kill во время записи | **5/5 полная потеря окон (total-loss)** |
| Контроль: graceful close | выживает |

Каталог LevelDB во всех случаях цел (никакого corruption-удаления БД браузером); `chrome://indexeddb-internals` показывает живую БД. Гипотезы corruption-удаления и потери «хвоста коммитов» **опровергнуты**.

## Установленный механизм

Пошаговая локализация (серия D): уже **внутри живой сессии** при непрерывной активности в БД `widgetInstances = 0`, при этом в DOM 20 окон:

```
seed после 5 доков:  {instances: 0, documents: 4,  domWindows: 5}
seed после 20 доков: {instances: 0, documents: 20, domWindows: 20}
после kill/reopen:   {instances: 0, documents: 20, domWindows: 0}  ← «всё стёрлось»
```

Первопричина — в приложении, `apps/project-board/src/App.tsx` (снапшот workspace, PBT-024):

1. Снапшот workspace ставится на запись через **debounce 300 мс с отменой предыдущего таймера** (`clearTimeout` → `setTimeout(save, 300)`).
2. Эффект снапшота — `useEffect` **без массива зависимостей**: пересобирает снапшот и перезапускает таймер **после каждого рендера** приложения.
3. При непрерывной активности (ввод пунктов/текста, перетаскивание — рендеры чаще ~3 Гц) таймер перезапускается бесконечно, и **ни один снапшот workspace не записывается** — окна/вкладки живут только в памяти.
4. Штатное закрытие спасает `pagehide`-флаш; при **аварийном завершении (kill/крах) `pagehide` не выполняется** — несохранённый workspace теряется.

Что теряется и что остаётся:

| Данные | Судьба при kill после активной сессии |
| --- | --- |
| Окна виджетов (`widgetInstances`), раскладки, часто вкладки | ❌ теряются (debounce «голодает») |
| Документы и их содержимое (автосохранение DocumentService) | ✅ сохраняются (20/20 с содержимым) |
| LevelDB-каталог БД | ✅ цел |

Пользовательская картина совпадает с жалобой: дашборд пуст («всё стёрлось»). Фактически документы живы в каталоге документов и открываются заново; бэкап не обязателен для спасения содержимого — теряется композиция рабочего пространства.

## Рекомендация митигации (фаза 2, отдельное решение)

1. **Потолок debounce (maxWait):** запись снапшота не реже, чем раз в 2–3 с, даже при непрерывной активности (сброс таймера, но с форсированной записью по истечении потолка от последней фактической записи).
2. **Флаш на `visibilitychange → hidden`** в дополнение к `pagehide`: фоновое вытеснение вкладки/PWA — самый частый «тихий kill» на практике.
3. Немедленная (без debounce) запись при структурных операциях: создание/удаление окна, вкладки, смена режима — редкие события, цена записи мала.
4. Проверки: unit на механизм отложенной записи (вынести в чистый модуль с инъекцией таймеров); e2e/локальный стенд `tests/persistence-crash/` как регресс (непрерывная активность > 2×maxWait → kill → окна восстанавливаются).

## Ограничения

- Стенд: чистый профиль, localhost-origin, Chrome 156/macOS; среда владельца (рабочий Chrome 154, публичный origin/PWA) не проверялась, но механизм воспроизводится на уровне приложения и от origin не зависит.
- kill-стенд не входит в CI (браузерные процессы); применение — локальный регресс по требованию.
- Потеря профиля браузера целиком (сознательная очистка) вне исследования; для неё остаётся ручной бэкап.
