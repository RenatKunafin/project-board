# PBT-138 — Потеря данных при аварийном завершении браузера (фаза 1: диагностика)

- **Дата:** 2026-11-09
- **Тип:** Исследование (фаза 1); митигация — отдельное решение
- **Change:** `pbt-138-crash-persistence` (skip_specs)
- **Ветвь:** `feature/pbt-138-crash-persistence` → PR в `develop`
- **Источник:** сообщение владельца: при экстренном выходе из браузера (kill процесса) «стирается всё», восстановление из бэкапа вручную

## Вопросы

1. Воспроизводится ли полная потеря данных при `kill -9` Chrome?
2. Каков механизм: повреждение/удаление БД браузером, потеря «хвоста» коммитов или что-то в приложении?
3. Что именно теряется и что остаётся?

## Стенд

- `tests/persistence-crash/diagnose.mjs` — серии kill-тестов: чистый профиль Chrome 156 (channel `chrome`), production preview (`npm run build` + preview 4173), создание чек-листов через UI, `kill -9` всех процессов профиля, перезапуск, подсчёт выживших окон + снимок `chrome://indexeddb-internals` + каталог LevelDB.
- Серии: A — kill в покое (7×); B — kill во время активной записи пунктов (7×); C — kill на грани debounce 350 мс (6×); D — тяжёлая БД (20 документов × 30 пунктов) + kill во время записи (5×).
- `tests/persistence-crash/control.mjs`, `localize.mjs` — контрольные эксперименты (graceful close vs kill) и пошаговая локализация с прямыми снимками IndexedDB из страницы (`tabs`/`widgetInstances`/`settings`/`documents`).

## Результаты

| Серия | Итог |
| --- | --- |
| A: kill в покое | 7/7 выжило |
| B: kill во время записи (малый объём) | 7/7 выжило |
| C: kill на грани debounce | 6/6 выжило |
| D: тяжёлая БД + kill во время записи | **5/5 полная потеря окон (total-loss)** |
| Контроль: graceful close | выживает |

Каталог LevelDB во всех случаях цел (никакого corruption-удаления БД браузером); `chrome://indexeddb-internals` показывает живую БД. Гипотезы corruption-удаления и потери «хвоста коммитов» **опровергнуты**.

## Установленный механизм (два независимых)

### Механизм 1: debounce-голод снапшота workspace (приложение)

Пошаговая локализация (серия D): уже **внутри живой сессии** при непрерывной активности в БД `widgetInstances = 0`, при этом в DOM 20 окон:

```
seed после 5 доков:  {instances: 0, documents: 4,  domWindows: 5}
seed после 20 доков: {instances: 0, documents: 20, domWindows: 20}
после kill/reopen:   {instances: 0, documents: 20, domWindows: 0}  ← окна потеряны
```

Первопричина — в приложении, `apps/project-board/src/App.tsx` (снапшот workspace, PBT-024):

1. Снапшот workspace ставится на запись через **debounce 300 мс с отменой предыдущего таймера** (`clearTimeout` → `setTimeout(save, 300)`).
2. Эффект снапшота — `useEffect` **без массива зависимостей**: пересобирает снапшот и перезапускает таймер **после каждого рендера** приложения.
3. При непрерывной активности (ввод пунктов/текста, перетаскивание — рендеры чаще ~3 Гц) таймер перезапускается бесконечно, и **ни один снапшот workspace не записывается** — окна/вкладки живут только в памяти.
4. Штатное закрытие спасает `pagehide`-флаш; при **аварийном завершении (kill/крах) `pagehide` не выполняется** — несохранённый workspace теряется.

Следствие: теряются окна/вкладки; **документы и LevelDB-каталог при этом живы**.

### Механизм 2: пересоздание БД браузером после аварийного завершения (среда)

Подтверждён уликами с рабочей машины владельца (10.11.2026, Chrome 154, корпоративный MacBook): после аварийного завершения браузера каталог IndexedDB origin'а **удалён и создан заново**:

| Улика (со слов владельца, копия каталога сохранена) | Значение |
| --- | --- |
| Каталог `https_renatkunafin.github.io_0.indexeddb.leveldb` — **32 КБ** при месяцах реальных данных (мегабайты) | данных физически нет |
| `MANIFEST-000001` — счётчик с единицы | БД создана с нуля, не наследница старой |
| Все файлы каталога датированы моментом запуска после краха; `chrome://indexeddb-internals`: Size ≈ 20 КБ | пересоздана при старте Chrome |
| В приложении после потери: `documents 0, tabs 1, widgetInstances 0` | погибли все данные; `tabs 1` — дефолтная вкладка, созданная приложением при первом открытии |

Механизм соответствует известному поведению Chromium: повреждение LevelDB после аварийного завершения → молчаливое удаление и пересоздание БД origin'а. На стенде (Chrome 156, macOS, малые БД, 20+ kill-серий) **не воспроизведён** — вероятные условия: версия Chrome 154 и/или большой размер БД/compaction; попытка воспроизведения на большой БД продолжается.

Итог: у владельца действуют **оба** механизма — механизм 2 уничтожает всё хранилище, механизм 1 дополнительно теряет workspace при живой БД.

Что теряется и что остаётся (по механизмам):

| Данные | Механизм 1 (debounce-голод) | Механизм 2 (пересоздание БД) |
| --- | --- | --- |
| Окна виджетов, раскладки | ❌ теряются | ❌ теряются |
| Документы и содержимое | ✅ сохраняются | ❌ теряются все |
| Каталог LevelDB / сама БД | ✅ цел | ❌ удалена и создана заново |

Пользовательская картина владельца объяснена обоими механизмами: пустой дашборд после краша («всё стёрлось»). При действии только механизма 1 документы живы в каталоге документов; при механизме 2 не спасается ничто — что и наблюдалось на рабочей машине (снимок `documents 0`).

## Рекомендация митигации (фаза 2, отдельное решение)

Оба механизма закрываются одним контуром — данные обязаны переживать и пропуск записи (мех. 1), и пересоздание основной БД (мех. 2):

1. **Избыточное хранилище:** автоматические снапшоты полного состояния (документы + workspace + настройки) в хранилище, физически отдельное от основной БД: вторая IndexedDB-БД и/или OPFS. Пересоздание основной БД его не затрагивает.
2. **Восстановление:** при старте с пустой/молодой основной БД и наличии снапшота — явное предложение восстановиться одним кликом («Обнаружена потеря хранилища; автоснапшот от HH:MM»), без молчаливого затирания.
3. **Потолок debounce (maxWait):** запись снапшота workspace не реже, чем раз в 2–3 с даже при непрерывной активности; флаш на `visibilitychange → hidden`; немедленная запись при структурных операциях (создание/удаление окон, вкладок).
4. Периодичность автоснапшотов и их удержание — параметр дизайна (цель: точка невозврата потерь с «всё» сужается до «минуты»).
5. Проверки: unit на механизм отложенной записи (чистый модуль, инъекция таймеров); воспроизведение мех. 1 локальным kill-стендом; для мех. 2 — воспроизведение на стенде (Chrome 154/большая БД, продолжается) либо приёмка на рабочей машине владельца по протоколу живой проверки.

## Ограничения

- Стенд: чистый профиль, localhost-origin, Chrome 156/macOS; среда владельца (рабочий Chrome 154, публичный origin/PWA) для механизма 2 подтверждена уликами постфактум (копия каталога БД), но живым стендом не воспроизводилась; попытка продолжается.
- Улики механизма 2 получены со слов владельца и сохранённой им копии каталога; полный дамп хранилища в git не входит (корпоративная среда).
- kill-стенд не входит в CI (браузерные процессы); применение — локальный регресс по требованию.
- Потеря профиля браузера целиком (сознательная очистка) вне исследования; для неё остаётся ручной бэкап.
