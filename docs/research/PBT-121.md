## Вопросы

1. Работает ли полный синтетический обмен: панель → локальный компонент (MCP stdio + loopback HTTP) → исполнитель → реальный сервис документов → чтение после reload?
2. Выдерживает ли канал границы доступа: чужая origin, несопряжённый клиент, занятый порт, restart, TTL?
3. Диагностируются ли отказы доставки и ошибки persistence без ложного успеха?
4. Переносим ли компонент на другую машину установкой артефакта без исходного checkout?

## Состав стенда

- `tests/agent-integration/server/` — изолированный npm-пакет `project-board-agent-probe-server@0.1.0`: один процесс, MCP stdio (официальный SDK) + HTTP JSON на `127.0.0.1` (порт по умолчанию 43821), одноразовое сопряжение (код ≥128 бит, 5 мин, ≤10 попыток), bearer-сессия 30 мин, один слот запроса `queued → processing → ready → applied` с TTL 10 минут, лимит JSON 32 KiB. Служебные записи — stderr; stdout только MCP.
- `tests/agent-integration/web/` — изолированная браузерная панель (собственный Vite-конфиг без продуктового bootstrap, SW, manifest и аналитики): сопряжение, запрос, ограниченный опрос (1 раз/с, сеанс ≤120 с), применение через `createDocumentService`/`createIndexedDbDocumentStore('project-board-pbt-121-probe-v1')`, `update(expectedRevision)` → `flushAll()` → контрольное чтение `store.get` → ACK; test-only обёртка отказа записи по `?pbt121fault=persistence`.
- `tests/agent-integration/preview/server.mjs` — статический preview для e2e; `tests/agent-integration/build.mjs` — сборка артефактов и manifest с хешами.
- MCP-инструменты стенда: `probe_session`, `claim_probe_request`, `submit_probe_result`, `fail_probe_request`. Имена — внутренний контракт эксперимента, не публичный API.

Продуктовые пакеты, `apps/project-board`, Pages-публикация продукта и PWA lifecycle не изменялись.

## Инструкция чистой установки (проверена локально)

```bash
mkdir agent-probe && cd agent-probe
npm install ./project-board-agent-probe-server-0.1.0.tgz --no-fund --no-audit
node node_modules/project-board-agent-probe-server/dist/cli.js \
  --allowed-origin https://<стенд-origin> --port 43821
```

Требуется Node ≥22 и доступ к npm-реестру для зависимостей SDK (tarball не автономен). Занятый порт — явная ошибка; компонент слушает только `127.0.0.1`.

## Runbook живой пробы для владельца (PBT-121, рабочая машина)

1. Установить артефакт по инструкции выше (получить tarball с личной машины; корпоративные данные не требуются).
2. Запустить компонент с origin опубликованного стенда; убедиться в stderr-строке `{"event":"listening",…}`.
3. Добавить MCP-сервер в клиент агента по его фактической конфигурации (наблюдение B-1 PBT-120): команда `node <путь>/dist/cli.js`, аргументы `--allowed-origin … --port 43821`.
4. Открыть стенд в Chrome (обычная вкладка), при запросе браузера на доступ к локальной сети — принять штатное разрешение (не отключать защиту).
5. Спросить агента: «Вызови инструмент probe_session и покажи код сопряжения и адрес». Перенести код и адрес в панель, нажать «Сопрячь».
6. Нажать «Обновить (синтетический запрос)», затем дать агенту явную команду: «Обработай запрос очереди пробного сервера: claim_probe_request, собери синтетический снимок по правилам fixture-b и верни через submit_probe_result. К корпоративным источникам не обращаться».
7. Зафиксировать: фазы панели (В очереди → Обработка → Сохранено), значения fixture/ревизия, реакцию браузера (разрешение локальной сети), reload без повторной доставки, остановку компонента (`POST /disconnect` из панели либо завершение процесса — прежние данные сохранены).
8. Вернуть обезличенный ответ: по каждому шагу ожидаемое/фактическое, текст ошибки без токенов, версия Chrome, режим (вкладка), использованные версии Node/клиента (без названия клиента, если не раскрывается).

## Ограничения

- Стенд сознательно не поддерживает: несколько одновременных запросов/исполнителей, восстановление очереди после падения, lease/retry, установленную PWA и другие браузеры (D1/D5, PBT-125/126).
- Страница панели на чужой origin получает сетевой отказ CORS без тела ответа — панель показывает «Компонент недоступен», причина на уровне браузера не раскрывается (ожидаемое поведение, не дефект стенда).
- **Блокер корпоративного Chrome (воспроизведён в живой пробе):** принудительный http→https-апгрейд затрагивает loopback — запрос из `https://renatkunafin.github.io` к `http://127.0.0.1:43821` превращается в `https://127.0.0.1:43821` (без TLS) и отклоняется («Permission was denied for this request to access the loopback address space»). На личном Mac без политики апгрейда тот же канал работает после LNA-разрешения. Ослабление защиты не применялось; для рабочей среды использован локальный http-origin.
- Коды сопряжения/токены в артефакты и отчёт не входят; в manifest попадают только хеши файлов.
- Временная Pages-публикация (`project-board-agent-probe`) и Release с tarball остаются доступными до отдельного решения владельца (могут понадобиться PBT-122+).

## Вывод для PBT-122

Проверенный кандидат транспорта подтверждён с обеих сторон: MCP stdio + HTTP JSON на loopback, ограниченное сопряжение и ACK после фактического сохранения работают воспроизводимо — автоматикой, живой LNA-пробой на личном Mac и живой пробой внутреннего агента на рабочем Mac. Существенные вводные для дизайна контракта:

1. **Размещение дашборда:** публичный HTTPS-сайт не сможет обращаться к http-loopback-компоненту в корпоративном Chrome (принудительный https-апгрейд). Кандидаты для PBT-122/PBT-123: локальная сборка/локальный origin стенда, https на loopback-компоненте или иной канал — выбор отдельным решением с владельцем.
2. **Клиент агента:** сторонние stdio-серверы поддерживаются (command/args); переключения серверов могут оставлять живые процессы — компонент должен переживать коллизию порта явным отказом (уже реализовано) и, возможно, предлагать `--port 0` с печатью фактического адреса.
3. **Лимиты:** внутренний прокси отдаёт 429 на запросы к модели — скилл и инструкции PBT-129 должны рассчитывать на короткие однократные команды, повторы с паузой.
4. Живые пункты D8 закрыты; Done проставлен.
